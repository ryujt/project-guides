# 시나리오 기반 상태 전이 분석서

회원과 비회원이 실물 상품을 구매하는 쇼핑몰의 **목표 설계(TO-BE) 예제**다. 고객이 무엇을 신청했는지, 지금 어디까지 처리됐는지, 다시 시도하거나 기다려야 하는지를 고객 화면과 운영 대시보드 양쪽에서 확인한다. 상태도는 목표 동작을, 테스트 케이스는 이를 재현하는 조건과 기대 결과를 설명한다. 범위는 상품 탐색과 계정 접근부터 주문·결제·배송, 취소·반품·교환, 구매 리뷰까지다.

화면 진입과 복귀는 [쇼핑몰 화면 시나리오](../navigation/shopping-mall-navigation.md), 실물 인계와 외부 통지는 [매크로뷰](../job-flow/macro.md), 상태 소유자와 사건의 순서는 [서비스뷰](../job-flow/system.md)의 가상 계약을 따른다. 예를 들어 결제사는 거래를 승인하고, 주문 서비스는 승인 금액과 재고 확보를 확인한 뒤 주문을 확정한다. 따라서 결제창에서 돌아온 순간, 주문을 출고할 수 있게 된 순간, 고객이 상품을 받은 순간을 각각 확인한다.

## E2E 테스트 준비

- 테스트 케이스마다 표의 시작 상태를 독립적으로 준비한다. 소유권을 비교할 때는 구매자와 다른 계정을, 수량 경합에는 같은 옵션의 마지막 한 개를 준비한다. 부분 취소·교환에는 상품별 결제 금액과 주문·신청·출고 번호를 구별할 수 있는 데이터를 쓴다.
- 고객 화면과 운영 대시보드는 각 역할의 권한으로 연다. 문자·메일은 시험 수신함에서 확인한다. 결제사·택배사·물류센터의 지연 또는 중복이 필요한 경우에는 시험 연동에서 **처리 자체의 실패**와 **처리는 끝났으나 회신만 유실**된 상황을 따로 재현한다. 기한이 있는 케이스는 시험 정책의 기한을 기준으로 시간을 진행시킨다.
- 표의 결과는 이 예제에서 채택한 기대 동작이다. 상태도는 한 객체가 소유한 상태 또는 한 화면에서 관찰하는 상태를 보여 준다. 여러 케이스가 같은 전이를 쓰더라도 행위자·시점·다음 행동이 달라지면 별도 ID로 확인한다. **미결정**으로 표시한 결과는 정책이 정해진 뒤 테스트의 합격 기준으로 삼는다.

## A1. 상품을 찾고 지금 살 수 있는 옵션을 고른다

**고객의 목표**는 원하는 조건에 맞는 상품과 옵션을 찾는 것이다. 고객프론트가 현재 검색 조건과 조회 결과의 표시 상태를 소유하고, 상품 서비스가 상품 공개 여부와 판매 옵션을 결정한다. 홈 검색이 실패하면 고객은 홈에서 다시 검색하고, 결과 화면을 연 뒤 조회가 실패하면 그 화면에서 복구한다. [상품 탐색의 진입·복귀 조건](../navigation/shopping-mall-navigation.md#s01-카테고리검색으로-상품-찾기)

```state
<s> --> (조회 중) : 고객이 검색하거나 저장한 검색 주소를 연다
(조회 중) --> (결과 있음) : 현재 조건에 맞는 상품이 있다
(조회 중) --> (결과 없음) : 조회는 성공했고 일치하는 상품이 없다
(조회 중) --> (조회 오류) : 현재 요청에 응답하지 못했다
(결과 있음) --> (조회 중) : 조건을 바꾸거나 같은 검색 주소를 다시 연다
(결과 없음) --> (조회 중) : 검색어 또는 필터를 바꾼다
(조회 오류) --> (조회 중) : 같은 조건으로 재시도한다
```

**주요 상태와 전이**

- **조회 중 → 결과 없음** · 검색이 끝났는데 조건을 모두 만족한 상품이 0개면 고객은 필터를 풀거나 검색어를 바꿀 수 있다. 조회 오류에서는 같은 검색 조건으로 다시 시도할 수 있다.

상세 화면에 진입하면 프론트가 공개 여부를 다시 확인한다. 품절 옵션이 있어도 공개 중인 상품의 다른 옵션을 볼 수 있다. 판매 가능한 옵션을 골라도 실제 주문 수량은 주문서에서 다시 확인한다.

```state
<s> --> (상세 확인 중) : 목록 또는 상품 링크에서 진입한다
(상세 확인 중) --> (옵션 선택 전) : 공개 중인 상품 상세를 받는다
(상세 확인 중) --> (열람 불가) : 상품이 없거나 공개가 끝났다
(상세 확인 중) --> (조회 오류) : 일시적으로 상세를 가져오지 못한다
(조회 오류) --> (상세 확인 중) : 같은 상품을 다시 조회한다
(옵션 선택 전) --> (담기 가능) : 판매 가능한 옵션과 수량을 선택한다
(옵션 선택 전) --> (선택 보완) : 필수 옵션이 빠지거나 품절 옵션을 고른다
(선택 보완) --> (담기 가능) : 판매 가능한 옵션과 수량으로 고친다
(담기 가능) --> (선택 보완) : 담기 요청 시 해당 옵션의 품절이 확인된다
```

**주요 상태와 전이**

- **담기 가능 → 선택 보완** · 옵션을 고른 뒤 담는 사이에도 마지막 수량이 팔릴 수 있다. 고객은 품절 안내를 보고 판매 중인 다른 옵션이나 수량을 고른다.

### 테스트 케이스 · CAT-01~CAT-06

| ID | 준비 조건 | 행동과 사건 순서 | 확인할 결과와 다음 행동 |
| --- | --- | --- | --- |
| CAT-01 | 같은 카테고리에 서로 다른 색상의 공개 상품을 둔다. | 고객이 색상으로 검색하고 정렬을 바꾼 뒤 상세를 열었다가 검색 결과로 돌아간다. | 검색어·필터·정렬이 유지되고 선택했던 상품을 같은 조건에서 다시 찾을 수 있다. 카테고리 목록으로 직접 들어온 고객에게는 해당 카테고리로 돌아가는 경로가 있다. |
| CAT-02 | 검색어와 다른 조건을 모두 만족하지만 색상 필터만 맞지 않는 상품 하나를 준비한다. | 고객이 필터가 적용된 검색 주소를 직접 열어 빈 결과를 확인하고 색상 필터를 해제한다. | 첫 화면에는 검색 조건과 빈 결과가 보인다. 필터를 풀면 준비한 상품이 나타나고 상세를 열 수 있다. |
| CAT-03 | 결과가 있는 검색어로 조회 한 번만 실패하게 한다. | 홈에서 검색을 시도한 경우와 저장한 검색 주소에서 조회한 경우에 각각 같은 조건으로 재시도한다. | 오류가 난 출발 화면에 입력 조건과 재시도 동작이 보인다. 복구 후 두 경우 모두 원래 검색어의 결과를 표시한다. |
| CAT-04 | 공개 중인 상품 상세의 첫 조회만 실패하게 한다. | 고객이 공유받은 상세 링크를 열고 같은 주소에서 다시 조회한다. | 처음에는 일시 오류와 재시도 동작이, 다음에는 공개 상품과 구매 가능한 옵션이 보인다. |
| CAT-05 | 목록을 연 뒤 해당 상품의 공개를 종료한다. | 첫 고객이 남아 있는 목록에서 상품을 누르고 다른 고객은 예전 상세 링크를 직접 연다. | 두 고객 모두 열람 불가 안내와 홈으로 가는 동작을 본다. 구매할 수 있는 옵션이나 담기 동작이 표시되지 않는다. |
| CAT-06 | 같은 상품에 품절 옵션과 재고가 있는 옵션을 둔다. | 고객이 필수 옵션 없이 담기를 누른 뒤, 품절 옵션과 판매 가능 옵션을 차례로 확인한다. | 빠진 선택을 보완하도록 안내한다. 품절 옵션의 구매는 제한되고 판매 가능한 옵션과 수량을 고르면 담기를 진행할 수 있다. |

**설계 검토 · CAT-03, CAT-04.** 일시 오류를 빈 검색 결과나 판매 종료와 똑같이 보이면 고객이 구매를 포기할 수 있다. 해당 요청을 복구했을 때 같은 조건으로 결과가 나타나는지 판정한다.

## A2. 가입하고 원래 하던 일로 돌아오거나 계정 접근을 복구한다

고객이 주문서나 회원 전용 기능에서 가입을 시작한다. 첫 그림은 고객프론트가 표시하는 가입 진행 상태다. 회원인증이 필수 동의 버전과 코드 유효성을 확인해 가입을 확정한다. 가입 뒤의 세션은 고객이 로그인했을 때 생긴다. [회원가입과 인증](../navigation/shopping-mall-navigation.md#s02-회원가입과-인증)

```state
<s> --> (약관 확인) : 가입을 시작하거나 동의 없이 가입 주소를 연다
(약관 확인) --> (정보 입력) : 현재 필수 약관에 동의한다
(정보 입력) --> (정보 입력) : 잘못된 값을 제출하거나 가입할 수 없는 정보다
(정보 입력) --> (약관 확인) : 제출할 때 약관 버전이 바뀌었다
(정보 입력) --> (코드 확인) : 인증 요청이 접수된다
(코드 확인) --> (코드 확인) : 코드를 잘못 입력하거나 재발송한다
(코드 확인) --> (정보 입력) : 요청이 만료되거나 정보를 수정한다
(코드 확인) --> (가입 완료) : 유효한 코드를 확인한다
```

**주요 상태와 전이**

- **정보 입력 → 약관 확인** · 가입 화면을 연 뒤 필수 약관이 바뀌면 고객은 새 버전을 확인해야 한다. **코드 확인 → 가입 완료**는 회원인증이 이번 가입 요청의 인증 코드를 확인해 계정을 만든 시점이다.

두 번째 그림은 고객프론트의 계정 접근 화면에 나타나는 진행 상태다. 회원인증이 로그인 세션과 일회용 재설정 권한을 각각 소유한다. 새 비밀번호를 설정하면 해당 링크의 권한을 소진한다. 회원 전용 기능은 새 세션의 회원과 대상의 소유권을 다시 확인한다. [로그인과 복귀](../navigation/shopping-mall-navigation.md#s03-로그인세션-만료로그아웃) · [비밀번호 재설정](../navigation/shopping-mall-navigation.md#s04-비밀번호-찾기재설정)

```state
<s> --> (로그인 필요) : 비회원이 보호 기능을 열거나 로그인 화면에 진입한다
(로그인 필요) --> (로그인 필요) : 자격 확인에 실패하거나 입력을 수정한다
(로그인 필요) --> (회원 기능 이용 가능) : 로그인 성공 후 접근 범위를 확인한다
(회원 기능 이용 가능) --> (로그인 필요) : 로그아웃이 완료되거나 세션이 만료된다
(로그인 필요) --> (재설정 메일 대기) : 형식이 올바른 이메일로 재설정을 신청한다
<s> --> (링크 확인 중) : 메일에 있는 재설정 링크로 직접 진입한다
(재설정 메일 대기) --> (링크 확인 중) : 받은 메일의 링크를 연다
(링크 확인 중) --> (링크 확인 중) : 확인 오류 후 같은 주소로 재시도한다
(링크 확인 중) --> (새 비밀번호 입력) : 사용 가능한 링크로 확인된다
(링크 확인 중) --> (새 링크 필요) : 만료됐거나 이미 사용했거나 유효하지 않다
(새 비밀번호 입력) --> (새 비밀번호 입력) : 입력 보완이 필요하다
(새 비밀번호 입력) --> (새 링크 필요) : 제출하는 사이 링크 효력이 끝난다
(새 비밀번호 입력) --> (로그인 필요) : 비밀번호 변경이 완료된다
(새 링크 필요) --> (재설정 메일 대기) : 고객이 이메일을 입력해 재발송을 신청한다
```

**주요 상태와 전이**

- **링크 확인 중 → 새 비밀번호 입력** · 회원인증이 재설정 링크의 사용 가능 여부를 확인하면 새 비밀번호를 입력할 수 있다. 입력 중 링크가 만료되면 제출할 때 새 링크를 요청하도록 안내한다.

## A3. 찜해 둔 상품을 다시 찾고 장바구니에서 주문 대상을 고른다

회원의 찜 목록은 회원과 상품의 조합별로 저장 여부를 관리한다. 장바구니는 고객이 담은 **옵션과 수량**을 소유한다. 이 예제에서는 담기 성공 시 장바구니, 찜 성공 시 찜 목록을 연다. 장바구니에 담아도 재고는 예약되지 않는다. [찜과 장바구니](../navigation/shopping-mall-navigation.md#s05-찜장바구니에-상품-담기) · [주문 진입 조건](../navigation/shopping-mall-navigation.md#s06-주문-진입과-비회원-주문-인증)

```state
<s> --> (찜 없음) : 해당 회원이 저장하지 않은 상품이다
(찜 없음) --> (찜 없음) : 저장 요청의 실패가 확정된다
(찜 없음) --> (찜에 있음) : 회원이 상품을 저장해 결과를 확인한다
(찜에 있음) --> (찜 없음) : 회원이 목록에서 해제를 확인한다
```

**주요 상태와 전이**

- **찜 없음 → 찜에 있음** · 저장이 확인되면 그 회원의 찜 목록에서 해당 상품을 다시 찾을 수 있다. 저장 실패가 확정되면 같은 상품을 다시 저장할 수 있다.

다음 그림은 장바구니 전체의 내용과 선택으로 정해지는 주문 진입 상태다. 주문서에 들어갈 때 선택을 다시 읽는다. 실제 판매 가격과 재고는 주문을 접수할 때 별도로 판정한다.

```state
<s> --> (빈 장바구니) : 담은 상품이 없다
(빈 장바구니) --> (상품 있음) : 유효한 옵션과 수량이 저장된다
(상품 있음) --> (주문 대상 선택) : 고객이 유효한 상품을 선택한다
(주문 대상 선택) --> (상품 있음) : 선택을 모두 해제한다
(주문 대상 선택) --> (주문 대상 선택) : 선택한 옵션의 유효 수량을 변경한다
(상품 있음) --> (빈 장바구니) : 마지막 상품을 삭제한다
(주문 대상 선택) --> (빈 장바구니) : 선택 중인 마지막 상품을 삭제한다
```

**주요 상태와 전이**

- **상품 있음 → 주문 대상 선택** · 담긴 옵션 중 주문할 행을 하나 이상 골라야 주문서를 열 수 있다. 선택을 모두 해제해도 담아 둔 행은 장바구니에 남는다.

| CART-05 | 고객의 장바구니에 서로 다른 상품 두 개를 담아 둔다. | 하나만 선택해 주문서에 진입한 뒤 되돌아와 선택을 바꾼다. | 주문서 상품과 수량은 그때 선택한 항목과 일치한다. 선택을 모두 해제하면 빈 주문이 생성되지 않는다. |
| CART-06 | 비회원이 한 상품만 선택해 주문자 인증 단계에 들어간다. | 같은 장바구니의 다른 탭에서 마지막 상품을 지운 뒤 원래 탭에서 인증을 마친다. | 연락처가 확인돼도 유효한 주문 대상이 없어 장바구니로 돌아간다. 상품을 다시 담아 주문할 수 있다. |

## A4. 비회원이 연락처를 인증해 주문하거나 기존 주문 한 건을 열람한다

주문 전 연락처 인증은 **이번 주문서**에 들어갈 자격을 준다. 이미 생성된 주문을 열람하려면 비회원이 **그 주문번호와 연락처**로 조회 인증을 다시 받아야 한다. 고객프론트가 각 인증의 진행 상태를 표시하고 회원인증이 권한을 판정한다. 주문은 조회할 때 인증된 번호와 실제 요청한 번호를 대조한다. [주문 전 비회원 인증](../navigation/shopping-mall-navigation.md#s06-주문-진입과-비회원-주문-인증) · [주문 한 건의 문자 발송·검증](../job-flow/system.md#s02-비회원이-주문-한-건을-열람할-권한-얻기)

```state
<s> --> (주문자 인증 필요) : 비회원이 유효한 주문 대상을 선택한다
(주문자 인증 필요) --> (주문자 코드 입력) : 인증 문자를 신청한다
(주문자 코드 입력) --> (주문자 코드 입력) : 코드가 다르거나 만료되어 다시 신청한다
(주문자 코드 입력) --> (주문자 인증 완료) : 입력한 코드가 이번 주문서의 연락처 인증에 성공한다
```

**주요 상태와 전이**

- **주문자 코드 입력 → 주문자 인증 완료** · 비회원이 이번 주문서에 입력한 연락처로 받은 코드를 제출하면 회원인증이 그 연락처를 확인한다. 성공하면 이 주문서 작성을 계속할 수 있다.

다음 그림은 기존 주문 한 건을 조회할 때 고객에게 보이는 인증 상태다.

```state
<s> --> (조회 인증 필요) : 비회원이 기존 주문을 열려고 한다
(조회 인증 필요) --> (코드 입력 대기) : 주문번호와 연락처로 인증을 신청한다
(코드 입력 대기) --> (코드 입력 대기) : 불일치 코드로 재입력 안내를 받는다
(코드 입력 대기) --> (검증 결과 대기) : 제출한 요청의 판정이 기한 내 도착하지 않는다
(코드 입력 대기) --> (해당 주문 열람) : 해당 주문의 미사용 조회 코드를 유효기간 안에 확인한다
(검증 결과 대기) --> (해당 주문 열람) : 같은 요청의 허용 결과가 확인된다
(검증 결과 대기) --> (코드 입력 대기) : 같은 요청에서 코드 불일치가 확인된다
(검증 결과 대기) --> (조회 인증 필요) : 같은 요청에서 코드 효력 종료가 확인된다
(코드 입력 대기) --> (조회 인증 필요) : 코드의 유효기간이 지났거나 이미 사용됐다
(해당 주문 열람) --> (조회 인증 필요) : 조회 권한이 만료되거나 다른 주문을 연다
```

**주요 상태와 전이**

- **조회 인증 필요 → 코드 입력 대기** · 화면은 주문번호와 연락처를 제출한 모든 고객에게 같은 접수 안내를 보여 준다. 주문 서비스가 해당 주문의 등록 연락처와 입력값을 대조하고, 일치하면 회원인증이 그 주문용 코드를 발급해 등록 연락처로 발송을 의뢰한다.
- **코드 입력 대기 → 해당 주문 열람** · 입력한 코드가 조회할 주문의 미사용 코드이고 유효기간 안에 있으면 그 주문 상세를 열 수 있다. 검증 응답이 늦으면 **검증 결과 대기**에서 같은 요청의 결과를 조회한다.

## B1. 주문서를 제출하고 구매 조건을 다시 확인한다

회원 또는 주문자 인증을 마친 비회원이 주문서에서 배송지·할인·결제 수단을 정한다. 그림의 주체는 **고객프론트의 주문서**다. 상품 서비스가 판매 조건을, 재고 서비스가 예약 가능 수량과 기한을, 주문 서비스가 고객이 동의한 주문 금액과 생성 결과를 소유한다. 이 예제는 주문서의 모든 항목을 확보한 경우에 한해 주문 한 건을 만든다. [주문서 작성·주문 생성](../navigation/shopping-mall-navigation.md#s07-주문서-작성주문-생성) · [주문 접수와 재고 예약](../job-flow/system.md#s05-1-주문-접수와-재고-예약)

```state
<s> --> (작성 중) : 선택한 상품으로 주문서 열기
(작성 중) --> (작성 중) : 필수 입력이나 약관 동의 보완
(작성 중) --> (제출 중) : 배송지와 적용 금액을 확인하고 제출
(제출 중) --> (인증 필요) : 회원 세션 또는 비회원 주문 인증 만료
(인증 필요) --> (작성 중) : 주문자 재인증 후 주문서 다시 열기
(제출 중) --> (조건 재확인) : 가격이나 할인 변경
(조건 재확인) --> (작성 중) : 변경 금액 확인 후 수정
(제출 중) --> (상품 재선택) : 판매 종료 또는 수량 부족
(상품 재선택) --> (작성 중) : 장바구니 구성을 바꿔 진입
(제출 중) --> (생성 확인 중) : 예약 또는 생성 결과 미도착
(생성 확인 중) --> (생성 확인 중) : 같은 제출을 조회해도 아직 미확정
(제출 중) --> (결제 가능) : 결제 대기 주문번호 수신
(생성 확인 중) --> (결제 가능) : 기존 제출에서 생성된 주문 확인
(제출 중) --> (생성 실패) : 주문 미생성 확정
(생성 확인 중) --> (생성 실패) : 재조회로 미생성 확정
(생성 실패) --> (작성 중) : 실패 사유 확인 후 다시 작성
```

**주요 상태와 전이**

- **제출 중 → 생성 확인 중** · 재고 예약이나 주문 생성의 응답이 늦으면 기존 제출을 다시 조회한다. 저장된 주문번호를 확인하면 그 주문으로 결제할 수 있고, 미생성이 확정되면 실패 사유에 맞게 주문서를 다시 작성한다.

| ORD-04 | 주문서에 구매 가능한 상품 두 종류를 담고, 그중 하나의 판매를 중단한다. | 고객이 이전에 열어 둔 주문서를 제출하고 판매 종료 상품을 제외해 다시 주문한다. | 첫 제출에서 문제 상품을 식별할 수 있다. 나머지 상품만 결제되는 시점은 고객이 새 구성을 제출한 뒤다. |
| ORD-05 | 고객 두 명이 같은 옵션의 마지막 한 개를 각자의 주문서에 담는다. | 첫 고객의 예약을 확정한 뒤 둘째 고객이 자신의 주문서를 제출한다. | 첫 고객만 해당 수량을 결제할 수 있다. 둘째 고객은 수량 부족 상품을 보고 장바구니에서 수량이나 상품을 바꿀 수 있다. |
| ORD-06 | 회원용 주문서와 비회원용 주문서를 별도 준비한다. | 제출 직전에 각각 회원 세션과 비회원 주문 인증을 만료시킨다. 각 고객이 다시 인증한 뒤 주문서를 제출한다. | 회원은 로그인, 비회원은 주문자 인증으로 안내된다. 재인증한 고객이 결제를 진행할 주문은 한 건이다. |
| ORD-07 | 본인 주문서 한 건의 생성 회신을 지연시킬 수 있게 한다. | 제출 직후 다시 누르고, 응답을 놓친 상태에서 주문 결과를 재확인한다. 이후 원래 요청의 성공을 회신한다. | 먼저 생성 확인 중이 보인다. 결제 화면과 주문 내역에 처음 제출한 상품·금액의 주문번호가 한 개만 남는다. |
| ORD-08 | 마지막 한 개를 예약한 뒤 주문 생성만 실패하도록 준비한다. | 고객이 제출하고 미생성 확정 안내를 확인한다. 예약 해제 뒤 다른 고객이 그 수량을 주문한다. | 첫 고객에게는 결제할 주문이 없고 실패 사유가 보인다. 둘째 고객은 해제된 수량의 주문번호를 받는다. |

**설계 검토 · ORD-03, ORD-07.** 금액이 달라지면 고객의 재동의가 필요하지만, 생성 결과만 늦으면 기존 제출의 조회가 필요하다. 변경 전후 금액과 ‘기존 주문 확인’을 각 상황에 맞게 구분해 표시하는 개선안을 검토한다. 채택하면 ORD-03과 ORD-07에서 첫 화면의 안내와 다음 동작을 각각 확인한다.

## B2. 결제창을 열고 돌아와 같은 거래의 결과를 확인한다

결제를 누른 고객은 결제사에서 쇼핑몰로 돌아오기도 하고 창을 닫은 뒤 주문 내역을 다시 열기도 한다. **결제 서비스**가 원래 요청에 대한 결제창 발급 결과와 결제 시도별 원거래 상태를 추적한다. 주문은 결제창을 고객에게 보내기 직전에도 주문 상태와 예약 기한을 확인한다. 이 예제에서는 결제사가 기존 요청의 발급 결과와 거래 상태 조회를 지원한다고 가정한다. [결제창 발급과 승인 확인](../job-flow/system.md#s05-2-결제창-발급과-승인-확인) · [외부 결제·결과 복구](../navigation/shopping-mall-navigation.md#s08-외부-결제실패취소결과-복구)

**결제창 발급 요청 한 건**

```state
<s> --> (발급 요청 중) : 결제 가능한 주문에서 결제 선택
(발급 요청 중) --> (주소 사용 가능) : 새 주소 또는 기존 유효 주소 확인
(발급 요청 중) --> (발급 확인 중) : 결제사 응답 미도착
(발급 요청 중) --> (사용할 주소 없음) : 미발급 확정
(발급 확인 중) --> (발급 확인 중) : 같은 요청 조회 결과 불명
(발급 확인 중) --> (주소 사용 가능) : 재조회로 유효 주소 확인
(발급 확인 중) --> (사용할 주소 없음) : 미발급 또는 주소 만료 확인
```

**주요 상태와 전이**

- **발급 확인 중 → 주소 사용 가능** · 결제사가 응답하지 않으면 원래 요청으로 발급 내역을 조회한다. 기존 결제창 주소가 살아 있으면 그 주소로 진입하고, 미발급이나 주소 만료가 확인되면 사용할 주소가 없는 상태로 표시한다.

**결제 시도 한 건의 승인 결과**

```state
<s> --> (승인 대기) : 결제 시도 시작
(승인 대기) --> (거래 확인 중) : 복귀 조회 또는 결제사 통지로 결과 대조
(거래 확인 중) --> (거래 확인 중) : 원거래 미확정 또는 조회 응답 유실
(거래 확인 중) --> (승인 확정) : 해당 거래의 실제 승인 확인
(거래 확인 중) --> (미승인 종결) : 거절 또는 고객 취소의 최종 결과 확인
(승인 확정) --> (승인 확정) : 동일 거래 재조회 또는 중복 통지
(미승인 종결) --> (미승인 종결) : 동일 거래 재조회 또는 중복 통지
```

**주요 상태와 전이**

- **거래 확인 중 → 승인 확정** · 결제 서비스가 해당 시도의 결제사 원거래에서 승인을 확인한 시점이다. 그 전에는 같은 거래를 재조회하고, 미승인이 확정된 뒤 주문이 결제 가능한 상태일 때 새 시도를 열 수 있다.

결제창 주소를 이미 받았더라도 주문이 취소·만료되면 고객에게 주문 상태를 안내한다.

## B3. 승인된 상품의 주문 확정 또는 환불 예정을 확인한다

고객은 결제 승인을 받은 뒤 어떤 상품이 실제로 출고되는지 확인한다. **주문 서비스**가 상품 수량별 이행 상태를 소유한다. 결제가 원거래 승인을 확인하고 재고가 판매 수량을 확정한 뒤, 주문이 확정된 상품을 배송에 전달한다. 한 주문 안에서도 취소 신청에 배정된 수량과 출고 수량의 결과가 다를 수 있다. [승인된 결제의 주문 확정](../job-flow/system.md#s05-3-승인된-결제의-주문-확정)

```state
<s> --> (결제 대기) : 주문과 예약 생성
(결제 대기) --> (확정 대기) : 원승인 금액 일치 및 확정 대상 수량 확인
(확정 대기) --> (확정 대기) : 예약 확정 회신 지연
(확정 대기) --> (출고 대상 확정) : 재고가 판매 수량 확정
(결제 대기) --> (이행 불가) : 늦은 승인에서 주문 만료 또는 금액 불일치 확인
(확정 대기) --> (이행 불가) : 해당 예약 만료 확정
(결제 대기) --> (취소 진행) : 취소 신청에 해당 수량 배정
(취소 진행) --> (취소 진행) : 같은 상품에 뒤늦게 승인 도착
(출고 대상 확정) --> (출고 대상 확정) : 이미 적용한 승인 다시 수신
```

**주요 상태와 전이**

- **확정 대기 → 출고 대상 확정** · 재고 서비스가 예약 수량을 판매 수량으로 확정해야 주문이 그 수량의 출고를 요청한다. 취소 신청에 배정된 수량은 **취소 진행**에 남아 기존 신청에서 정산한다.

이행 불가 수량은 주문이 보상 환불을 의뢰하고 그 상품의 남은 예약을 해제한다.

**설계 검토 · CONF-04.** 한 주문에 ‘확정’만 표시하면 고객은 취소 상품도 받을 것으로 예상할 수 있다. 상품·수량 옆에 출고 여부와 연결된 취소 신청을 표시하는 안을 검토하고, 채택하면 고객이 상세에서 두 상품의 후속 절차를 올바르게 찾는지 확인한다.

## B4. 환불이 지연된 이유와 최종 결과를 확인한다

이행 불가 상품에 보상이 필요해지면 고객은 주문 상세에서 해당 상품의 환불액을 확인한다. **결제 서비스**가 원거래에 대한 환불 의뢰 한 건의 상태를 소유한다. 주문은 그 결과를 같은 상품의 보상 내역에 반영하고 알림을 의뢰한다. 접수 여부를 알 수 없을 때는 원래 의뢰 번호로 조회한다. 운영 조사가 필요하면 담당자가 대시보드의 같은 건을 열어 결제사 거래 근거를 확인한다. [주문 확정 실패 후 환불 종결](../job-flow/system.md#s05-4-주문-확정-실패-후-환불-종결)

```state
<s> --> (의뢰 접수 중) : 주문이 보상 금액으로 환불 요청
(의뢰 접수 중) --> (환불 진행 중) : 결제사 접수 확인
(의뢰 접수 중) --> (접수 확인 중) : 접수 여부 불명
(접수 확인 중) --> (환불 진행 중) : 같은 의뢰의 접수 확인
(접수 확인 중) --> (미접수) : 같은 의뢰의 미접수 확정
(의뢰 접수 중) --> (환불 완료) : 접수 회신 전에 원거래와 환불액에 맞는 완료 통지
(접수 확인 중) --> (환불 완료) : 접수 재조회 중 같은 의뢰의 실제 환불 확인
(환불 완료) --> (환불 완료) : 종결 후 늦은 접수 회신이나 중복 완료 통지
(의뢰 접수 중) --> (미접수) : 접수 불가 사유 확인
(미접수) --> (의뢰 접수 중) : 일시 제한 해소 후 같은 의뢰 재접수
(미접수) --> (운영 조사 중) : 원거래 또는 금액 대조 필요
(환불 진행 중) --> (환불 진행 중) : 기한까지 최종 결과 미확정
(환불 진행 중) --> (환불 완료) : 의뢰 금액 전부의 실제 환불 확인
(환불 진행 중) --> (운영 조사 중) : 실패 통지에 근거 대조 필요
(운영 조사 중) --> (운영 조사 중) : 증빙 보완 요청
(운영 조사 중) --> (환불 완료) : 실제 환불한 거래와 금액 확인
(운영 조사 중) --> (최종 실패) : 대조 근거로 실패 확정
```

**주요 상태와 전이**

- **접수 확인 중 → 환불 진행 중** · 같은 의뢰를 결제사가 접수했음을 확인한 상태다. 원거래와 의뢰 금액에 맞는 실제 환불을 확인하면 **환불 완료**가 된다. 먼저 도착한 완료 통지도 같은 근거로 판정한다.

## C1. 운영자가 오늘 보낼 상품을 골라 택배사에 넘긴다

운영자는 포장 목록에서 **출고 건 한 건**을 선택한다. 배송 서비스가 주문 확정 수량으로 출고 건을 열고, 운송장 등록과 실제 인계 여부를 기록한다. 교환 출고에는 교환 의뢰에서 확정된 옵션·수량·배송지를 사용한다. [출고 건과 포장 목록](../job-flow/system.md#s06-1-주문-확정에서-운영자의-운송장-등록까지)

```state
<s> --> (포장 대기) : 출고할 수량 확정
(포장 대기) --> (포장 대기) : 운송장 정보 보완 필요
(포장 대기) --> (출고 중지) : 인계 작업 전에 중지 확정
(포장 대기) --> (인계 작업 중) : 유효한 운송장 등록
(인계 작업 중) --> (인계 작업 중) : 실물 인계 여부 미확인
(인계 작업 중) --> (출고 중지) : 취소 신청 상품을 보유한 채 인계 중단 확인
(인계 작업 중) --> (발송 확정) : 운영자가 실물 인계 확인
(출고 중지) --> (포장 대기) : 해당 중지 해제 후 출고 자격 확인
```

**주요 상태와 전이**

- **인계 작업 중 → 출고 중지 / 발송 확정** · 취소가 접수되면 배송은 해당 상자의 실물 위치를 확인한다. 창고가 인계를 중단한 수량은 출고 중지로 기록하고, 기사가 이미 인수한 수량은 인계 증빙을 확인해 발송으로 확정한다.

포장 목록을 조회하는 동안 출고 건은 현재 상태를 유지한다. 구매후처리는 배송이 중지 결과를 회신한 뒤에 취소 절차를 이어 간다.

## C2. 상품을 받았는데 배송 중이거나 같은 안내가 다시 도착한다

배송 서비스가 소유하는 **운송장별 배달 기록**을 본다. 고객의 실물 수령, 택배사의 완료 통지, 고객에게 보내는 메일은 각각 다른 시점에 일어난다. 아래 그림은 운송장 등록 직후부터 관찰한다. [배송 상태와 고객 안내](../job-flow/system.md#s06-2-발송-등록과-배송-완료에-따른-고객-안내)

```state
<s> --> (인계 작업 중) : 운송장 등록
(인계 작업 중) --> (발송 확정) : 실물 인계 등록
(인계 작업 중) --> (배달 완료) : 발송 등록보다 같은 운송장 완료 통지가 먼저 도착
(발송 확정) --> (발송 확정) : 수령 후 완료 통지 도착 전
(발송 확정) --> (배달 완료) : 해당 운송장의 첫 완료 통지

```

**주요 상태와 전이**

- **인계 작업 중 → 배달 완료** · 같은 운송장의 완료 통지가 발송 등록보다 먼저 와도 해당 출고의 배달 완료를 기록한다. 늦은 발송 등록과 중복 완료 통지는 추가 배송이나 알림을 일으키지 않는다.

알림은 배송이 처음 확정한 발송·완료 사건을 받아 고객 안내를 의뢰한다. 교환품이면 구매후처리가 해당 교환 출고의 배달 완료를 확인해 신청 마감을 진행한다.

## C3. 내 주문을 다시 열어 배송 경과를 확인한다

회원은 주문 목록에서, 비회원은 인증한 주문 상세에서 시작한다. 첫 그림은 **고객 화면의 주문 내역 조회 상태**다. 주문 서비스는 상세 진입 때마다 열람 권한을 확인한다. [주문 내역과 배송 조회](../job-flow/system.md#s06-3-권한을-확인한-주문의-배송-조회) · [회원 주문 화면](../navigation/shopping-mall-navigation.md#s09-회원-주문-조회배송-조회)

```state
<s> --> (목록 조회 중) : 회원이 주문 목록 열기
(목록 조회 중) --> (빈 목록) : 본인 주문 없음
(목록 조회 중) --> (목록 표시) : 본인 주문 있음
(목록 표시) --> (상세 조회 중) : 주문 선택
<s> --> (상세 조회 중) : 주문 상세 직접 열기
(상세 조회 중) --> (상세 표시) : 조회 권한과 주문 확인
```

## D1. 출고 전에 취소하고 환불 결과를 확인한다

고객이 주문 상세에서 취소할 상품과 수량을 제출한다. **구매후처리**가 취소 신청 한 건을 추적한다. 배송은 실물 인계를 확인하고, 주문은 취소 가능한 수량을 배정하며, 결제는 해당 수량에 배분된 승인 금액을 확인한다. 신청 화면에서 돌아가기만 하면 신청은 생기지 않는다. [취소 화면](../navigation/shopping-mall-navigation.md#s11-출고-전-주문-취소) · [출고 중지와 원거래 확인](../job-flow/system.md#s07-1-출고-중지와-취소-거래-확인)

```state
<s> --> (취소 가능 여부 확인 중) : 대상 수량을 제출
(취소 가능 여부 확인 중) --> (인계 확인 중) : 인계 작업 중에 중지를 요청
(인계 확인 중) --> (취소 불가) : 운영자나 택배사의 기록으로 인계를 확인
(취소 가능 여부 확인 중) --> (취소 불가) : 이미 인계됐거나 배정할 수량 없음
(취소 가능 여부 확인 중) --> (거래 확인 중) : 인계 전 중지와 취소 수량 배정 확인

(거래 확인 중) --> (환불 진행 중) : 취소 대상에 배분된 승인 금액 확인

(환불 조사 중) --> (주문 반영 중) : 조사에서 환불 완료 확인
(환불 조사 중) --> (환불 실패) : 조사에서 최종 실패 확인
(주문 반영 중) --> (취소 완료) : 해당 수량의 주문 및 재고 반영 확인
```

**주요 상태와 전이**

- **인계 확인 중 → 거래 확인 중** · 운영자가 실물 인계 중지를 확인하고 주문이 취소할 수량을 배정하면, 구매후처리가 같은 주문의 결제 시도를 조회해 환불할 금액을 확인한다.

결제사 응답이 늦으면 신청은 거래 확인 중에 머문다. 구매후처리가 같은 주문·결제 시도를 다시 확인한다. 환불을 마친 뒤 주문 회신만 유실됐으면 기존 수량의 반영 여부를 조회한다. 이때 고객에게 같은 돈을 한 번 더 환불하지 않는다. [신청 마감과 결과 재확인](../job-flow/system.md#s07-4-금융배송-결과로-신청-마감)

| CAN-01 | 결제 시도가 없는 주문에 동일 상품 두 개가 있고 인계 전이다. | 고객이 한 개만 취소하고 신청 상세와 주문을 다시 연다. | 신청은 한 개 취소 완료다. 차감된 금액이나 환불 내역은 없고, 고객은 남은 한 개 금액으로 결제를 진행할 수 있다. |
| CAN-02 | 전액 승인된 주문에 서로 다른 상품 두 개가 있고 둘 다 출고 전이다. | 고객이 한 상품을 취소한다. 결제사가 환불을 접수한 시점과 실제 환불 완료 후에 각각 조회한다. | 처음에는 해당 상품이 환불 진행 중이다. 주문 반영 뒤 그 상품만 취소 완료이고 환불액은 배분된 승인액과 같다. 운영자의 포장 목록에는 나머지 상품만 있다. |
| CAN-03 | 고객이 취소 폼을 열었고 배송 인계 기록은 아직 없다. | 기사가 먼저 상품을 인수하고 운영자가 발송을 등록한다. 고객이 열린 폼을 제출한다. | 고객은 최신 주문 상세에서 취소 불가 사유와 인도 후 반품 방법을 확인한다. 환불은 시작되지 않는다. |
| CAN-04 | 승인된 주문에 운송장을 등록한 운영자가 상품을 아직 갖고 있다. | 고객이 취소를 제출한다. 운영자는 대시보드의 인계 확인 대상에서 상품 보유 및 중지를 확인한다. | 고객은 처음에 인계 확인 중을 보고, 중지 확정과 승인액 대조 뒤 같은 신청에서 환불 진행을 본다. 운영자는 해당 수량의 출고 중지를 확인한다. |
| CAN-05 | 운송장 등록 후 고객이 취소를 신청해 인계 확인 중이다. | 운영자가 확인하는 동안 택배사의 배달 완료 통지가 먼저 온다. 고객이 기존 신청을 다시 연다. | 신청에는 인계에 따른 취소 불가와 반품 절차가 보인다. 뒤늦게 발송을 등록해도 같은 상품이 취소 완료로 바뀌지 않는다. |
| CAN-06 | 고객이 유효한 취소를 제출했고 접수 직후 회신만 끊긴다. | 다시 접속해 같은 요청으로 접수 여부를 확인하고 주문의 신청 내역을 연다. | 기존 신청 번호 한 건으로 돌아온다. 같은 상품의 취소 수량이나 환불 의뢰가 두 배가 되지 않는다. |
| CAN-07 | 취소 수량이 배정됐고 원래 결제 시도의 결과는 확인 중이다. | 고객이 화면을 닫은 뒤 결제사가 원래 시도의 승인을 확인해 준다. 고객이 신청을 다시 연다. | 확인 중이던 신청이 같은 번호로 환불 진행을 표시한다. 결제가 중복 생성되지 않고 취소된 수량의 승인액만 환불 대상이다. |
| CAN-08 | 승인된 두 개 중 한 개의 취소 환불이 끝났지만 주문 반영 회신이 늦는다. | 고객이 신청을 조회하고, 주문의 기존 반영 결과가 도착한 뒤 다시 조회한다. | 처음에는 취소 처리가 진행 중이며, 이후 한 개만 취소 완료다. 원거래 환불 내역은 한 건이고 나머지 한 개는 유지된다. |
| CAN-09 | 주문 상품 한 개의 취소 가능 수량이 다른 신청에 모두 배정됐다. | 같은 고객이 다른 창에 남은 이전 신청 폼에서 새 요청으로 한 개를 제출한다. | 취소할 수량이 없다고 안내한다. 원래 신청의 수량·번호가 유지되고 추가 환불을 신청할 수 없다. |

**설계 검토.** CAN-04와 CAN-05에서 고객이 운송장 발급만 보고 취소 결과를 잘못 판단할 수 있다. 신청 상세에 ‘운영자가 실물 인계 여부를 확인하고 있습니다’를 표시하는 안을 검토한다. 채택하면 인계 전 중지와 이미 인계된 경우에 각각 같은 신청이 올바른 결과로 이어지는지 다시 본다.

## D2. 받은 상품을 돌려보내고 환불을 확인한다

고객이 주문 상세에서 반품 수량·사유·수거 정보를 제출한다. **구매후처리**는 반품 신청을 소유한다. 배송은 택배사의 수거 사실을, 물류센터는 실제 입고와 검수 결과를, 결제는 환불 사실을 각각 확인한다. 이 예제에서는 반품 가능 기간 안에 있는 상품과 이미 기간을 넘긴 상품을 따로 준비한다. [반품 신청 화면](../navigation/shopping-mall-navigation.md#s12-배송-완료-후-반품교환) · [수거 접수](../job-flow/system.md#s07-2-반품교환-수거-접수) · [신청 종결](../job-flow/system.md#s07-4-금융배송-결과로-신청-마감)

```state
<s> --> (신청 자격 확인 중) : 반품 신청 제출
(신청 자격 확인 중) --> (신청 불가) : 대상이나 잔여 수량 또는 기간 조건 불충족
(신청 자격 확인 중) --> (신청 자격 확인 중) : 인도 기록이 늦어 같은 주문 재확인
(신청 자격 확인 중) --> (수거 접수 확인 중) : 인도와 반품 자격 확인
(수거 접수 확인 중) --> (수거 예정) : 택배사 접수 확인
(수거 접수 확인 중) --> (수거 불가) : 택배사가 미접수와 수거 불가를 확정
(수거 예정) --> (검수 대기) : 수거 완료 통지
(검수 대기) --> (반품 거절) : 실물 검수 거절
(검수 대기) --> (환불 진행 중) : 실물 검수 수락
(수거 예정) --> (환불 진행 중) : 수거 통지보다 검수 수락이 먼저 도착
(수거 예정) --> (반품 거절) : 수거 통지보다 검수 거절이 먼저 도착
(환불 진행 중) --> (환불 조사 중) : 결제 결과에 운영 확인 필요
(환불 조사 중) --> (환불 실패) : 최종 실패 확인
(환불 조사 중) --> (주문 반영 중) : 조사에서 환불 완료 확인
(환불 진행 중) --> (주문 반영 중) : 의뢰 금액 환불 완료 확인
(주문 반영 중) --> (반품 완료) : 주문이 해당 상품 수량의 반품 반영을 확인
```

**주요 상태와 전이**

- **수거 예정 → 환불 진행 중** · 물류센터의 실물 검수 수락이 수거 완료 통지보다 먼저 도착하면 환불을 진행한다. 늦게 온 수거 통지는 수거 이력에 추가한다.

환불이 끝나면 주문의 해당 수량에 반품을 반영한다. 반품한 상품의 재판매 가능 여부는 별도로 실물 상태를 확인해 결정한다.

## D3. 교환품을 예약하고 도착한 상품을 확인한다

고객은 받은 상품의 교환 옵션을 고른다. **구매후처리**가 같은 신청 번호로 원상품의 수거·검수와 교환품의 출고·인도를 추적한다. **재고**는 교환 옵션의 수량을 예약하고 검수 수락 후 출고 수량으로 확정한다. 고객에게 보이는 ‘교환 준비’와 실제 운송장 발급 사이에는 시차가 생길 수 있다. [검수 후 교환 출고](../job-flow/system.md#s07-3-검수-결과에-따른-환불과-교환-출고) · [교환품 인도 후 신청 마감](../job-flow/system.md#교환품이-고객에게-도착했을-때)

```state
<s> --> (교환 옵션 확인 중) : 인도와 교환 자격이 확인된 신청 제출
(교환 옵션 확인 중) --> (옵션 선택 필요) : 선택한 옵션의 수량 부족
(옵션 선택 필요) --> (교환 옵션 확인 중) : 고객이 다른 옵션을 선택해 제출
(교환 옵션 확인 중) --> (수거 접수 확인 중) : 교환 수량 예약
(수거 접수 확인 중) --> (수거 불가) : 택배사가 수거 불가 확정
(수거 접수 확인 중) --> (수거 예정) : 택배사 접수 확인

(수거 예정) --> (교환 거절) : 수거 통지보다 검수 거절이 먼저 도착
(교환 수량 확인 중) --> (교환 준비) : 교환 수량 확정
(교환 수량 확인 중) --> (공급 불가) : 예약 대조 후 공급 불가 확정

(주문 반영 중) --> (교환 완료) : 해당 주문 상품의 교환 반영 확인
```

**주요 상태와 전이**

- **교환품 배송 중 → 주문 반영 중** · 교환품 인도 통지의 출고 번호와 교환 신청 번호가 모두 맞으면 해당 주문 상품에 교환 결과를 반영한다. 주문이 반영을 확인하면 신청을 마친다.

수거와 검수에는 반품과 같은 회수 계약을 적용한다. 수거가 무산되거나 검수가 거절되면 교환에 배정한 예약 수량을 해제한다.

## D4. 배송받은 상품에 리뷰 한 건을 등록한다

**리뷰** 서비스는 회원과 주문 상품의 조합별로 리뷰 등록을 확정한다. 조회 시점과 제출 시점에 각각 회원 자격과 구매 상태를 대조한다. 주 객체는 해당 주문 상품의 리뷰 등록 여부다. 입력 폼의 내용은 고객프론트에 있으며 필수 항목을 보완하거나 로그인하는 동안 등록 상태는 그대로다. [리뷰 작성 화면](../navigation/shopping-mall-navigation.md#s13-구매-리뷰-작성) · [리뷰 자격과 등록 계약](../job-flow/system.md#s07-5-구매-리뷰-작성-자격과-등록)

```state
<s> --> (미등록) : 해당 회원의 주문 상품을 처음 조회
(미등록) --> (미등록) : 인증 필요·자격 없음·입력 보완·작성 취소
(미등록) --> (등록 완료) : 제출 시 회원과 구매 자격 및 입력 확인
(등록 완료) --> (등록 완료) : 같은 주문 상품을 다시 제출
```

**주요 상태와 전이**

- **미등록 → 등록 완료** · 제출할 때 회원, 인도 완료된 주문 상품의 구매 자격, 평점·본문을 확인한다. 같은 주문 상품에서 다시 제출하면 기존 리뷰 한 건을 안내한다.

| 시험 사건 | 연쇄와 판정 증적 |
| --- | --- |
| ① 창고가 실물을 보유 | 운영자가 실물을 확인하고 인계를 중단한다. [출고 건](#c1-운영자가-오늘-보낼-상품을-골라-택배사에-넘긴다) D01은 ‘인계 작업 중’에서 ‘출고 중지’로 바뀐다. PG가 취소를 확정한 뒤 고객의 C01에서 환불액 18,000원, PG의 P01에서 같은 금액의 취소 1건, 포장 목록에서 T01의 인계 가능 수량 0개를 대조한다. 이전 포장 화면을 다시 제출해도 같은 D01에서 인계 사실이 새로 생기면 실패다. |
| ② 기사가 이미 실물을 인수 | 운송장 W01을 기사 인수 기록과 대조한 뒤 운영자가 D01의 인계를 확정한다. D01은 ‘발송 확정’, C01은 ‘취소 불가’이며 고객은 회수 경로를 확인한다. 이 경로에서 P01의 즉시 환불은 0건이다. 같은 인계 사실을 다시 통지해도 두 번째 출고나 C01의 취소 승인이 생기면 실패다. |

두 시험에서 T01의 주문 원본, P01의 18,000원 승인, D01에 W01을 등록한 기록, C01의 신청 시각은 동일하다. 조건 ①의 창고 실물 확인과 조건 ②의 기사 인수 증빙만 달리 주입한다. 시험 자료를 바꿨는데도 두 경로가 모두 즉시 환불되거나 모두 취소 불가이면 실패다. 두 경로의 판정 시점은 현장 확인 뒤다. 확인 전에는 운송장 발급만으로 취소를 거절하거나 환불을 확정할 수 없다. 시험자는 주문 상세·포장 목록·PG 취소 내역의 식별자를 함께 기록한다. 이 사례는 가상 운영 규칙에 대한 기대 결과이며 실제 연동 시험은 별도로 수행한다.

## 먼저 결정할 정책과 남은 범위

| 후보 | 결정할 질문 | 결정 뒤 확인할 경계 |
| --- | --- | --- |
| CART-07 | 로그인 전에 담은 수량과 기존 회원 수량을 어떻게 합칠 것인가? | 합산 수량이 재고 한도를 넘는 경우까지 장바구니와 주문서의 수량·금액을 대조한다. |
| PAY-06, REF-02, REF-06 | 장시간 확인 중인 결제·환불을 언제 수동 확인으로 넘기고 누가 고객에게 결과를 알릴 것인가? | 인계 직전과 직후에 고객이 같은 거래를 다시 찾아 결과를 보는지, 승인·환불이 한 번만 반영되는지 확인한다. |

이 분석은 국내 단일 판매자의 실물 상품 주문을 가정한다. 마켓플레이스 판매자 정산, 정기 구독·디지털 상품, 해외 배송·통관은 다른 역할과 상태가 필요해 범위에서 제외했다. 쿠폰 중복 적용, 결제 수단별 입금 대기, 분실·파손 보상과 구체적인 반품 기한·비용은 실제 운영 정책을 받아 확장할 부분이다.
