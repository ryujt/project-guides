# 모듈 경계와 최소 맥락 가이드

목표는 **한 기능을 바꿀 때 해당 모듈의 구현과 직접 연결된 공개 계약만으로 판단할 수 있는 구조**다. 낮은 결합도는 상대 구현을 덜 알아도 되는 성질이고, 높은 응집도는 같은 이유로 바뀌는 규칙과 상태가 함께 있는 성질이다. 파일 수, 계층 수, 이벤트 수가 품질을 대신하지 않는다.

이 문서는 모듈 경계·계약·작업 맥락·변경 검증의 공통 기준이다. 방법론은 [method-R](method-R.md), 조율 방식은 [Orchestrator–Worker](orchestrator-worker-pattern-guide.md), 파일 배치는 [프로젝트 구조](project-structure-guide.md), 협업 실행은 [멀티 에이전트 프롬프트](../prompts/multi-agent-task-prompt.md)를 필요할 때 읽는다.

## 1. 적용 순서

1. 현재 사용자의 목표·범위·완료 기준과 실행 환경의 상위 지시를 확인한다. 이 가이드는 사용자가 정한 요구사항이나 프로젝트의 실제 제약을 덮어쓰지 않는다.
2. 현재 구현을 설명할 때는 코드·설정·테스트를 근거로 삼고, 제안 설계와 구분한다. 구현이 문서와 다르다고 곧바로 코드를 문서에 맞추지 않는다.
3. 기존 프로젝트의 명명·폴더·계약을 우선 사용한다. 개선이 필요한 경계만 근거를 남겨 바꾼다.
4. 작업에 해당하는 규칙만 적용한다. 적용하지 않는 중요한 항목에는 이유를 한 줄 적으며, 빈 템플릿을 채우기 위해 기능을 만들지 않는다.

## 2. 무엇을 한 조각으로 묶는가

모듈은 이름 붙은 책임과 공개 경계를 가진 코드 단위다. 작은 경우 함수 몇 개나 파일 하나로 충분하다. 패키지·서비스·배포 단위와 반드시 일치하지 않는다.

| 판단 | 분리할 근거 | 함께 둘 근거 |
| --- | --- | --- |
| 변경 이유 | 정책·릴리스·담당 책임이 따로 바뀐다 | 같은 요구사항 때문에 항상 같이 바뀐다 |
| 정보 | 계약만으로 상대를 사용할 수 있다 | 분리하면 내부 상태와 처리 순서를 계속 물어야 한다 |
| 상태 | 독립된 불변조건과 쓰기 소유자가 있다 | 하나의 원자적 불변조건을 함께 지킨다 |
| 검증 | 경계에서 입력·결과·실패를 검증할 수 있다 | 테스트마다 양쪽 내부 구현을 모두 대체해야 한다 |
| 수명·자원 | 독립된 생성·종료·확장이 필요하다 | 같은 수명과 트랜잭션 안에서 항상 실행된다 |

**분할 중단 조건**: 책임·불변조건·입출력·검증 방법이 명확하고, 외부 구현을 펼치지 않아도 해당 변경을 설명할 수 있으면 멈춘다. 한 줄 메서드를 감싸는 클래스, 전달만 하는 이벤트, 비어 있는 계층을 만들지 않는다. 분리 뒤 동시 수정과 탐색이 늘면 병합하거나 계약을 다시 설계한다.

## 3. 상대에게 무엇을 알려주는가

조각은 상대의 **공개 계약**만 안다. 계약은 함수 시그니처뿐 아니라 성공·실패·상태 변경·시간적 보장을 포함한다. 작은 내부 함수에는 타입·테스트·짧은 설명으로 충분하며, 모든 함수마다 계약 문서를 만들지는 않는다.

### 모듈 계약 양식

기존 타입·스키마·테스트가 기준 원본이면 경로와 식별자를 링크한다. 같은 정의를 문서에 복제하지 않는다.

```markdown
# 모듈: Orders

- 책임 / 비책임: 무엇을 보장하며 무엇은 다른 소유자에게 맡기는가
- 구현 위치 / 공개 진입점: 실제 경로와 export·함수·API·이벤트 이름
- 계약 원본: 타입·스키마·테스트 경로와 현재 버전 또는 기준 커밋
- 입력 / 결과: 필수 필드, 단위, 유효 범위, 빈 값·순서 의미
- 불변조건: 호출 전후에 항상 지켜야 하는 도메인 규칙
- 상태·데이터 소유권: 쓰기 소유자, 트랜잭션 범위, 외부 읽기 방식
- 의존: 소비하는 공개 계약과 조립 위치; 상대 내부 경로 의존 여부
- 부작용: DB 쓰기, 외부 호출, 이벤트 발행과 각각의 완료 시점
- 실패: 오류 코드·의미, 부분 성공, 타임아웃·취소 후 결과 불명 가능성
- 재시도: 담당 계층, 허용 오류, 횟수·전체 시간 상한, 멱등 키·중복 처리
- 수명 / 동시성: 생성·종료 책임, 동시 호출 가능 여부, 자원 정리
- 호환성: 알려진 소비자, 허용 변경, 이전·롤백 방법
- 검증: 계약 테스트·소유자 내부 테스트·필요한 통합 테스트 위치/명령
```

해당 없는 항목은 제거하거나 `해당 없음: 이유`로 표시한다. 필드 수를 맞추기보다 소비자가 내부를 몰라도 올바르게 호출할 수 있는지 확인한다.

## 4. 의존과 제어 흐름

기본 취향은 **상위 조율자가 형제 조각의 결과를 연결하고, 각 조각은 자신의 일에 집중하는 구조**다. 단일 작업은 직접 호출과 반환으로 표현할 수 있다. 여러 독립 작업의 순서·분기·복구를 연결할 때 조율자를 둔다.

- 조율자는 어떤 작업을 언제 호출하는지 정한다. 도메인 판정과 상태 불변조건은 해당 모듈이 소유한다.
- Worker는 다음 형제 Worker나 전역 서비스 탐색기를 찾아 호출하지 않는다. 자신에게 필요한 하위 순수 함수나 명시적으로 주입된 공개 계약은 사용할 수 있다.
- 계약은 그것을 보장하는 제공자가 관리한다. 소비자가 필요한 port를 선언하는 구조라면 소비자가 port를 관리하고 adapter가 양쪽 계약을 연결한다. 어느 경우든 변경 책임자를 명시한다.
- 외부 SDK·DB·파일·네트워크 접근은 경계 adapter/Gateway에 둔다. 도메인 코드로 SDK 객체·ORM 엔티티·DB 연결을 넘기지 않고 필요한 데이터로 변환한다.
- 생성과 의존 주입은 조립 지점에서 수행한다. 숨은 전역 상태, 다른 모듈 내부 import, 순환 의존을 경계 위반으로 점검한다.
- 같은 이름의 `utils`, `shared`, `common`에 도메인 규칙을 몰아넣지 않는다. 여러 곳에서 모양이 비슷해도 의미·변경 이유가 다르면 중복을 잠시 유지할 수 있다.

**정적 의존, 런타임 호출, 이벤트 전달, 배포 경계는 별도 관점**이다. 이벤트로 바꿔도 스키마·전달 순서·가용성에 대한 결합은 남는다. 화살표를 줄이기 위해 이벤트 버스나 마이크로서비스를 도입하지 않는다.

## 5. 상태·데이터와 실패의 소유권

- 각 변경 가능한 데이터와 불변조건에는 쓰기를 통제하는 모듈을 둔다. 여러 인스턴스는 그 모듈이 정한 동시성 정책 아래 동작한다.
- 다른 모듈은 소유자의 공개 명령·조회·이벤트 계약을 사용한다. DB를 함께 쓰더라도 테이블 직접 수정과 내부 스키마 결합을 허용한다는 뜻은 아니다.
- 조회용 복제본이나 캐시는 원본 소유자, 허용 지연, 갱신·폐기 규칙을 명시한다. 공유 읽기 모델은 쓰기 소유권과 구분한다.
- 하나의 트랜잭션이 필요한 규칙을 먼저 확인한다. 경계를 나눠 원자성이 사라지면 불일치 허용 범위와 복구 책임을 설계한다. 분산 처리가 필요하지 않으면 같은 모듈에 유지한다.
- 외부 호출의 타임아웃은 상대 작업 취소나 실패 확정을 뜻하지 않을 수 있다. 부작용이 있는 재시도에는 중복 방지와 결과 조회 경로를 둔다.
- 재시도는 같은 실패를 처리하는 한 계층에서 조율한다. 여러 계층의 재시도가 겹치면 총 시도·대기 시간과 책임을 명시한다.
- 이벤트를 쓰면 발행 조건, 페이로드 원본, 구독 연결 소유자, 전달·순서 보장, 중복·유실·재처리 정책을 적는다. 도식만으로 브로커 기능을 보장하지 않는다. 저장 직후 발행 전에 종료되는 경우도 고려하여 저장·발행의 원자성 또는 재발행·대사 정책을 정한다. Outbox 등은 이런 보장이 필요한 경계에서 선택하며 모든 모듈에 의무화하지 않는다.

## 6. AI에 전달할 작업 맥락

### 먼저 읽을 범위

저장소 인덱스 → 해당 작업 프롬프트 → 대상 모듈 계약과 구현 → 직접 소비·제공하는 계약 → 관련 테스트 순서로 좁혀 읽는다. 링크가 있다는 이유로 연결된 문서를 재귀적으로 모두 읽지 않는다. 긴 가이드는 적용 범위·목차를 확인한 뒤 필요한 절과 그 절의 필수 제약을 읽는다.

작업 시작 시 대상과 직접 연결된 호출자·소비자·조립 지점을 **검색**한다. 전역 검색은 의존의 위치를 찾는 데 사용하고, 발견한 모든 파일의 본문을 읽는 것으로 확대하지 않는다.

```markdown
## 작업 맥락 패킷
- 목표 / 비목표:
- 완료 기준: 관찰 가능한 동작과 검증 방법
- 기준 상태: 브랜치·커밋 또는 조사 시점, 기존 미커밋 변경
- 수정 소유 범위: 파일·모듈, 다른 작업과 공유하는 경계
- 읽을 자료: 대상 구현·공개 계약·관련 테스트의 경로와 필요한 절
- 관련 경계: 호출자·소비자 검색 결과와 변경 전후 계약
- 지켜야 할 불변조건 / 오류·부작용:
- 확인된 사실 / 가정 / 미확인 사항:
- 검증 명령 / 환경 / 아직 실행할 수 없는 항목:
- 맥락 확대 조건: 어떤 근거가 나오면 어느 파일·계약을 추가로 읽는가
```

이 패킷은 대화나 작업 기록에 짧게 전달한다. 별도 파일 생성은 재사용·인계가 필요할 때만 한다. 요약만으로 원본을 대체하지 않고 필요한 근거로 돌아갈 수 있게 경로를 남긴다.

### 맥락을 넓히는 조건

공개 시그니처·오류 의미·이벤트·스키마·공통 설정이 바뀌거나, 예상 밖 소비자·순환 의존·동시성·회귀 실패가 발견되면 관련 경계를 추가로 읽는다. `import`만으로 찾기 어려운 문자열 라우팅, 플러그인 등록, 이벤트 구독, 동적 로딩은 조립·설정도 확인한다. 외부 소비자는 저장소 검색만으로 전부 확인할 수 없으므로 알려진 계약과 버전 정책을 확인하고 미확인 범위를 남긴다.

맥락 한도를 맞추려고 필요한 의존을 숨기지 않는다. 읽은 범위가 커지면 원인이 나쁜 경계인지, 본래 여러 경계에 걸친 작업인지 구분한다.

## 7. 변경과 검증

1. **영향 확인**: 변경 요구사항을 책임 모듈·공개 계약·소비자·테스트에 연결한다. 여러 요구사항과 여러 설계 요소의 관계를 허용하고 누락을 검사한다.
2. **구현**: 소유 모듈 내부에서 해결할 수 있는지 먼저 확인한다. 새 공유 추상화는 실제로 공유할 의미와 변경 책임이 있을 때 도입한다.
3. **계약 확인**: 정상 입력뿐 아니라 비어 있는 입력, 오류, 부분 성공, 중복 호출 등 해당 경계의 반례를 검증한다. 모든 모듈에 같은 테스트 종류를 강제하지 않는다.
4. **통합 확인**: 타입·인터페이스 검사만으로 발견할 수 없는 실제 adapter 연결, 저장·발행 경계, 사용자 핵심 시나리오를 필요한 수준에서 확인한다. mock만 통과한 결과를 통합 성공으로 보고하지 않는다.
5. **호환성 확인**: 계약 변경 시 소비자·이전·롤백 경로까지 확인한다. 내부 변경이면 외부 계약이 유지됐다는 근거를 남긴다.
6. **독립 검토**: 작성자와 다른 에이전트 또는 분리된 검토 단계가 반례·범위 이탈·경계 누출을 확인한다. 필수 결함이 남으면 완료로 판정하지 않는다.

### 예시: 주문 취소 정책 변경

| 단위 | 공개 책임 | 내부에 감출 것 |
| --- | --- | --- |
| Orders | 취소 가능 상태 판정, 취소 요청/완료 상태 저장 | 주문 테이블, 상태 전이 구현 |
| Payments | 멱등한 환불 요청과 결과 조회 | 결제사 SDK, 결제 저장 스키마 |
| CancelOrder 조율자 | 주문·환불 계약의 호출 순서와 실패 복구 연결 | 각 모듈의 도메인 판정 |

새로운 취소 제한만 추가하면 Orders 구현·취소 계약·관련 테스트와 조율자의 호출 조건을 확인한다. Payments 구현 전체를 읽을 필요는 없다. 환불 오류의 의미가 달라지면 Payments 계약과 조율자의 복구·통합 테스트까지 범위를 넓힌다.

취소 가능 판정과 상태 변경은 Orders가 원자적으로 수행하거나 버전 조건으로 충돌을 막는다. 취소 진행 상태에서 출고 같은 경쟁 명령을 허용하는지도 Orders 계약에 정의하고, 취소·출고 동시 요청을 검증한다. 환불이 성공했는데 응답이 유실된 경우 조율자는 같은 멱등 키로 결과를 확인하고, Orders는 중복 완료를 안전하게 처리한다. 이 보장은 각 계약·테스트에 있어야 하며 “조각이 서로 모른다”는 설명만으로 해결되지 않는다.

## 8. 품질 평가

0점은 근거 없음/위반, 1점은 일부 충족·예외 명시, 2점은 확인 가능한 근거로 충족이다. 아래 점수는 비교 도구이며 합격을 자동 결정하지 않는다.

| 평가축 | 확인할 근거 |
| --- | --- |
| 응집도 | 같은 변경 이유·불변조건이 한 소유 범위에 모여 있는가 |
| 결합도 | 소비자가 공개 계약으로 작업하고 상대 내부를 참조하지 않는가 |
| 상태 소유권 | 쓰기·원자성·동시성·복구 책임을 식별할 수 있는가 |
| 맥락 효율 | 패킷만 받은 구현자가 필요한 근거를 찾고 제한된 범위를 수정할 수 있는가 |
| 검증 가능성 | 완료 기준에 정상·실패 반례와 실행 증거가 연결되는가 |
| 구조 비용 | 불필요한 계층·이벤트·문서 중복 없이 변경이 가능한가 |

대표 변경 하나로 변경 파일 수·읽은 구현 범위·계약 변경 수·검증 결과를 전후 비교한다. 절대 파일 수나 임의 점수 목표를 맞추지 않는다. 정적 리뷰만 했다면 실제 개발 시간·토큰 절감까지 검증했다고 주장하지 않는다.
