# 시스템 설계 문서 양식 — AS-IS·TO-BE 공통

시스템 수준 AS-IS·TO-BE 문서의 **파일 배치·절 번호·제목·표 열·그림 규칙·ID·검증** 원본이다. 조사·판단은 [AS-IS 프롬프트](../prompts/system-design-as-is-prompt.md)와 [TO-BE 프롬프트](../prompts/system-design-to-be-prompt.md)를 따른다. 같은 절 번호와 표 열로 현재와 목표를 대조한다.

**읽기 지도** — 할 일에 맞는 절만 읽는다.

| 할 일 | 읽을 절 |
|---|---|
| 산출물 폴더·파일과 분석 크기를 정한다 | [§2](#2-산출물-배치)·[큰 분석과 작은 분석](#큰-분석과-작은-분석) |
| 핵심 문서를 쓴다 | [§3](#3-핵심-문서-골격) — 번호표 3.1, 머리 블록 3.2, 절별 규칙 3.3(신규 설계는 [빼는 것](#신규-설계에서-빼는-것)) |
| 시스템·패키지 구성, 시나리오별 설계서와 화면별 레이아웃을 쓴다 | [필수 상세 설계서](#21-필수-상세-설계서)·[§4](#4-흐름-절--경계-수준-jobflow) |

| 경계별 상세와 내부 Job Flow를 쓴다 | [§5](#5-상세-문서-골격)·[§6](#6-경계-내부-job-flow-드릴다운) |

### 설계 문서의 Job Flow 작성 기준

이 기준은 AS-IS·TO-BE·기능·사이트 설계의 모든 `jobflow`에 적용한다. 아래 절의 파일 생성·표·해설 요구도 Job Flow에는 이 기준을 우선 적용한다. 다른 설계 관점의 산출 범위는 바꾸지 않는다.

- **실제 흐름에 참여하는 서로 다른 object가 3개 이상인 시나리오만 작성한다.** 각 그림의 `Object:`에 선언하고 흐름에서 사용하는 객체로 센다. 메서드·호출·분기 수나 같은 객체의 반복 등장은 객체 수에 더하지 않는다. 내부 드릴다운과 대표 그림에도 같은 기준을 적용한다.
- object가 1~2개인 흐름은 Job Flow 그림·전용 파일을 만들지 않는다. 수를 맞추려고 객체를 추가·분할하거나 무관한 시나리오를 합치지 않는다. 해당 시나리오의 요구·계약·검증은 기존 소유 문서에 유지하고, 시나리오 색인의 Job Flow 칸은 링크 없이 `—`로 둔다. Navigation 파일은 기존 기준을 따른다.
- **Job Flow 출력은 다이어그램과 바로 아래의 주요 흐름을 설명하는 짧은 문장만으로 구성한다.** 서두·목적·읽는 법·등장 객체 목록·계약표·근거표·추적표·단계별 장문 해설·재요약은 넣지 않는다. 여러 그림이 필요하면 이 구성만 반복한다. 주요 분기·실패·완료 의미는 필요한 만큼 짧게 설명한다.
- 분석의 깊이와 사실 확인은 유지한다. 계약·코드 근거·내부 추적·검증·미확인 기록이 필요하면 소유 경계의 계약·검증 절이나 근거 브리프에 둔다. 경계별 상세·브리프를 생략한 작은 분석은 구성 설명서의 소유 경계 소절에 둔다. 이 기록을 Job Flow 파일이나 그림 아래에 다시 붙이지 않는다.

## 2. 산출물 배치

한 분석의 산출물은 `docs/design/{DATE}/` 한 폴더에 둔다. 핵심 문서는 전체 줄거리를 설명하고, `details/`에는 시스템·패키지 구성 설명서, 시나리오별 Job Flow·Navigation 설계서, 화면별 Screen Layout 설계서를 반드시 둔다. 경계별 상세와 큰 분석의 근거 브리프가 이를 보완한다.

```text
docs/design/{DATE}/
  _evidence-brief.md            # 큰 분석: 기준선·경계 목록·이슈 색인·검증 기록·검토 반영·한계
  as-is/system-design-as-is.md  # 간명한 전체 설명과 상세 색인
  as-is/details/system-configuration.md
  as-is/details/package-configuration.md
  as-is/details/jobflow/<scenario>.md
  as-is/details/navigation/<scenario>.md
  as-is/details/layout/<screen>.md
  as-is/details/<boundary>.md   # 경계별 상세 — 아래 규모·범위 기준 적용
  to-be/_evidence-brief.md      # 큰 TO-BE 설계의 브리프 — 같은 DATE에 AS-IS 브리프가 있을 때
  to-be/system-design-to-be.md
  to-be/details/system-configuration.md
  to-be/details/package-configuration.md
  to-be/details/jobflow/<scenario>.md
  to-be/details/navigation/<scenario>.md
  to-be/details/layout/<screen>.md
  to-be/details/<boundary>.md
```

- `as-is/`·`to-be/`는 작성하는 쪽에 적용한다. 각각의 필수 상세 설계서는 [다음 절](#21-필수-상세-설계서)을 따른다. Job Flow 파일을 생성하는 시나리오는 Navigation과 같은 `<scenario>` 이름을 소문자·하이픈으로 쓴다. Navigation과 핵심 색인에서는 존재하는 Job Flow 파일만 링크하며, 생략한 파일의 링크는 만들지 않는다. Job Flow 파일에는 상호 링크 목록을 추가하지 않는다.
- 화면별 Layout 파일의 `<screen>`도 화면 식별자를 소문자·하이픈으로 쓰고, 다른 화면과 구분되며 Navigation의 화면 이름과 대응되게 한다. 전체 화면 목록이 길면 `details/layout/index.md`를 추가할 수 있다.
- **경계별 상세**는 독립 프로세스·모듈·패키지 묶음 단위로 `details/<boundary-name>.md`에 둔다. 파일 이름은 경계 이름을 소문자·하이픈으로 쓰며, 필수 구성 설명서와 이름이 겹치지 않게 한다. 고정 골격은 [§5](#5-상세-문서-골격)를 따른다.
- 작고 밀접한 두 경계의 상세는 한 파일에 `# A.` / `# B.` 두 부분으로 담을 수 있다. 절 번호는 `A.1`…, ID 번호대는 나눈다([§7](#7-id와-교차-참조)). 이 결합은 시나리오별 두 파일에 적용하지 않는다.
- `{DATE}`를 정하는 법과 AS-IS·TO-BE의 날짜 관계는 각 프롬프트가 정한다. 기존 문서 위치나 사용자 지정이 있으면 그것이 우선이다.
- 큰 TO-BE 설계의 브리프는 자리가 둘이다. 같은 `{DATE}` 폴더에 AS-IS 브리프가 있으면 그 파일을 고치지 않고 `to-be/_evidence-brief.md`를 따로 둔다. TO-BE가 새 `{DATE}` 폴더를 쓰면 `{DATE}/_evidence-brief.md`에 둔다([§8](#8-근거-브리프)).
- 검증 산출물(SVG·PNG)은 문서 폴더에 넣지 않는다([§10](#10-검증)).

### 2.1 필수 상세 설계서

아래 다섯 종류는 분석·설계 크기와 무관하게 반드시 생성한다. 시스템·패키지 구성 설명서는 각각 한 파일, Navigation 설계서는 범위 안의 시나리오마다 한 파일, Job Flow 설계서는 작성 기준에 해당하는 시나리오마다 한 파일, Screen Layout 설계서는 범위 안의 화면마다 한 파일이다. 시나리오나 화면이 하나여도 해당 파일을 만들고, 핵심 문서에 그림이 있다는 이유로 생략하지 않는다. 사용자가 산출 범위나 파일을 명시한 경우에는 그 지정을 우선하고 제외 범위를 기록한다.

| 파일 | 반드시 설명할 내용 |
|---|---|
| `details/system-configuration.md` | 실행 프로세스·서비스·배포 단위와 각 책임, 저장소·외부 시스템, 통신 방향·방식과 공개 접점, 기동·종료·수명과 실패 책임의 경계. 구성도와 설명을 함께 두고 코드·설정 또는 요구·결정 근거를 연결한다 |
| `details/package-configuration.md` | 주요 소스 디렉터리·패키지 트리와 각 책임, 공개 API·허용 의존 방향, 내부 구현과 공개 진입점의 구분, 조립 위치, 테스트·검증 위치, 실행·배포 경계와 패키지의 대응. 의존 라이브러리 목록만 나열하고 끝내지 않는다 |
| `details/jobflow/<scenario>.md` | [Job Flow 작성 기준](#설계-문서의-job-flow-작성-기준)에 해당하는 다이어그램과 바로 아래의 짧은 주요 흐름 설명만 작성한다 |
| `details/navigation/<scenario>.md` | 같은 시나리오의 사용자 과업·진입 조건·진입 방법, 화면·주소·소유 경계, `navigation`과 각 이동 단계의 설명, 이동을 결정하는 사용자 동작·API·판단 데이터, 성공·오류·취소·뒤로 가기·직접 진입·새로고침 중 해당하는 경로, 사용자에게 보이는 최종 결과와 근거·미확인 범위 |
| `details/layout/<screen>.md` | 화면 목적·진입/접근 조건·주소 또는 식별자, `layout` 블록과 영역 트리·배치 순서 설명, 영역별 역할·입력·출력·상호작용과 계약 링크, 적용되는 로딩·빈값·오류·권한 상태의 표시·배치 차이, 반응형 차이가 있으면 폭별 블록과 적용 조건, 근거·제안·미확인 범위 |

- 각 문서는 기준 날짜·범위·AS-IS 근거 또는 TO-BE 제안 상태, 핵심 문서의 해당 절 링크를 남긴다. 두 구성 설명서는 서로와 관련 경계 상세를, 시나리오별 두 설계서는 서로와 필요한 구성·경계 상세를 연결한다. 화면별 Layout은 핵심 §7·관련 Navigation·사용하는 계약을 링크하고 Navigation도 등장 화면의 Layout을 링크한다. 해당하지 않는 동작이나 확인하지 못한 근거는 이유와 함께 구분한다.
- Job Flow는 서비스·객체 협력, Navigation은 사용자가 보는 화면 이동과 그 판단, Screen Layout은 화면 안의 영역 배치·포함 관계를 설명한다. 각각 [Job Flow 가이드](job-flow-diagram-guide.md)·[Navigation 가이드](navigation-diagram-guide.md)·[Layout 가이드](screen-layout-guide.md)를 문법·의미의 원본으로 삼고 Mermaid로 바꾸거나 임의 문법을 추가하지 않는다.
- **화면 전수 식별**: 대표 시나리오에 등장한 화면만으로 범위를 정하지 않는다. AS-IS는 대상 라우트·화면 등록·진입점과 사용자 과업을, TO-BE는 요구·화면 계획과 유지 화면을 대조해 범위 안의 모든 화면을 찾는다. 주소 없는 앱 화면과 사용자 과업의 주요 오버레이·Dialog도 독립된 화면 식별자로 포함한다. 화면 내부 영역·컴포넌트는 해당 화면 파일 안에서 상세히 설명하며 모든 컴포넌트에 별도 파일을 강제하지 않는다.
- Screen Layout은 정상 화면의 블록만 두고 끝내지 않는다. 각 영역이 무엇을 표시하고 어떤 입력·동작을 받아 어떤 결과를 내는지, 적용되는 상태에서 무엇이 바뀌는지 설명한다. 상태 전이 자체는 소유 경계의 `state`·계약 원본을 링크한다. 반응형 조건은 본문에 쓰고, 필요한 화면 폭별로 `layout` 블록을 나누며 새 DSL 연산자를 만들지 않는다.
- UI나 화면 이동이 없는 시나리오도 Navigation 파일은 생성한다. 진입 조건·완료 결과, `해당 없음 — <UI 또는 이동이 없는 이유>`, 대응 Job Flow 링크를 적고 가짜 화면이나 이동 화살표를 만들지 않는다.
- 대상 범위에 UI가 없으면 가짜 화면이나 Layout 파일을 만들지 않고 핵심 §7·§8에 `Layout 파일 0개 — <UI가 없는 이유>`를 명시한다. UI는 있지만 화면 간 이동이 없는 경우에는 각 화면의 Layout 파일이 필요하다. Navigation 비대상 파일 의무는 앞 규칙대로 유지한다.
- TO-BE에서 유지되는 구성·시나리오·화면도 해당 파일을 생성하고 목표 기준의 설명을 작성한다. Job Flow·Navigation·Layout 파일에는 적용되는 목표 도표와 단계별 또는 영역별 상세 설명을 실제로 담고, AS-IS 링크만으로 대체하지 않는다. 목표 전제·완료 결과 또는 화면 구성·유지 근거를 적으며 AS-IS는 유지 판단과 계약·상태 원본의 근거로 링크한다. AS-IS 원본이 없어도 필수 설명·도표는 작성한다. UI/이동이 없는 Navigation은 앞의 비대상 기록 규칙을 따른다. 제거된 화면은 전수 색인에 제거 이유·근거와 AS-IS 원본 링크를 남기고 목표 Layout 파일은 요구하지 않는다.
- 계약·상태·이슈의 원본은 소유 경계 상세이며, 이를 생략하는 작은 분석은 [다음 절의 대체 위치](#큰-분석과-작은-분석)를 따른다. 경계 간 시나리오 그림·단계별 설명은 Job Flow 설계서, 화면 이동 그림·설명은 Navigation 설계서, 화면 영역 배치·설명은 화면별 Layout 설계서가 원본이다. 핵심 문서는 이들의 요약과 링크를 둔다. 같은 기준의 계약·상태 상세 원본을 여러 파일에 복제하지 않는다. AS-IS와 TO-BE는 각각의 기준을 설명하는 별도 설계서이므로 각 파일의 도표·단계별/영역별 설명 의무는 유지한다.

### 2.2 경계별 상세와 분석 규모

#### 큰 분석과 작은 분석

경계가 둘 이상이고 경계 사이 계약이 분석 대상이면 **큰 분석**이다 — 경계별 상세와 근거 브리프를 둔다. 경계가 하나이면 **작은 분석**이다 — 경계별 상세와 브리프는 생략할 수 있으나 핵심 문서와 [필수 상세 설계서](#21-필수-상세-설계서)는 모두 생성한다. 사용자가 핵심 문서만 요청하면 그 지정 범위를 우선하고 상세 제외를 명시한다. TO-BE의 큰 설계와 작은 설계도 같은 기준으로 가른다.

작은 분석에서 경계별 상세·브리프를 생략하면 아래에 배치한다. 핵심에는 판단에 필요한 요약을 두고 상세 설명은 관련 필수 설계서로 연결한다.

| 큰 분석의 자리 | 작은 분석의 자리 |
|---|---|
| 상세 「8. 이슈」 표 `ID \| 분류 \| 내용 \| 근거 \| 영향` | 핵심 §9가 원본이다. 접두 → 근거 표 매핑은 뺀다 |
| 브리프 §2의 조사 ID(경계마다 정하는 대문자 한 글자 — [§7](#7-id와-교차-참조)) | 핵심 §3 경계 표의 첫 열 `조사 ID` |
| 상세 §2 공개 계약, §4~§7 소유 상태·의존·실패 경계·검증 경계 | 계약은 시나리오 Job Flow의 계약표, 구성·의존은 두 구성 설명서에 둔다. 소유 상태·데이터·불변조건·수명과 실패 정책의 상세 원본은 `system-configuration.md`의 소유 경계 소절에, AS-IS 검증 결과·TO-BE 검증 계획은 담당 시나리오 Job Flow의 검증 소절 한 곳에 둔다. 핵심 §4·§6·§9.2에는 요약과 링크만 두고, 다루지 않은 것은 §8.1에 확인 범위 밖이라고 적는다 |
| 상세 §3 드릴다운 | 범위 안의 내부 드릴다운은 소유하는 시나리오 Job Flow 파일 한 곳에 별도 소절로 두고 [§6](#6-경계-내부-job-flow-드릴다운)을 따른다. 파일 수를 줄여도 내부 분석의 깊이·완료 기준은 줄이지 않는다. 다른 시나리오는 링크하고 핵심 5.N은 그 위치를 가리킨다. 사용자가 핵심 문서만 요청했으면 5.N과 §8에 상세 제외 이유를 적는다 |
| 상세·브리프의 근거 | 근거의 상세 내용은 각 필수 설계서에 두고, 핵심 §8 표 아래에는 필요한 관찰 요약과 원본 위치만 `관찰 항목 \| 경로·심볼 \| 확인한 동작 \| 사실·추론·미확인`으로 적는다 |
| 브리프 §1 기준선·§7 한계 | 핵심 머리 블록과 §8.1 |
| 브리프 §5 검증 기록·§6 검토 반영 | 최종 보고 |
| TO-BE 상세 §7 검증 계획, §8 위험·미확정 | 검증 계획은 담당 시나리오 Job Flow, 위험·미확정은 관련 구성 설명서 또는 시나리오 설계서 한 곳이 원본이다. 핵심 9.2·9.5에는 요약과 원본 링크를 둔다 |

- **부분 상세**(큰 분석인데 일부 경계에만 상세를 두는 것)는 사용자가 분석 범위를 좁혔을 때만 허용한다. 그 이유를 브리프 §1.1, 핵심 §8, §5의 드릴다운 색인(5.N)에 쓴다. 경계별 상세의 생략·통합 예외로 필수 상세 설계서를 생략하지 않는다.
- TO-BE 경계별 상세는 신규·변경 경계마다 하나다. 경계별 상세의 예외는 위와 같고, 유지되는 경계의 AS-IS 상세를 참조하는 규칙은 [§5](#5-상세-문서-골격)를 따른다.

## 3. 핵심 문서 골격

핵심 문서는 머리 블록과 번호가 고정된 §0~§9로 이뤄진다. 처음 보는 독자가 시스템의 목적, 주요 구성과 역할, 대표적인 시작부터 결과까지의 흐름, 중요한 문제나 설계 판단을 쉽게 따라가도록 간명하게 쓴다. 구성 전수·세부 계약·단계별 절차·긴 실패 분기·화면별 배치와 상태별 표시 설명은 필수 상세 설계서와 경계별 상세로 보내고 링크한다. 3.1은 번호와 제목, 3.2는 머리 블록, 3.3은 절마다 쓰는 법이다.

### 3.1 절 번호표

AS-IS와 TO-BE가 같은 절 번호를 쓴다. 첫 표는 절마다 담는 것이고, 둘째 표는 글자 그대로 쓰는 고정 제목이다.

| § | AS-IS | TO-BE |
|---|---|---|
| 머리 | 머리 블록 — DATE·기준 커밋·범위·근거·표기·원칙·공통 한계([§3.2](#32-머리-블록)) | 같은 머리 블록 + 설계 유형(신규 / 개선 / 혼합)·입력 근거(AS-IS 경로·커밋) |
| 0 | 한눈에 보기 — 토폴로지 Mermaid + 범례 + 요지 3~4줄 | 같음 — 목표 토폴로지(신규·변경·제거 구분), 요지 = 문제 → 해법 → 효과·남은 위험 |
| 1 | 핵심 용어 `용어 \| 뜻 \| 원본` | 같음 — 새 용어만 두고 AS-IS §1 링크 |
| 2 | 기능 — `사용자·업무 결과 \| 트리거 \| 책임 경계` + 기능 트리(PBS) 한 단락 | 기능·요구 — 2.1 사용자·업무 결과(`요구`·`AS-IS 대비` 열 추가), 2.2 요구 `R-ID`, 2.3 설계 항목 `C-ID`(`AS-IS 대비`·`상태` 열), 2.4 주요 결정 `D-ID`(대안·선택·근거·AS-IS 대비) |
| 3 | 구조 — 경계 표 `경계 \| 포트·형태 \| 한 줄 책임 \| 공개 진입점 \| 소유 상태 \| 나가는 의존` + 3.1 | 같은 표 + `AS-IS 대비` 열(신규·변경·유지·제거와 이유) |
| 4 | 경계별 기능 목록 — §3 행마다 `### 4.n`, `기능 \| 내용 \| 진입점` | 같음 + `AS-IS 대비`·`C-ID` 열 |
| 5 | 흐름 — 대표 경계 수준 `scope:` jobflow 한 장, 전체 시나리오 색인과 짧은 설명·상세 링크([§4](#4-흐름-절--경계-수준-jobflow)) | 같음 — 목표 계약, 시나리오 목록에 `AS-IS 대비` 열, 대표 실패 요약, 같은 시나리오는 AS-IS와 **같은 소절 번호** |
| 6 | 데이터 — 6.1 입력, 6.2 권위 소유자와 생명주기, 6.3 트랜잭션 경계 | 같음 — 목표 소유자, 이행 중 권위 |
| 7 | 주요 화면 요약 `화면 \| 주소 \| 핵심 상호작용 \| 서버 계약`, 전수 화면·Layout 색인 또는 색인 파일 링크 | 같음 |
| 8 | 상세·근거 인덱스와 한계 `상세 문서 \| 경계 \| 이슈 ID` + 8.1 | 같음 — ID 열은 `R`·`C`·`D`, 마지막 행은 입력 AS-IS 핵심·브리프 한 행(ID 칸은 물려받는 AS-IS ID) |
| 9 | 이슈 — 주제별 교차 뷰(전수 아님, 접두 → 근거 표 매핑 + 주제 소절) | 구현·검증·이행 — 9.1~9.5 |

TO-BE의 `AS-IS 대비` 열은 변화 종류이고, `상태` 열은 2.3에만 있는 설계 반영 여부다([§2 기능](#2-기능)). 신규 설계는 `AS-IS 대비` 열·불릿을 모두 뺀다 — [신규 설계에서 빼는 것](#신규-설계에서-빼는-것).

**공통 규칙**

- **번호는 고정한다.** 해당 없는 절도 제목은 남기고 본문에 `해당 없음 — <이유>` 한 줄을 쓴다(프레임워크의 이유 한 줄 생략과 같은 규칙). 그래야 앵커가 문서마다 같다.
- 고정 제목 뒤에 ` — <보충>`을 붙이지 않는다. 개수 같은 보충은 본문 첫 줄에 쓴다. 이름이 문서마다 다른 곳은 §0 요지, `4.n` 경계, `5.n` 시나리오와 선택 소절, AS-IS `9.n` 주제, TO-BE 2.4의 결정 주제다.
- **결론 줄**: §2~§5·§7과 TO-BE §9는 `**결론**:` 한 줄로 시작하고 → 표·도표 → 필요한 설명 순으로 쓴다. §6은 바로 아래에 결론을 두지 않고 6.1~6.3이 각자 결론으로 시작한다. AS-IS §9는 `**결론**: 이 절은 전수 목록이 아니다 — <원본 위치>`로 시작한다(작은 분석의 AS-IS §9는 `**결론**: 이 절이 이슈 원본이다 — …` — [§3.3](#33-절별-작성-규칙)). 교차 사실 같은 선택 소절도 결론 한 줄로 시작한다. §0은 요지가, §1·§8은 표가 그 역할을 하고, §5의 시나리오 소절은 짧은 설명과 상세 링크를 둔다([§4.3](#43-시나리오-절-구성)).
- 분량 목표(줄 수)는 두지 않는다. 핵심은 줄거리·판단의 요약과 상세 링크, 경계 간 흐름은 시나리오 Job Flow, 화면 이동은 시나리오 Navigation, 화면 배치는 화면별 Layout, 경계 안의 사실은 경계 상세가 맡는다. 같은 기준의 상세 원본을 핵심과 다른 상세에 반복하지 않으며, AS-IS·TO-BE 각 기준의 도표·해설 작성은 [§2.1](#21-필수-상세-설계서)을 따른다.
- 이슈·근거는 문장 끝에 ID로 인용한다(`B-01`). 실행으로 확인한 것만 문장이나 표 칸 끝에 (`사실·실행`)을 붙이고, 돌린 명령과 결과를 함께 적는다. 그 밖의 런타임 서술은 "코드상 예상"이다.
- 처음 쓰는 전문용어는 §1에 넣거나 그 자리에서 풀어 쓴다.
- 산출 문서에는 작성한 컴퓨터에서만 유효한 경로·링크를 남기지 않는다. 가이드를 가리키는 법은 [§3.2](#32-머리-블록)의 가이드 링크 규칙을 따른다.

### 3.2 머리 블록

핵심 문서 제목은 `# <시스템 이름> — AS-IS 시스템 설계서`(TO-BE는 `— TO-BE 시스템 설계서`)이고, 제목 다음에 blockquote 한 덩어리를 둔다. 아래 자리표시자를 조사 결과로 채운다.

```markdown
# <시스템 이름> — AS-IS 시스템 설계서

> **DATE** <날짜> · **기준 커밋** `<해시>`(<커밋 시각>·<브랜치·머지 맥락>), 작업 트리 <상태>
> **범위** <분석한 트리·경계>. <제외한 것>은 제외([근거 브리프 §1.2](../_evidence-brief.md))
> **근거** <방법 — 소스 역추출·경계별 병렬 조사·문서 대조> → [`_evidence-brief.md`](../_evidence-brief.md), 경계별 상세는 [§8](#8-상세근거-인덱스와-한계)
> **표기** 구조·의존은 Mermaid `flowchart`, 협력 흐름은 `jobflow`(`job-flow-diagram-guide.md`), 상태 전이는 `state`(`state-diagram-guide.md`), 화면 이동은 `navigation`(`navigation-diagram-guide.md`), 화면 배치는 `layout`(`screen-layout-guide.md`)
> **원칙** AS-IS는 현 코드를 있는 그대로 적는다. 찾은 결함은 고치지 않고 ID로 드러낸다([§9](#9-이슈--주제별-교차-뷰) — TO-BE 입력).
> **공통 한계** <띄우지 않은 프로세스·접속하지 않은 외부>. 런타임 동작은 코드상 예상이며, 실행으로 확인한 것만 (`사실·실행`)으로 표시한다.
```

TO-BE는 같은 블록에 두 줄을 더한다.

```markdown
> **설계 유형** 기존 시스템 개선 — <근거>. 혼합이면 영역별로 적는다
> **입력 근거** 요구 <원문 위치>, AS-IS [`../as-is/system-design-as-is.md`](../as-is/system-design-as-is.md)(DATE <날짜>·커밋 `<해시>`)
```

| 줄 | AS-IS | TO-BE | 쓰는 것 |
|---|---|---|---|
| DATE·기준 커밋 | 필수 | 필수 | DATE, 짧은 해시와 커밋 시각, 작업 트리 상태. 코드가 없는 신규 설계는 설계 기준 날짜만 |
| 범위 | 필수 | 필수 | 분석·설계한 범위와 제외한 것(TO-BE는 범위 밖 포함). 제외 근거는 브리프 §1.2 |
| 근거 | 필수 | 필수 | 관찰·설계 방법 + 브리프 링크 + §8 링크 |
| 표기 | 필수 | 필수 | 쓰는 DSL과 각 가이드 — 가리키는 법은 아래 가이드 링크 규칙 |
| 원칙 | 필수 | 필수 | AS-IS: 있는 그대로 적고 결함은 ID로. TO-BE: 확인된 사실·제안·가정·미확인의 표시법, 2.3의 `상태`가 구현 완료가 아니라 설계 반영 여부라는 것 |
| 공통 한계 | 필수 | 필수 | 실행·접속하지 못한 범위 |
| 설계 유형 | — | 필수 | 신규 / 개선 / 혼합과 그 근거 |
| 입력 근거 | — | 필수 | 요구 원문, AS-IS 문서의 경로·DATE·기준 커밋. AS-IS 문서가 없으면 요구·제약·외부 계약의 출처 |

- 머리 블록의 기준 커밋·범위는 브리프 §1과 같아야 한다.
- 머리 줄의 ` · `(양옆을 띄운 가운뎃점)은 굵은 필드 사이에만 쓴다. 한 필드 안에서는 낱말과 괄호 안 하위 항목을 `·`로 붙여 쓰고(`(<커밋 시각>·<브랜치·머지 맥락>)`), 구절을 늘어놓을 때는 쉼표로 잇는다. 상세 문서의 머리([§5](#5-상세-문서-골격))도 같다.
- **가이드 링크 규칙**: 가이드 사본이 산출 문서와 같은 저장소 안에 있을 때만 상대 링크를 건다(`[jobflow](<저장소 안 사본까지의 상대 경로>)`). 사본이 그 저장소에 없으면(개인 설치 사본 등) 링크하지 않고 가이드 파일 이름과 절 제목을 적는다(예: `job-flow-diagram-guide.md` 「scope 그림의 출발점은 실제 요청자다」). 저장소 루트를 넘는 `../` 링크는 다른 컴퓨터에서 깨진다 — [§10](#10-검증)의 `LINK-OUTSIDE` 경고가 이것을 잡는다.

### 3.3 절별 작성 규칙

절마다 무엇을 어떤 순서로 쓰는지 정한다. §5는 [§4](#4-흐름-절--경계-수준-jobflow)가 따로 정한다.

#### §0 한눈에 보기

- 순서: Mermaid `flowchart` 토폴로지 1장 → `**범례**` 한 줄 → `**요지**` 불릿 3~4개 → (선택) "정적 → 동적 순으로 전개한다" 한 줄.
- 토폴로지: 경계 = 노드(이름·포트·한 줄 역할), 같은 역할의 묶음 = `subgraph`, 외부 시스템 = 실린더 노드. 관계 종류(런타임 호출·기동 시 1회 등)가 둘 이상이면 선 모양을 달리하고 범례에 적는다. 경계 내부는 그리지 않는다.
- AS-IS 요지: 전체 그림, 핵심 책임, 구조의 성격, 가장 큰 약점. 각 줄 끝에 근거 ID를 단다.
- TO-BE: 신규·변경·제거를 `classDef`로 구분해 범례에 적는다(신규 설계는 [빼는 것](#신규-설계에서-빼는-것)). 요지는 문제 → 해법 → 효과·남은 위험이다.

#### Mermaid 라벨 안전 규칙

핵심·상세의 모든 Mermaid 블록에 적용한다. 문법을 바꾸는 규칙이 아니라 렌더러마다 다른 파싱 오류를 피하는 작성 규칙이다. `erDiagram`은 관계 라벨을 큰따옴표로 감싸고 2~4를 지킨다.

1. `flowchart`의 노드·엣지·`subgraph` 라벨은 큰따옴표로 감싼다 — `A["라벨"]`, `DB[("UsageDB")]`, `-->|"라벨"|`, `subgraph X["제목"]`.
2. 라벨 안에 괄호 `(` `)`를 쓰지 않는다. `·`이나 ` — `로 바꾼다.
3. 줄바꿈은 `<br/>`로 쓴다(`<br>` 금지).
4. 라벨에 예약어 `end`·`subgraph`나 연산자 `-->`·`==>`·`---`·`;`를 넣지 않는다.
5. Mermaid 렌더 도구가 있으면 그려 본다. 없으면 [§10](#10-검증)의 `MERMAID` 검사와 위 규칙 대조까지만 하고 정적 검토라고 적는다.

#### §1 핵심 용어

- 표 `용어 | 뜻 | 원본`. 원본은 정의가 있는 코드·문서 경로나 상세 절 링크다. 본문에서 정의 없이 먼저 나오는 약어·도메인 용어를 빠뜨리지 않는다.
- TO-BE §1은 새 용어만 두고 AS-IS §1을 링크한다. AS-IS 문서가 없으면 필요한 용어를 모두 둔다.

#### §2 기능

- AS-IS: 결론 → 표 `사용자·업무 결과 | 트리거 | 책임 경계`(행 하나 = 사용자가 얻는 결과 하나) → `**기능 트리와 소유 모듈**(PBS 관점):` 한 단락. 기능 트리는 묶음과 소유 경계를 적는다.
- TO-BE 소절과 표 열:

| 소절 | 표 열과 쓰는 법 |
|---|---|
| 2.1 사용자·업무 결과 | `사용자·업무 결과 \| 트리거 \| 책임 경계 \| 요구 \| AS-IS 대비` |
| 2.2 요구 | `R-ID \| 필요한 기능/해결할 문제 \| 근거 \| 성공 기준 \| 우선순위` |
| 2.3 설계 항목 | `C-ID \| AS-IS 대비 \| 무엇을 설계하나 \| 근거 요구·이슈 \| 소유 경계 \| 상태 \| 상세` |
| 2.4 주요 결정 | 결정마다 `#### D-01 <결정 주제>` → 표 `대안 \| 장점 \| 단점 \| 판단` → `선택`(목표 경계·계약)·`근거`(대안이 갈린 비교 기준)·`AS-IS 대비` 불릿. 장점·단점 칸은 앞머리에 비교 기준 이름(응집·의존 방향·작업 맥락·검증·이행/운영 비용)을 쓴다. 비교 기준의 원본은 TO-BE 프롬프트다 |

- **열 이름 하나에 뜻 하나**: `AS-IS 대비`는 변화 종류다 — 2.1·§3·§4·§5에서는 `신규`·`변경`·`유지`·`제거`, 2.3에서는 `신규`·`변경`. `상태`는 2.3에만 두고 설계 반영 여부 `반영`·`부분`·`보류`·`잠정`을 쓴다(구현 완료가 아니다).

#### 신규 설계에서 빼는 것

신규 설계(견줄 현재 시스템이 없는 설계)는 AS-IS와 견주는 열·불릿·표시를 모두 뺀다. 이 목록이 원본이고, 프롬프트와 이 가이드의 다른 절은 여기를 링크한다.

| 자리 | 빼는 것 | 대신 |
|---|---|---|
| §0 | 신규·변경·제거를 가르는 `classDef`와 그 범례 | 목표 토폴로지만 |
| 2.1·2.3·§3·§4 | `AS-IS 대비` 열 | —(2.3의 `상태` 열은 남긴다) |
| 2.4 | `AS-IS 대비` 불릿 | — |
| §5 | 시나리오 목록 표·노드 표의 `AS-IS 대비` 열 | 시나리오 번호는 `5.2`부터 |
| 9.4 | 처분 표 | `해당 없음 — 신규 설계` 한 줄 |
| 브리프 §2 | `AS-IS 대비` 열 | — |

- 머리 블록의 입력 근거는 요구·제약·외부 계약의 출처로 채운다([§3.2](#32-머리-블록)).
- 혼합 설계는 이 열들을 두고, 신규 영역의 행에 `신규`를 쓴다.

#### §3 구조

- 결론 → 경계 표 → `### 3.1 의존 방향에서 드러나는 사실` 불릿 3~5개.
- 시스템·패키지 구성의 상세 설명은 각각의 필수 구성 설명서를 링크한다. 경계 표에는 전체 구조를 이해할 책임·공개 접점·의존만 요약하고 패키지 트리나 배포 설정을 전량 싣지 않는다.
- `경계` 칸은 상세 문서 링크다(A/B 부분 문서는 그 부분의 앵커). 공유 패키지·조립 지점도 행으로 두고 `포트·형태` 칸에 형태나 `—`를 쓴다.
- `소유 상태`는 그 경계가 쓰기를 통제하는 파일·표·캐시다. `나가는 의존`은 실제로 부르는 경계·외부이며, 없으면 `0개`로 적는다.
- 3.1 불릿: 누가 흐름을 조율하는가, 예상 밖의 직접 호출, 깊은 결합, 의존이 없거나 문서 주장과 다른 경계. 각 불릿에 근거 ID.
- §3의 모든 행은 조사 ID 하나에 속한다(큰 분석은 브리프 §2, 작은 분석은 이 표의 첫 열 `조사 ID`). A/B 부분 문서는 두 행이 한 ID다.
- TO-BE의 `AS-IS 대비` 열에는 `신규`·`변경`·`유지`·`제거`와 이유를 쓴다. 없어지는 경계도 `제거` 행으로 남긴다. AS-IS 문서가 있으면 AS-IS의 행 순서를 그대로 두고 신규 경계는 표 끝에 더한다 — 그래야 같은 경계가 AS-IS와 같은 `4.n` 번호를 쓴다.

#### §4 경계별 기능 목록

- 결론 → §3 행 순서대로 `### 4.n <경계> :<포트>`(포트가 없으면 `(<형태>)`) → 표 `기능 | 내용 | 진입점`.
- 행 하나가 경계 안에서 코드가 실제로 하는 일 하나다. `진입점`은 라우트·메시지 소비자·타이머·부팅·CLI 같은 실제 시작점이다.
- 이 절에는 기능과 진입점만 둔다. 입력·오류·줄 번호 같은 계약 세부는 상세 §2가 원본이다.
- 진입점이 없는 묶음(공유 패키지·조립 지점)은 `패키지 | 기능`이나 `구성 | 기능` 2열로 쓸 수 있다.
- TO-BE 표는 `기능 | 내용 | 진입점 | AS-IS 대비 | C-ID`다. 유지 경계의 소절은 AS-IS 링크 한 줄로 대신할 수 있다(AS-IS 문서가 없으면 필요한 현재 맥락을 요약한다).
- TO-BE §3의 `제거` 행도 번호를 비우지 않는다. `### 4.n <경계> :<포트>` 아래에 `해당 없음 — 제거·<D-ID 또는 이유>` 한 줄을 쓴다 — §5의 없어진 시나리오와 같은 방식이다([§4.2](#42-전체-한-장과-시나리오-분할)).

#### §6 데이터

| 소절 | 표 열 | 쓰는 법 |
|---|---|---|
| 6.1 입력 | `입력 \| 출처·신뢰 경계 \| 형식·단위 \| 검증·누락 처리 \| 소유` | 프레임워크 [Input Data](system-design-framework.md#1-input-data) 표의 열을 따른다. 경계 단위라 마지막 칸은 `소유`이고, 그 입력의 소유 경계를 쓴다 |
| 6.2 권위 소유자와 생명주기 | `데이터 \| 권위 소유자 \| 저장 \| 보존 \| 일관성·실패 책임` | 쓰기 주체가 둘 이상이면 소유자 칸에 그 사실을 쓴다(예: `없음 — 쓰기 주체 둘`) |
| 6.3 트랜잭션 경계 | 표 없음 | 원자적인 구간과, 중간에 실패하면 남는 상태의 목록. 원본이 상세에 있으면 요약 + 링크 |

- 6.1~6.3은 각자 `**결론**:` 한 줄로 시작한다. `## 6.` 바로 아래에는 결론을 두지 않는다.
- TO-BE는 목표 소유자를 쓰고, 이행 중에 어느 쪽이 권위인지(이중 쓰기 기간 포함) 적는다.

#### §7 화면

- 결론 → 주요 화면 표 `화면 | 주소 | 핵심 상호작용 | 서버 계약` → 대표 이동과 화면 사이의 교차 사실(직접 진입·고정 되돌림·편집 동시성 등) → 전수 화면·Layout 색인 순서다.
- 주요 화면과 대표 이동 결과만 쉽게 설명하고, `navigation` 이동 다이어그램과 단계별 설명은 시나리오별 Navigation 설계서, 모든 대상 화면의 `layout`과 영역별 상세 설명은 화면별 Layout 설계서를 링크한다. 화면 상태 전수와 `state`의 원본은 소유 경계 상세이며 Layout은 상태별 표시·배치 차이를 설명하고 원본을 링크한다.
- **전수 화면·Layout 색인**은 `화면 | 주소·식별자 | 소유 경계 | Layout | 관련 Navigation | 근거·상태` 표다. [화면 전수 식별](#21-필수-상세-설계서)로 찾은 모든 화면·주요 오버레이·Dialog를 넣고 각 Layout 파일과 직접 연결한다. 주요 화면 요약이나 대표 시나리오에 나오지 않은 화면도 빠뜨리지 않는다. 주소가 없으면 화면 식별자를 쓰고, 관련 Navigation이 없으면 이유를 적는다. TO-BE의 제거 화면은 근거·AS-IS 링크와 `— 제거`로 구분한다.
- 전수 색인이 길면 같은 표를 `details/layout/index.md`로 옮기고 §7에는 전체·작성·제외 화면 수와 색인 링크를 둔다. 이 색인은 각 화면별 Layout 파일을 대신하지 않으며 핵심 §8에서도 찾을 수 있어야 한다.
- UI가 없으면 `해당 없음 — <이유>`, `Layout 파일 0개 — <이유>`와 각 시나리오 Navigation 파일의 비대상 기록 링크를 둔다. UI가 있으나 이동이 없다는 이유로 Layout을 생략하지 않는다.

#### §8 상세·근거 인덱스와 한계

- 표 `상세 문서 | 경계 | 이슈 ID`(ID 범위). 마지막 행은 근거 브리프다. 상세를 두지 않은 경계도 행을 남기고 이유를 쓴다 — 큰 분석에서 상세를 빼는 것은 사용자가 범위를 좁혔을 때뿐이다([큰 분석과 작은 분석](#큰-분석과-작은-분석)).
- 시스템·패키지 구성 설명서는 각각 행을 둔다. 시나리오별 두 설계서와 화면별 Layout 설계서도 빠짐없이 가리키되, 파일이 많으면 각각 §5.1의 전체 시나리오 색인과 §7의 전수 화면 색인 또는 `details/layout/index.md`로 연결할 수 있다. 필수 파일의 생성 여부와 확인 범위가 드러나야 한다. UI가 없으면 `Layout 파일 0개 — <이유>`를 명시한다.
- TO-BE는 마지막 열을 `ID`로 두고 그 상세가 다루는 `R`·`C`·`D`를 쓴다. 끝 행은 TO-BE 브리프(있을 때)와, 입력 AS-IS 핵심·브리프를 함께 가리키는 한 행(AS-IS 문서가 있을 때)이다. 그 AS-IS 행의 ID 칸에는 물려받는 AS-IS 이슈 ID를 쓴다(처분은 9.4).
- 작은 분석은 표 아래에 근거 표 `관찰 항목 | 경로·심볼 | 확인한 동작 | 사실·추론·미확인`을 둔다. 관찰 요약과 원본 위치만 남기고 세부 근거는 각 필수 상세 설계서에 둔다.
- `### 8.1 확인하지 못한 범위` — 번호 목록. 런타임·테스트 실행·원본 대조·외부 소비자처럼 확인하지 못한 것과 이유를 적는다.

#### §9 이슈 / 구현·검증·이행

AS-IS는 세 부분을 차례로 쓴다.

1. 첫 줄 `**결론**: 이 절은 전수 목록이 아니다 — 원본은 상세 「8. 이슈」 표와 브리프 §3이다`.
2. `접두 → 근거 표` 매핑. 접두마다 상세 이슈 절을 링크한다.
3. `### 9.n <주제>` 소절. 표 `ID | 한 줄`이나 ID 나열로 쓴다. 주제는 여러 경계에 영향이 겹치는 이슈 묶음이다(예: 조용한 열화, 중복과 정합성, 절반만 닫히는 중지, 문서와 코드의 불일치).

- AS-IS 작은 분석은 §9가 이슈 원본이다. `**결론**: 이 절이 이슈 원본이다 — <주제 요약>`으로 시작하고, 매핑 대신 이슈 표 `ID | 분류 | 내용 | 근거 | 영향`을 둔 뒤 주제 소절을 둔다.
- TO-BE: `**결론**:` 한 줄(무엇을 어떤 순서로 만들고 어떻게 확인하는가) → 아래 소절.

| 소절 | 쓰는 법 |
|---|---|
| 9.1 독립 작업 순서 | 표 `순서 \| 작업(C-ID) \| 쓰기 소유 \| 완료 기준 \| 검증`. 서로 기다리지 않는 작업은 같은 순서 번호로 둔다. 쓰기 소유가 겹치면 순서와 함께 밝힌다 |
| 9.2 검증 | 이미 실행한 검사와 구현 후 실행할 검증을 나눈다. 구현 후 검증 표는 상세 §7과 같은 `검증 \| 대상 계약·시나리오 \| 방법·명령 \| 시점`이다. 경계 안의 검증은 상세 §7이 원본이고, 여기는 경계를 넘는 것만 |
| 9.3 이행·롤백 | 배포 순서, 데이터 이전, 되돌릴 수 있는 범위, 되돌릴 수 없는 시점. 이행 대상이 없으면 `해당 없음 — <이유>` |
| 9.4 물려받는 이슈 처분 | 표 `AS-IS ID \| 처분 \| 근거` — 처분은 `C-n`·`D-n`·`보류`·`비대상`. AS-IS 문서 없이 개선하면 조사에서 찾은 결함을 행으로 두고 ID 칸에 출처를 쓴다. 신규 설계는 `해당 없음 — 신규 설계`([빼는 것](#신규-설계에서-빼는-것)) |
| 9.5 미확정·필요 입력 | 표 `항목 \| 잠정안 \| 영향 \| 필요 입력`. 경계 안의 미확정은 상세 §8이 원본 |

## 4. 흐름 절 — 경계 수준 jobflow

핵심 §5는 대표 흐름 한 장과 전체 시나리오 색인·요약을 두고, 시나리오별 그림·계약표·단계별 설명은 `details/jobflow/<scenario>.md`에 둔다. 핵심과 시나리오 설계서의 경계 수준 그림은 경계끼리의 요청·응답·이벤트만 `scope:` jobflow로 그린다. 경계 안의 협력은 경계 상세 §3에서 연다([§6](#6-경계-내부-job-flow-드릴다운)). 문법과 일반 의미는 [Job Flow 가이드](job-flow-diagram-guide.md)가 원본이다.

경계 수준 그림은 **L0 요약**이다. 시나리오 파일 전체를 L0만으로 끝내라는 뜻이 아니다. 각 시나리오에서 [§6.4 내부 추적과 완료 기준](#64-내부-추적과-완료-기준)에 따라 L1·필요한 L2 이하로 찾아갈 수 있어야 한다. HTTP 계약표·소스 파일 목록·긴 해설만으로 내부 객체·모듈의 협력 그림을 대신하지 않는다.

아래와 [§6](#6-경계-내부-job-flow-드릴다운)에서 **상위 §5 노드**는 핵심 §5 그림뿐 아니라 §5에서 링크한 모든 시나리오 Job Flow의 경계 수준 노드를 포함한다. 핵심의 대표 그림에서 생략했어도 시나리오 그림에 있는 계약은 드릴다운 대응에서 빠뜨리지 않는다.

- §5 첫머리: `**결론**:` 한 줄(대표 흐름은 어떻게 시작해 무엇으로 끝나는가, 조율자는 누구인가, 응답이 접수 확인인가 업무 완료인가) → 세부 흐름은 시나리오 설계서, 경계 안은 드릴다운 색인에서 연다는 한 문장.
- 소절 순서: `5.0 표기` → `5.1 전체 한 장`(끝에 전체 시나리오 목록 표) → `5.2`… 시나리오별 짧은 설명과 두 설계서 링크 → (선택) 트리거 비교·교차 사실 → 마지막 `5.N 경계 내부 Job Flow 드릴다운 색인`.

### 4.1 표기 약속

`### 5.0 표기`에는 핵심 그림에 필요한 약속과 객체 ↔ 경계 범례 표(`객체 | 경계 | 객체 | 경계` 2열 쌍)를 간명하게 둔다. 시나리오별 범례·계약 매핑은 해당 Job Flow 설계서에 둔다. 공통 문법은 복제하지 않고 [메시지 사용 범위](job-flow-diagram-guide.md#메시지-사용-범위), [실제 요청자](job-flow-diagram-guide.md#scope-그림의-출발점은-실제-요청자다), [선 교차 줄이기](job-flow-diagram-guide.md#선-교차-줄이기)를 따른다. 이 문서의 예외·해석만 덧붙인다.

| 약속 | 경계 수준 그림에 적용하는 법 | 원본 |
|---|---|---|
| 헤더 | 모든 그림이 `scope:`다. 경계 안을 그리지 않으므로, 조율자가 하나뿐인 흐름도 `orchestrator:`로 쓰지 않는다 | [헤더 키워드](job-flow-diagram-guide.md#헤더-키워드--orchestrator-vs-scope) |
| 노드 | `경계객체.공개계약`. 계약은 HTTP 라우트·메시지 소비자·타이머·부팅·CLI를 뜻이 보이는 이름으로 쓴다(`Boundary.action` = 해당 공개 계약). 원문 경로는 그림 아래 표에 둔다. 사용자 동작으로 시작하는 흐름은 화면 객체의 동작에서 출발한다(`Browser.submit` — 무엇인지는 시나리오 목록 표의 트리거 열이 말한다) | [시나리오의 시작점](job-flow-diagram-guide.md#시나리오의-시작점) |
| 실행 노드 | 응답(202 등)을 돌려준 뒤 따로 도는 실행 단위가 하류를 부르면 `<경계객체>.<실행>` 한 칸으로 둔다(`Boundary.work` — 접수 응답 뒤의 실행). 응답 전에 하류를 부르는 계약 처리기는 그 계약 노드가 출발점이라 실행 노드가 없다. 실행 단위마다 한 칸이고, 종결 입구와 달리 경계마다 하나로 제한하지 않는다. 같은 경계 안에서 별도 스레드로 넘긴 일은 넘긴 노드에서 출발시켜도 된다(`Boundary.OnReady --> Client.send`). 실행 안의 단계와 결과 갈래(중지 확인 등)는 그리지 않고 상세 드릴다운에서 연다 | [출발점은 실제 요청자](job-flow-diagram-guide.md#scope-그림의-출발점은-실제-요청자다) |
| 종결 입구 노드 | 여러 트리거(회신·생존 확인·마감)가 모이는 단일 종결 입구는 한 칸으로 둔다(`Boundary.finish`). 경계마다 하나까지다. 같은 경계 안 화살표(`Boundary.receive --> Boundary.finish`)는 종결 입구로 들어가는 길을 보일 때만 쓴다 | [합류와 재호출 구분](job-flow-diagram-guide.md#합류와-재호출-구분) |
| 다음 동작 노드 | 응답을 받은 원 요청자의 다음 동작(화면 표시·다음 요청)은 요청자 객체의 한 칸으로 둔다(`Browser.showResult`) | [출발점은 실제 요청자](job-flow-diagram-guide.md#scope-그림의-출발점은-실제-요청자다) |
| 묶음 노드(5.1 전용) | 5.1에서는 같은 요청자 → 제공자 사이의 여러 계약을 한 칸으로 묶을 수 있다(`Boundary.operate` = 관련 운영 API). 묶은 계약은 5.1의 읽는 법 불릿에 적고, 시나리오 그림에서는 실제 계약 노드로 연다 | — |
| 그릴 객체 | 실제 홉이면 관통 프록시도 그린다(`Proxy.forward`). 여러 경계가 직접 읽고 쓰는 디렉터리는 객체로(`SharedDir`), 외부 시스템도 객체로 둔다(`ExternalStore`·`Sender`). 프로세스 안에 링크되는 공유 라이브러리는 경계 사이에서 주고받는 것이 없어 그리지 않는다 | — |
| 프록시를 지나는 응답 | 응답 화살표는 프록시 칸을 생략하고 원 요청자에게 바로 잇는다 — 요청자의 다음 동작 노드로(`Provider.get --> Browser.showResult`). 응답이 같은 프록시를 지나 돌아간다는 것은 5.0 불릿에 한 줄로 적는다 | [출발점은 실제 요청자](job-flow-diagram-guide.md#scope-그림의-출발점은-실제-요청자다) |
| 결과 전달 | 다음 동작은 메서드끼리 잇고, 접수 확인인지 업무 완료인지 표나 불릿에 적는다. 호출자에게 돌려주는 응답 경계를 명시할 때의 표기는 원본을 따른다 | [표시할 결과 선택](job-flow-diagram-guide.md#표시할-결과-선택) |
| 한 노드로 모이는 화살표 | 합류인지 재호출인지와, 두 번째 진입을 막는 가드를 불릿에 적는다. 합류 뒤 후속이 일부 결과에만 해당하면 해당 조건의 이벤트에서 잇고, 조건과의 대응을 설명한다(`Boundary.OnReady --> Client.send`) | [합류와 재호출 구분](job-flow-diagram-guide.md#합류와-재호출-구분) |

**예외 노드** — 실행 노드·종결 입구 노드·다음 동작 노드·묶음 노드를 이렇게 부른다. 경계 수준 그림에서 위 노드 행의 꼴(공개 계약 하나, 또는 사용자 동작 출발점)을 벗어나는 칸은 이 넷뿐이다. 별도 소유 문서의 계약 기록에 공개 계약이 아니라는 것과 그 역할을 적고, 묶음 노드는 5.1의 읽는 법 불릿에 묶은 계약과 펼쳐 볼 시나리오 링크를 적는다.

### 4.2 전체 한 장과 시나리오 분할

`### 5.1 전체 한 장`은 시스템의 주된 줄거리를 이해할 대표 경계 간 흐름 한 장이다. 모든 계약·운영 분기·복구 경로를 한 그림에 밀어 넣지 않는다.

- 대표 그림에서 뺀 기동·운영·실패 회수 등의 흐름은 "읽는 법"에 범위를 짧게 밝히고 시나리오 색인과 상세 설계서에 빠짐없이 둔다.
- 그림 다음 순서: `**읽는 법**` 한 단락(시작 주체·주요 경유 경계·최종 결과) → 필요한 불릿(묶은 계약, 접수와 완료의 차이, 생략 범위) → 전체 시나리오 목록 표 `§ | 시나리오 | 트리거 | 완료 사실 | Job Flow | Navigation`(§ 칸은 소절 링크, 뒤 두 칸은 각각 실제 상세 파일 링크, TO-BE는 `AS-IS 대비` 열 추가).
- **분할 기준**: 트리거·조율자·완료 사실 중 하나라도 서로 다른 흐름이 둘 이상이면 시나리오로 나눈다. 큐 메시지·콜백·완료 이벤트처럼 경계를 넘는 비동기 이음에서 조율자가 바뀌면 다른 트리거로 센다. 트리거는 사용자 동작·타이머·기동·외부 이벤트·실패 회수 같은 것이다.
- 흐름이 하나뿐이어도 시나리오 목록 한 행, `5.2` 요약과 두 상세 파일을 둔다. 마지막 드릴다운 색인은 이때 `5.3`이다. 같은 트리거의 작은 변형은 해당 시나리오 설계서에서 설명한다.
- 객체 수는 보조 기준이다. 시나리오 그림 하나의 객체가 대략 8개를 넘으면(예시 기준, 강제 수치 아님) 해당 상세 파일 안에서 단계로 더 나눌지 본다. 5.1의 배치가 복잡해지면 주된 흐름만 남기거나 묶음 노드를 사용하고, 상세 시나리오가 범위를 모두 설명하는지 확인한다.
- 시나리오 소절 제목은 `### 5.n <시나리오 이름>`이다.

**TO-BE**

- AS-IS 문서가 있으면 같은 시나리오는 AS-IS와 같은 소절 번호와 파일 식별자를 쓰고, 유지되는 계약은 AS-IS와 같은 노드 이름을 쓴다. AS-IS의 선택 소절(교차 사실 등)도 번호를 유지한다. 바뀌지 않는 시나리오도 TO-BE의 두 상세 파일에 목표 전제·완료 결과·유지 근거와 적용되는 목표 도표·단계별 설명을 실제로 작성한다. AS-IS 링크는 유지 판단·계약 원본의 근거이며 목표 도표·설명을 대신하지 않는다.
- 이전 양식의 단일 흐름 AS-IS에 시나리오 소절이 없으면 TO-BE에서 `5.2`를 부여하고 AS-IS `5.1`과의 대응을 밝힌다. 이때 마지막 드릴다운 색인 번호가 밀린 이유도 적는다.
- AS-IS 문서가 없으면 시나리오 번호는 `5.2`부터 매기고, 바뀌는 흐름의 현재 모습은 필요한 만큼 불릿으로 요약한다.
- 없어진 시나리오는 제목을 남기고 `해당 없음 — 제거·<D-ID 또는 이유>`와 AS-IS 원본 링크를 쓴다. 시나리오 색인의 두 상세 링크 칸은 `— 제거`로 두며 목표 범위에서 제거된 시나리오에는 TO-BE의 두 파일 생성을 요구하지 않는다.
- 새 시나리오는 AS-IS 번호를 다시 쓰지 않고 드릴다운 색인 바로 앞 번호를 받는다. 그래서 새 시나리오가 AS-IS 선택 소절 뒤에 와도 된다 — 같은 시나리오와 선택 소절의 번호를 지키는 것이 먼저다. 드릴다운 색인은 항상 마지막이라 번호가 그만큼 밀린다.
- 대표 실패 흐름(타임아웃·부분 실패·회수 중 하나 이상)은 핵심에서 결과·책임을 짧게 설명하고 해당 시나리오 상세로 연결한다. 상세 설계서는 범위 안의 다른 실패 경로도 다룬다.
- 신규 설계는 [신규 설계에서 빼는 것](#신규-설계에서-빼는-것)을 따른다.

### 4.3 시나리오 절 구성

핵심의 `### 5.n <시나리오 이름>`은 누가 무엇을 시작해 어떤 결과를 얻는지, 주요 경계가 어떻게 협력하는지 짧고 쉬운 설명을 쓴 뒤 **Navigation 링크와, 생성한 경우에만 Job Flow 링크**를 둔다. 세부 그림·노드 계약표·단계별 절차를 핵심에 다시 싣지 않는다. 기존 소절 번호와 앵커는 보존한다.

`details/jobflow/<scenario>.md`는 [Job Flow 작성 기준](#설계-문서의-job-flow-작성-기준)에 해당할 때만 생성하고, 다이어그램과 바로 아래의 짧은 주요 흐름 설명만 담는다. 계약·근거·내부 추적·검증 기록은 이 기준에서 정한 소유 문서에 둔다.

Navigation 설계서의 필수 내용과 UI 비대상·TO-BE 유지 예외는 [§2.1](#21-필수-상세-설계서)을 따른다. 시스템·내부 상태 전이를 화면 이동으로 바꿔 넣지 않는다.

**선택 소절** — 시나리오 뒤, 드릴다운 색인 앞에 둔다.

| 소절 | 언제 | 모양 |
|---|---|---|
| 트리거 비교 | 같은 결과에 이르는 길이 여럿이고 주체가 갈릴 때 | 표 `흐름 \| 조율자 \| <비교할 주체> … \| 보관` — 열은 비교 대상에 맞춘다 |
| 교차 사실 | 한 작업의 상태를 두 경계가 따로 소유하는 것처럼 경계를 넘는 사실 | 결론 한 줄 + 비대칭 표 + 소유자별 상세 링크. `state` 블록은 소유자 상세에만 둔다 |

### 4.4 드릴다운 색인

`### 5.N 경계 내부 Job Flow 드릴다운 색인`은 항상 §5의 마지막 소절이다.

- 첫 문장: 핵심과 연결된 모든 시나리오 그림의 각 노드는 경계 상세의 내부 Job Flow 절로 대응되며, 상위 노드의 입력·출력·실패 의미는 하위 그림의 진입점과 같다. 상위 별칭과 실제/제안 심볼의 이름이 다르면 [내부 추적표](#64-내부-추적과-완료-기준)의 근거로 연결한다. 경계별 상세를 생략한 경우에는 아래 이유와 대체 위치를 밝힌다.
- 표 `경계 | 내부 Job Flow 절 | 그림 수 | 상위 노드 → 대표 하위 그림`. 절 칸은 상세 §3 앵커 링크([§7](#7-id와-교차-참조)의 고정 앵커), 그림 수는 그 절의 jobflow 블록 수, 대표 칸은 `상위 노드 → JF-n → JF-n.m` 꼴의 경로 1~3개다. 경로는 상위 노드 이름으로 시작한다.
- 표 다음에 `**드릴다운에서 드러난, 상위 그림을 읽을 때 알아야 할 사실**` 불릿 2~4개를 둔다. 예: 상위의 두 노드가 경계 안에서 한 함수로 합류한다, 상위 노드에 대응하는 코드가 그 경계에 없다(호출자가 라우트를 조합한 이름), 접수 응답이 업무 완료보다 먼저 온다.
- 상세가 없는 경계도 행을 두고 절 칸에 `—`, 대표 칸에 이유를 쓴다([큰 분석과 작은 분석](#큰-분석과-작은-분석)).
- 경계별 상세를 생략한 작은 분석의 절 칸은 시나리오 Job Flow 파일에 둔 내부 드릴다운 소절 링크다([큰 분석과 작은 분석](#큰-분석과-작은-분석)). 핵심에는 내부 그림을 다시 싣지 않는다.

## 5. 상세 문서 골격

경계 하나를 고치는 사람이 읽는 **경계별 상세**의 머리와 고정 절이다. 경계 1개 = 파일 1개다(A/B 부분 문서는 [§2](#2-산출물-배치)). 두 구성 설명서·시나리오별 설계서·화면별 Layout 설계서는 이 골격을 강제하지 않고 [필수 상세 설계서](#21-필수-상세-설계서)를 따른다. 머리는 제목과 blockquote다.

```markdown
# <경계> (:<포트>) — AS-IS 상세

> **대상**: `<대상 경로>/**`(소스 N파일·M줄) · **기준**: 커밋 `<해시>`·<날짜>, 작업 트리 <상태>
> **근거 색인**: [`../../_evidence-brief.md`](../../_evidence-brief.md) · **상위**: [`../system-design-as-is.md`](../system-design-as-is.md) · **짝**: [`<짝 문서>.md`](<짝 문서>.md)
> **표기**: <이 상세에서 처음 쓰는 DSL — 있을 때만>
> **범위 한정**: <다루지 않는 영역과 이유 — 있을 때만>
> **본문의 베어 경로 해석**: <대상 루트가 여럿일 때만 — §A는 `a/` 기준, §B는 `b/` 기준>
> **관찰 방법**: <핵심 문서의 공통 한계와 다를 때만>
```

- 제목: TO-BE는 `— TO-BE 상세`. 포트가 없는 경계는 `(<형태>)`(예: `(정적 SPA)`), 두 경계를 담은 파일은 `# <A> (:<포트>)·<B> (:<포트>) — AS-IS 상세`.
- `짝`은 함께 읽어야 하는 다른 상세가 있을 때만 쓴다. 파일 구성(파일별 줄 수와 역할)을 짧은 코드 블록으로 머리 아래에 둘 수 있다.
- TO-BE 상세의 머리는 같은 줄을 TO-BE의 뜻으로 쓴다 — **대상**은 바뀌는 범위와 그 `C-ID`, **기준**은 입력 AS-IS의 커밋·DATE, **표기**는 `(제안)` 표시법이다. 짝은 같은 경계의 AS-IS 상세다(있을 때).

```markdown
# <경계> (:<포트>) — TO-BE 상세

> **대상**: <바뀌는 범위>(`C-01`·`C-03`·`C-04`) · **기준**: 입력 AS-IS 커밋 `<해시>`·<날짜>
> **표기**: `(제안)` = 새 계약·제안 심볼 · **짝**: [`../../as-is/details/<boundary>.md`](../../as-is/details/<boundary>.md)
```

- TO-BE 상세는 신규·변경 경계마다 하나다(예외는 [큰 분석과 작은 분석](#큰-분석과-작은-분석)). 유지 경계는 상세를 새로 쓰지 않고 AS-IS 상세를 링크한다. AS-IS 문서가 없으면 그 경계의 필요한 현재 맥락을 핵심 §4 소절에 요약한다.

| § | 고정 제목 | 담는 것 — AS-IS | TO-BE |
|---|---|---|---|
| 1 | `## 1. 책임 / 비책임` | 책임, 비책임, 아무도 하지 않는 것 — 세 항목 이름을 글자 그대로 쓴다 | 같음 |
| 2 | `## 2. 공개 계약` | 전수 표 `메서드·경로 \| 입력 \| 출력 \| 오류 \| 구현`(구현 = `파일:줄`). 첫 줄에 전수 개수와 선언 위치. 라우트가 아닌 계약(export·CLI·메시지 소비자·해시 라우트)도 같은 열. 불변조건·부작용·재시도·호환성은 필요한 것만 표 아래 불릿([모듈 계약 양식](module-boundary-guide.md#모듈-계약-양식)) | 신규·변경 계약은 전수로 두고, 유지 계약은 개수와 AS-IS 상세 §2 링크 한 줄로 대신한다(AS-IS 문서가 없으면 전수). 새 계약은 `(제안)` |
| 3 | `## 3. 내부 Job Flow — 드릴다운` | [§6](#6-경계-내부-job-flow-드릴다운) | 같음. 노드는 제안 심볼, 근거 열은 [§6.3](#63-그림-아래-근거) |
| 4 | `## 4. 소유 상태·데이터` | 권위 상태 전수. DB는 `표 \| 주요 열 \| 비고`, 파일·레코드는 `데이터 \| 경로 \| 쓰기 주체 \| 생명주기·보존 \| 원자성`. `state` 상태 기계는 소유자 문서 한 곳에만 | 같음 |
| 5 | `## 5. 의존 — 나가는 방향` | `상대 \| 쓰는 계약 \| 배선·설정 \| 타임아웃 \| 결합` | 같음 |
| 6 | `## 6. 실패 경계` | `항목 \| 기본값 \| 설정 키 \| 위치`(타임아웃·재시도·동시성 한도) + 인증·동시성·최후 방어 불릿 | 같음 |
| 7 | `## 7. 검증 경계`, TO-BE `## 7. 검증 계획` | `테스트 \| 무엇을 보장하나 \| 실행 결과`(실행한 것만 `사실·실행`) | `검증 \| 대상 계약·시나리오 \| 방법·명령 \| 시점` |
| 8 | `## 8. 이슈`, TO-BE `## 8. 위험·미확정` | `ID \| 분류 \| 내용 \| 근거 \| 영향` — 이슈의 유일한 원본(분류 어휘는 아래) | `관련 ID \| 분류 \| 내용 \| 근거 \| 영향·대응` — 분류는 `위험`·`미확정`, 관련 ID는 `R`·`C`·`D` |
| 9 | `## 9. 미확인·한계` | 번호 목록 — 확인하지 못한 것과 이유 | 같음 |

- 제목 뒤에 ` — <보충>`을 붙이지 않는다(앵커 고정). "라우트 전수 12개" 같은 보충은 본문 첫 줄에 쓴다.
- A/B 부분 문서는 `# A. <경계> (:<포트>)` 아래에 `## A.1 책임 / 비책임` … `## A.9 미확인·한계`를 두고 이어서 `# B.`를 둔다. 한쪽에만 해당하는 절은 다른 쪽에 `해당 없음 — <이유>`를 쓴다.
- **이슈 `분류`의 기본 어휘**: `정합성`·`계약공백`·`문서불일치`·`중복`·`숨은결합`·`죽은코드`·`무인증`·`복수쓰기`. 맞는 말이 없으면 새 낱말을 쓰고 핵심 §1에 정의한다.
- **경계 고유 주제**(내부 단계·틱 단계·집계·검색 등)는 가장 가까운 절의 소절로 둔다 — 화면 계약·관련 Navigation·Layout 링크는 `2.x`, 내부 단계 표는 `3.x`, 화면 상태·상태 기계·보존·색인은 `4.x`, 외부 발송 채널은 `5.x`, 동시성은 `6.x`. 경계 간 시나리오 단계와 화면 이동은 각 시나리오 설계서, 화면 영역 배치는 화면별 Layout 설계서가 원본이다. 새 최상위 번호를 끼우지 않는다. 그래야 `#8-이슈`가 모든 경계 상세에서 같다. §3의 주제 소절은 JF 소절들 뒤에 `### 3.1 <주제>`로 둔다. 소절 번호는 점으로 쓴다(`2.1`).
- `state` 블록 옆에는 상태 소유자·초기화·불변조건([범위와 상태 소유권](state-diagram-guide.md#범위와-상태-소유권))과 기호 범례 한 줄([구성 요소](state-diagram-guide.md#구성-요소))을 둔다. 데이터 관계를 코드로만 맺으면(FK 없음 등) §4에 `erDiagram`을 둘 수 있다 — [Mermaid 라벨 규칙](#mermaid-라벨-안전-규칙)을 지킨다.

**레트로핏 예외** — 다른 문서가 이미 링크하고 있는 기존 상세에 드릴다운을 덧붙일 때만, 번호를 다시 매기지 않고 번호 없는 `## 내부 Job Flow — <경계> 드릴다운`을 공개 계약 절 바로 뒤에 넣는다. 앵커는 `#내부-job-flow--<경계>-드릴다운`이다. 새로 쓰는 상세는 항상 위 번호 골격을 쓴다.

## 6. 경계 내부 Job Flow 드릴다운

경계 상세 §3은 상위 §5의 노드를 경계 안에서 재귀적으로 연다(`JF-1` → `JF-1.1` → `JF-1.1.1`). 상위 §5 노드에는 링크된 모든 시나리오 Job Flow의 경계 수준 노드가 포함된다([§4](#4-흐름-절--경계-수준-jobflow)). 상위 노드에 대응하는 실제/제안 진입 심볼이 하위 그림의 시작점이며, 입력·출력·실패 의미는 상위 계약과 같다([재귀적 세분화](job-flow-diagram-guide.md#재귀적-세분화)). 별칭은 근거로 대응시키고 같은 실제 심볼은 이름을 유지한다. 작은 분석에서 경계 상세를 생략하면 [대체 위치](#큰-분석과-작은-분석)에 이 규칙을 적용한다.

- **L0**는 경계 사이의 간명한 요약, **L1**은 상위 §5 노드를 실제 내부 객체·모듈·함수 협력으로 처음 연 그림(`JF-n`), **L2 이하**는 그 안의 협력자를 다시 연 그림(`JF-n.m`…)이다. API 별칭을 다른 별칭으로 바꾼 그림은 L1이 아니다. L은 이 문서의 확대 단계이며 Method-R의 네 설계 깊이와 일대일 번호 대응은 아니다.

**절 첫머리 순서**

1. `**결론**:` 한 줄 — 이 경계의 실제 조율자(클래스·함수·없음)와 바깥으로 나가는 클라이언트 객체.
2. 상위 링크 문장 — "상위 §5의 노드에 대응하는 실제/제안 진입점을 아래에서 연다. 입력·출력·실패 의미가 같다." 별칭이 있으면 드릴다운 지도와 근거에서 대응을 밝힌다.
3. `**드릴다운 지도**` 표([§6.1](#61-드릴다운-지도)).
4. (필요할 때) 상위의 바깥 노드 ↔ 이 경계의 클라이언트 객체 대응 — 한 줄이나 표(외부 계약과 이 경계의 클라이언트 메서드).
5. `**표기**` — 객체 이름 규칙, 줄 번호의 기준 커밋, 렌더 확인 범위 한 줄. 실제 심볼이 `on…`으로 시작하면(`onTick` 같은 핸들러 메서드) 이름을 바꾸지 않고, 렌더러가 이벤트 모양으로 그린다는 것을 여기 적는다. 클래스가 없는 모듈은 구획 표 `객체 | 코드 범위 | 담는 심볼`을 둔다.
6. (선택) 단계 표와 그림의 관계, 합류를 읽는 법 한 단락. 열지 않은 것 한 줄.

### 6.1 드릴다운 지도

상위 §5 노드가 이 경계의 어느 그림에서 열리는지 보이는 표다.

- 표 `상위 §5 노드 | L1 그림 | L2 이하`. 그림 칸은 그 JF 소절 링크다.
- 상위 §5에 나오는 이 경계의 노드는 전부 한 행 이상에 나온다. 여러 노드를 한 행에 묶어도 된다.
- 행 순서는 5.1 전체 한 장의 줄 순서다 — 행에 든 노드 가운데 5.1에 가장 먼저 나오는 것의 자리를 따른다. 5.1의 묶음 노드에 든 계약은 그 묶음 노드의 자리이고, 5.1에 없는 노드는 처음 나오는 시나리오 색인 순서·해당 상세 그림의 줄 순서로 그 뒤에 둔다. 상위 칸에서 해당 시나리오 Job Flow를 링크해 출처를 찾게 한다. JF 번호도 이 순서를 따른다([§6.2](#62-깊이와-분해-중단)).
- 상위 노드에 대응하는 코드가 이 경계에 없으면(호출자가 라우트를 조합한 이름 등) 그 사실을 행에 쓴다.
- §5 노드가 없는 진입점(부팅·내부 타이머)도 그림이 있으면 표 끝에 행을 두고, 상위 칸에 `(§5 노드 없음)`이나 가장 가까운 노드를 쓴다.
- 열지 않은 협력자(단순 워커·순수 함수)는 표 아래 한 줄로 밝힌다.

### 6.2 깊이와 분해 중단

그림을 몇 단계까지 열지와 단계별 번호·제목·크기를 정한다.

| 항목 | 규칙 |
|---|---|
| 번호 | `JF-1` → `JF-1.1` → `JF-1.1.1` — 깊이가 번호에 보인다. 번호는 드릴다운 지도의 행 순서(5.1 전체 한 장의 줄 순서 — [§6.1](#61-드릴다운-지도))를 따르고, §5 노드가 없는 부팅·내부 타이머는 끝에 둔다. A/B 부분 문서는 `JF-A1`·`JF-B1.2` |
| 제목 | `### JF-n <무엇> — <진입 심볼>`. ①② 같은 기호를 넣지 않는다(앵커가 깨진다) |
| L1 | 상위 §5 진입점(또는 그 묶음)마다 그 경계의 최상위 협력 그림. 단일 조율자의 배선을 설명하면 `orchestrator:`, 단일 조율자를 선언하지 않는 관점이면 `scope:`를 쓰고 이유를 한 줄 적는다. 내부에 실제 호출자가 여럿인 호출 사슬과 조율 배선은 [구분 규칙](job-flow-diagram-guide.md#코드-호출-사슬과-조율-배선의-구분)을 따른다 |
| L2 이하 | 정책·I/O·상태 변경·비동기 처리 등 내부 협력을 숨긴 채 동작을 설명할 수 없는 협력자를 다시 연다. 이름이 Worker·helper·순수 함수여도 제외하지 않는다. 필요성과 중단 근거는 [§6.4](#64-내부-추적과-완료-기준)로 판단한다. 고정 깊이·그림 수나 새 클래스·Sub-Orchestrator 도입을 요구하지 않는다 |
| 노드 | 메서드·선언된 이벤트는 실제 코드 심볼(`Class.method`·`module.function`·`OnXxx`)을 쓴다. 반환값 판정을 결과 이벤트로 표현하면 [조건의 출처](job-flow-diagram-guide.md#조건의-출처와-그림-적용-범위)에 따라 실제 메서드·판정 근거와 대응시킨다. 확인하지 못한 심볼·판정은 그리지 않고 "미확인"으로 적는다. 실제 심볼이 `on…`이어도 이름을 바꾸지 않는다(절 첫머리의 표기 줄에 적는다). 이름 없는 실재 함수는 아래 익명 함수 식별 규칙을 따른다 |
| TO-BE | 신규·변경 노드는 제안 심볼(`(제안)` 표시)이며 R·C·D에 연결한다. 유지 부분은 현재 기준과 [§6.4](#64-내부-추적과-완료-기준)를 충족하는 AS-IS JF 절을 재사용한다. AS-IS가 없거나 L0뿐이면 필요한 현재 내부 흐름을 조사·보완하며, 링크만으로 분석 완료로 치지 않는다 |
| 다른 경계 | 한 경계 그림에서는 자기 클라이언트·게이트웨이 객체까지만 그린다(`RemoteClient`·`StorageGateway`). 상대도 분석 범위이면 상대의 진입점·내부 JF 절로 이어 준다. 계약에서 멈출 수 있는 외부 범위는 [§6.4](#64-내부-추적과-완료-기준)대로 분류한다 |
| 크기 | 한 그림의 Object는 대략 8개 이하(예시 기준). 넘치거나 상한 가까이에서 분기 칸이 몰리면 단계 묶음 `#### JF-nA <묶음 이름>`·`#### JF-nB <묶음 이름>`으로 나눈다. 진입 심볼은 상위 `JF-n` 제목에 있다. 묶음 사이 관계(같은 메서드의 연속인지, 예외 출구인지)를 한 단락으로 적는다 |
| 단계 표 | 단계 표가 따로 있으면 그림이 표를 대체하지 않는다. 근거 표에 `단계 #` 열을 둬 대응시킨다 |

**익명 함수 식별**: 실제 본문을 확인한 이름 없는 callback·handler는 정의/등록 위치와 본문 범위에 대응하는 문서용 별칭으로 식별할 수 있다. 구획 표에 `익명 함수 식별용 별칭 — 원문 이름 아님`, 등록 위치, 실제 실행 주체를 적고 새 서비스·메서드가 존재한다고 주장하지 않는다. 이름 유무로 헤더를 고르지 않고 실제 조율 관계로 고른다. 등록 시점과 callback 실행 시점을 구분하며, 본문을 확인하지 못한 동적 함수는 별칭으로 채우지 않고 미확인으로 남긴다.

### 6.3 그림 아래 근거

그림 아래에는 주요 흐름을 짧은 문장으로만 설명한다. 근거표·추적표·이슈 목록은 붙이지 않는다. 코드 위치·실제 호출/등록·제안의 R·C·D·검증·미확인은 [Job Flow 작성 기준](#설계-문서의-job-flow-작성-기준)의 별도 소유 문서에 기록한다. 선언 위치만으로 호출을 증명하지 않으며 실제 직접 호출과 조율자의 결과 전달을 구분한다. 합류·재호출·결과 이벤트의 의미는 주요 흐름 설명에 짧게 밝힌다. 상위와 코드의 불일치는 통합 담당에게 보고한다.

### 6.4 내부 추적과 완료 기준

목표는 독자가 **어느 진입점에서 어떤 객체·모듈·함수를 거쳐, 누가 판단·읽기·쓰기·외부 호출을 하고, 결과와 오류가 어디로 돌아가는지** 코드와 대응해 이해하는 것이다. 모듈을 더 쪼개지 않기로 한 설계 결정과 그 모듈 내부를 분석하지 않는 결정은 다르다. 이미 존재하는 협력을 설명하려고 코드를 재구조화하지 않는다.

**근거의 단계 구분**: 아래의 실제 본문·호출 위치·검증 위치 요구는 AS-IS와 TO-BE의 유지 부분에 적용한다. TO-BE 신규·변경 부분은 제안 심볼·관계·입출력·상태/오류 소유자, R·C·D 근거와 구현 후 검증 계획으로 판정한다. 이때 `펼침`은 내부 협력 설계, `말단 확인`은 단일 규칙·연산과 중단 이유가 설계로 명확함을 뜻하며 각각 `(제안)`을 병기한다. 미구현이라는 사실 자체는 설계 미확인이 아니지만, 결정에 필요한 외부 계약·연결이 불명확하면 미확인으로 남긴다. 설계 완료를 코드 확인·런타임 검증 완료로 보고하지 않으며 존재하지 않는 파일·줄·실행 결과를 만들지 않는다.

**시나리오별 내부 추적표** — 다음 표는 Job Flow 출력에 넣지 않고 [작성 기준](#설계-문서의-job-flow-작성-기준)의 별도 소유 문서에 둔다. 모든 상위 노드를 포함하며, 경계 상세의 드릴다운 지도는 하위 그림의 원본 색인으로 유지한다.

| 상위 노드 | 실제/제안 진입 심볼 | 내부 그림 또는 말단 근거 | 판정·중단 이유 |
|---|---|---|---|
| 각 L0 노드·묶음 안의 계약 | 클래스·메서드 / 모듈·함수 / 핸들러와 코드 위치 | 정확한 L1·L2 절 링크 또는 말단 근거 절 | 펼침 / 말단 확인 / 외부 경계 / 미확인 중 하나와 이유 |

- **펼침**: 실제 내부 협력 그림과 노드·연결 근거가 있다. 상위 별칭과 코드 이름이 다르면 라우팅·등록·호출 근거로 대응시킨다. 이름을 맞추려고 없는 `Service.process` 같은 심볼을 만들지 않는다.
- **말단 확인**: 실제 본문을 확인해 관련 내부 협력이 없거나, 단일 규칙·변환·위임의 입력·결과·실패와 대상이 드러난다. 코드 위치와 중단 이유를 적는다. 단순 위임이면 위임 대상의 내부 그림·확인한 말단 근거 또는 외부 경계까지 연결해야 한다. 이름이 helper·SDK·repository라는 이유만으로 멈추지 않는다.
- **외부 경계**: 사용자 지정 범위 밖이거나 제3자 구현을 분석 대상으로 삼지 않은 계약이다. 호출 측 adapter·계약·패키지 버전과 멈춘 이유를 적고, 내부 분석 완료 건수에 넣지 않는다. 대상 범위에 포함된 서버·공유 모듈을 다른 프로세스라는 이유로 여기서 끊지 않는다.
- **미확인**: 동적 연결·구현·버전 근거 등에 접근하지 못했다. 마지막 확인 심볼, 필요한 소스/등록/버전 정보, 설명하지 못한 동작을 남긴다. 접근 가능한 대상 코드를 읽지 않은 것은 생략 근거가 아니다. 미확인을 해소하지 못하면 해당 범위는 미완료로 보고한다.

**확대와 중단**:

1. 대상 시나리오의 실제 진입점을 찾고 직접 호출·반환·주입·구독을 따라간다. UI이면 관련 Page·컴포넌트·hook·action·client까지, 서버이면 라우트·handler·service/workflow·저장 adapter까지 실제 존재하는 구성을 확인한다. 이 나열은 강제 계층이나 모든 코드의 조사 목록이 아니다. import는 의존 후보일 뿐 실행 순서의 증거가 아니다.
2. L1은 내부 책임과 협력 관계를 보여 준다. 내부 객체 이름을 본문에 언급하거나 소스 경로만 붙여 두고 두 경계 사이 화살표를 반복하면 부족하다. 호출 순서·조건·전달 데이터·결과 반영을 그림과 해설로 연결한다.
3. 하위 협력자 안에 결과를 바꾸는 규칙·권한·캐시·읽기/쓰기·트랜잭션·오류 변환·비동기 수명·재시도가 숨으면 그 부분을 L2 이하로 연다. 단일 연산으로 충분히 설명되는 말단은 근거 표에 규칙·상태 접근·오류와 중단 이유를 적고 별도 그림을 만들지 않는다. 모든 private helper·직렬화·표준 라이브러리 내부를 전개하지 않는다.
4. 마지막 그림까지 읽은 독자가 책임 소유자, 실제 호출 사슬, 읽고 쓰는 데이터, 성공·중요 실패의 반환 경로, 수정 시작점과 관련 검증 위치를 찾을 수 있으면 멈춘다. 테스트가 없으면 그 사실과 필요한 검증을 적는다. 핵심에 전부 복제하지 않고 링크로 확대한다.

**완료 판정** — 각 시나리오에 성공 경로와 중요한 실패/대체 경로를 적용해 L0 → L1 → 필요한 L2 → 근거를 따라간다. 해당 실패/대체 경로가 없으면 코드 또는 목표 계약에 근거해 이유를 적는다. 범위 안의 노드가 `펼침` 또는 `말단 확인`으로 설명되고 연결 근거가 맞아야 내부 분석 완료다. 미확인·외부 경계는 별도 집계하고 전체 완료와 섞지 않는다. 그림 수·깊이 수치·파일 존재·정적 검사 통과는 이 판정을 대신하지 않는다.

## 7. ID와 교차 참조

ID는 조사 단계에 한 번 정하고 다시 매기지 않는다. 아래 표가 ID의 형식과 정하는 곳이다.

| 대상 | 형식 | 정하는 곳 |
|---|---|---|
| 경계(조사 ID) | 대문자 한 글자 `A`·`B`·… | 브리프 §2(작은 분석은 §3 표의 첫 열 `조사 ID`) |
| 이슈 | `<접두>-<두 자리>`(`B-01`). 접두 = 조사 ID. A/B 부분 문서는 번호대를 나눈다(`E-01`~ / `E-20`~) | 상세 이슈 표(작은 분석은 §9 이슈 표) |
| TO-BE 요구·설계 항목·결정 | `R-01`·`C-01`·`D-01` | TO-BE §2 |
| 드릴다운 그림 | `JF-1`·`JF-1.1`·`JF-A1` | 상세 §3 |

- 조사 단계의 ID를 그대로 최종 ID로 쓴다. 번호를 다시 매기지 않고, 비는 번호는 브리프 §3에 이유를 적는다.
- 문장과 표에서 ID는 모두 코드 표기로 쓴다(`B-01`·`R-01`·`C-01`·`D-01`·`JF-1.1`). AS-IS 이슈와 TO-BE의 R·C·D를 다른 표기로 나누지 않는다.
- 이슈의 내용·근거·영향은 상세 「8. 이슈」 표 **한 곳**에만 쓴다(작은 분석은 §9). 핵심 §9는 주제별 교차 뷰이고(중복 정의가 아니다), 브리프 §3은 접두 → 근거 표 위치를 매핑한다.
- 인용은 문장 끝에 ID로 단다. TO-BE는 AS-IS ID를 그대로 인용하고 처분을 TO-BE §9.4에 쓴다. TO-BE 상세의 위험·미확정은 새 ID를 만들지 않고 관련 `R`·`C`·`D`로 단다.
- AS-IS 이슈 접두가 `R`·`C`·`D`와 겹치면 TO-BE 문서에서는 `AS-IS C-03`처럼 앞에 붙여 TO-BE의 `C-03`과 구분한다.
- `JF-n`은 상세 문서 안에서만 유일하다. 다른 문서에서 가리킬 때는 문서 이름과 함께 쓴다("<경계> 상세 `JF-1.1`").

**고정 앵커** — 링크 대상 제목이 고정이므로 앵커도 문서마다 같다(GitHub 방식 슬러그). 링크 대상 제목에 ①② 같은 기호나 이모지를 넣지 않고, 한 문서 안에서 같은 제목을 두 번 쓰지 않는다(슬러그에 `-1`이 붙는다).

| 대상 | AS-IS | TO-BE |
|---|---|---|
| 핵심 §5 | `#5-흐름--경계끼리-어떻게-소통하나` | 같음 |
| 핵심 §8 | `#8-상세근거-인덱스와-한계` | 같음 |
| 핵심 §9 | `#9-이슈--주제별-교차-뷰` | `#9-구현검증이행` |
| 상세 공개 계약 | `#2-공개-계약`, A/B는 `#a2-공개-계약` | 같음 |
| 상세 드릴다운 | `#3-내부-job-flow--드릴다운`, A/B는 `#a3-내부-job-flow--드릴다운`, 레트로핏은 `#내부-job-flow--<경계>-드릴다운` | 같음 |
| 상세 이슈 | `#8-이슈`, A/B는 `#a8-이슈` | `#8-위험미확정` |
| 브리프 이슈 색인 | `#3-이슈-색인` | 같음 |

## 8. 근거 브리프

`_evidence-brief.md`는 원본을 찾는 색인이다. 요약으로 원본 검증을 대신하지 않는다 — 머리 blockquote에 이 문장을 둔다. 제목은 `# 근거 브리프 — <DATE> AS-IS 역추출`이고, TO-BE는 `# 근거 브리프 — <DATE> TO-BE 설계`다.

AS-IS 브리프가 있으면 그 경계 목록·이슈 ID·기준선이 TO-BE의 입력이다. 없어도 TO-BE를 시작할 수 있고, 그때는 설계에 필요한 현재 맥락을 TO-BE 브리프 §1에 요약한다.

| 절 | 내용 |
|---|---|
| `## 1. 기준선` | 표 `항목 \| 값` — DATE·기준 커밋·브랜치·작업 트리·관찰 시점·관찰 방법 |
| `### 1.1 분석 범위` | 대상 트리와 그 근거 명령(예: 추적 파일 분포). 사용자가 범위를 좁혔으면 그 지정과, 상세를 두지 않은 경계 |
| `### 1.2 제외한 것과 이유` | 표 `경로 \| 이유 \| 근거` — 근거는 다시 돌릴 수 있는 명령 |
| `### 1.3 문서 대조 기준선` | 표 `문서 \| 이 브리프에서의 지위` — 검증 대상인지, 근거로 쓰지 않는 문서인지 |
| `## 2. 경계 목록과 조사 산출물` | 표 `조사 ID \| 경계 \| 포트 \| 상세 문서` — 병렬 작업의 공유 계약 |
| `## 3. 이슈 색인` | 표 `접두 \| 범위 \| 건수 \| 근거 표가 있는 곳`(링크) + 번호 공백의 이유 |
| `## 4. 재확인 명령` | 표 `목적 \| 명령` |
| `## 5. 검증 기록` | 정적·렌더링·의미 세 묶음. **실제로 돌린 것만** 다시 돌릴 수 있게 쓰고, 돌리지 못한 것은 "실행하지 못함"과 이유 |
| `## 6. 검토 반영` | 필수 결함(표 `지적 \| 조치`), 표현 교정, 보강, 고치지 않고 남긴 것과 이유 |
| `## 7. 한계` | 전체 공통 한계 |

- 브리프 §4·§5의 명령은 다른 컴퓨터에서도 다시 돌릴 수 있게 쓴다. 저장소 밖의 도구·렌더러·출력 폴더는 `<가이드 사본>`·`<렌더러>`·`<임시 폴더>` 같은 자리표시자로 적고, 작성한 컴퓨터의 절대 경로를 남기지 않는다.
- TO-BE도 큰 설계면 같은 골격을 쓴다. §1에 설계 유형과 입력 근거, §2에 목표 경계(표 `ID | 목표 경계 | 포트 | 상세 문서 | AS-IS 대비`), §3에 `R`·`C`·`D` 범위와 물려받는 AS-IS 접두를 쓴다.
- 작은 분석은 브리프를 두지 않는다. 각 항목의 자리는 [큰 분석과 작은 분석](#큰-분석과-작은-분석)에 있다.

## 9. 작성 순서와 병렬화

여러 작성자가 나눠 쓸 때의 순서다. 공유 계약(경계 목록·ID 번호대·전체 시나리오와 화면 목록·각 파일명·§5 및 시나리오 Job Flow 노드 이름)을 먼저 정하고, 구성 설명서·시나리오별 설계서·화면별 Layout·경계별 상세의 쓰기 소유를 나눈 뒤 통합 담당이 합친다. 병렬 실행이 안 되는 환경이나 작은 분석은 같은 순서를 한 사람이 차례로 따른다.

**AS-IS**

| 단계 | 담당 | 산출물·끝나는 조건 |
|---|---|---|
| 1. 기준선 확정 | 통합 담당 | 브리프 §1·§2 — 경계 목록·조사 ID·ID 번호대(공유 계약) |
| 2. 경계별 조사·상세 | 경계별 작성자(상세 1개 = 1명), 병렬 | 상세 §1·§2·§4~§9 초안과 이슈 ID |
| 3. 핵심·공유 흐름 확정 | 통합 담당 | 두 구성 설명서 초안, 핵심 §0~§4·§5 대표 흐름과 전체 시나리오 색인·§7 전수 화면 목록, 시나리오별 노드·계약명·진입·완료 조건, 화면 식별자·소유 경계 |
| 4. 필수 상세·드릴다운 | 파일별 작성자, 병렬 | 두 구성 설명서, 전체 시나리오의 Job Flow·Navigation 설계서, 모든 대상 화면의 Layout 설계서, 경계 상세 §3. 드릴다운 시작점은 단계 3에서 확정한 핵심·시나리오 노드다. 상위 불일치는 고치지 않고 보고한다 |
| 5. 통합 | 통합 담당 | 보고를 코드로 재확인해 상위를 고치고, 이미 끝난 하위 문서에 남은 옛 이름도 정정 |
| 6. 검증·검토 | 검증 담당 + 작성자와 다른 검토자 | [§10](#10-검증) 검사 → 사실·구조 검토 → 필수 결함 수정 → 영향 부분 재검증 → 브리프 §5·§6 기록 |

**TO-BE** — 단계 1·2·4가 다르다. 3·6은 AS-IS와 같고, 5는 대조할 근거만 다르다.

| 단계 | 담당 | 산출물·끝나는 조건 |
|---|---|---|
| 1. 기준선·요구 | 통합 담당 | 설계 유형·입력 근거·`DATE`와 요구 `R`. 큰 설계는 브리프 §1·§2도 이때 시작한다 |
| 2. 결정과 공유 계약 | 통합 담당(대안 조사는 병렬 가능) | 대안 비교 → 결정 `D`·설계 항목 `C` → 목표 경계 목록·경계 간 계약명(공유 계약) |
| 3. 핵심·공유 흐름 확정 | 통합 담당 | 두 구성 설명서 초안, 핵심 §0~§4·§5 대표 흐름과 전체 시나리오 색인·§7 전수 화면 목록, 시나리오별 노드·목표 계약명·진입·완료 조건, 화면 식별자·소유 경계 |
| 4. 필수 상세·경계 상세 | 파일별 작성자, 병렬 | 두 구성 설명서, 유지 시나리오를 포함한 전체 Job Flow·Navigation 설계서, 유지 화면을 포함한 모든 대상 화면의 Layout 설계서, 신규·변경 경계 상세 §1~§9. 드릴다운 시작점은 단계 3의 핵심·시나리오 노드다. 상위·계약 불일치는 고치지 않고 보고한다 |
| 5. 통합 | 통합 담당 | 보고를 근거(`R`·`C`·`D`와 AS-IS 코드)로 재확인해 핵심과 `C`·`D` 표를 고치고, 이미 끝난 상세에 남은 옛 이름도 정정 |
| 6. 검증·검토 | AS-IS와 같음 | AS-IS와 같음 |

- 위임할 때 주는 것: 공유 계약(경계 목록·ID 번호대·전체 시나리오와 화면 목록·각 파일명·상위 노드 이름·이 가이드 링크), 소유 파일, 읽을 범위, 보고 형식. 상위 불일치는 `상위 노드 | 코드 근거 | 제안 이름`으로 보고받는다. 패킷 형식은 [작업 맥락 패킷](module-boundary-guide.md#6-ai에-전달할-작업-맥락), 역할과 검토 반복은 [멀티 에이전트 프롬프트](../prompts/multi-agent-task-prompt.md)를 따른다.
- 한 파일은 한 작성자만 쓴다. 다른 작성자의 파일에서 고칠 것을 찾으면 보고한다.
- 단계 3 전에 단계 4를 시작하지 않는다 — 상위 노드 이름이 바뀌면 하위를 다시 고쳐야 한다. 분석 깊이의 적합성을 처음 확인하는 작업은 단계 4에서 대표 내부 추적을 먼저 완성하고 [결과 적합성 게이트](#101-결과-적합성-게이트와-지침-개선)로 검토한 뒤 같은 방식을 나머지 범위에 적용한다.

## 10. 검증

산출 문서를 넘기기 전의 확인이다. 정적 검사, 렌더링 확인, 의미 검토를 나눠 하고 실제로 돌린 것만 기록한다.

**정적 검사** — [`design-doc-check.mjs`](./tools/design-doc-check.mjs)(의존성 없는 Node 18+ 단일 파일). 폴더를 주면 `*.md`를 재귀로 모은다.

```bash
node guides/tools/design-doc-check.mjs [--renderer <path>] [--out <dir>] [--strict] <file-or-dir>...
```

- 위 경로는 가이드 묶음의 루트(`guides/`가 있는 폴더)에서 부를 때다. 다른 프로젝트에서는 스크립트를 가이드 사본 경로로 부르고, 문서 폴더는 그 프로젝트 기준으로 준다 — `node <가이드 사본>/guides/tools/design-doc-check.mjs docs/design/<DATE>`.
- 출력은 `LEVEL CODE file:line 메시지` 줄이고, 끝에 파일·jobflow 블록·FAIL·WARN 수를 세는 집계(`files=… blocks=… fail=… warn=…`)가 나온다.
- exit 0 = FAIL 없음, 1 = FAIL 있음, 2 = 사용법 오류. `--strict`는 WARN도 실패로 센다.

검사 코드·옵션은 `node guides/tools/design-doc-check.mjs --help`, 코드별 판정 조건은 [도구 머리 주석](./tools/design-doc-check.mjs)을 확인한다. 정적 검사는 펜스·jobflow 구조·링크·앵커·Mermaid 라벨을 다루며, 그림 의미나 실제 화면 배치를 보장하지 않는다. 필수 파일의 생성 여부·시나리오와 화면 수록 범위·Navigation/Layout 문법 전체를 검사하는 도구가 아니므로 아래 대조를 별도로 수행한다.

- 작성한 AS-IS·TO-BE 각각에 시스템·패키지 구성 설명서가 있고, 핵심 §5.1의 범위 안 시나리오마다 같은 이름의 Job Flow·Navigation 두 파일이 모두 있는지 대조한다. 단일 시나리오·작은 분석·TO-BE 유지 시나리오도 포함한다.
- 대상 라우트·화면 등록·사용자 과업 또는 목표 요구의 전체 화면 목록을 §7의 전수 색인과 대조하고, 모든 화면·주요 오버레이·Dialog에 Layout 파일이 있는지 확인한다. 단일 화면·작은 분석·TO-BE 유지 화면, 대표 Navigation에 등장하지 않는 화면도 포함한다. UI가 없으면 §7·§8의 파일 0개 사유를 확인한다.
- 핵심 색인에서 두 파일로, 각 파일에서 핵심·짝 시나리오·계약 소유 경계로 찾아갈 수 있는지 확인한다. UI 비대상 Navigation은 이유·진입 조건·완료 결과·Job Flow 링크가 있는지 본다.
- Layout 파일에서 핵심 §7·관련 Navigation·영역별 계약으로, Navigation에서 등장 화면 Layout으로 연결되는지 확인한다. 유지 TO-BE도 해당 기준의 도표·단계별/영역별 해설을 실제로 담았는지 보고 AS-IS 링크만 있는 파일로 완료 판정하지 않는다.
- `navigation`은 [전용 가이드](navigation-diagram-guide.md)의 문법·직접 진입·화면 노드 의미, `layout`은 [전용 가이드](screen-layout-guide.md)의 단일 루트 트리·방향·자식 순서·크기·폭별 블록 규칙과 대조한다. 사용 가능한 파서·렌더러가 있으면 실제 검증 결과를 기록하고, 없으면 정적 검토와 미실행 범위를 명시한다.

- **정적 검사 합격 기준**은 FAIL 0과, 남은 WARN마다 본문에 적은 이유(합류·재호출 등)다. 문서 전체의 완료는 필수 산출물·[내부 추적 기준](#64-내부-추적과-완료-기준)·아래 의미 검토도 충족해야 한다. 단 `LINK-OUTSIDE`는 이유를 적어 남기지 않고 고친다 — 다른 컴퓨터에서 깨지는 링크라서다([§3.2](#32-머리-블록)의 가이드 링크 규칙). `JF-REDRAW`는 줄 순서를 고쳐 0으로 만드는 것이 먼저고, 남기면 그 줄과 이유를 그림 아래 불릿에 적는다. 이유를 적고 남긴 WARN이 있으면 `--strict`는 실패하므로 합격 판정에 쓰지 않는다 — WARN을 모두 없애기로 한 문서에서만 쓴다.
- 앵커를 다른 방법으로 검사할 때 코드펜스는 **줄 맨 앞 펜스만** 지운다. 본문 속 인라인 코드의 백틱 세 개(예: ```` ```yaml ````)를 펜스로 오인하면 그 뒤의 제목이 전부 사라진다.

**렌더링 확인** — jobflow 렌더러가 있으면 `--renderer <렌더러 모듈>`로 블록마다 SVG를 만들고, PNG로 바꿔(예: `rsvg-convert -b white -z 0.6 in.svg -o out.png`) 눈으로 본다.

- 렌더러 모듈은 `generateSVG(jobflow 원문)` → SVG 문자열을, default export 객체의 메서드나 이름 있는 export로 내야 한다.
- SVG는 `<out>/<문서 basename>-NN.svg`로 생긴다(NN = 그 문서 안 jobflow 블록 순번). basename이 같은 문서가 여럿이면 공통 상위 폴더부터의 경로를 `__`로 이어 이름으로 쓴다(`as-is__details__boundary-01.svg`).
- 기본 출력 폴더 `./.design-doc-check`는 현재 폴더에 생긴다. 대상 저장소에서 돌릴 때는 `--out`에 그 저장소에 속하지 않는 임시 폴더를 준다(예: `mktemp -d`로 만든 폴더).
- 눈으로 볼 것:
  - 흐름이 한 줄로 이어지는가 — 앞에서 그린 노드에서 다시 나가는 화살표가 그 칸에서 나가고, 같은 이름 칸이 끊겨 새로 그려지지 않았는가(`JF-REDRAW`가 같은 곳을 잡는다).
  - 선이 서로 가로지르지 않는가 — 서로 다른 출발점의 선이 「+」로 교차하거나, 한 줄기에서 좌우로 갈라진 가지가 같은 행에서 만나 두 타깃을 잇는 한 줄처럼 보이지 않는가. 메서드와 결과 칸을 잇는 점선도 선이다. 검사 도구는 이것을 보지 않으므로 렌더 결과로 확인한다.
  - 이벤트·응답이 관련 호출과 명확히 대응하고, 발생·판정 조건과 후속 처리를 읽을 수 있는가.
  - 화살표 출발점이 실제 요청자로 읽히는가.
  - 왼쪽으로 가는 화살표가 앞 행의 빈칸에 끼어들어 시간 순서가 흐트러지지 않는가.
  - 화살표 머리가 의도한 칸에 닿고, 타깃 칸이 빠지지 않았는가. 렌더러는 합류 뒤 화살표를 같은 이름의 마지막 칸에 붙인다 — 합류 뒤 후속이 일부 결과에만 해당하면 해당 조건의 이벤트(`Boundary.OnReady --> Client.send`)에서 이었는지 본다([합류와 재호출 구분](job-flow-diagram-guide.md#합류와-재호출-구분)). 앞 행에 끼어든 칸을 다음 줄의 출발점으로 쓰면 다른 칸에 붙을 수 있다.
- 선이 꼬이거나 겹치면 [선 교차 줄이기](job-flow-diagram-guide.md#선-교차-줄이기)에 따라 조정한다. 렌더러가 없으면 정적 검토라고 쓴다. SVG 생성 성공을 화면 표시 성공으로 쓰지 않는다.

**의미 검토** — 작성자와 다른 검토자가 사실(수치·경로·단정)과 구조(이 양식·DSL 의미)를 나눠 본다. 필수 결함을 고친 뒤 영향 부분만 다시 검증한다([비판 → 개선 → 평가](../prompts/multi-agent-task-prompt.md#비판--개선--평가)·[교차 검증과 종료](system-design-framework.md#교차-검증과-종료)).

- 각 시나리오의 [내부 추적표](#64-내부-추적과-완료-기준)를 대조한다. API 두 칸과 계약표·산문만 있거나, 내부 파일 링크가 있어도 실제 협력 그림으로 이어지지 않으면 필수 결함이다. 말단 확인은 본문 근거로, 외부 경계·미확인은 범위와 판정으로 확인한다. TO-BE의 유지 AS-IS 링크도 같은 기준으로 검사한다.
- 작성자가 고른 쉬운 경로만 보지 않고 검토자가 성공·중요 실패/대체 입력을 골라 실제 호출 위치·데이터 접근·오류 처리까지 추적한다. `검토 경로 | L0 → L1 → L2/말단 | 코드/설계 근거 | 누락·판정·수정 결과`를 브리프 검토 기록(작은 분석은 최종 보고)에 남긴다. 정적 의존 목록을 런타임 호출 증거로 오인하지 않았는지 본다.
- 상위 §5 노드와 하위 진입점의 입력·출력·실패 의미가 같고, 이름이 다른 별칭은 코드/설계 근거로 대응되는가(드릴다운 지도 대조)? 같은 실제 심볼의 이름을 임의로 바꾸지 않았는가?
- 대표 그림에서 생략한 시나리오 계약도 각 상세와 드릴다운 대응에 포함되는가. 핵심은 쉬운 줄거리·대표 결과를 설명하고 상세에 세부 그림·계약·정상 및 실패 단계를 충분히 남겼는가.
- 시스템 구성의 실행 경계와 패키지 구성의 소스 책임·조립·의존·검증 위치가 서로 대응하며, 시나리오 참여 경계와 모순되지 않는가.
- 각 시나리오의 Job Flow 완료 사실과 Navigation의 사용자 결과가 맞고, 화면 이동이 없는 시나리오에 이동을 날조하지 않았는가.
- 전수 화면 색인·Navigation의 화면·Layout 식별자가 대응하고, 각 영역의 입력·동작·결과와 로딩·빈값·오류·권한 등 적용 상태, 폭별 배치가 실제 근거 또는 명시된 목표 제안으로 설명되는가. 주요 시나리오에 없는 화면을 빠뜨리지 않았는가.
- 핵심이 인용한 ID가 모두 상세 이슈 표에 있고, 브리프 §3의 범위·건수와 맞는가.
- 처음 보는 검토자가 대표 버그 1~2건의 수정 시작점을 핵심 → 상세 → 코드 경로로 찾아가는가.

**기록** — 브리프 §5에 실제로 돌린 것만 정적·렌더링·의미로 나눠 쓴다(작은 분석은 최종 보고). 확인 범위에서 뺀 것도 적는다. 저장소 밖의 도구·렌더러·출력 폴더는 [§8](#8-근거-브리프)대로 자리표시자로 쓴다.

**작성 체크리스트**

- [ ] 머리 블록(AS-IS 6줄·TO-BE 8줄)의 기준 커밋·범위가 브리프 §1과 같다.
- [ ] 핵심 §0~§9와 경계 상세 §1~§9 제목이 고정 제목과 글자까지 같고, 해당 없는 절은 `해당 없음 — <이유>` 한 줄이다. 필수 구성·시나리오 설계서는 [§2.1](#21-필수-상세-설계서)의 내용을 갖췄다.
- [ ] 작성한 AS-IS·TO-BE 각각에 시스템·패키지 구성 설명서, 범위 안 모든 시나리오의 Job Flow·Navigation 두 파일, 모든 대상 화면의 Layout 파일이 있다. 작은 분석·단일 시나리오/화면·유지 범위도 대조했고, 사용자 지정 제외는 명시했다.
- [ ] 핵심 §5.1 색인·각 시나리오 소절의 두 링크와 상세의 역방향 링크가 실제 파일을 가리킨다. 핵심은 쉬운 요약이고 상세에 정상 단계·실패/복구·완료 결과·근거가 있다.
- [ ] UI 없는 시나리오도 Navigation 파일에 비대상 이유·진입 조건·완료 결과·Job Flow 링크를 남겼으며, 가짜 이동을 그리지 않았다.
- [ ] 대상 전체 화면 목록과 §7 전수 화면·Layout 색인 및 실제 파일이 맞는다. UI가 없으면 §7·§8에 Layout 파일 0개와 사유를 기록했고, UI가 있으나 이동이 없는 화면의 Layout도 만들었다.
- [ ] 각 Layout 파일에 `layout`과 영역별 역할·입출력·상호작용·적용 상태·필요한 폭별 배치 설명, 근거/제안·미확인, 핵심·Navigation·계약 링크가 있다. 유지 TO-BE도 세 DSL 도표와 상세 해설을 링크만으로 대신하지 않았다.
- [ ] §2~§5·§7과 TO-BE §9가 `**결론**:` 한 줄로 시작하고, §6은 6.1~6.3이 각자 결론으로, AS-IS §9는 `**결론**: 이 절은 전수 목록이 아니다 — …`로 시작한다(작은 분석의 AS-IS §9는 `**결론**: 이 절이 이슈 원본이다 — …` — [§3.3](#33-절별-작성-규칙)).
- [ ] §3의 모든 행이 §4 소절·§8 행·조사 ID와 대응한다.
- [ ] 핵심 §5와 시나리오 설계서의 경계 수준 그림은 `scope:`이고 경계 내부가 없다 — 예외는 [§4.1](#41-표기-약속)의 예외 노드뿐이다. 별도 소유 문서의 계약 기록에 원문 계약이나 그 역할이 있다(5.1 묶음 노드는 읽는 법 불릿과 시나리오 링크).
- [ ] 화살표 출발점이 실제 요청자이고, 접수 확인과 업무 완료를 구분해 적었다.
- [ ] 렌더 결과에서 합류 뒤 화살표가 의도한 칸에 붙는다 — 합류 뒤 후속이 일부 결과에만 해당하면 해당 조건의 이벤트에서 이었다([합류와 재호출 구분](job-flow-diagram-guide.md#합류와-재호출-구분)).
- [ ] §5 마지막 소절이 드릴다운 색인이고, 연결된 모든 시나리오의 상위 노드까지 하위 진입점이나 상세 제외 이유·대체 위치가 있다.
- [ ] 드릴다운 노드는 실제 심볼(TO-BE는 제안 심볼)이거나, [실제 반환값 판정에 대응하는 결과 이벤트 표기](job-flow-diagram-guide.md#조건의-출처와-그림-적용-범위)다. 그림 아래에는 짧은 주요 흐름 설명만 있고, 심볼·판정 근거는 별도 소유 문서에 있다.
- [ ] 시나리오마다 상위 노드별 내부 추적표가 있고, 정확한 JF 절·말단 근거로 이동할 수 있다. 범위 안의 복잡한 협력을 API 별칭·설명문만으로 대신하지 않았다.
- [ ] 주요 연결의 호출·등록 근거, 상태 읽기/쓰기와 결과·오류 반영 주체가 확인된다. 말단은 근거로 중단했고, 외부·미확인을 완료로 계산하지 않았다. 유지 AS-IS 링크도 이 기준을 충족한다. TO-BE 신규·변경은 [§6.4의 근거 단계 구분](#64-내부-추적과-완료-기준)에 따라 제안 관계·R/C/D·검증 계획으로 확인했다.

### 10.1 결과 적합성 게이트와 지침 개선

AS-IS를 먼저 분석하고 그 결과로 TO-BE·프로토타입·구현을 이어가는 작업에 적용한다. 독립적인 신규 설계나 AS-IS 분석을 요청하지 않은 작은 변경에 별도 AS-IS 문서를 강제하는 규칙은 아니다. 이 게이트는 분석 결과의 검토이며, 기존에 허용된 자율 작업에 사용자 승인을 새로 요구하지 않는다.

1. **의도와 검토 질문을 고정한다.** 내부 동작을 이해하려는 분석이면 검토자가 구체적인 성공 입력과 중요한 실패·대체 입력을 고른다. [§6.4](#64-내부-추적과-완료-기준)에 따라 L0에서 실제 호출자·판단자·상태 변경자·결과/오류 수신자까지 찾을 수 있는지를 묻는다. 화면이 있는 범위는 같은 과업의 Navigation·Layout에서 진입·복귀·표시 상태도 대조한다.
2. **대표 경로를 먼저 검토한다.** 대량 작성 전에 코드 근거까지 연결된 대표 내부 추적을 완성해 정적·렌더링·의미 검토를 구분해 수행한다. 문서 수·그림 수·정적 FAIL 0을 의도 충족으로 대신하지 않는다. 대표 경로 통과는 작성 방식의 확인이며 전체 AS-IS 완료가 아니다.
3. **의도와 어긋나면 종속 작업을 멈춘다.** API 요약에 머물거나, 내부 협력·중요 실패 책임·화면 결과를 설명하지 못하면 해당 결과를 근거로 삼는 TO-BE·프로토타입·구현을 시작하거나 확정하지 않는다. 원본 조사와 독립적인 검증은 계속할 수 있다. 이미 진행한 종속 산출물은 영향 범위를 표시해 재검토 대상으로 둔다.
4. **문서와 생성 지침을 함께 고친다.** 누락된 관계·잘못 읽힌 조건을 실제 결과의 반례로 기록한다. 지침의 누락·충돌·모호함이면 해당 가이드 원본을 고치고, 적용 누락이면 프롬프트의 실행 순서·인계·검토 조건을 보완한다. 같은 규칙을 여러 곳에 복제하거나 한 사례의 기술·수치를 모든 작업에 강제하지 않는다. 지침 수정과 분석 문서 수정은 서로 대체하지 못한다.
5. **수정 지침을 다시 적용한다.** 변경된 지침의 버전·영향을 작성자에게 전달하고 부족한 원본 조사를 수행한 뒤 영향받는 AS-IS를 다시 작성한다. 검토자는 같은 반례를 재검토하고 변경으로 영향을 받은 경로도 확인한다. 필수 결함이 남으면 원인이나 접근을 바꿔 이 과정을 계속하며, 반복 횟수만으로 합격시키지 않는다.
6. **전체 범위를 확인한 뒤 인계한다.** 모든 대상 시나리오의 추적표·필수 산출물·의미 검토를 마치고 필수 결함이 해결되어야 AS-IS를 확정한다. 외부 경계와 미확인은 확인된 내부와 구분하며, 후속 결정에 필요한 미확인 사실이 있으면 그 사실에 의존하는 결정은 보류한다. 자료가 없어 더 진행할 수 없으면 필요한 입력과 미완료 범위를 밝힌다.

브리프 §6(작은 분석은 기존 검토 기록)에 `의도·검토 입력 | 부족한 결과·근거 | 가이드/프롬프트 수정 | 다시 작성한 범위 | 재검토 결과 | 후속 단계 판정`을 남긴다. 지침을 수정하지 않은 통과 경로는 수정 칸에 해당 없음으로 적는다. 후속 단계 판정은 `작성 방식 확인 / AS-IS 미완료 / AS-IS 확정`을 구분하고, 확인한 기준선과 지침 버전을 함께 남긴다. 별도 회차 파일을 늘리거나 검토자가 보지 않은 결과를 승인한 것처럼 적지 않는다.
