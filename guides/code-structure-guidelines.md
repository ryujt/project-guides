# 코드 구조 및 스타일 가이드라인

코드를 처음 보는 사람이나 AI가 **대상 기능과 인접 계약만 읽고 안전하게 수정할 수 있는 구조**를 지향한다. 파일 수나 함수 길이보다 변경 이유, 불변식, 필요한 맥락을 기준으로 판단한다. 경계·계약·작업 맥락의 공통 기준은 [모듈 경계 가이드](./module-boundary-guide.md)를 따른다.

## 1. 가독성과 책임

* 함수·타입·파일 이름에 수행하는 일과 대상이 드러나게 쓴다. `Manager`, `Helper`, `process`만으로 책임을 설명하지 않는다.
* 불필요한 축약, 과도한 한 줄 처리, 여러 추상화 수준을 섞은 함수를 피한다.
* 하나의 파일은 응집된 책임을 가진다. 함께 바뀌는 작은 타입·함수는 같은 파일에 둘 수 있다.
* 줄 수가 많다는 이유만으로 분리하지 않는다. 독립적인 변경 이유나 테스트 경계가 있고 공개 계약을 작게 유지할 수 있을 때 분리한다.
* 분리 후 호출을 따라 여러 파일을 왕복해야 하거나 항상 함께 수정된다면 합치는 편이 나은지 검토한다.

## 2. 흐름과 세부 구현

* 진입점은 요청 해석, 의존성 조립, 기능 호출이 드러나게 구성한다.
* 여러 독립 조각의 순서·분기·실패 처리는 유스케이스별 조율자에 모은다. [Orchestrator-Worker 가이드](./orchestrator-worker-pattern-guide.md)를 적용한다.
* 조율자는 조각의 내부 모델·저장 구조를 만지지 않고 공개 계약으로 협력한다. 비즈니스 판단은 그 규칙과 상태를 소유한 조각에 둔다.
* 단순한 계산이나 응집된 내부 단계는 함수 호출로 표현한다. 모든 함수를 Worker나 이벤트로 만들지 않는다.
* 외부 I/O와 순수한 판단 로직을 구분한다. 실패·시간·상태 의존성이 필요한 곳에만 드러나게 한다.

## 3. 의존성과 상태

* 기능별 코드를 가까이 두고, 외부에서는 해당 기능의 공개 진입점만 사용한다. 폴더 안쪽 구현에 대한 직접 import를 피한다.
* DB·HTTP·파일·시계 등 외부 의존은 필요한 좁은 계약으로 전달한다. 생성자나 함수 인자로 필요한 의존을 확인할 수 있어야 한다.
* 객체 생성만을 위해 모든 클래스에 인터페이스를 만들지 않는다. 교체·테스트·외부 경계를 분리하는 데 필요한 계약부터 둔다.
* 변경 가능한 전역 상태와 숨은 Singleton 접근을 피한다. 공유 인스턴스가 필요하면 생성 위치, 수명, 쓰기 소유권을 명시한다.
* 다른 기능의 데이터를 직접 수정하지 않는다. 소유자에게 명령하거나, 소유자가 제공한 읽기 계약으로 조회한다.
* 공용 코드로 올리기 전에 실제 소비자와 같은 변경 이유를 확인한다. 작은 중복 때문에 서로 다른 도메인 규칙을 하나로 묶지 않는다.

## 4. 값·상수·오류

* 의미나 정책을 가진 리터럴에는 이름을 붙인다. `0`, 빈 문자열 등 문맥상 분명한 값까지 상수로 추출할 필요는 없다.
* 상수는 사용 책임에 가장 가까운 곳에 둔다. 프로젝트 전체 상수 파일에 도메인 규칙을 모으지 않는다.
* 배포 환경별 값은 설정 경계에서 읽고 검증한다. 비밀값을 소스나 오류 메시지에 넣지 않는다.
* 예상 가능한 실패는 구별 가능한 결과나 오류 타입으로 표현한다. 호출자가 의미를 판단할 수 없는 문자열 하나로 모든 오류를 합치지 않는다.
* 예외를 잡아 성공처럼 반환하지 않는다. 취소·타임아웃·재시도 책임은 계약에 따라 전달하거나 처리한다.

## 5. 주석과 설명

* 코드가 말하는 동작을 반복하는 주석은 쓰지 않는다. 이름과 구조로 의도가 드러나는 방식을 우선한다.
* 코드만으로 복원하기 어려운 **이유**는 짧게 남긴다. 외부 규약, 동시성 불변식, 호환성 우회, 성능상 선택이 해당한다.
* 설명이 길어지면 결정 문서나 계약 문서를 링크한다. 라이선스·생성 코드 표식 등 도구에 필요한 주석은 유지한다.
* 주석을 없애기 위한 무의미한 추상화와 파일 분리는 하지 않는다.

## 6. 변경 완료 확인

1. 대상 기능의 책임·입출력·불변식이 변경 요구와 맞는가?
2. 공개 계약 변경 시 호출자·구독자·테스트를 역방향으로 찾아 호환성을 확인했는가?
3. 기능 내부 변경이 관련 없는 모듈의 구현 수정으로 번지지 않는가?
4. 해당 변경의 성공·실패·상태 경계를 기존 테스트나 필요한 검증으로 확인했는가?
5. 추가된 추상화·파일이 필요한 맥락을 줄이는가? 줄이지 못한다면 단순화한다.
