# 상세 로깅 작성·관리 가이드

대상 흐름의 **어느 경계에서 무엇이 실패했고 어떻게 복구됐는지** 추적할 수 있도록 기존 로깅을 보완한다. 한 줄 요약과 필요한 상세 자료를 연결하는 2계층 구조를 사용하되, 로그 때문에 업무 모듈의 의존성과 전역 상태를 늘리지 않는다.

## 입력과 실행 범위

- 입력: 대상 모듈/사용자 흐름, 진단할 문제, 실행 환경, 기존 로거·수집기, 보존·성능 제약.
- [모듈 경계 가이드](./module-boundary-guide.md)의 최소 맥락으로 진입점·공개 계약·관련 오류 경로부터 읽고 직접 호출자·소비자·조립 위치를 검색한다. 진단에 필요한 경계로 본문 읽기/계측 범위를 확장한다.
- 이미 허용된 로깅 구현·검증은 자율 진행한다. 가정은 기록하고 기존 변경은 보존한다. 별도 권한이 필요한 운영 설정 변경은 기존 권한을 확인한다.
- 진단 질문과 추가할 이벤트를 먼저 연결한다. 모든 함수·프로세스에 로그를 넣거나 기존 로거를 일괄 교체하지 않는다. 무관한 결함은 후속 과제로 남긴다.
- 테스트·오류 분석과 다중 에이전트 작업에서 상세 로그를 작성할 때 이 가이드를 공통 기준으로 사용한다. 작업 범위와 협업 절차는 각각의 실행 프롬프트를 따른다.

## 1. 경계별 계측 계획

`진단 질문 · 생산 모듈 · 이벤트 · 허용 필드 · 관련 요청/작업 ID · 검증 방법` 표를 작성한다.

우선 계측 대상은 요청 진입, 외부 호출 결과, 권위 상태 변경, 분기 판정, 비동기 작업 완료/실패다. 기존 로그나 trace로 이미 답할 수 있으면 중복 계측하지 않는다. 로그가 없다는 사실만으로 해당 동작이 없었다고 결론 내리지 않는다.

- **조율자**: 시나리오 단계와 다음 단계 선택을 기록한다.
- **Worker/도메인**: 필요할 때 자기 책임의 처리 결과만 기록한다. 다른 Worker나 로그 저장 위치를 알 필요가 없어야 한다.
- **Gateway/adapter**: 외부 호출 시간·상태 코드·오류 분류를 기록하고 내부 예외를 공개 오류 계약으로 변환한다.
- **UI**: 사용자에게 보인 상태·중요 행동 결과를 기록한다. 서버의 권한·업무 완료 판정을 추론해 덮어쓰지 않는다.

상세 로그에는 진단에 필요한 입력의 허용 필드, 분기와 판단 근거, 상태 변경 전후의 값·버전, 외부 호출 결과, 오류 원인과 안전하게 정제한 스택, 재시도·복구 결과를 연결한다. 성공/실패 한 단어만으로 처리 과정을 재구성할 수 없으면 필요한 정보를 보강한다. 민감 정보나 진단에 무관한 원문 전체는 수집하지 않는다.

### 테스트·오류 분석 중 지속 보강

1. 테스트 실패나 오류를 분석할 때 현재 로그로 실행 경로·상태·원인 가설을 구분할 수 있는지 확인한다.
2. 부족하면 필요한 경계의 이벤트·필드·상관 ID를 추가하고, 상세 자료가 필요하면 해당 범위의 기록을 활성화한다. 추측만으로 원인을 확정하지 않는다.
3. 같은 조건을 재현하거나 가설을 구분하는 테스트를 다시 실행해 새 로그가 실제 경로에서 생성되고 원인 판별에 도움이 되는지 확인한다.
4. 새로운 정보 부족이 드러날 때마다 보강→재현→분석을 반복한다. 조사가 끝나면 일회성 출력과 중복만 정리하고, 재발 분석·운영에 필요한 상세 로그 작성 코드는 유지한다. 기록물은 아래 7일 보존 정책에 따라 삭제한다. 원인 확인에 필요한 로그 추가는 관련 결함 해결 범위에 포함한다.

## 2. 2계층 로깅 계약

### 1계층: 검색 가능한 요약 이벤트

기존 구조화 로거/표준 출력 수집기를 우선 사용한다. 파일 출력은 실제 환경에 필요할 때 추가한다. 기본 필드 후보:

| 필드 | 의미 |
|---|---|
| `timestamp`, `level` | 시간대가 명확한 시각과 로그 수준 |
| `service`, `module`, `event` | 생산 위치와 안정된 이벤트 이름 |
| `trace_id` 또는 `operation_id` | 한 요청/업무를 연결하는 비밀 아닌 식별자 |
| `outcome`, `error_code` | 성공·실패·취소와 공개 오류 분류 |
| `duration_ms`, `attempt` | 소요 시간과 재시도 횟수, 해당할 때만 |
| `artifact_ref` | 허용된 상세 자료 참조, 있을 때만 |

DEBUG는 개발 진단, INFO는 중요한 업무 경계, WARN은 복구 가능한 이상, ERROR는 처리 실패에 쓴다. 정상 취소/입력 오류의 수준은 계약에 따라 정한다. `DEBUG_MODE=false` 때문에 운영 오류까지 꺼지게 만들지 않는다.

```json
{"timestamp":"2026-09-05T00:00:00Z","level":"WARN","service":"orders","module":"submit","event":"payment.response_timeout","operation_id":"op-example","outcome":"unknown","error_code":"UPSTREAM_TIMEOUT","attempt":1}
```

타임아웃은 응답을 받지 못한 사실이며 결제 같은 외부 부작용의 실패 확정과 다르다. 예시의 업무 결과는 `unknown`으로 기록하고 결과 조회/복구 계약으로 확인한다. 이 예시는 특정 도메인·필드의 강제가 아니며 실제 진단에 필요한 최소 필드만 채택한다.

### 2계층: 진단에 필요한 상세 자료

요약만으로 원인을 판별하기 어려운 경우에만 크기와 보존 기간을 제한한 JSON/Markdown 자료를 만든다. 기본은 **허용 필드만 뽑은 요약**이다.

- LLM 호출: 실제 사용 모델 식별자, 프롬프트 템플릿 버전, 토큰 수/길이, 지연, 결과 분류. 시스템·사용자 프롬프트와 응답 전문을 기본 저장하지 않는다.
- 외부 API: 메서드, 경로 템플릿, 상태, 지연, 안전한 오류 코드. 요청/응답 body와 헤더 전체를 덤프하지 않는다.
- 상태 스냅샷: 필요한 상태 이름·버전·개수·허용 식별자만 저장한다. 모듈 내부 객체 전체를 직렬화하지 않는다.
- 재현 입력이 필요하면 합성 데이터나 최소화한 표본을 우선한다. 민감 원문은 일반 진단 로그에 보관하지 않는다.

상세 기록의 범위·필드·수준은 진단 필요와 데이터 정책으로 정한다. 테스트·오류 분석에서 요약 로그만으로 부족하면 해당 상세 기록을 활성화하고 검증한다. 파일은 저장 성공 후 참조를 반환하고 실패한 쓰기를 정상 링크로 남기지 않는다. `artifact_ref`는 업무 반환값에 섞지 않고 로깅/추적 문맥으로 연결하는 것을 우선한다.

## 3. 민감 정보와 자원 관리

- 토큰·쿠키·비밀번호·비밀키·개인정보·원문 미디어는 허용 필드 밖에 둔다. 식별자는 필요할 때만 비식별화하고, 해시가 개인정보 위험을 자동 제거한다고 가정하지 않는다.
- 호출 지점의 필드 제한과 최종 출력기의 필터를 함께 검증한다. 중첩 객체, 배열, 오류의 message/stack/cause, 문장 중간 URL·토큰, 개행·제어 문자를 포함한다.
- 로그·상세 자료·브라우저 trace/HAR·생성된 진단 리포트에는 아래 7일 보존과 접근 정책을 적용한다. 표시 화면에서 가리는 것으로 원본 수집 위험이 해결되지 않는다.
- 파일 출력이 필요하면 충돌 없는 작업 ID, 최대 크기/개수, 회전, 접근 권한을 정한다. 정리는 로거가 소유하는 진단 자료에만 적용하며 소스·설계 문서·테스트 fixture·다른 작업 파일은 삭제하지 않는다.
- 큐와 버퍼에 상한을 두고 샘플링/드롭 정책과 드롭 계측을 남긴다. 매 이벤트 전체 파일 재생성이나 동기 디스크 쓰기를 피한다.
- 일반 진단 로그 저장 실패가 제품을 중단시키지 않도록 제한된 대체 경로를 둔다. 예외를 조용히 버리거나 실패 로거를 재귀 호출하지 않는다. 감사 기록이 성공 조건인 업무는 별도 계약에 따라 실패 정책을 정한다.

### 로그 보존 기간 — 7일 경과 시 자동 삭제

- 보존 기간은 **7일(168시간)**이다. UTC 기록 시각(`recorded_at`, 기존 `timestamp` 등 실제 로그 필드에 매핑)으로 `cutoff = now_utc - 7일`을 계산하고 `recorded_at <= cutoff`인 로그와 그 상세 자료를 다음 정리 주기에 삭제한다. 원래 기록 시각은 수집·복사·압축 시 갱신하지 않으며, 파일 수정시각(`mtime`)으로 보존 기한을 다시 계산하지 않는다.
- 실행 시작 시 한 번, 실행 중에는 **최대 1시간 간격**으로 정리한다. 중단 중 만료된 기록은 다음 시작 시 정리하며, 외부 로그 수집기를 사용하면 그 저장소에도 7일 만료 정책을 설정하고 실제 삭제 지연을 확인한다.
- 오래 실행되는 세션도 기록 시각에 따라 회전한다. 쓰는 중인 파일은 먼저 새 파일로 전환하고 핸들을 닫은 뒤 정리한다. 활성 세션이라는 이유로 오래된 로그 전체를 무기한 보존하지 않는다.
- 최근 기록과 만료 기록이 한 파일에 섞여 있으면 만료 기록만 제거하거나 저장 단계에서 시간 구간별로 분리한다. 최근 기록까지 지우거나 파일의 최신 기록 때문에 오래된 기록을 계속 남기지 않는다. 외부 저장소는 이벤트별 만료 등 동등한 정책을 사용한다.
- 삭제 권한·I/O 오류가 발생하면 실패와 미삭제 범위를 요약 로그/메트릭으로 남기고 다음 주기에 다시 시도한다. 삭제 성공을 확인하지 않고 정리 완료라고 보고하지 않는다.

## 4. 동시 실행과 의존성

- 한 전역 가변 `current_session`에 요청 문맥을 보관하지 않는다. 명시적 문맥 전달 또는 환경의 요청별 문맥 기능으로 병렬 작업을 격리한다.
- 비동기 작업·큐·재시도에 동일 업무 식별자를 전파하되 실행 시도/이벤트 ID는 구분한다. 외부에서 받은 식별자의 길이·형식을 검증하고 비밀값을 식별자로 사용하지 않는다.
- 기존 로거가 있으면 재사용한다. 도메인은 작은 로그 포트나 이벤트 계약만 알고, 저장소·Markdown 생성기·수집 SDK는 외부 adapter가 담당하도록 한다. 이를 위해 불필요한 공통 프레임워크를 새로 만들지 않는다.
- 시작/종료 자원 정리는 오류·취소에도 적용한다. 종료 시 제한된 flush와 미완료 이벤트 표시가 가능해야 한다.

## 5. 선택 기능: 실행 흐름 시각화

반복·분기·병렬 수행 때문에 사건 순서를 이해하기 어려울 때 추가한다. 단순 요청은 로그/trace만으로 충분하다.

- 시나리오 조율자가 있는 뷰는 [jobflow 가이드](./job-flow-diagram-guide.md)와 같은 **조율자 관점**으로 기록한다. `A → B`는 A의 결과로 조율자가 B를 실행했다는 뜻이며 Worker 직접 의존을 만들지 않는다.
- Worker 내부 상세는 별도 자료/하위 뷰로 연결한다. 독립 이벤트 협력에 존재하지 않는 전역 조율자를 만들어 넣지 않는다.
- 이벤트에 `event_id`, `parent_id/caused_by`, 작업/시도 ID, 단계, 결과를 필요한 만큼 기록한다. 시각만 정렬해 병렬 수행을 인과 순서로 오인하지 않는다.
- 관측된 시작·분기·합류·완료만 그린다. `phase` 이름만으로 fan-out/fan-in을 추측하지 않는다. 누락/진행 중/중단도 표시한다.
- 사람이 작성하는 설계 흐름은 `jobflow` DSL을 유지한다. 실행 로그에서 자동 생성한 Mermaid `flowchart`는 **관측된 실행 기록**임을 명시한다. 설계 다이어그램의 대체물이 아니다.
- 라벨·링크는 이스케이프/허용 목록을 적용하고 내부 경로·원문을 노출하지 않는다. 실제 렌더러가 없으면 문법 확인과 렌더링 미검증을 구분한다.

## 6. 검증과 완료

필요한 동작을 구현한 뒤 아래를 실제 출력과 대조한다.

1. 정상·실패·취소 흐름에서 관련 경계의 작업 ID와 결과를 연결할 수 있다.
2. 병렬 요청/비동기 작업의 문맥이 섞이지 않고, 재시도와 중복 처리가 구분된다.
3. 민감 표본이 최종 출력·상세 자료·오류 경로에 노출되지 않는다.
4. 디스크 실패·버퍼 포화·종료 중 오류에서 정한 실패/자원 상한 정책이 지켜진다.
5. 변경 전후 지연·로그량을 필요한 범위에서 비교했고 진단 효과에 비해 비용이 과하지 않다.
6. 부족한 로그를 보강한 뒤 재현·분석으로 효과를 확인했고, 재발 분석에 필요한 로그를 남긴 채 임시·중복 출력만 정리했다. 실제 제품 경로가 로거를 호출하는지 확인하며 로거 단위 테스트만으로 통합 완료라 하지 않는다.
7. 7일 직전·경계·직후 기록, 7일 넘게 실행되는 세션, 최근/만료 기록 혼합, `mtime` 변경, 정리 실패에서 보존·삭제 정책을 확인했다. 최근 기록과 로거 소유 범위 밖 파일이 삭제되지 않아야 한다.

최초 검증 뒤 결함이 있으면 원인을 고치고 영향 부분을 재검증한다. 조건 변화 없는 재시도를 반복하지 않는다. 필수 검증이 막히면 미완료와 필요한 환경을 기록한다.
