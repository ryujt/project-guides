# 시나리오 기반 상태 전이 분석서 작성 가이드

이 분석서는 “이 사람은 무엇을 하려 하고, 이 조건에서 어떤 결과를 보며, 다음에 무엇을 할 수 있는가?”에 답한다. 그 경험을 설명하는 객체의 상태와 사건을 추적해 E2E 테스트의 기대 결과와 설계를 검토할 근거로 쓴다. 제목은 **시나리오 기반 상태 전이 분석서**로 하고, 첫 단락에서 대상 업무·역할·분석 범위를 밝힌다.

## 시나리오 선정과 근거

- 업무별로 **역할과 목표 → 진입점 → 수행 중 선택 → 결과 확인 → 다음 행동**을 따라가며 가능한 사용자 경험을 최대한 찾는다. 기능·업무 규칙, 화면·공개 인터페이스, 기존 테스트와 문의·결함 사례 등 확보한 자료에서 경로를 대조한다. 일반 사용자와 운영자처럼 한 사람의 행동이 다른 사람에게 영향을 주면 양쪽이 결과를 확인하는 시점까지 살핀다. UI가 없는 업무도 기한 도래·외부 통지·자동 처리의 결과를 누가 어느 조회·알림·공개 응답에서 확인하는지 추적한다.
- 각 여정에서 실제로 경험을 가르는 조건을 바꿔 본다. 예를 들어 첫 이용과 재방문, 권한과 소유권, 빈 데이터와 한도·기한 경계, 잘못된 입력과 보완, 취소·뒤로 가기·재진입을 살핀다. 외부 처리가 있다면 접수와 완료 사이의 대기, 응답 유실과 확정 실패, 중복 제출·늦은 통지, 다른 사용자나 기기에서 먼저 처리한 경우를 확인한다. 대기 뒤 완료, 실패 뒤 복구처럼 여러 단계에 걸쳐 나타나는 경험도 하나의 여정으로 따라간다.
- 시작 조건, 보이는 결과, 가능한 다음 행동 또는 다른 역할에 미치는 영향이 달라지면 구별되는 E2E 후보로 기록한다. 상태가 유지되어도 입력을 고칠 수 있는 경우와 접근이 차단된 경우는 각각 확인한다. 재현 절차와 판정 기준이 같은 입력값 변형은 한 후보의 데이터 예로 묶는다. 검토 순서는 위험도·빈도로 정할 수 있고, 아직 조사하지 못한 역할이나 경계 조건은 남은 범위에 적는다.
- **AS-IS**에서는 코드의 상태 쓰기 위치, 테스트, 관찰한 동작 등으로 현재 전이를 확인한다. 업무 규정과 구현 동작이 다르면 각각의 근거를 적는다. **TO-BE**에서는 요구사항·제약과 채택한 설계 결정을 전이에 연결하고 가정·미결정을 표시한다. 기존 AS-IS가 있으면 대응 시나리오에서 달라지는 조건과 결과를 밝힌다.
- 업무 사례만 주어진 경우에는 사례의 전제를 명시하고 가정한 전이와 확인된 사실을 구분한다. 근거가 부족해 다음 상태를 판단할 수 없는 경로는 해당 지점과 필요한 자료를 적는다.

### 참여자별 시도와 독립 사건

업무 하나를 고르고 대상 시스템의 화면·역할·연동 계약·운영 절차에서 **누가 먼저 사건을 일으키거나 결과를 바꿀 수 있는지** 찾아 적는다. 작성자는 시작 주체, 그 주체가 시도할 행동이나 보낼 사건, 그때 가능한 대상 상태를 대조한다.

| 살필 관점 | 후보를 찾기 위한 질문 |
| --- | --- |
| 서로 다른 이용자 | 첫 방문자와 재방문 회원, 비회원, 다른 계정, 요청자와 실제 수령인의 권한·정보·목표가 어떻게 다른가? 한 사람이 여러 기기나 계정을 오갈 때도 같은 건을 열 수 있는가? |
| 예상 밖의 시도 | 오래된 탭에서 이미 끝난 작업을 다시 제출하거나, 다른 주문에 받은 코드를 입력하거나, 단계가 끝나기 전에 다음 단계로 가면 무엇이 보이는가? 잘못 고른 수량이나 대상을 어떻게 알아차리고 고치는가? |
| 운영·외부·자동 사건 | 담당자가 잘못된 대상에 작업하거나 이전 작업 목록을 재사용하면 어떻게 되는가? 결제사, 운송사, 알림 사업자, 기한 처리·대사 담당이 고객 접속 없이 먼저 승인·정정·실패·완료를 알릴 수 있는가? 각 참여자가 아는 사실과 그 처리 결과를 누가 확인하는가? |
| 경합과 거절 | 같은 수량·금액·권한을 두 참여자가 바꾸려 할 때 중요한 선후를 뒤집는다. 어느 요청이 수락·보류·거절되며, 무엇이 유지되는가? 이미 발생한 실물 인계·외부 승인을 누가 확인해 차이를 해소하는가? |

분석서에 **시작 주체와 시도·사건 / 시작 상태 또는 경합 상대 / 연결한 후보 ID·절**을 짧게 대응시킨다. 계약상 들어올 수 있지만 처리가 미정인 사건은 필요한 결정과 영향을 받는 사람을 남긴다. 실제 권한·계약·시간 순서상 일어날 수 없는 조합에는 그 이유를 적는다. 건수 목표를 채우기 위한 조합 대신, 관찰 결과·허용되는 다음 행동·정합성 판단이 달라지는 경로를 각각 검토한다. [쇼핑몰 참여자별 검토 예제](../examples/diagram/state/shopping-mall-scenario-state-analysis.md#누가-먼저-어떤-사건을-일으키는가)

## 문서 구성

처음에 분석 관점과 기준 자료를 밝히고, 업무 영역·역할별 시나리오 목록에서 각 본문 절로 연결한다. 제목은 ‘기한이 지난 예약을 다시 열어 수령 가능 여부를 확인한다’처럼 사용자 상황과 목표가 드러나게 쓴다.

1. **상황과 관찰 대상**을 소개한다. 누가 어떤 목표로 어디서 시작하는지, 어떤 객체의 상태를 누가 변경하는지 적는다.
2. **시나리오별 상태도**에 주 객체의 시작 상태와 사건·조건별 결과를 그린다. 상태 이름은 전후에 확인할 수 있는 값으로 쓰고, 추론한 상태에는 전제를 밝힌다. 같은 상태 경로를 쓰는 E2E 후보는 그림을 공유하고 해당 분기나 유지 상태를 짚는다. [State 가이드](state-diagram-guide.md)의 문법과 [설치된 출력 형식](diagram-output-guide.md)을 적용한다.
3. **분기와 연쇄 변화**를 그림 아래에서 설명한다. 어떤 조건에서 상태가 유지되거나 바뀌는지, 다른 객체가 어느 사건을 받아 어떻게 달라지는지 근거와 함께 적는다. 관련 절이 있으면 연결한다. 연쇄가 복잡하면 ‘계기 사건 | 영향받는 객체 | 전후 상태 | 관련 절’ 표를 쓴다.

### E2E 테스트 후보

시나리오 절마다 아래 항목을 표나 짧은 단계로 적는다. 하나의 후보는 다른 사람이 독립적으로 준비하고 재현해 결과를 판정할 수 있는 단위다.

| 항목 | 기록할 내용 |
| --- | --- |
| 식별자와 상황 | 갱신 후에도 추적할 수 있는 ID, 역할과 목표, 구별하려는 조건. 기존 요구사항·테스트 ID가 있으면 연결한다. |
| 준비 | 시작 위치, 계정·권한, 필요한 데이터와 초기 상태. 재현에 필요한 경우에만 시간이나 외부 응답 조건을 적는다. |
| 행동과 사건 순서 | 사용자가 실제로 하는 행동을 차례로 적는다. 도중에 다른 사람이 처리하거나 통지가 도착하면 어느 행동 전후인지 표시한다. |
| 확인할 결과와 다음 행동 | 누가 언제 어느 화면·알림·내역·공개 응답에서 어떤 값이나 허용 동작을 확인하는지 적는다. 대기가 있으면 처음 보이는 결과, 대기가 풀리는 조건, 나중에 확인할 최종 결과를 나눈다. 중복 방지가 중요하면 다시 조회해 같은 건이 한 번만 반영됐는지도 확인한다. |

후보의 판정 기준은 AS-IS에서는 근거로 확인한 현행 결과, TO-BE에서는 채택한 설계의 기대 결과다. 내부 로그나 저장 상태는 원인을 추적하는 근거로 쓰고, E2E 판정에는 사용자나 연동 주체가 확인할 수 있는 결과를 적는다. 결과를 관찰할 수 없거나 재현 조건이 부족하면 필요한 관찰 지점·자료를 명시한다.

### 시스템 검증용 사례의 깊이

시스템 검증에 사용할 분석서는 다른 검증자가 같은 상태를 만들고 결과를 판정할 수 있게 쓴다. 분야별 담당자가 함께 쓸 때는 진입 문서에 공통 용어·가상 데이터·역할과 권한·시험용 외부 연동 조건을 정리한다. 한 사례의 결과를 다음 시험의 전제로 쓰는지, 독립적으로 초기화하는지 명시한다.

결과가 여러 객체에 걸치거나 금전·권한·실물 처리에 영향을 주는 사례는 다음 항목을 채운다. 관련 후보가 같은 상태도를 사용하면 소유 절과 상태 이름을 연결한다.

| 항목 | 검증자가 재현하고 판정하는 데 필요한 내용 |
| --- | --- |
| 사례와 시작값 | 사례 ID, 시작 사건을 일으킬 주체, 주 객체와 상태 소유자, 서로 구별되는 업무 식별자·권한·수량·금액·시각 등 결과를 가르는 실제 입력값 |
| 분기·금지 전이 | 어떤 조건에서 어느 상태로 바뀌거나 유지되는지, 이미 확정된 상태에서 허용되지 않는 동작과 계속 지켜야 하는 불변조건. 순서가 중요한 두 사건은 선후를 바꿔 각각 실행한다. |
| 다른 객체의 연쇄 | 계기 사건 → 수신한 소유자와 객체 → 전후 상태 또는 유지 값 → 대응 절. 후속 작업이 늦어지는 동안 보이는 중간 결과와 최종 확정 조건을 구분한다. |
| 시험 단계·판정 증적 | 누가 어떤 값으로 어디에서 실행하고, 누가 어느 화면·조회 응답·작업 목록·외부 시험 내역에서 어떤 ID·금액·건수를 대조하는지 쓴다. 중복·거절은 발생하면 안 되는 출고·승인·권한까지 검사한다. |
| 실제 실행 | 설계 근거·가정·미결정과 예상 결과를 밝힌다. 실제로 실행한 경우에는 사용한 환경·사례 ID·관찰값·증적과 통과 또는 실패를 남긴다. 아직 정하지 못한 판정 조건은 미결정으로 추적한다. |

검토 시 담당자가 고객의 ‘완료’ 표시만 보고 통과시킬 수 있는 사례를 골라, 다른 주체의 기록이 누락되거나 두 번 반영된 경우에도 그 판정을 내렸을지 반문한다. 판정이 같다면 원거래·후속 거래 대조나 수량·권한 불변조건을 보완한다. [배송과 취소 경합의 상세 검증 예제](../examples/diagram/state/shopping-mall-scenario-state-analysis.md#인계-확인-중인-주문을-두-조건에서-검증한다)

### 설계 검토

사용자가 성공 여부를 알 수 없는 순간, 다시 눌러도 되는지 판단할 수 없는 대기, 복구 방법이 없는 오류처럼 **어느 단계에서 어떤 불편이나 오해가 생기는지** 해당 후보 ID에 기록한다. 그 자리에서 현재 확인한 결과, 바꿀 동작이나 결정할 질문, 수정 후 같은 절차로 확인할 기대 결과를 연결한다. 미채택 제안과 정책 미결정은 별도로 표시해 이미 확인한 동작이나 확정된 테스트 기준과 구분한다.

## 작성 예

장비 대여를 설계하면서 ‘수령 전에 기한이 지나면 예약을 만료한다’고 정했다고 하자. 다음 상태도는 예약 한 건을 추적한다.

```state
<s> --> (수령 대기) : 예약 확정
(수령 대기) --> (수령 완료) : 기한 내 인수 확인
(수령 대기) --> (만료) : 미수령 상태로 기한 도래
```

이 예제에서는 이용자와 담당자가 각각 예약 상태를 조회할 수 있다. 담당자는 수령 대기 상태에서만 인수를 확인할 수 있다. 예약이 만료되면 그 예약에 배정했던 장비를 대여 가능 상태로 되돌려 다른 이용자의 목록에도 표시하기로 했다.

| ID · 상황 | 준비와 행동 | 사용자가 확인할 결과 |
| --- | --- | --- |
| R1 · 기한 내 수령 | 수령 대기 예약을 준비한다. 기한 전에 담당자가 인수를 확인한 뒤 이용자가 예약 상세를 연다. | 해당 예약이 ‘수령 완료’로 표시된다. |
| R2 · 자리를 비운 사이 만료 | 장비 한 대를 배정한 수령 대기 예약에서 인수 확인 없이 기한을 넘긴다. 이용자가 예약을 다시 열고 다른 이용자는 대여 목록을 연다. | 예약 상세에 ‘만료’가 표시되고 수령을 진행할 수 없다. 다른 이용자의 목록에는 해당 장비가 대여 가능으로 표시된다. |
| R3 · 확인 직후 응답 유실 | 담당자가 기한 내 인수를 확인한다. 처리는 완료됐지만 응답이 도달하지 않은 조건에서 담당자가 예약 상세를 다시 연다. | 다시 연 상세에는 이미 확정된 ‘수령 완료’가 그대로 표시되고 인수 확인은 다시 선택할 수 없다. |
| R4 · 기한과 인수 확인이 겹침 | 수령 대기 예약을 준비한다. 만료 처리와 담당자의 인수 확인이 같은 시점에 도착하게 한 뒤 두 역할이 같은 예약을 조회한다. | **미결정.** 어느 사건을 우선하는지 정해야 이용자와 담당자가 보게 될 상태를 판정할 수 있다. |

**R2 설계 검토**에서 ‘만료’만 보이고 다시 대여하는 방법을 찾을 수 없다면, 예약 가능한 장비를 조회하는 동작을 제안할 수 있다. 채택하면 R2에서 그 동작으로 대여 목록을 열 수 있는지도 확인한다.

## 검증

- 범위에 둔 역할·목표·진입점과 결과를 가르는 조건을 후보 ID에 대조한다. 정상 흐름에서 조건 하나 또는 함께 일어날 수 있는 사건의 순서를 바꿔 누락된 경험을 찾는다. 포함한 상황, 제외 사유, 미조사·미확인·미결정 경로와 필요한 후속 확인을 밝힌다.
- 참여자 목록을 후보 ID에서 역으로 확인한다. 외부 주체가 고객 행동의 응답자로만 등장하면 스스로 보내는 통지·정정·미전달 사건을 실제 계약에서 다시 찾는다. 정상 처리와 거절에서 유지 또는 변경되는 상태, 영향을 받는 두 번째 역할의 관찰 결과를 대조한다.
- 각 후보의 준비와 행동만 읽고 다른 사람이 같은 상황을 재현할 수 있는지, 관찰 결과로 성공·거절·대기·복구 등을 판정할 수 있는지 검토한다. 그림의 분기, 상태 소유자, 다른 객체의 변화, 사용자에게 보이는 결과가 근거와 일치하는지 대조한다. 상태 변화가 없는 경로도 사용자의 결과와 유지 근거를 확인한다.
- 설계 검토 항목에서 원래 상황과 수정 후 다시 확인할 후보를 찾을 수 있는지 확인한다. 문서 검토·도표 변환·렌더링 결과와 실제 실행한 E2E 테스트 결과는 각각 수행한 범위만 기록한다.
