# 시나리오 기반 상태 전이 분석서 작성 가이드

이 분석서는 “이 상황에서 무엇의 상태가, 어떤 사건과 조건 때문에, 어떻게 달라지는가?”에 답한다. 문서 제목은 **시나리오 기반 상태 전이 분석서**로 하고, 첫 단락에서 대상 업무와 분석 범위를 밝힌다.

## 시나리오 선정과 근거

- 업무 영역별로 누가 무엇을 하려는지, 어떤 사건이 결과를 바꾸는지 조사한다. 사람의 요청뿐 아니라 범위에 속하는 기한 도래, 외부 통지, 백그라운드 처리도 살핀다. 기본 흐름에서 취소·거절·실패·복구 등 결과가 달라지는 조건을 찾고, 독립적으로 시작되는 상황은 별도 시나리오로 다룬다.
- **AS-IS**에서는 코드의 상태 쓰기 위치, 테스트, 관찰한 동작 등으로 현재 전이를 확인한다. 업무 규정과 구현 동작이 다르면 각각의 근거를 적는다. **TO-BE**에서는 요구사항·제약과 채택한 설계 결정을 전이에 연결하고 가정·미결정을 표시한다. 기존 AS-IS가 있으면 대응 시나리오에서 달라지는 조건과 결과를 밝힌다.
- 업무 사례만 주어진 경우에는 사례의 전제를 명시하고 가정한 전이와 확인된 사실을 구분한다. 근거가 부족해 다음 상태를 판단할 수 없는 경로는 해당 지점과 필요한 자료를 적는다.

## 문서 구성

처음에 분석 관점과 기준 자료를 밝히고, 업무 영역별 시나리오 목록에서 각 본문 절로 연결한다. 제목은 ‘예약’ 같은 기능명보다 ‘수령 기한이 지난 예약이 만료된다’처럼 상황과 결과가 드러나게 쓴다.

1. **상황과 관찰 대상**. 각 절의 첫 문장에서 행위자 또는 사건의 출처, 시작 조건, 상태를 추적할 주 객체와 그 상태를 변경하는 소유자를 식별한다.
2. **시나리오별 상태도**. 주 객체의 시작 상태에서 사건·조건별 결과까지 그린다. 상태 이름은 전후에 관찰할 수 있는 값으로 쓰고, 업무상 구분을 추론한 경우 그 전제를 표시한다. [State 가이드](state-diagram-guide.md)의 문법으로 작성한 뒤 [설치된 출력 형식](diagram-output-guide.md)을 적용한다.
3. **분기와 연쇄 변화**. 그림 아래에 결과를 가르는 조건과 근거를 설명한다. 거부·중복·재시도가 적용된다면 해당 입력을 받았을 때 상태가 유지되는지, 어떤 전이가 일어나는지 적는다. 다른 객체도 바뀌면 어느 사건을 받아 어떤 상태로 바뀌는지 적고 해당 객체의 시나리오 절이 있으면 연결한다. 연쇄가 복잡하면 ‘계기 사건 | 영향받는 객체 | 전후 상태 | 관련 절’ 표를 쓴다.

예를 들어 장비 대여를 설계하면서 ‘수령 전에 기한이 지나면 예약을 만료한다’고 정했다고 하자. 다음은 예약 한 건을 추적하는 작성용 DSL이다.

```state
<s> --> (수령 대기) : 예약 확정
(수령 대기) --> (수령 완료) : 기한 내 인수 확인
(수령 대기) --> (만료) : 미수령 상태로 기한 도래
```

예약의 두 결과는 인수 확인 여부로 갈린다. 만료된 예약에 배정했던 장비를 다시 대여할 수 있게 한다면, 장비의 ‘배정됨 → 대여 가능’은 만료에 따른 연쇄 변화로 설명한다. 기한과 인수 확인이 겹칠 때의 우선순위가 정해지지 않았다면 미결정으로 남긴다.

## 검증

시나리오 목록을 범위 안의 업무·사건과 대조하고, 각 그림에서 시작 상태부터 정상 결과와 적용되는 예외 결과까지 따라간다. 분기 조건·상태 소유자·연쇄 사건이 시나리오 설명 및 근거와 일치하는지 확인한다. 조사 범위에 상태 변화가 없으면 분석서에 대상과 확인 근거를 기록한다. 전이의 근거가 부족한 경우는 미확인으로 남긴다. 실제 수행한 문법 검사·변환·렌더링 범위를 구분해 기록한다.
