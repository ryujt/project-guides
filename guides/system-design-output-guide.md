# AS-IS·TO-BE 공통 산출물 배치 가이드

AS-IS·TO-BE 설계 문서의 저장 위치·고정 폴더 구조·화면별 HTML·누락 검증을 정의한다. 문서 내용과 Job Flow 파일의 작성 기준은 [AS-IS 프롬프트](../prompts/system-design-as-is-prompt.md)·[TO-BE 프롬프트](../prompts/system-design-to-be-prompt.md)를 따른다.

## 저장 위치와 고정 구조

문서 생성 일시를 `YYYYMMDD-HHMMSS` 형식의 `{DATE}`로 정하고 `docs/design/{DATE}/` 아래에 작성한다. 같은 설계 작업의 AS-IS·TO-BE는 같은 `{DATE}`를 사용하며, 후속 작성에서는 해당 폴더를 재사용한다. 사용자가 저장 위치를 지정하면 상위 위치를 따르되, 그 아래의 구조는 유지한다.

`{design-type}`은 `as-is` 또는 `to-be`다. 작성할 유형에 다음 구조를 항상 적용한다. 날짜·설계 유형·서비스와 화면 식별자를 제외한 폴더 이름·깊이·문서 이름을 작업마다 바꾸지 않는다.

```text
docs/design/{DATE}/{design-type}/
├── system-design-{design-type}.md
├── navigation.md
├── screen-layout.md
└── details/
    ├── job-flow/
    │   ├── macro.md
    │   ├── system.md
    │   └── <service-name>.md
    └── screens/
        └── <screen-id>.html
```

- `system.md`의 생략 조건과 서비스별 파일 분리는 각 프롬프트를 따른다.
- Navigation은 `navigation.md` 한 파일, Layout은 `screen-layout.md` 한 파일에 모은다. 시나리오·화면마다 Markdown 파일이나 별도 폴더로 다시 나누지 않는다.
- 화면 HTML은 `details/screens/`에 둔다. 공통 CSS·바닐라 JavaScript·이미지 파일이 필요하면 `details/screens/assets/`에 둔다.
- 문서·HTML·자산 간 링크는 상대 경로로 작성하고, 작성 컴퓨터에서만 유효한 경로·링크를 남기지 않는다.

## 페이지·장면 목록

`screen-layout.md`의 처음에 대상 UI의 전체 페이지 목록을 둔다.

| 화면 ID | 페이지 이름·Navigation 표기 | 실제 경로·진입점·접근 조건 | 관련 시나리오 | Layout 절·HTML | 근거·확인 상태 |
| --- | --- | --- | --- | --- | --- |

- 페이지는 사용자가 인지하는 독립 화면 단위다. 라우트가 있는 UI는 실제 페이지와 등록 경로를 대조한다. 중첩된 생성·편집·작업 라우트가 독립 화면을 표시하면 목록·상세에 흡수하지 않고 각각 식별한다. UI가 없는 라우트 그룹·고정 리다이렉트는 경로와 결과만 기록하며 HTML을 만들지 않는다.
- 동적 경로의 데이터 ID별 인스턴스는 같은 페이지로 묶는다. 별칭 경로가 같은 페이지를 표시하면 정규 화면 ID 하나에 경로 대응을 남긴다. 반대로 서로 다른 페이지를 공통 셸·유사한 이름·같은 기능 영역이라는 이유로 하나로 합치지 않는다.
- 페이지 안의 탭·폼 단계·모달·드로어·로딩·빈값·검증 오류·요청 실패·접근 거부·완료 표시는 **장면**으로 구분한다. 독립 라우트가 있는 작업 화면은 앞의 페이지 기준을 적용한다. 중요한 장면이 Navigation의 별도 화면/오버레이 노드나 `Page(Component)`로 표현돼도 소속 페이지와 장면의 대응을 남긴다. API·처리·메시지 노드는 페이지나 장면으로 세지 않는다.
- `<screen-id>`는 페이지를 알아볼 수 있는 영문 소문자·하이픈 이름이며 HTML 파일의 이름과 같다. 같은 페이지가 여러 시나리오에 등장하면 같은 ID·파일을 재사용하고, 같은 설계 작업의 AS-IS·TO-BE에서 대응하는 페이지는 같은 ID를 쓴다. HTML의 기본 이름을 Navigation 표기와 위 표에서 대응시켜 파일명만 보고도 페이지를 찾을 수 있게 한다.

각 페이지 절에는 다음 장면 표를 둔다. 구현에 적용되는 장면과 시나리오상 중요한 변형을 기록하며, 모든 페이지에 같은 상태를 기계적으로 추가하지 않는다. 같은 장면을 여러 시나리오에서 재사용하면 같은 장면 ID를 쓴다.

| 장면 ID·이름 | 관련 시나리오·진입 동작/조건 | 보이는 내용·다음 동작/결과 | HTML의 장면 링크·전환 방법 | 근거·확인/재현 상태 |
| --- | --- | --- | --- | --- |

Navigation의 페이지·장면은 이 목록의 ID와 이름으로 대응시키고 Layout 절·HTML 장면으로 링크한다. UI가 있으나 화면 이동이 없는 페이지도 목록·Layout·HTML에 포함하고, `navigation.md`에 진입 방법과 현재 페이지에서의 과업·결과를 기록한다. 따라서 다이어그램의 화살표에 나오지 않는다는 이유로 페이지를 누락하지 않는다.

## 화면별 HTML

- **전체 페이지 목록의 페이지마다 `details/screens/<screen-id>.html` 하나를 생성한다.** Navigation에 보이는 서로 다른 페이지를 하나의 HTML에 합치거나 대표 페이지로 대신하지 않는다. 같은 페이지의 장면별 HTML을 따로 늘리지 않고 해당 페이지 파일 안에서 각 장면을 재현한다. 기본 장면 하나만 만든 뒤 나머지 장면을 문장으로만 나열한 결과는 장면 재현 완료가 아니다.
- 바닐라 HTML·CSS와 필요한 경우 바닐라 JavaScript로 작성한다. 프레임워크·패키지 설치·빌드·백엔드 연결 없이 브라우저에서 HTML 파일을 직접 열어 확인할 수 있게 한다.
- 화면의 실제 모양을 확인할 수 있도록 주요 콘텐츠·메뉴·버튼·입력 폼·목록과 색상·글꼴·간격·정렬을 표현한다. 영역 이름만 적힌 빈 상자나 프레임워크 컴포넌트 파일로 대신하지 않는다. AS-IS는 코드·화면 관찰로 확인한 현재 모습을 재현하고 근거가 부족한 부분은 미확인으로 기록한다. TO-BE는 제안한 목표 모습을 표현하며 확정 사항·가정을 구분한다.
- 장면은 페이지 안의 실제 동작 또는 검토용 장면 선택으로 열어 볼 수 있게 한다. 각 장면에 안정된 fragment나 query 식별자를 부여하고, 그 링크로 HTML을 직접 열었을 때 해당 장면을 표시한다. 선택 UI를 쓰면 제품 UI와 구별한다. 화면 상태 확인에 필요한 동작은 예시 데이터와 바닐라 JavaScript로 표현하고 실제 API 동작과 구분한다. 적용 상태와 반응형 차이는 `screen-layout.md`의 설명과 맞춘다.
- 페이지 간 이동은 대응 HTML 상대 링크로 연결하고, 같은 페이지의 장면 전환은 해당 파일 안에서 처리한다. 구현한 대상 이동을 빈 링크나 안내 메시지로만 대신하지 않는다. 확인되지 않은 이동·내용을 추측해 만들지 않고, 미재현 장면과 부족한 근거를 목록에 표시한다.
- `screen-layout.md`의 페이지별 절에 화면 이름·식별자·HTML 및 각 장면 링크를 적는다. `navigation.md`에서는 [시나리오별 화면 확인 링크 기준](navigation-diagram-guide.md#문서-구성과-화면-확인-링크)에 따라 매 시나리오의 표에 등장 페이지의 기본 화면·사용하는 장면·Layout 링크를 직접 표시한다. 세 산출물에서 같은 페이지·장면 이름을 사용한다.

UI가 없으면 `navigation.md`·`screen-layout.md`에 화면과 HTML이 0개인 이유를 기록하고, 가상의 화면 HTML을 만들지 않는다.

## 검증

문서 대조·브라우저 확인과 재검증은 [테스트 실행 이력 기준](module-boundary-guide.md#테스트-실행-이력)에 따라 이전 관련 이력을 확인하고 매 실행 결과와 다음 확인 사항을 남긴다.

다음 대응을 각각 확인한다. 총 파일 수가 같아도 빠진 페이지 대신 중복·무관한 페이지가 있으면 통과가 아니다.

1. **조사 대상 → 시나리오·페이지 목록**: 실제 라우트·메뉴·작업 진입점·조건부 페이지를 목록과 대조한다. AS-IS는 코드/관찰 근거, TO-BE는 요구·유지/변경 범위와 대조하며 대표 과업만 선택하지 않았는지 본다. 대상·제외·미확인을 나누고, 목록 자체의 누락도 검사한다.
2. **시나리오 → 상세 분석**: 기능과 각 페이지의 과업이 `navigation.md`의 시나리오 절에 대응하는지 확인한다. [시나리오 검토 기준](navigation-diagram-guide.md#검토와-확인)으로 조건·분기·결과를 조사·설계 근거와 대조한다. 시나리오 수나 `navigation` 블록 수만으로 완료를 판정하지 않는다.
3. **페이지 → Layout·HTML**: 전체 페이지 목록의 화면 ID 집합, `screen-layout.md`의 페이지 절 ID 집합, `details/screens/`의 HTML 기본 이름 집합이 같은지 양방향으로 대조한다. Navigation의 모든 페이지 노드와 화면/오버레이 노드가 목록의 페이지·장면으로 해석되는지도 확인한다. 별칭·동적 경로·UI 없는 리다이렉트의 대응과 제외 이유를 확인한다.
4. **장면 → 재현**: 각 시나리오의 단계·분기·종료에서 보이는 장면이 소속 페이지의 장면 표와 HTML의 실제 표시로 대응하는지 본다. 시나리오마다 `화면 확인 링크` 표가 있고 등장 페이지의 기본 화면과 해당 장면을 모두 직접 여는지 확인한다. 링크로 직접 열기, 장면 전환, 적용되는 실패·취소·복귀 경로와 페이지 간 이동을 확인한다. 장면 이름만 있고 실제 내용이 바뀌지 않으면 미재현이다.
5. **참조와 자산**: 문서 링크·앵커·페이지/장면 ID·HTML 간 이동·CSS/JavaScript/이미지 경로를 확인한다. 같은 페이지의 중복 파일이나 대상 없는 파일을 정리하고, 공통 자산은 `assets/`에 둔다.

페이지 누락·깨진 링크·필수 장면의 미확인/미재현이 남으면 전체 완료로 판정하지 않는다. 대상·작성·제외·미확인 페이지/시나리오와 미재현 장면의 수와 목록을 기록하고, 완료한 부분과 남은 조사를 구분한다. 외부 자료에 접근할 수 없으면 필요한 입력을 밝힌다.

HTML을 브라우저에서 열어 화면 모양·적용 상태·필요한 폭별 배치를 확인한다. 실제로 수행한 정적 검토와 브라우저 확인 결과를 구분하고, 브라우저 확인을 수행하지 못하면 미검증 범위를 기록한다. 다이어그램도 파서·렌더러 없이 확인했다면 정적 검토라고 보고한다.
