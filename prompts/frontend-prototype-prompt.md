# 백엔드 없는 프론트엔드 프로토타입 구현 프롬프트

TO-BE 설계, 네비게이션 다이어그램, 화면 레이아웃 등을 바탕으로 **직접 조작할 수 있는 코드 기반 인터랙티브 프로토타입**을 만든다. 개발자가 설계한 화면 구성과 흐름을 체험하고, 실제 제품을 개발하기 전에 만족하는 부분과 수정할 부분을 판단할 수 있게 하는 것이 목표다. 대상은 웹 또는 데스크톱 앱이다.

코드 기반 프로토타이핑에 서비스 대역(fake/mock)을 조합한다. **기본은 정상 처리 흐름(happy path)**이며, 백엔드를 호출할 자리에서 가짜 결과를 반환해 화면 이동과 상태 변경을 재현한다. 실행 가능한 프론트엔드와 검토 방법까지 제공한다.

## 입력과 실행 규칙

- 입력: 검토할 설계 문서나 해당 절, 대상 화면·사용자 흐름, 웹/데스크톱 여부, 구현 위치, 기존 실행 환경·기술 제약, 개발자가 확인하려는 질문. 모든 설계 문서가 갖춰져 있어야 시작할 수 있는 것은 아니다.
- 먼저 변경 상태와 대상 파일의 기존 변경을 확인하고 보존한다. [최소 맥락·산출물 경로 기준](../guides/module-boundary-guide.md#6-ai에-전달할-작업-맥락)에 따라 대상 설계와 관련된 화면·공개 계약·실행 설정만 읽는다. UI를 만든다는 이유로 전체 백엔드를 분석하지 않는다.
- 기존 프로젝트의 기술 스택·컴포넌트·라우팅 관례를 우선한다. 새 프로젝트는 검토 목적을 충족하는 작은 구성을 선택하고 이유를 남긴다. 특정 프레임워크·폴더 구조·라이브러리를 필수로 삼지 않는다.
- 빠진 입력은 확인된 사실·가정·미확정으로 구분한다. 되돌릴 수 있는 선택은 가정과 영향을 적고 진행한다. 핵심 사용자 흐름의 의미를 바꾸는 결정은 필요한 입력을 요청하고, 그 결정에 의존하지 않는 부분을 계속 만든다.
- 이미 허용된 구현·실행·수정은 자율 진행한다. 계획이나 화면 목록에서 끝내지 않고 조작 가능한 프로그램을 만든다. 무관한 기능 추가나 기존 제품 흐름의 교체로 범위를 넓히지 않는다.

## 1. 설계에서 검토 범위 추출

개발자가 확인할 질문을 먼저 정한다. 화면의 정보 배치, 행동의 발견 가능성, 입력부터 완료까지의 흐름, 이전 화면으로 돌아갔을 때의 상태 등 **직접 조작하며 판단할 항목**으로 쓴다.

`설계 위치/식별자 · 검토 질문 · 화면/영역 · 사용자 행동 · 가짜 처리 결과 · 도착 화면/상태 · 구현 위치 · 검증 결과`를 연결한 대응표를 짧게 유지한다. 기존 설계의 ID와 명칭을 재사용하고 원문을 통째로 복사하지 않는다.

- TO-BE에서는 이번 검토에 필요한 사용자 시나리오와 외부 처리 결과만 추출한다. 전체 시스템·서버·DB 구현을 작업으로 가져오지 않는다.
- 화면 이동·분기는 [navigation 가이드](../guides/navigation-diagram-guide.md), 배치·포함 관계는 [layout 가이드](../guides/screen-layout-guide.md), 화면 내부 전이는 [state 가이드](../guides/state-diagram-guide.md)를 기준으로 해석한다. 입력에 쓰인 DSL을 임의 확장하거나 Mermaid로 치환하지 않는다.
- 다이어그램을 다시 그리는 것은 필수가 아니다. 설계 간 이름·분기·배치가 충돌하면 근거와 영향을 기록한다. 핵심 의미가 불명확한 부분은 미확정으로 남기고, 원본 설계를 조용히 바꾸지 않는다.
- layout이 정하지 않는 색상·서체·여백·정확한 크기·반응형 동작은 기존 디자인 기준을 따른다. 기준이 없으면 검토 가능한 수준의 잠정 스타일을 적용하고 가정으로 남긴다.
- 대상 흐름에 필요한 화면·모달·탭·폼과 진입·완료 조건을 정한다. 범위 밖 요소는 생략하거나 미지원임을 표시하고, 눌러도 아무 반응이 없는 주요 버튼을 남기지 않는다.

## 2. 실행 형태 선택

- **웹**: 실제 브라우저에서 화면 이동과 상호작용을 확인할 수 있게 만든다. URL·새로고침·뒤로 가기가 설계에 해당하면 그 동작까지 연결한다.
- **데스크톱**: 지정된 데스크톱 실행 환경과 화면·창 이동 방식을 따른다. 창 크기 변경, 메뉴, 단축키 등 검토 범위에 포함된 동작을 구현한다. OS 기능이나 네이티브 연동은 필요한 UI 반응을 대역으로 재현한다.
- 플랫폼이 미정이면 기존 실행 환경에서 판단한다. 기존 환경도 없고 데스크톱 고유 동작이 요구되지 않으면 웹으로 잠정 구현하고 선택 근거를 남긴다. 데스크톱이 요구됐는데 브라우저에서만 확인했다면 데스크톱 실행은 미검증으로 남긴다.
- 프론트엔드 개발 서버나 데스크톱 실행 셸은 사용할 수 있다. 핵심 검토 흐름은 별도 업무 서버·DB·실제 인증·외부 서비스 없이 동작하게 한다. 프로토타입을 위해 불필요한 배포·설치 패키징을 추가하지 않는다.

## 3. 가짜 처리와 데이터 구성

[모듈 경계 가이드](../guides/module-boundary-guide.md)의 책임·상태 소유권 기준을 적용한다. 화면은 사용자 입력과 표현을 담당하고, 외부 처리를 대신하는 작은 함수나 adapter가 가짜 결과와 데이터 변경을 맡는다. 이 분리를 위해 빈 계층·범용 서버·과도한 도메인 모델을 만들지 않는다.

- **대역 경계**: 기존 API 클라이언트가 있으면 해당 계약에 맞는 대역이나 네트워크 mocking을 선택한다. API가 정해지지 않았으면 필요한 화면 행동만 표현하는 작은 함수 계약을 만든다. 가짜 URL·응답 필드를 실제 백엔드의 확정 명세로 기록하지 않는다.
- **정상 처리**: 유효한 입력 → 처리 중 표시 → 가짜 성공 결과 → 화면 이동/데이터 반영의 순서를 연결한다. 설계에 있는 입력 검증·확인·취소는 유지하고, 잘못된 입력까지 무조건 성공시키지 않는다. 로딩·중복 제출 방지 등은 해당 상호작용에 필요한 만큼 구현한다.
- **데이터 일관성**: 같은 가상 데이터의 원본과 쓰기 책임을 한 곳에서 관리한다. 입력·추가·수정·삭제 결과가 관련 목록·상세·요약 화면에 일관되게 반영되게 한다. 화면마다 서로 다른 고정값을 보여 주어 흐름이 끊기지 않게 한다.
- **재현 가능성**: 초기 데이터와 초기화 방법을 제공한다. 메모리 상태를 기본으로 하고, 새로고침/재실행 시 유지가 검토에 필요하면 앱 내부 저장소를 선택해 범위와 초기화 방법을 적는다. 임의의 랜덤 성공·실패나 재현할 수 없는 데이터를 넣지 않는다.
- **선택 시나리오**: 기본 정상 흐름을 먼저 완성한다. 설계나 검토 범위에 필요한 빈 목록·오류·권한·재시도 등만 추가하며, 같은 조건을 다시 선택할 수 있게 한다. 전체 장애 체계나 모든 서버 정책을 구현하지 않는다.
- **가상 부작용**: 인증·결제·메일·파일 처리 등은 가상 결과로 끝낸다. 실제 업무 서비스 호출이나 업무 데이터 변경으로 성공을 흉내 내지 않는다. 모의 처리임을 검토자가 알 수 있는 안내를 두고, 대역을 끄거나 빠뜨렸을 때 실제 서비스로 요청이 흘러가지 않게 한다.

## 4. 화면과 흐름 구현

1. 검토 질문을 대표하는 핵심 흐름을 진입부터 완료까지 먼저 연결한다. 레이아웃, 주요 입력·버튼, 가짜 처리, 결과 화면을 함께 만든다.
2. 설계의 정보 계층·배치·용어를 유지한다. 별도 요청이 없으면 시각적 재설계보다 흐름을 판단할 수 있는 완성도를 우선한다. 지정된 화면 크기와 창 크기 변화에서 내용·스크롤·주요 행동을 확인한다.
3. 대상 흐름의 이동·뒤로·취소·모달 닫기·재진입과 상태 유지/초기화를 필요한 범위에서 연결한다. 공유 데이터의 쓰기 소유자를 화면마다 중복해서 만들지 않는다.
4. 주요 컨트롤에 이름·레이블을 제공하고, 키보드 조작·포커스·입력 피드백을 검토 가능하게 한다. 설계에서 빠진 동작을 임의의 제품 정책으로 확정하지 않는다.
5. 개발자가 초기화하고 같은 흐름을 다시 체험할 수 있게 한다. 시나리오 선택 같은 검토 보조 기능은 제품의 업무 메뉴와 구분하고, 내부 API·상태 저장 방식 같은 구현 정보를 사용자 흐름에 섞지 않는다.

병렬 구현이 필요하면 공유할 화면 행동·대역 계약·상태 소유권을 먼저 정하고 쓰는 파일을 나눈다. 역할 분담은 [협업 프롬프트의 역할과 규모](./multi-agent-task-prompt.md#역할과-규모)를 참고하되, 이번 산출물의 검증 범위는 이 프롬프트가 정한 설계 검토용 프로토타입이다.

## 5. 실행 검증과 독립 검토

가능한 환경에서 프로그램을 실행하고 대응표의 시나리오를 직접 조작한다. 핵심 행동 후 도착 화면과 표시 데이터가 설계대로 바뀌는지, 초기화 후 같은 결과를 재현할 수 있는지 확인한다. 웹/데스크톱의 선택한 실행 환경에서 확인한 범위를 기록한다.

- 앱 시작과 핵심 행동 중 실제 업무 서비스 요청이 없는지 확인한다. 기존 앱을 활용했다면 초기 조회·토큰 갱신·백그라운드 구독 등 클릭 외의 요청도 대역 범위에 포함됐는지 확인한다.
- 기존 빌드·타입·린트 등 변경에 필요한 검사를 수행한다. 실행·조작 확인과 정적 검사를 구분하고, 빌드 성공만으로 화면 흐름을 검증했다고 쓰지 않는다.
- 기존 테스트 도구가 있으면 상태 변경·화면 간 데이터 반영·핵심 이동처럼 결함을 찾는 데 유효한 검증을 추가한다. 모든 버튼의 구현을 그대로 복제하는 테스트나 별도 테스트 체계를 의무적으로 만들지 않는다.
- 작성자 외 검토자가 설계 대응표와 실제 흐름을 대조해 누락된 행동, 잘못된 도착 상태, 데이터 불일치, 대역 누락에 따른 실제 서비스 호출 가능성, 범위 이탈을 찾는다. 독립 검토가 불가능하면 분리된 순차 검토와 그 한계를 밝힌다.
- 필수 결함을 수정하고 영향받는 흐름을 재검증한다. 횟수나 점수만으로 완료를 판정하지 않는다.
- 실행·조작 도구가 없으면 정적 검토 결과와 미실행 시나리오를 남긴다. DSL 렌더러가 없으면 다이어그램은 정적 검토로 보고하고 렌더링 성공을 추정하지 않는다.

이 검증이 보여 주는 것은 **가정한 처리 결과에서의 화면·상태·이동 동작**이다. 실제 백엔드 계약·보안·성능·데이터 정합성이나 외부 연동 성공을 검증한 것으로 보고하지 않는다.

## 6. 개발자 검토와 산출물

실행 가능한 코드와 함께, 프로토타입 가까이의 README 또는 기존 문서 위치에 다음을 남긴다. 별도 문서는 독립된 내용이 길어질 때만 나누며, [산출물 경로 기준](../guides/module-boundary-guide.md#6-ai에-전달할-작업-맥락)에 따라 다른 환경에서도 사용할 수 있는 경로·링크를 쓴다.

- **실행 방법**: 필요한 도구·설치/실행 명령·진입 화면·종료 방법. 데스크톱은 실행한 대상 환경도 적는다.
- **체험 순서**: 초기화 → 시작 조건 → 입력/조작 → 기대 화면·결과. 초기 데이터, 저장 수명, 선택 시나리오 전환 방법을 포함한다.
- **설계 대응표**: 구현한 화면·행동과 근거 설계, 실제 검증 결과. 미구현·미실행·가정·설계와 다른 점을 구분한다.
- **검토 기록**: `검토 질문/설계 위치 · 관찰/개발자 의견 · 유지/수정/보류 · 후속 설계 변경`을 연결한다. 개발자 의견이 아직 없으면 `검토 대기`로 남긴다.
- **한계와 후속 작업**: 가짜 처리 범위, 제외한 동작, 실제 제품 개발에서 다시 검증할 계약·정책·플랫폼 동작을 적는다.

프로토타입 구현·검증 상태와 개발자의 설계 수용 여부를 따로 보고한다. 개발자가 직접 검토하지 않았다면 만족·승인했다고 단정하지 않는다. 피드백을 받으면 관련 화면과 흐름을 수정하고 다시 체험할 수 있게 하며, 원본 설계 변경은 허용된 범위에서만 반영한다.

최종 보고에는 코드·검토 문서 위치, 실행 방법, 구현한 흐름, 수행한 검증과 미확인, 개발자 검토 상태를 간결하게 적는다. 실제 제품 구현을 이어갈 때는 [검증 우선 구현 프롬프트](./verify-first-implementation-prompt.md)로 필요한 계약과 실제 연결을 검증한다. 프로토타입 코드를 그대로 제품용으로 확정하지 않는다.

## 접근 방식의 참고 자료

- [코드 프로토타입 활용 안내](https://www.gov.uk/service-manual/design/making-prototypes): 실제로 조작하며 설계 아이디어를 검토하는 접근과 프로토타입 코드의 용도를 설명한다.
- [API mocking 공식 문서](https://mswjs.io/docs/): 네트워크 요청을 가로채 가짜 응답을 제공하는 방식이다. 기존 요청 계층을 유지할 필요가 있을 때 참고하며, 이 도구의 도입이 필수는 아니다.
