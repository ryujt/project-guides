# 프론트엔드 네비게이션 다이어그램 작성 프롬프트

실제 코드에서 **라우트 페이지 사이의 이동**을 추출해 설명한다. 페이지 내부 상태는 [상태 프롬프트](./frontend-state-diagram-prompt.md)에서 다룬다. 원본 코드는 수정하지 않는다.

## 파일 저장 위치

사용자 지정·기존 문서 위치를 우선한다. 위치가 없으면 `docs/design/{DATE}/frontend/navigation.md` 한 파일에 작성한다. `{DATE}`는 생성 일시의 `YYYYMMDD-HHMMSS` 형식이다. 문서 간 링크는 상대 경로로 쓴다.

## 작성 내용

- 라우트 맵: 실제 경로·페이지/진입점·접근 조건·근거 파일/심볼
- 전체 요약: 페이지 간 이동과 짧은 트리거를 먼저 보여 주고 API·처리 노드는 생략한다. 너무 크면 사용자 목적별로 나눈다.
- 필요한 시나리오 상세: 진입 방법·이동과 분기·관련 API와 판단·최종 결과
- 미확인 사항과 관찰 이슈

각 다이어그램 아래에는 주요 흐름을 짧은 문장 목록으로 설명한다. 이동·API 분기가 없는 단순 화면은 라우트 맵과 설명으로 충분하다.

## 작성 기준

- [최소 맥락 기준](../guides/module-boundary-guide.md#6-ai에-전달할-작업-맥락)에 따라 실제 라우트 등록·Page 진입점·접근 가드·공개 API부터 확인한다. 확인한 동작과 추론·미확인을 구분한다.
- 표기는 [Navigation 가이드](../guides/navigation-diagram-guide.md)의 `navigation` 문법을 따른다. 이 문서의 화면 노드는 실제 라우트 페이지로 한정한다.
- 라우트 없는 Dialog·Panel·폼 Step·탭의 API와 이동은 소속 Page에 귀속시킨다. 페이지 내부 처리·다른 모듈의 구현 세부를 섞지 않는다.
- 실제 기본 진입 페이지를 쓰고 독립 진입점이 여럿이면 설명한다. 없는 홈 화면이나 진입 화살표를 만들지 않는다.
- 직접 URL 진입·새로고침은 도착 Page 또는 진입 가드에서 시작하고 주소·진입 매체는 본문에 적는다. Browser·User·Email을 화면 노드로 만들지 않는다.
- 상세에는 화면 이동을 결정하는 API·판단만 넣는다. 실제 API 경로와 DSL 이름이 다르면 대응을 기록한다.
- 성공·오류·권한·취소는 실제 있는 흐름만 그린다. 빠진 보호·복구 처리는 관찰 이슈로 남긴다.

## 검증

모든 화면 노드가 실제 라우트에 대응하고, 이동·가드·API 조건이 코드 및 공개 계약과 일치하는지 확인한다. 직접 진입을 화면 클릭으로 표현하지 않았는지, API 이름 대응·근거·링크와 DSL 문법이 맞는지 검토한다.

문법 대조와 실제 렌더링을 구분하고 렌더러가 없으면 정적 검토라고 기록한다. 오류·누락을 수정한 뒤 문서 위치·분석 범위·검증 결과와 한계·남은 문제를 보고한다.
