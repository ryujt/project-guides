# 프론트엔드 네비게이션 다이어그램 작성 프롬프트

실제 코드에서 **라우트 페이지 사이의 이동**을 추출해 설명한다. 페이지 내부 모드/상태는 [상태 프롬프트](./frontend-state-diagram-prompt.md)에서 다룬다. 이 프롬프트는 일반 navigation 가이드보다 좁은 **라우트 페이지 뷰**를 사용한다.

## 입력과 실행 규칙

- 입력: 대상 프로젝트·라우트/사용자 흐름, 분석 범위, 문서 위치.
- [모듈 경계 가이드](../guides/module-boundary-guide.md)의 최소 맥락에 따라 라우터·Page 진입점·접근 가드·공개 API 계약부터 읽고 이동 호출자/소비자를 검색한다. 관련 본문만 확장한다.
- 이미 허용된 조사/문서 작성은 자율 진행한다. 원본 코드는 수정하지 않고 기존 변경을 보존한다. 확인한 동작·추론·미확인을 구분한다.
- 독립된 읽기는 병렬화한다. 가이드 문법은 [navigation-diagram-guide.md](../guides/navigation-diagram-guide.md)를 따른다.

## 1. 라우트 맵

`실제 경로 · 페이지/진입점 · 접근 조건 · 근거 파일/심볼`을 추출한다. `pages/` 폴더가 없거나 파일 기반 라우터를 써도 실제 라우트 등록을 근거로 한다. 예제 폴더/컴포넌트 이름을 강제하지 않는다.

라우트 없는 Dialog·Panel·폼 Step·탭은 이 뷰의 화면 노드로 만들지 않는다. 이들이 유발하는 API/화면 이동은 소속 Page에 귀속시킨다. URL 직접 진입을 가로채 도착 페이지를 가르는 가드는 해당 시나리오의 시작 판단 노드가 될 수 있다.

## 2. 전체 요약

대상 범위의 **페이지 간 이동만** `navigation` 한 장으로 먼저 보여 준다. 요약에는 API/처리 노드를 생략하고 짧은 트리거를 표시한다.

- 실제 기본 진입 페이지를 사용한다. `HomePage`가 없으면 만들지 않는다. 독립 진입점이 여러 개면 이를 설명한다.
- 직접 URL로만 도달하는 오류/콜백 페이지에 가짜 진입 화살표를 만들지 않는다. 라우트 맵과 해당 시나리오에서 다룬다.
- 요약 아래에 주요 목적과 이동을 짧게 설명한다. 너무 크면 목적별 요약으로 나누고 전체 색인을 둔다.

## 3. 시나리오 상세

사용자 목적별로 필요한 상세를 작성한다. 각 시나리오는 `트리거/진입 방법 → 이동과 분기 → navigation → 실제 API 경로·근거`를 포함한다.

- 화면 이동의 성공/실패를 결정하는 API는 `(/api_name)` 형태로, 판단은 `(process)` 형태로 표현한다. 실제 경로의 파라미터/기호와 DSL 이름이 다르면 매핑을 남겨 충돌을 피한다.
- API·판단 명명과 라벨 문법은 가이드를 따른다. 내부 처리·동기화 이벤트를 무조건 노드로 만들지 않는다.
- 직접 URL 진입은 도착 Page 또는 진입 가드에서 시작하고 주소/진입 매체는 산문으로 설명한다. Browser·User·Email을 화면 노드로 만들지 않는다.
- 이동·API 분기가 없는 단순 화면은 별도 도표를 강제하지 않는다. 해당 시나리오 설명과 라우트 맵으로 충분하다.
- 성공·오류·권한·취소 분기는 실제 존재하는 것만 넣는다. 빠진 보호/복구 흐름을 구현된 사실로 보충하지 말고 관찰 이슈로 기록한다.

## 4. 산출물과 검증

사용자 지정/기존 문서 위치에 **라우트 맵 → 전체 요약 → 필요한 시나리오 상세 → 미확인/이슈** 순서의 문서를 작성한다. 위치가 없으면 `docs/design/{DATE}/frontend/navigation.md`를 사용한다. 쉬운 말·짧은 문장으로 설명하며 사용자 DSL을 다른 형식으로 치환하지 않는다.

확인할 것:

- 모든 화면 노드가 실제 대상 범위의 라우트로 연결되는가?
- 이동·가드·API의 조건이 코드 및 공개 계약과 일치하는가?
- 직접 진입/새로고침을 일반 화면 클릭으로 잘못 표현하지 않았는가?
- 페이지 내부 상태나 다른 모듈 구현 세부가 섞이지 않았는가?
- API 이름 매핑·근거·링크와 DSL 문법을 확인했는가?

실제 렌더러가 없으면 렌더링 미검증을 밝힌다. 잘못된 사실/누락을 수정한 뒤 영향 부분을 재검증하고, [협업 프롬프트](./multi-agent-task-prompt.md)의 반복 기준을 적용한다. 최종 보고에는 문서 위치·분석 범위·검증/한계·코드를 고치지 않고 남긴 문제를 적는다.
