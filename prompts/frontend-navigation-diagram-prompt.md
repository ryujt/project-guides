# 프론트엔드 네비게이션 다이어그램 작성 프롬프트

## 목적

프로젝트의 **화면(페이지) 이동 흐름**을 문서화한다.
네비게이션 다이어그램은 "사용자가 어느 화면에서 어느 화면으로, 무엇 때문에 이동하는가"에 집중한다.
`/Users/ryu/projects/project-guides/guides/navigation-diagram-guide.md` 의 표기법을 **기본 형태로 그대로 따른다.** 아래 규칙은 그 위에 얹는 프로젝트 제약이다.

## 화면 노드 규칙 (react.js 기준)

가이드는 "사용자가 인지하는 화면·오버레이"를 노드로 허용하지만, 이 프로젝트에서는 화면 노드를 **라우트(주소)를 가진 페이지로 한정**한다. 라우트 없는 내부 컴포넌트가 화면 노드로 섞이면서 복잡해지는 것을 막기 위해서다.

* **화면 노드는 `pages/` 폴더의 라우트 페이지만 사용한다.**
  라우터(`App.tsx` 등)에 경로로 바인딩된 페이지 컴포넌트(`HomePage`, `LoginPage`, `ClassroomPage` 등)만 화면 노드다.
* **라우트가 없는 내부 컴포넌트/오버레이/다이얼로그/스텝은 화면 노드로 쓰지 않는다.**
  예: `RoomAccessGate`, `PaidHostAccessGate`, `EndDialog`, `WaitingHostCard`, `*Step`, `*Dialog`, `*Panel`, `Classroom(MeetingGallery)` 같은 컴포넌트 상태.
  이들이 유발하는 화면 이동·API 호출·판단은 **그것을 품고 있는 라우트 페이지 노드에 귀속**시킨다.
* **URL이 바뀌지 않는 페이지 내부 전환은 표기하지 않는다.**
  `PageA(StepB)` 같은 컴포넌트 교체, 탭 전환, 해시 스크롤 등은 네비게이션이 아니다. 필요하면 산문으로만 언급한다.

## 그 외 노드는 가이드를 그대로 따른다

화면 노드만 위처럼 제한할 뿐, **나머지 표기는 가이드의 기본 형태를 그대로 쓴다.**

* **API 호출은 `(/api_name)` 노드로 표기한다.** (가이드의 `(backend api)` 규칙)
  화살표 레이블에 API/경로 문자열을 텍스트로 적지 말고, 반드시 `(/api)` 노드로 그린다.
  명명 규칙: 소문자·숫자·`/`·`_` 만. 경로 파라미터·하이픈은 밑줄로 치환하고 실제 경로는 산문으로 밝힌다.
  예: `LoginPage --> (/auth/login)` / `(/auth/login) --> ClassroomListPage : success`
* **`(process)` 노드는 화면 이동을 좌우하는 판단 단계만 최소한으로 쓴다.**
  검증·접근 방식 결정처럼 이동의 성공/실패/분기를 가르는 처리만 노드로 만든다. 순수 내부 로직·상태 전이는 넣지 않는다. (자세한 프로세스는 별도 다이어그램의 대상)
* **분기는 `: success`, `: error`, `: invalid` 처럼 상태만** 콜론 뒤에 적는다. 콜론 뒤 설명에는 괄호를 쓰지 않는다.
* **`Browser` 진입 노드는 상세 시나리오에서 URL 직접 진입(초대 링크·북마크·새로고침)을 표현할 때 쓴다.**
  단, 전체 네비게이션 **요약도는 `HomePage` 에서 시작**하며 `Browser` 로 시작하지 않는다.

## 지시사항

라우트를 가진 페이지 사이의 이동을 중심으로, 사용자가 이용할 수 있는 화면 이동 시나리오를 설명한다.

### 세부 요구사항

1. **라우트 맵을 먼저 파악한다.**
   * 라우터 정의에서 `경로 ↔ 페이지 컴포넌트 ↔ 접근 조건`을 추출한다.
   * 여기 등장하는 페이지 컴포넌트만 이후 다이어그램의 **화면 노드** 후보다.

2. **전체 네비게이션 요약도를 먼저 제시한다.**
   * 라우트 페이지 사이의 이동만으로 전체 흐름을 하나의 ```` ```navigation ```` 다이어그램으로 요약해 문서 앞에 둔다.
   * **`HomePage` 에서 시작한다.** 요약도에는 `Browser`·`(/api)`·`(process)` 를 넣지 않고, 페이지 간 이동과 짧은 트리거 레이블만 둔다.
   * **페이지 간 이동으로 도달할 수 없는 화면은 요약도에 넣지 않는다.** URL 직접 진입으로만 닿는 폴백·오류 화면(예: `NotFoundPage`)은 들어오는 화살표가 없어 "거기서 시작하는" 것처럼 읽히는 떠 있는 노드가 되므로, 라우트 맵과 해당 시나리오에서만 다룬다.
   * 바로 아래에 핵심 흐름을 짧은 불릿으로 설명한다.

3. **요약도 이후, 시나리오 단위의 상세 다이어그램을 이어서 작성한다.**
   * 각 시나리오는 사용자의 목적(회원가입, 강의실 개설, 참여, 강의 시작 등) 기준으로 나눈다.
   * 상세 다이어그램은 **가이드의 기본 형태를 그대로** 쓴다: 라우트 페이지 노드 + `(/api)` 노드 + 최소 `(process)` 노드 + `: success`/`: error` 분기, 직접 진입은 `Browser`.
   * 화면 노드는 라우트 페이지로 한정하고, 게이트·다이얼로그 등 비라우트 컴포넌트의 동작은 그 페이지 노드에 귀속시킨다.
   * 각 블록은 ```` ```navigation ```` 언어 태그로 감싼다.

4. **화면 이동을 좌우하는 API·판단만 포함한다.**
   * 이동의 성공/실패/분기를 결정하는 `(/api)`·`(process)` 만 노드로 남긴다.
   * 화면이 바뀌지 않는 순수 내부 처리·동기화 이벤트는 넣지 않는다.

5. **각 시나리오마다 상세 설명을 덧붙인다.**
   * 트리거(어느 페이지·액션에서 시작하는지), 이동 페이지, 화면 이동을 가르는 조건, `(/api)` 노드가 대응하는 실제 경로, 근거 파일을 밝힌다.

## 산출물

* **라우트 맵 → 전체 네비게이션 요약 → 시나리오 상세** 순서의 마크다운 문서 하나.
  1. **라우트 맵** — `경로 / 페이지 컴포넌트 / 접근 조건` 표.
  2. **전체 네비게이션** — `HomePage` 에서 시작하는 페이지 간 이동 요약도 1개(가상 진입·API·프로세스 노드 없음) + 불릿 설명.
  3. **시나리오별 상세** — 각 시나리오마다 제목 + 설명(트리거, 이동 페이지, 분기 조건, `(/api)` 실제 경로, 근거 파일) + 가이드 기본 형태의 ```` ```navigation ```` 다이어그램.
