# AS-IS 설계 분석 문서 생성 프롬프트

> **무엇을 하나**: 첨부된 소스 코드·문서를 분석해 현 상태(AS-IS) 설계 문서를 생성한다. 이 프롬프트에 **분석할 코드·문서를 첨부**하고 **분석 요구사항을 직접 입력**해 실행한다. AS-IS 는 현 코드를 **있는 그대로** 역추출한다 — 개선·목표는 [TO-BE 프롬프트](./system-design-to-be-prompt.md)의 몫이다.
> **최우선 가치 — 독자의 이해 속도**: 독자는 이 프로젝트를 처음 보는 개발자다. 핵심 문서 5분 스캔으로 전체 그림을, 상세 파일로 수정 착수 지식을 얻는다. 완전한 나열과 빠른 이해가 충돌하면 **항상 빠른 이해가 이긴다**(깊이는 삭제하지 말고 상세 파일로 옮긴다).
> **종료 판정**: [§5 검증](#5-검증--종료-게이트)에서 기계 확인(분량·골격·링크)을 먼저, 의미 확인(날조·상세 실재)을 이어서 통과해야 종료한다.

## 1. 출력 스타일 계약 (모든 산출물 공통 — 위반은 §5 검증 대상)

### 두괄식 3계층 — 요점·키워드 먼저, 상세는 뒤에

| 계층 | 규칙 |
|---|---|
| 문서 | 첫 화면 = `## 0. 한눈에 보기`. **이것만 읽고도 시스템을 남에게 설명할 수 있어야 한다** |
| 섹션 | 첫 줄 = **볼드 한 줄 결론** → 표·다이어그램 → 보충 불릿. 결론이 제목의 재진술이면 위반 — 그 섹션에서 가장 중요한 **판단**을 담는다 |
| 다이어그램 | 바로 아래 설명 불릿 3~5개. 한 불릿 = 한 문장, 노드를 옮겨 적지 말고 "무엇이 무엇을 왜 하는지" |

### 쉬운 말 — 결론 구역과 용어 다이어트
- **결론 구역**(= §0 전체 + 모든 섹션·소절의 첫 결론 줄)에는 **키워드 표에 없는 전문용어를 쓰지 않는다.** 방법론 용어(method-R·L1~L4·O-W·Orchestration/Choreography·PBS·6원칙)만이 아니라 도메인·인프라 약어(예: 아웃박스·FIFO·presigned·SigV4·KMS)도 같다. 첫 문장은 일상어로 열고, 전문용어는 둘째 줄부터 등장시킨다.
- **방법론 용어는 문서 표면 어디에도 주인공이 아니다**: 본문에서 꼭 필요하면 첫 사용에 괄호로 풀어쓴다. "왜 이 깊이로 나눴나" 류의 분해 근거는 본문에 섞지 말고 상세 파일 말미 `## 부록: 분해 근거`로 접는다.
- 키워드 표에 없는 전문용어를 본문에서 쓰게 되면 첫 등장에서 괄호로 한 번만 푼다(표와 중복 정의 금지). **용어 풀이가 10개로 부족하면 용어를 늘리지 말고 본문의 전문용어를 줄여라** — 그만큼 문서가 과잉 전문화됐다는 신호다.
- 최소 조각 표의 `종류` 열에 역할 어휘(오케스트레이터·워커·게이트웨이 등)를 쓰려면 그 어휘를 키워드 표에 등재한다. 자리가 없으면 `종류` 열을 빼고 '한 줄 책임'만 남긴다.
- 짧은 문장 · 불필요한 수식어 제거 · 불릿은 한 줄.

### 분량 예산
- **총량이 최종 게이트**: 핵심 문서 ≤ **200줄**(`wc -l`, P0). 아래 국소 상한은 배분 안내(초과는 P1)이며, 충돌하면 총량이 우선하고 초과분은 삭제가 아니라 **상세 파일로 이동**한다.
- 국소 상한: §0 ≤ 50줄 / 본문 섹션은 §3 골격의 괄호 예산 / 상세 파일 ≤ 500줄 / 표 ≤ 8행(넘치면 중요한 순 + "전체 N건은 …" 링크) / 다이어그램 최대 5장·장당 노드 ≤ 12(하한 없음 — 억지 다이어그램 금지).
- **관통 대표 다이어그램 예외**: 흐름의 jobflow 1장과 화면의 navigation 1장은 진입→핵심 결과를 관통해야 하므로 국소 상한 예외 — 단 jobflow 객체 ≤ 14·45줄, navigation ≤ 25줄 안에서, 한 단계 = 독자가 인지하는 한 동작으로 병합한다(내부 세부 호출은 상세로). **관통 다이어그램이 들어가는 섹션의 괄호 예산은 그 다이어그램을 제외한 산문·표에 적용한다.**
- **우선순위(충돌 시)**: ① 가이드 DSL 문법·의미(분량 계약이 문법을 깨지 못한다) ② §3 골격의 섹션 제목·순서 ③ 분량·표현 계약. 관통 요건과 분량이 부딪히면 관통을 살리고 깊이를 상세로 옮긴다.

### 반복·근거·코드
- 같은 내용은 한 곳에만 쓴다. 두 번째 등장부터는 링크. 같은 흐름을 여러 다이어그램이 반복하면 위반.
- 근거는 인라인 `(경로:라인)` 또는 표의 근거 열로. **근거 전용 표는 상세 파일 말미 "부록: 근거"에만**(대표 근거만).
- 코드 붙여넣기 금지 — `경로:라인` 참조로 대체.
- 본문·표가 인용하는 이슈 ID(R-0X)는 ⓐ §0 이슈 표에 있거나 ⓑ 인용 지점에 한 줄 뜻을 병기하거나 ⓒ 브리프 해당 항목으로 링크한다. 맨몸 ID 인용 금지.

### 다이어그램 일반 규칙
- **DSL 읽기 보조**: `docs/design/_dsl-읽는법.md`가 없으면 1회 생성한다(≤30줄) — jobflow(`A.행위 --> B.행위` = A의 행위가 끝나면 B가 이어서 · `.On이벤트`=외부 트리거 수신 · `.result`=반환 · `.message.X`=X 전달 · `.조건.true/.false`=분기 · `orchestrator:`=조율자 · `scope:`=조율자 없는 경계) / navigation(맨단어=화면 · `(/path)`=API · 백틱=실행 시점 대상 · `화면(하위)`=하위 모드) / state(`(X)`=상태 · `<s>`/`<e>`=시작·끝) / layout(`V`/`H`=세로·가로 배치 · `>`=포함 · `: N`=폭 비율 %) 를 가이드 문법 그대로 요약. **핵심 문서와 각 상세 파일에서 DSL 이 처음 등장하는 블록 바로 위**에 `읽는 법: <경로>/_dsl-읽는법.md` 링크 한 줄을 단다.
- **표기 통일**: 같은 프로젝트의 AS-IS·TO-BE·상세는 같은 DSL 을 같은 문법으로 쓴다(layout 문법 혼용 금지). 비율·숫자 표기는 뜻을 1회 명시.
- **범례는 뜻으로**: 색·굵기·이모지로 의미를 나누면 바로 아래 범례 1줄 — 방법론 이름이 아니라 "무엇"으로 설명한다(예: "굵은 테두리 = 상태 변경이 모두 지나는 관문").
- **mermaid 방어 규칙**: 모든 노드·엣지 레이블 큰따옴표(`A["레이블"]`·`-->|"라벨"|`) · 레이블 안 괄호 금지(`·`나 `<br/>`로 치환) · `<br/>` self-closing 고정 · subgraph 타이틀 동일 · 레이블에 `end`·`subgraph`·화살표 연산자 금지.

## 3. 핵심 문서 골격 (섹션 제목·순서 verbatim · 괄호는 섹션 분량 예산)

독자 질문 순서의 5부 구성이다. framework 8섹션의 깊이는 상세 파일이 1:1 로 담고, 핵심 문서는 그 요약이다.

```
# {시스템} AS-IS — {시스템을 한 구절로} ({DATE})
> 근거: _evidence-brief.md · 기준 커밋 {hash} · 읽는 법: ../../_dsl-읽는법.md

## 0. 한눈에 보기  (≤50줄)
   ① 세 줄 요약: 무엇을 하는 시스템 / 구조 한 구절 / 지금 가장 아픈 곳
   ② 조감 mermaid flowchart 1장 — 실제 구성요소와 데이터 흐름(방법론 계층도 금지) + 설명 불릿
   ③ 키워드 표: | 용어 | 뜻 |  (≤10개 — 본문·다이어그램의 중심 개념·역할 어휘)
   ④ 핵심 이슈 표: | R-0X | 심각도 | 한 줄 | 위치 |  ≤5행 (🔴 P0·🟠 P1·🟡 운영·🟢 기술부채 / 전체는 브리프 링크)

## 1. 기능 — 무엇을 해주나  (≤10줄)
   한 구절 능력 진술 + 대표 기능 불릿 3~5. 전체 기능 트리는 상세로 — 본문 첫 섹션은 카탈로그가 아니다.
## 2. 구조 — 무엇으로 이뤄져 있나  (≤20줄)
   최소 조각 표(4~8행). 6모듈 대응·위반 상세는 details 로.
## 3. 흐름 — 일이 어떻게 흘러가나  (관통 jobflow 제외 ≤12줄)
   대표 트리거 표 + 진입→핵심 결과 관통 jobflow 1장(관통 예외 적용).
## 4. 데이터 — 무엇이 들어오고 무엇이 남나  (≤20줄)
   원천 데이터 표 + 대표 상태 다이어그램 1개(사용자가 기다리는 대상 위주).
## 5. 화면 — 사용자는 어디를 오가나  (관통 navigation 제외 ≤7줄)
   전체 navigation 1장(관통 예외 적용). 화면 레이아웃은 링크만.

## 상세 파일 인덱스  (≤10줄)
   | 파일 | framework § | 담는 것 |
```

- 본문 섹션(1~5) 공통 구성: **결론 1줄(볼드)** → 표 또는 다이어그램 → 불릿 ≤ 5 → `상세: <details 링크>`. 한 섹션이 framework 두 §를 요약하면(§3=2+5, §4=1+7, §5=6+8) **두 § 상세 링크를 모두 건다.**
- 코드에 해당 개념이 없으면(예: 헤드리스 시스템의 화면) 그 섹션은 결론 1줄 `해당 없음 — {이유}` 로 닫고 다이어그램을 생략한다(제목은 유지).
- jobflow 헤더: 단일 조율자가 있으면 `orchestrator:`, 경계·이벤트 연쇄면 `scope:`.
- 이슈(R-0X)는 발견한 사실만 서술한다 — 수정 제안·임의 교정 금지(TO-BE 의 몫). 원칙 위반도 위반 사실만 노출한다.

## 4. 작업 절차

### Step 0. 선행 준비 (1회)
1. **날짜 확정**: `DATE`(`YYYY.MM.DD`) 1회 고정 — 입력 날짜 > 세션 날짜 > `bash date +%Y.%m.%d`. 이후 모든 경로에 동일 DATE, TO-BE 에도 인계.
2. **분석 대상 인벤토리**: 첨부·지정 대상을 실제 `ls`/glob 으로 확인해 표로 고정(실경로만 인용). 후보: `docs/코드분석/`·`docs/코드리뷰/` → `docs/design/<날짜>/code-analysis/*` → 없으면 소스코드 직접 분석(어느 트리가 근거인지 명시).
3. **근거 브리프 생성** — `_evidence-brief.md`, 필수 4항목: 근거 인벤토리 표 / 이슈 목록(`R-NN`·심각도·위치 — TO-BE 변경점의 입력) / 최소 조각 4~8개(조각·종류·한 줄 책임) / method-R 깊이 사전판정 표(4계층 어디까지 여는지, 불균등 허용 — **Step 1.5 상세 파일의 개방 깊이가 이 표를 따른다**).
4. 이후 모든 단계는 원본 대신 브리프를 인용한다(환각 인용 방지).

### Step 1. 핵심 문서
§3 골격대로 작성한다. 분석은 method-R 순서(매크로→시스템→모듈→상세)로 하되 **코드가 실제 도달한 깊이까지만** 역추출한다(없는 계층 날조 = P0). 표현은 §1 스타일 계약을 따른다.

### Step 1.5. 상세 파일 (독립 파일 병렬 작성)
- **framework 8섹션과 1:1**: `as-is-{1..8}-{slug}.md`(slug 은 소문자 kebab-case 2~4단어, 한글 금지). 상세로 넘길 깊이가 코드에 없는 §만 파일 없이 인덱스에 `상세 없음` 표기.
- 서두 인용블록: `> 대상: 핵심 문서 §{0~5} · framework §{N}` + `> 근거: _evidence-brief.md 해당 항목` + `> 읽는 법: ../../../_dsl-읽는법.md`(DSL 을 쓰는 파일만) → 이어서 `## 0. 한눈에 보기`(요지 불릿 3~5 — 결론 구역 규칙 적용). 본문 소제목은 한국어 질문형으로 쓴다.
- 담는 것: 계층·조각별 `jobflow` 전체, 시나리오별 `navigation`(시나리오마다 트리거 조건·관련 화면/API·주요 분기·예외 설명을 붙인다)·`state`·`layout`, 예외·오류 분기, 책임 소유 표, 데이터 모델·경계 계약, 6모듈 대응·원칙 위반 상세, 말미 `## 부록: 분해 근거`·`## 부록: 근거`.
- **계층 중복 금지**: 같은 흐름을 계층마다 다시 그리지 않는다 — 한 단계 더 열어 상위에 없던 분기·반환·경계 메시지가 처음 드러나는 경우에만 추가.
- 150줄 초과 파일은 서두에 목차를 둔다. 500줄 초과 시 **응집 우선 분할** — 하나의 계약·상태기계·흐름을 여러 파일로 가르지 말고, 독립적으로 이해되는 소주제만 나눈다. 응집 판단으로 분할하지 않은 500줄 초과 파일은 목차가 있으면 상한 위반으로 치지 않는다.
- 핵심 문서가 수리로 바뀌면 영향 상세 파일만 동기화한다(무관 파일 동결).

## 5. 검증 — 종료 게이트 (P0 0건까지 지적 부분만 수리 → 재검증)

**판정 기준 정의**: *방법론 계층도* = 노드 레이블이 L1~L4·매크로/시스템/모듈/상세 등 방법론 어휘인 다이어그램(실제 구성요소 이름이면 허용). *노드 재진술 불릿* = 새 분기·순서·조건·이유 없이 노드명만 옮긴 설명 불릿. *새 정보* = 상위 계층에 없던 분기·반환·경계 메시지.

**① 기계 확인** (명령으로): `wc -l` 총량·상한 / §3 골격 제목 존재 / §0 4요소 순서 / 인덱스·본문 링크 파일 실존 / 본문에서 링크되지 않은 고아 상세 파일 없음 / `_dsl-읽는법.md` 존재.

**② 의미 확인** (코드·브리프 대조로):

**P0 (반드시 수정)**
- 깊이 날조(코드에 없는 계층·동작 서술) / 근거 인벤토리·브리프 미참조·환각 인용
- 핵심 문서 200줄 초과 / `## 0` 필수 4요소 누락·순서 위반 / §3 골격 섹션 제목 이탈(`해당 없음` 한 줄은 통과)
- **상세 유실**: 핵심 문서가 "상세로 옮긴" 각 항목이 상세 파일에 실재하는지 목록 대조로 확인 — 링크만 있고 내용이 요약 재탕이면 위반
- framework §1~§8 이 상세 파일+인덱스에서 미커버 / 고아 상세 파일(본문 어느 섹션에서도 링크 안 됨)
- job flow 를 `jobflow` 아닌 sequenceDiagram 으로 그림
- **결론 구역에 키워드 표 밖 전문용어** — 이 문서의 존재 이유(처음 읽는 독자)에 직결되므로 P0 다
- **재구성 테스트 실패**: §0 만 읽고 "무엇을/어떻게/문제는" 3문장을 재구성할 수 없음

**P1 (권장)**
- 결론 줄 부재·제목 재진술 / 정의 없는 역할 어휘 노출 / 맨몸 R-0X 인용
- 섹션·표·다이어그램 국소 상한 초과 / 중복 서술·중복 다이어그램 / 깨진 링크
- 다이어그램 하단 설명 누락·노드 재진술 불릿 / 범례 없는 색·이모지 의미 / DSL 첫 블록에 읽는 법 링크 없음 / 표기 혼용
- 근거 전용 표가 본문에 등장(부록 위치 위반) / 분해 근거가 본문 흐름에 혼입 / 원칙 위반의 임의 교정 / §6 시나리오 상세 설명(트리거·화면/API·분기·예외) 누락

**종료**: P0 위반 0 → ① 코드가 도달하지 못해 담지 못한 깊이 한계 ② 남은 P1 을 보고하고, 산출물 + `DATE` 를 [TO-BE 프롬프트](./system-design-to-be-prompt.md) 입력으로 인계한다.
