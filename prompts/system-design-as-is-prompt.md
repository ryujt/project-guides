# AS-IS 설계 분석 문서 생성 프롬프트

현재 코드와 문서에서 **실제 모듈 경계·데이터 소유권·흐름·의존성**을 역추출한다. 처음 보는 개발자는 핵심 문서로 전체 그림을, 담당 모듈 문서로 수정에 필요한 맥락을 얻어야 한다. 개선안은 [TO-BE 프롬프트](./system-design-to-be-prompt.md)에서 다룬다.

## 입력과 실행 규칙

- 입력: 대상 저장소/첨부 자료, 분석 범위, 중점 질문, 출력 위치. 전체 분석이면 전체 경계 목록을 만들되 모든 내부 파일을 같은 깊이로 읽지 않는다.
- [모듈 경계 가이드](../guides/module-boundary-guide.md)의 최소 맥락과 탐색 확대 기준을 적용한다. README·실행/조립 지점·공개 계약부터 읽고 호출자·소비자를 검색한다. 질문에 답하기 위해 필요한 구현·테스트만 단계적으로 연다.
- 이미 허용된 조사/문서 작성은 자율 진행한다. 원본 코드와 기존 사용자 변경을 보존하고 가정·미확인·관찰 사실을 구분한다.
- 독립된 조사는 병렬화하되 공유 계약과 원본 근거를 먼저 정한다. 상세 파일이 서로 다른 파일이라는 이유만으로 독립됐다고 가정하지 않는다.
- AS-IS를 선호 아키텍처에 맞춰 교정하지 않는다. 숨은 결합·복수 쓰기·순환 의존이 있어도 실제 상태로 기록한다.

## 1. 기준선과 근거

날짜 `DATE`를 한 번 확정하고 기준 커밋/작업 트리 변경 여부·관찰 시점을 적는다. 문서와 실제 코드가 다르면 각각의 근거와 불일치를 기록한다.

`관찰 항목 · 경로/심볼 · 확인한 동작 · 사실/추론/미확인`을 수집한다. 큰 분석이면 `docs/design/{DATE}/_evidence-brief.md`에 모듈 목록·근거·이슈를 모으고 TO-BE의 입력으로 공유한다. 작은 분석이면 본문 근거 표로 충분하다.

브리프는 원본을 찾는 색인이다. 이후 판단의 근거가 부족하면 원본을 다시 확인한다. 요약만으로 원본 검증을 금지하지 않는다. 외부 런타임·배포 환경을 확인하지 못한 부분은 코드상 예상과 실제 관측을 구분한다.

## 2. 실제 경계 분석

[method-R](../guides/method-R.md)은 관찰 깊이를 정하는 도구로 사용한다. 코드에 존재하지 않는 계층·조율자·이벤트를 만들지 않는다.

| 관점 | 확인할 내용 |
|---|---|
| 기능/변경 이유 | 어떤 사용자·업무 결과를 책임지는가 |
| 공개 계약 | 공개 진입점, 입력/출력, 오류·부작용 |
| 소유권 | 규칙·상태·데이터의 쓰기 주체와 읽기 경로 |
| 의존성 | import/호출 방향, 실제 조립 위치, 이벤트 소비자 |
| 실패 경계 | 타임아웃·취소·재시도·부분 실패·복구 담당 |
| 검증 경계 | 어떤 테스트가 실제 계약/결과를 보장하는가 |
| 맥락 비용 | 한 모듈 변경에 함께 알아야 하는 다른 모듈 내부 |

구성 역할은 [O-W 가이드](../guides/orchestrator-worker-pattern-guide.md)를 참고해 설명할 수 있으나 모든 실제 파일을 여섯 폴더에 억지로 대응시키지 않는다. 위반을 지적하면 어느 가이드의 어떤 적용 조건을 충족하는지 근거를 남긴다.

## 3. 핵심 문서

기본 경로는 `docs/design/{DATE}/as-is/system-design-as-is.md`이며 기존 문서 위치/사용자 지정을 우선한다. 약 200줄을 목표로 하되 필요한 경계·근거를 삭제하며 숫자를 맞추지 않는다.

1. **한눈에 보기**: 시스템 목적, 주요 구성/흐름 조감, 핵심 용어, 확인된 중요 이슈.
2. **기능 — 무엇을 해주나**: 대표 사용자/업무 결과.
3. **구조 — 무엇으로 이뤄져 있나**: 모듈·한 줄 책임·공개 진입점·소유 상태·의존 방향.
4. **흐름 — 일이 어떻게 흘러가나**: 대표 트리거부터 관찰 가능한 결과까지.
5. **데이터 — 무엇이 들어오고 남나**: 권위 소유자·생명주기·일관성·실패 책임.
6. **화면 — 사용자는 어디를 오가나**: 실제 진입점·이동, UI가 있을 때.
7. **상세/근거 인덱스와 한계**: 필요한 모듈 문서와 확인하지 못한 범위.

각 절은 결론 → 표/도표 → 필요한 설명으로 쓴다. 처음 쓰는 전문용어는 풀어 쓰고 비유·과장을 피한다. 중요한 사실을 읽는 속도와 계약을 이해하는 데 필요한 깊이를 함께 유지한다.

## 4. 상세 문서와 표기

[시스템 설계 프레임워크](../guides/system-design-framework.md)의 8섹션은 빠진 관점을 확인하는 목록이다. 섹션당 파일 하나를 강제하지 않는다. 필요한 상세만 `details/{module-or-flow}.md`에 **독립 모듈/계약/흐름 단위**로 나눈다. 하나의 계약·상태기계를 여러 문서로 찢지 않는다.

- 각 상세에는 대상 모듈, 공개 계약, 직접 의존/소비자, 근거, 관련 검증을 넣는다. 상위 문서를 전량 읽어야만 이해되게 만들지 않는다.
- 같은 흐름을 여러 계층에 복제하지 않는다. 새 분기·계약·실패 책임이 드러날 때만 하위 뷰를 추가한다.
- 구조·의존은 Mermaid `flowchart`, 필요한 데이터 관계는 `erDiagram`으로 표현한다.
- 객체 협력은 [jobflow](../guides/job-flow-diagram-guide.md), 사용자 이동은 [navigation](../guides/navigation-diagram-guide.md), 한 소유자의 상태 전이는 [state](../guides/state-diagram-guide.md), 필요한 화면 배치는 [layout](../guides/screen-layout-guide.md)를 사용한다.
- 사용자 DSL을 다른 형식으로 치환하지 않는다. 외부 시스템의 시간순 통신은 필요할 때 `sequenceDiagram`을 별도 사용한다.
- 헤더·화살표·컨테이너 문법은 가이드가 원본이다. 첫 등장에 해당 가이드 링크를 달고 범례·핵심 설명을 둔다. 새로운 DSL 설명서 파일을 매 분석에 만들지 않는다.

## 5. 비판·검증·종료

[협업 프롬프트](./multi-agent-task-prompt.md)의 역할·반복 기준에 따라 검토한다.

**구조 확인**: 링크/인덱스 실존, 근거 경로, 깨진 펜스, 본문·도표의 이름/계약 일치. 실제 렌더링 도구를 썼는지 별도 기록한다.

**의미 확인**:

- 원본에 없는 모듈·흐름·권한·호환성을 날조하지 않았는가?
- 명목상 구조와 실제 import·공유 상태·쓰기 경로의 차이를 드러냈는가?
- 공개 계약·상태 소유자·오류 책임으로 대표 흐름을 설명할 수 있는가?
- 핵심에서 상세로 보낸 내용이 실제 존재하고 불필요하게 중복되지 않는가?
- 처음 보는 검토자가 시스템의 목적·흐름·중요 문제를 재구성할 수 있는가?
- 담당 모듈의 수정 시작점을 원본 경로와 검증 명령으로 찾을 수 있는가?

사실 오류·핵심 분석 누락·깨진 필수 참조는 수정하고 바뀐 부분을 재검증한다. 스타일 선호는 필수 결함과 구분한다. 필수 근거에 접근할 수 없으면 분석 범위의 한계를 명시하고 전체 확인 완료라고 하지 않는다.

최종 보고에는 생성/갱신 문서, 분석 범위와 기준선, 핵심 비판 반영, 미확인 범위를 남긴다. TO-BE에는 실제 AS-IS 경로·기준 날짜/커밋·중요 이슈 ID와 근거를 인계한다.
