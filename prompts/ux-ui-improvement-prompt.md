# UX/UI 개선 설계 프롬프트

대상 화면과 사용자 흐름의 문제를 조사하고, 관찰한 문제 → 근거 → 개선안 → 검증 방법을 연결해 설계한다. 코드 구현은 별도 요청에 따른다.

## 파일 저장 위치

사용자 지정 또는 기존 문서 위치를 우선한다. 위치가 없으면 `docs/design/YYYYMMDD-HHMMSS/ux-ui/ux-ui-improvement.md`에 작성한다. 날짜와 시간은 문서 생성 일시로 정한다.

## ux-ui-improvement.md

다음 내용을 한 문서에 담는다. 독립적으로 길어지는 근거와 시나리오만 별도 파일로 나누고 링크한다.

- 개선 범위: 대상 사용자·화면·과업·성공 기준·제약
- 현재 문제: 관찰한 동작·사용자 영향·근거
- 조사 결과: 참고 자료·확인한 사실·적용 한계
- 개선안: 변경 내용·선택 이유·우선순위·부작용·기대 효과
- 필요한 변경 전후 다이어그램
- 적용 순서·검증 방법·남은 가설과 미확정 사항

## 조사 기준

- 관련 코드·화면에서 문제를 확인하고, 개선할 질문에 필요한 공식 지침·연구·공개 구현·유사 서비스를 조사한다.
- 출처 링크·확인 시점·실제 확인한 내용과 적용 한계를 남긴다. 검색 결과 요약만으로 판단하거나 접근하지 못한 화면을 확인했다고 쓰지 않는다.
- 벤치마킹이 범위에 있으면 유사 서비스의 관련 화면이나 설명서를 직접 확인한다. 사용자·기기·제품 제약의 차이를 함께 검토한다.
- 핵심 질문에 답할 근거가 모이면 정리한다. 확인하지 못한 내용은 가설과 추가 조사 항목으로 남긴다.

## 설계와 검증 기준

- 개선안마다 현재 문제·근거·기대 효과·검증 방법을 연결한다. 대안과 부작용을 비교하고, 측정하지 않은 효과나 수치를 사실로 쓰지 않는다.
- 디자인 시스템·접근성·실제 API 제약을 확인한다. 키보드·포커스·오류 안내·대비 등 해당하는 항목을 검토한다.
- UI 표현의 변경과 서버 정책·계약의 변경을 구분한다. 상태와 계약의 소유권은 [모듈 경계 가이드](../guides/module-boundary-guide.md)를 따른다.
- 이동 변경은 [Navigation](../guides/navigation-diagram-guide.md), 상태 변화는 [State](../guides/state-diagram-guide.md), 배치 변경은 [Layout](../guides/screen-layout-guide.md)으로 표현한다. 기존 도표는 재사용하고 변경점을 짧게 설명한다.
- 출처·링크·다이어그램 문법을 확인한다. 정적 검토·실제 렌더링·사용성 검증 결과를 구분하고, 검증하지 않은 사용자 효과는 가설로 남긴다.

다이어그램을 작성·수정한 경우 Markdown을 완성한 뒤 [편집 링크 전달 기준](../guides/diagram-editor-link-guide.md)을 적용한다.
