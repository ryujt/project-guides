# UX/UI 개선 설계 프롬프트

대상 화면/사용자 흐름의 마찰을 조사하고 **관찰 → 근거 → 개선안 → 검증 방법**이 연결된 설계 문서를 만든다. 전체 사이트를 새로 설계하면 [사이트 설계 프롬프트](./site-design-prompt.md)를 사용한다. 이 작업은 설계 범위이며 코드 변경은 별도 요청에 따른다.

## 입력과 실행 규칙

- 입력: 대상 프로젝트·화면/흐름, 개선 요구와 성공 기준, 사용자/기기, 디자인 시스템, 변경 불가 영역, 참고 서비스 후보, 조사 범위/예산.
- [모듈 경계 가이드](../guides/module-boundary-guide.md)의 최소 맥락으로 관련 라우트·Page·상태 소유자·공개 API부터 읽고 직접 호출자·소비자 연결을 검색한다. 관련 본문은 영향 증거에 따라 확장하며 UI 변경을 이유로 전체 백엔드를 분석하지 않는다.
- 가정·관찰·제안을 구분하며 이미 허용된 조사/문서 작성은 자율 진행한다. 기존 변경을 보존하고 무관한 발견은 후속 과제로 남긴다.
- 독립 검색/페이지 읽기는 묶어서 수행한다. 접근하지 못한 페이지·조작하지 않은 화면을 확인했다고 쓰지 않는다. 출처는 실제 본문/코드를 확인하고 URL·경로·확인 시점을 남긴다.
- 설명은 신입 개발자가 이해할 수 있게 짧고 직접적으로 쓴다. 검색량·방문 수를 품질 점수로 삼지 않는다.

## 1. 현재 상태와 조사 범위

1. 실제 코드·화면에서 `화면/흐름 · 관찰한 문제 · 사용자 영향 · 근거 위치`를 수집한다.
2. 개선 항목에 `UX-ID · 성공 기준 · 우선순위`를 붙인다. 요구가 없으면 주요 사용자 여정에서 관찰한 문제부터 선택한다.
3. 조사할 질문, 참고 서비스, 검색/방문 범위와 종료 기준을 정한다. 사용자 지정이 없으면 유사 서비스 2개 내외와 관련 핵심 흐름부터 시작한다. 표본 크기는 발견된 불확실성에 따라 조정한다.
4. 기존 디자인 시스템·접근성 요구·실제 API 제약을 확인한다. 참고 서비스와 사용자·환경이 다른 점을 기록한다.

## 2. 근거 수집 — 필요한 트랙 선택

| 트랙 | 목적 | 확인 방법 |
|---|---|---|
| 웹 문서/연구 | 패턴·접근성·사용성의 근거 | 공식 지침/연구 본문을 읽고 적용 조건 기록 |
| 공개 구현 | 패턴을 구현할 때의 제약 | 해당 코드·데모·컴포넌트 문서의 실제 내용 확인 |
| 유사 서비스 | 용어·구조·복구 흐름 비교 | 관련 공개 화면·도움말·사용설명서를 직접 확인 |
| 대상 제품 관찰 | 우리 사용자 문제의 직접 근거 | 재현 가능한 화면/행동·실제 제공 데이터 확인 |

- 모든 트랙을 기계적으로 강제하지 않는다. 주장에 필요한 트랙을 수행하고 제외/접근 불가 이유를 기록한다. 벤치마킹을 요청받았다면 유사 서비스 직접 확인을 포함한다.
- 도움말은 목차로 관련 흐름을 찾은 뒤 필요한 문서를 읽는다. 모든 하위 페이지 전수 순회를 기본으로 하지 않는다. 전수 조사가 명시되면 대상 목록과 완료/미완료를 관리한다.
- 검색 결과 요약만으로 인용하지 않는다. 공개 데모를 실행하지 못했으면 문서 확인과 실제 동작 확인을 구분한다.
- 충분한 근거가 생겼거나 정한 범위에 도달하면 정리한다. 핵심 질문이 남으면 추가 조사의 목적을 정하거나 미확인 가설로 남긴다. 출처를 억지로 확보할 때까지 무한 검색하지 않는다.

근거 표: `S-ID · 유형 · URL/경로 · 확인 방법/시점 · 확인한 사실 · 적용 한계 · 관련 UX-ID`.

대상 제품의 재현 가능한 결함도 유효한 근거다. 경쟁 서비스에서 발견한 패턴을 우리 사용자에게 효과가 입증된 사실처럼 쓰지 않는다.

## 3. 개선안 설계

`UX-ID · 현재 문제 · 근거 S-ID · 개선안 · 관련 상태/모듈 소유자 · 우선순위 · 기대 효과 · 검증 방법` 표를 작성한다.

- 패턴은 `채택/수정 후 채택/제외 + 이유`로 비교한다. 브랜드·고유 문구·도메인 규칙은 복제하지 않는다.
- 화면에서 해결할 표현 문제와 서버의 정책/계약 변경이 필요한 문제를 구분한다. UI가 서버 권한·가격·가입 정책을 추론해서는 안 된다.
- 기대 효과는 가설로 쓰고 과업 성공·오류율·완료 시간 등 실제 확인할 기준을 제시한다. 측정하지 않은 수치를 발명하지 않는다.
- 키보드·초점·오류 공지·대비·입력 방식 등 관련 접근성 요구를 확인한다. 특정 표준 준수를 주장하면 해당 범위와 검증 근거를 남긴다.

## 4. 다이어그램과 산출물

- 이동 변경은 [navigation](../guides/navigation-diagram-guide.md), 상태 처리 변경은 [state](../guides/state-diagram-guide.md), 배치 변경은 [layout](../guides/screen-layout-guide.md)를 사용한다. 사용자 DSL을 다른 형식으로 치환하지 않는다.
- 대상 범위 전체 흐름을 먼저 제시하고 복잡한 시나리오만 상세화한다. 전/후 비교는 변경점을 알아볼 만큼 작성하고 기존 도표가 있으면 링크한다. 바뀌지 않는 화면을 전량 재작성하지 않는다.
- 각 도표에는 트리거·주요 분기·개선 이유를 짧게 설명한다. 모듈 내부 협력은 navigation에 넣지 않는다.
- 기본 경로는 `docs/design/{DATE}/ux-ui/ux-ui-improvement.md`이며 기존 문서 위치/사용자 지정을 우선한다. 핵심은 개선안 표 → 비교 근거 → 필요한 전/후 도표 → 적용 순서다.
- 상세 파일은 근거 표나 독립 시나리오가 길어질 때만 추가한다. 모든 검색 결과·원문·폐기한 페이지를 보고서에 복사하지 않는다.

## 5. 비판·수정·평가

[협업 프롬프트](./multi-agent-task-prompt.md)의 검토 절차를 적용한다. Critic은 다음을 확인한다.

- 개선안에 실제 관찰/출처가 있고 근거와 추론이 구분됐는가?
- 대상 사용자·제품 제약에 맞는가, 부작용과 대안이 검토됐는가?
- 화면·상태·API 계약의 소유권이 유지되고 변경 범위가 과하지 않은가?
- 전/후 차이와 검증 가능한 성공 기준이 있는가?
- 링크·DSL 문법 확인과 실제 렌더링/사용성 검증을 구분했는가?

근거 없는 핵심 주장·사실과 다른 인용·범위 위반은 수정한다. 단순 취향 차이는 필수 결함으로 취급하지 않는다. 수정 후 바뀐 부분을 다시 평가하고 필수 미해결 항목이 남으면 미완료로 보고한다.

최종 보고: 우선 개선안, 핵심 근거, 적용 순서, 접근/검증 한계, 남은 가설. 설계 검토 완료를 실제 사용자 효과 검증 완료로 표현하지 않는다.
