# 특정 요구사항 설계 요청 프롬프트

한 요구사항이 건드리는 모듈과 계약을 설계한다. **담당 모듈의 계약·관련 구현·테스트만으로 구현을 시작할 수 있는 문서**가 목표다. 전체 시스템 분석은 [AS-IS](./system-design-as-is-prompt.md), 전체 신규 설계·재설계는 [TO-BE](./system-design-to-be-prompt.md), 사이트 설계는 [사이트 프롬프트](./site-design-prompt.md)를 사용한다.

## 입력과 실행 규칙

- 입력: 요구사항, 대상 코드/문서, 성공 기준, 제약. 기존 프로젝트가 없으면 신규 설계임을 표시한다.
- [모듈 경계 가이드](../guides/module-boundary-guide.md)의 최소 맥락을 사용한다. 관련 README·공개 계약·구현/테스트부터 읽고 호출자·소비자·조립 위치는 먼저 검색한다. 발견된 영향에 따라 해당 본문으로 확장한다.
- 요구사항에 소켓 통신(TCP·WebSocket 등)이 포함되면 [소켓 서버 안정성 가이드](../guides/socket-server-stability-guide.md)에서 변경할 연결·전달·역압·복구 계약과 관련 검증 기준을 참고한다.
- 이미 허용된 설계 문서 작성은 자율 진행한다. 코드 수정은 포함하지 않는다. 기존 변경을 보존하고 무관한 문제는 후속 과제로 남긴다.
- 빠진 입력은 사실과 가정으로 구분한다. 되돌릴 수 있는 선택은 근거를 적어 진행하고, 중요한 미확정 정책은 잠정 설계와 필요한 입력으로 표시한다.
- 독립된 조사만 병렬화한다. 계약이 공유되는 종속 설계를 동시에 확정하지 않는다. 쉬운 말·짧은 문장을 사용한다.

## 1. 요구사항과 영향 범위

`FR-ID · 요구 · 성공 기준 · Must/Should/Optional`을 정리한다. 가정은 `근거 · 틀렸을 때 영향`을 적는다.

기존 코드가 있으면 `모듈/화면/API · 실제 경로 · 신규/변경/계약 접촉 · 관련 FR`을 작성한다. 영향을 받는 호출자·소비자·공유 상태의 소유자도 확인한다. 새 설계 경로는 제안이며 실재 경로와 구분한다.

요구가 넓더라도 자동으로 전체 시스템 재설계를 시작하지 않는다. 경계별로 나눌 수 있으면 관련 기능을 설계하고, 구조 결정이 선행돼야 하면 그 부분을 미확정으로 남긴다. 전환 권고만 하고 이미 가능한 설계까지 누락하지 않는다.

## 2. 경계·계약 설계

[method-R](../guides/method-R.md)로 필요한 깊이만 열고 [O-W 가이드](../guides/orchestrator-worker-pattern-guide.md)의 적용 범위를 정한다. 단순 로직을 계층 수에 맞춰 분할하거나 모든 반환을 이벤트로 바꾸지 않는다.

- **책임**: 각 모듈이 소유하는 규칙과 상태, 공개 진입점, 소유하지 않는 일을 적는다.
- **계약**: 입력·출력·오류·부작용·상태/데이터 쓰기 소유자·호환성을 정의한다. 재시도·취소·멱등성·순서가 관련되면 함께 명시한다.
- **의존**: 호출/이벤트 방향, 포트·adapter·조립 위치를 표시한다. 다른 모듈의 내부 경로/테이블/store를 직접 참조하지 않게 한다.
- **분할 판단**: 독립된 변경 이유·검증 경계가 있으면 나누고, 나눈 뒤에도 늘 함께 바뀌거나 과도한 연결만 늘면 합치는 안과 비교한다.
- **변경 영향**: 기존 소비자·저장 데이터·구버전 계약과의 호환성, 필요한 이행/롤백을 적는다.

큰 계약 정의를 프롬프트에 재복사하지 말고 [모듈 계약 양식](../guides/module-boundary-guide.md)을 사용한다. 새 폴더/클래스는 실제 책임을 구현할 때만 제안하고 기존 프로젝트 구조를 우선한다.

## 3. 필요한 뷰만 작성

[시스템 설계 프레임워크](../guides/system-design-framework.md)의 8섹션은 선택 가능한 관점이다. 관련 없는 UI·데이터·상태 섹션을 만들지 않는다.

| 질문 | 표기 |
|---|---|
| 영향 모듈·의존·경계 | Mermaid `flowchart`와 계약 표 |
| 객체 협력의 업무 흐름 | [jobflow](../guides/job-flow-diagram-guide.md) |
| 사용자 화면 이동·관련 API 판단 | [navigation](../guides/navigation-diagram-guide.md) |
| 한 소유자의 상태 전이 | [state](../guides/state-diagram-guide.md) |
| 화면 배치 변경 | [layout](../guides/screen-layout-guide.md) |
| 변경되는 데이터 관계 | Mermaid `erDiagram` |
| 외부 시스템의 시간순 통신 | Mermaid `sequenceDiagram`, 필요할 때 |

사용자 DSL을 다른 형식으로 치환하지 않는다. 표기 의미와 헤더는 해당 가이드를 따른다. 같은 흐름을 모든 계층에서 반복하지 않고 새 분기·책임·계약이 드러날 때만 상세 뷰를 추가한다. 도표 아래에는 트리거·핵심 결과·실패 경계를 짧게 설명한다.

## 4. 산출물과 구현 인계

기본은 `docs/design/{DATE}/feature/{slug}/feature-design.md` 하나다. 날짜는 한 번 확정하고 사용자 지정/기존 문서 위치가 있으면 따른다.

순서: **요구와 해법 요약 → 영향 범위 → 필요한 계약·다이어그램 → 검증/추적성 → 구현 인계·미확정 사항**. 상세가 독립적으로 길어질 때만 분리하고 핵심에서 링크한다. 문서 분량을 위해 계약을 누락하지 않는다.

- `FR ↔ 설계 위치 ↔ 소유 모듈 ↔ 검증 방법 ↔ 상태`를 연결한다. 관계는 다대다일 수 있으며 1:1을 강제하지 않는다.
- 상태는 `반영/부분/보류`를 구분한다. 보류 이유와 영향, 필요한 결정을 명시한다.
- 각 구현 작업에는 읽을 계약·쓰기 범위·의존 작업·검증을 전달한다. 구현 순서는 공통 계약/소유권 확정 → 독립 작업 → 통합 검증으로 정한다.

## 5. 비판·수정·평가

[협업 프롬프트](./multi-agent-task-prompt.md)의 검토·종료 기준을 따른다. 작성자와 다른 관점으로 다음 반례를 점검한다.

- 담당 모듈 계약만 보고 구현 가능한가, 다른 모듈 내부 지식이 숨어 있는가?
- 상태·쓰기 소유권과 오류/재시도 책임이 한 곳에 있는가?
- 신규 추상화가 실제 변경 이유/검증 격리를 만드는가, 연결 비용만 늘리는가?
- FR이 누락되거나 범위 밖 기능이 추가되지 않았는가?
- 실제 근거와 제안 경로를 구분했는가, 계약/다이어그램/본문이 같은 의미인가?
- 완료 기준을 검증할 테스트나 관찰 방법이 있는가?

필수 계약 누락·실현 불가능한 흐름·근거 날조·요구 누락은 수정한다. 스타일 선호와 권장 개선은 필수 결함과 구분한다. 링크/문법을 확인하되 렌더러가 없으면 렌더링 미검증을 밝힌다.

완료 보고에는 설계 결과, 핵심 비판과 반영, 검증 결과, 보류 FR/결정, 구현 인계를 남긴다. 필수 결정이 남으면 설계 초안과 구현 준비 완료를 구분한다.
