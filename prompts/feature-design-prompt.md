# 기능 설계 문서 생성 프롬프트

하나의 기능 요구사항을 관련 모듈과 공개 계약 중심으로 설계한다. 요구사항·성공 기준·제약과 관련 코드·문서를 바탕으로, 구현할 내용과 검증 방법을 명확히 한다. 코드 구현은 별도 요청에 따른다.

## 파일 저장 위치

사용자 지정 또는 기존 문서 위치를 우선한다. 위치가 없으면 `docs/design/YYYYMMDD-HHMMSS/feature/<feature-name>/feature-design.md`에 작성한다. 날짜와 시간은 문서 생성 일시로 정한다.

## feature-design.md

다음 내용을 한 문서에 담는다. 독립적으로 길어지는 상세만 별도 파일로 나누고 링크한다.

- 개요: 목적·범위·요구사항·성공 기준
- 영향 범위: 관련 모듈·화면·API·데이터와 변경할 부분
- 설계: 모듈별 책임·입출력·오류·상태 소유권·의존 관계
- 필요한 다이어그램과 주요 흐름 설명
- 구현 및 검증 계획: 작업 순서·완료 기준·검증 방법
- 미확정 사항: 가정·보류한 요구·필요한 결정과 영향

## 작성 기준

- 관련 공개 계약·구현·테스트부터 확인하고, 영향받는 호출자와 소비자로 조사 범위를 넓힌다. 확인된 현황과 제안·가정을 구분한다.
- 책임 분리와 계약은 [모듈 경계 가이드](../guides/module-boundary-guide.md)를 따른다. 기존 구조를 우선하고, 이번 요구와 관련된 부분을 설계한다.
- 내부 협력은 [Method-R](../guides/method-R.md)에 따라 필요한 객체·메서드까지 설명한다. 단순한 로직을 설명하기 위해 계층을 추가하지 않는다.
- 각 요구사항이 어느 설계와 검증 방법에 반영됐는지 알 수 있게 작성한다. 부분 반영과 보류는 이유를 적는다.
- 기존 소비자나 저장 데이터에 영향이 있으면 호환성·이행·복구 방법을 포함한다.

다이어그램은 필요한 것만 작성한다. 내부 협력은 [Job Flow](../guides/job-flow-diagram-guide.md), 화면 이동은 [Navigation](../guides/navigation-diagram-guide.md), 상태 변화는 [State](../guides/state-diagram-guide.md), 화면 배치는 [Layout](../guides/screen-layout-guide.md) 문법을 따른다. 각 다이어그램 아래에는 주요 내용을 짧게 설명한다.

## 검증과 인계

- 요구사항과 주요 성공·실패 흐름이 설계에 반영됐는지 확인한다.
- 계약·소유권·다이어그램이 일치하고, 다른 모듈의 내부 구현을 알아야 하는 의존이 없는지 검토한다.
- 링크·문법을 확인하고, 정적 검토와 실제 렌더링·실행 검증을 구분해 기록한다.
- 구현할 작업과 선행 관계, 먼저 검증할 가정, 남은 결정을 전달한다. 구현 시에는 [검증 우선 구현 프롬프트](./verify-first-implementation-prompt.md)를 참고한다.
