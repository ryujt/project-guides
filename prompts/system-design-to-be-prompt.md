# TO-BE 설계 문서 생성 프롬프트

요구사항과 제약을 바탕으로 신규 시스템 또는 기존 시스템의 목표 구조를 설계한다. AS-IS 문서는 있는 경우 참고하며, 별도 작성을 선행 조건으로 삼지 않는다. 확인된 현황과 제안·가정·미확정 사항을 구분한다.

책임 분리·공개 계약·시나리오 검증은 [모듈 경계 가이드](../guides/module-boundary-guide.md)를 따른다. 문서 내용은 이 프롬프트, 파일 배치는 아래 공통 가이드를 기준으로 한다.

## 파일 저장 위치

[공통 산출물 배치 가이드](../guides/system-design-output-guide.md#저장-위치와-고정-구조)의 고정 구조를 적용해 `docs/design/{DATE}/to-be/`에 작성한다. 날짜·폴더 재사용·상대 링크·파일 분리 규칙은 이 가이드를 따른다. 아래에서는 각 문서의 내용을 정의한다.

## system-design-to-be.md

`system-design-to-be.md`에는 다음 내용을 담는다.

- 개요: 목적·설계 범위·신규 설계 또는 기존 시스템 개선 여부
- 요구사항과 제약: 주요 요구와 성공 기준
- 시스템 구조
  - Mermaid로 작성한 목표 시스템 구성도와 간단한 설명
  - 서비스·모듈별 책임·공개 계약·데이터 소유권
- 핵심 용어 목록
- 기능 목록
- 주요 설계 결정: 검토한 대안과 선택 이유·비용·위험
- 구현 및 검증 계획: 작업 순서·시나리오별 검증 방법·미확정 사항

기존 시스템을 개선한다면 유지·변경·추가·제거할 부분을 구분하고, 필요한 호환성·데이터 이전·복구 계획을 적는다. 검증 계획과 실제 수행한 결과를 구분하며, 렌더링하지 않은 다이어그램은 정적 검토로 기록한다.

## job-flow 폴더

[Method-R](../guides/method-R.md)의 설계 깊이에 따라 `to-be/details/job-flow/`에 작성한다. 표기는 [Job Flow 가이드](../guides/job-flow-diagram-guide.md)를 따른다.

각 파일 안에서 시나리오별로 제목을 나누고, 한 다이어그램에 모든 흐름을 담지 않는다. 예를 들어 회원가입·로그인 시나리오, 장바구니 시나리오처럼 구분한다. 정상 흐름과 주요 실패 흐름을 표현한다. 각 그림 아래는 [Job Flow 하단 설명](../guides/job-flow-diagram-guide.md#다이어그램-하단-설명) 기준을 따른다.

| 파일 | 작성 내용 |
|---|---|
| `macro.md` | [매크로 설계 기준](../guides/method-R.md#3-매크로-설계-시스템을-하나의-경계로-보기)에 따라 대상 시스템과 외부 객체의 시나리오를 작성한다. |
| `system.md` | 목표 시스템을 구성하는 독립 서비스 간의 협력을 시나리오별로 표현한다. 서비스가 하나뿐이면 생략한다. |
| `<service-name>.md` | 서비스마다 파일을 생성하고, 해당 서비스의 내부 흐름을 시나리오별로 표현한다. 파일명에는 서비스의 영문 이름을 사용한다. |

파일 분리는 서비스 단위까지만 한다. 각 서비스의 내부는 모듈과 상세 수준으로 필요한 만큼 재귀적으로 확대하되, 시나리오·확대 대상별로 하위 제목을 나누어 해당 서비스 파일에 모두 담는다. 시나리오·모듈·상세별로 Job Flow 파일을 추가하지 않는다.

## navigation.md

설계한 화면 이동 흐름을 `to-be/navigation.md` 한 파일에 작성한다. 표기는 [Navigation 가이드](../guides/navigation-diagram-guide.md)의 `navigation` 문법을 따른다.

- 설계 범위의 전체 시나리오 색인을 두고, [시나리오별 상세 분석](../guides/navigation-diagram-guide.md#시나리오별-상세-분석)에 따라 과업별 제목·다이어그램·진입 조건·단계와 분기·관련 API/처리·결과와 복귀·근거/가정을 담는다. 유지 시나리오도 포함하며 대표 흐름만으로 대신하지 않는다.
- 작성 전에 [Navigation 작성 샘플](../examples/diagram/navigation/document-template.md)을 확인하고 [고정 구성·화면 확인 링크 기준](../guides/navigation-diagram-guide.md#문서-구성과-화면-확인-링크)을 적용한다. 각 시나리오의 `화면 확인 링크` 표는 생략하지 않는다.
- 각 다이어그램 아래에는 주요 흐름을 짧은 문장 목록으로 설명하고, 추가 조건·근거·미확인은 같은 시나리오 절에 둔다.
- 각 시나리오의 `화면 확인 링크` 표에서 등장 페이지의 기본 화면과 사용하는 장면을 `screen-layout.md`의 해당 절과 HTML 장면으로 직접 연결한다. 화면 이름·식별자·파일/장면 대응은 [공통 기준](../guides/system-design-output-guide.md#페이지장면-목록)을 따른다.

UI가 없으면 해당 없음과 이유를 기록한다. UI가 있지만 화면 이동이 없는 과업은 현재 페이지의 동작·결과 장면을 설명하고 Layout·HTML로 연결한다.

## screen-layout.md

설계 범위의 모든 화면 배치를 `to-be/screen-layout.md` 한 파일에 작성한다. 처음에 [전체 페이지·장면 목록](../guides/system-design-output-guide.md#페이지장면-목록)을 두고, 표기는 [스크린 레이아웃 가이드](../guides/screen-layout-guide.md)의 `layout` 문법을 따른다.

- 화면별로 하위 제목을 나누고, 각 화면의 목표 영역 배치와 포함 관계를 그린다.
- 각 다이어그램 아래에는 영역별 역할·입출력·상호작용을 설명한다. 적용되는 로딩·빈값·오류·권한 상태와 반응형 배치 차이도 함께 적는다.
- 같은 화면의 배치 설명은 이 파일의 해당 절을 원본으로 두고, 다른 문서에서는 링크로 참조한다.

UI가 없으면 화면 0개라는 사실과 이유를 기록하고, 가상의 화면을 만들지 않는다.

## details/screens 폴더

[화면별 HTML 규칙](../guides/system-design-output-guide.md#화면별-html)에 따라 목표 화면의 실제 모양을 표현하는 바닐라 HTML을 `to-be/details/screens/`에 생성한다. 전체 화면과 Navigation 등장 화면의 누락·링크·화면 확인은 [공통 검증 기준](../guides/system-design-output-guide.md#검증)으로 확인한다.

Markdown 문서·다이어그램의 tools.camp 링크 생성 여부 확인과 전달은 [편집 링크 전달 기준](../guides/diagram-editor-link-guide.md)을 따른다.
