# TO-BE 설계 분석 문서 생성 프롬프트

요구사항과 제약을 근거로 신규 시스템 또는 기존 시스템의 목표 구조를 설계한다. AS-IS 분석 없이도 최초 설계를 시작할 수 있다. **어떤 기능·변경이 어떤 모듈 안에서 끝나고, 어떤 공개 계약만 함께 알아야 하는지** 드러내며 가능한 한 간결하고 유연하게 설계한다. 다이어그램과 다양한 시나리오 검증으로 빠진 요구사항을 찾고 설계에 반영한다. 문서·객체·연결 수의 증감 자체로 품질을 평가하지 않는다. 절 번호·제목·표 열·그림 규칙은 AS-IS와 같은 [설계 문서 양식](../guides/system-design-document-guide.md)이 원본이고, 이 프롬프트는 설계 판단과 TO-BE에서 달라지는 점만 정한다. 아래의 `§n`은 핵심 문서의 절, `상세 §n`은 상세 문서의 절, `양식 §n`은 양식 가이드의 절이다.

## 입력과 실행 규칙

- 공통 입력: 시스템 목적·대상 사용자/주요 시나리오, 요구사항·범위·성공 기준·제약. [AS-IS](./system-design-as-is-prompt.md) 산출물, 현재 구조 자료, 코드/테스트, 외부 연동 계약은 있는 범위에서 추가한다.
- 시작할 때 **신규 설계 / 기존 시스템 개선**과 그 근거를 명시한다. 혼합 범위라면 영역별로 구분한다. AS-IS 문서가 없다는 이유만으로 신규 시스템으로 간주하지 않는다.
  - 신규 설계: 요구와 시나리오에서 책임·계약을 도출한다. 존재하지 않는 현재 구조·결함·코드/테스트를 만들거나 AS-IS 선행 작성을 요구하지 않는다.
  - 기존 시스템 개선: AS-IS가 있으면 날짜/커밋과 현재 상태를 대조하고 오래된 부분은 관련 코드로 재확인한다. AS-IS가 없으면 설계에 필요한 현재 계약·구현·제약만 조사하고 근거와 미확인 범위를 남긴다. 별도 AS-IS 문서 작성은 선행 조건이 아니다. 관찰된 결함을 목표 설계의 사실로 복제하지 않는다.
- [모듈 경계 가이드](../guides/module-boundary-guide.md)의 최소 맥락과 계약을 사용한다. 기존 자료가 있으면 관련 모듈·공개 계약부터 읽고 호출자·소비자·조립 지점을 검색한다. 신규 설계는 요구와 외부 연동 계약부터 확인하며, 필요한 근거가 생기면 읽을 범위를 확장한다.
- 설계 범위에 소켓 통신(TCP·WebSocket 등)이 포함되면 [소켓 서버 안정성 가이드](../guides/socket-server-stability-guide.md)에서 적용 범위에 맞는 연결·전달·역압·복구 계약과 검증 기준을 참고한다.
- 확인된 사실·제안·가정·미확인을 구분한다. 신규 모듈의 경로·계약·테스트는 제안으로 표시한다. 빠진 입력은 잠정안·영향·필요 입력으로 남기고 진행 가능한 설계부터 작성한다.
- 이미 허용된 설계는 자율 진행한다. 코드와 원본 AS-IS는 보존한다. 기존 사용자 변경을 덮어쓰지 않는다.
- 독립 조사/대안 비교는 병렬화할 수 있다. 공유 계약을 정한 뒤 파일별 쓰기 담당을 나누고 종속 설계의 일관성을 통합 담당자가 확인한다. 큰 설계([큰 분석과 작은 분석](../guides/system-design-document-guide.md#큰-분석과-작은-분석))는 [양식 §9](../guides/system-design-document-guide.md#9-작성-순서와-병렬화)의 TO-BE 순서로 진행한다. 대안 비교로 정한 결정(D)·설계 항목(C)과 목표 경계 목록·경계 간 계약명을 통합 담당자가 먼저 공유 계약으로 확정하고, 신규·변경 경계의 상세(드릴다운 포함)는 핵심 §5 노드를 확정한 뒤 그 노드를 진입점으로 맡긴다. 하위 작성자는 상위·계약과 어긋난 점을 고치지 않고 보고한다.

## 1. 요구사항과 대안

요구는 §2.2에 `R-ID`마다 필요한 기능·해결할 문제, 근거, 성공 기준, 우선순위로 정리한다. 신규 설계의 근거는 사용자 요구·시나리오·제약으로 연결한다. 성공 기준은 시험·명령·관찰로 확인할 수 있게 쓴다. 기존 이슈 ID는 다시 매기지 않고 근거로 인용한다(접두가 `R`·`C`·`D`와 겹칠 때의 표기는 [양식 §7](../guides/system-design-document-guide.md#7-id와-교차-참조)). 모든 AS-IS 결함을 이번 요구로 자동 승격하지 않는다.

요구 목록은 설계 중에도 갱신한다. 다이어그램·시나리오 검증으로 발견한 빠진 요구에는 발견 경로·필요한 이유·영향을 남긴다. 확인된 요구는 `R`에 반영하고 관련 `C`·`D`·그림·검증을 함께 갱신한다. 확인이 필요한 내용은 가정·잠정안으로 구분하고 §9.5 또는 상세 §8로 연결한다. 이 과정에서 객체·연결·산출물이 늘어나는 것은 허용하며, 단순히 처음보다 줄었는지로 설계를 판단하지 않는다.

각 중요한 구조 결정은 다음을 비교한다.

- 신규 설계는 요구를 충족하는 최소 구조, 기존 시스템 개선은 현 구조의 작은 수정으로 해결하는 안.
- 책임별로 경계/소유권·계약을 나누거나 기존 배치를 조정하는 안.
- 필요할 때 독립 모듈/프로세스로 분리하는 안.

비교 기준은 [연결 최소화와 시나리오 검증](../guides/module-boundary-guide.md#연결-최소화와-시나리오-검증)의 트레이드오프를 따른다. 결정은 §2.4에 `D-ID`마다 대안·선택·근거·AS-IS 대비(현재 구조를 확인한 경우)로 남긴다. 기존 대안 표의 장점·단점·판단에 비교축별 이득과 비용을 쓰고, 선택에는 목표 경계·계약과 남겨야 하는 연결을, 근거에는 대안이 갈린 기준·기각 이유·감수할 비용과 위험을 쓴다. 요구와 결정을 실제 변경으로 옮기는 설계 항목은 §2.3에 `C-ID`로 둔다. 미래 확장 가능성만을 이유로 추상화·큐·분산 저장소를 추가하지 않는다.

## 2. 목표 경계와 계약

[method-R](../guides/method-R.md)의 깊이별 협력 방식 선택 기준으로 필요한 경계만 설계한다. 오케스트레이터–워커를 선택한 범위에는 [O-W 가이드](../guides/orchestrator-worker-pattern-guide.md)를 적용한다. 메시지·직접 호출·이벤트 선택은 실제 실패/배포/응답 계약에 따른다. 조율자 시나리오 안의 Worker 고립과 모든 코드의 직접 호출 금지를 혼동하지 않는다.

모듈별로 다음을 설계한다. 경계 목록·의존은 §3, 경계별 기능은 §4, 경계 사이 흐름은 §5, 데이터 권위와 이행 중 권위는 §6에 쓰고, 경계마다의 아래 결정은 상세(공개 계약은 상세 §2 — [양식 §5](../guides/system-design-document-guide.md#5-상세-문서-골격))에 쓴다.

| 관점 | 필요한 결정 |
|---|---|
| 책임 | 소유 규칙과 함께 바뀌는 이유 |
| 공개 계약 | 입력·출력·오류·부작용·호환성 |
| 데이터/상태 | 권위 소유자, 단일 쓰기 책임, 읽기 경로 |
| 의존 방향 | 호출자/소비자, 포트/adapter, 조립 위치 |
| 실패 | 타임아웃·취소·재시도·중복/역순·부분 실패 책임 |
| 검증 | 모듈 단독 검사, 계약 검사, 필요한 통합 검사 |
| 작업 맥락 | 담당자가 읽어야 할 계약·구현·테스트와 확장 조건 |

목표 구조는 [연결 최소화와 시나리오 검증](../guides/module-boundary-guide.md#연결-최소화와-시나리오-검증)의 순서로 검토한다. 요구·상태·외부 계약에서 도출한 모든 대상 시나리오가 후보의 연결만으로 처리되는지 확인하고, 부족하거나 잘못된 연결·계약을 추가·수정한다. 객체의 책임 재배치·분할·추가·병합·제거도 비교하여 불필요한 연결을 줄이고, 영향받는 시나리오를 재검증한 뒤 구조를 확정한다. 연결 감소를 위해 하나의 객체에 서로 다른 책임을 몰지 않는다.

검토 결과는 기존 양식을 유지하여 배치한다. 경계 간 경로는 §5, 내부 경로는 상세 §3을 원본으로 삼고, 시나리오별 판정·근거·미확인은 §9.2 또는 상세 §7의 이미 수행한 검토 기록에서 해당 경로를 참조한다. 대안 선택은 §2.4의 `D-ID`, 남은 위험·미확정은 §9.5 또는 상세 §8로 연결한다. 작은 설계의 상세 생략은 양식 §2를 따른다. 전체 흐름 그림에 선을 덜 그리는 것을 실제 연결 감소로 취급하지 않는다.

## 3. 구현·검증과 이행

결과는 §9의 9.1 독립 작업 순서, 9.2 검증, 9.3 이행·롤백, 9.4 물려받는 이슈 처분, 9.5 미확정·필요 입력에 쓴다. 모든 설계에서 최초 동작 가능한 범위와 계약·소유권 확정 후의 독립 구현 순서를 정하고, 작업마다 쓰기 소유·선행 관계(§9.1의 순서 번호)·완료 기준과 검증 방법을 둔다. 수용 검증은 연결 검토에서 도출한 대상 시나리오에 대응시키고, 기존 시스템 개선은 관련 소비자·회귀 검증을 포함한다. 이미 실행한 검사와 구현 후 실행할 검증 계획을 구분한다. 기존 시스템 개선이면 물려받는 AS-IS 이슈를 고치는 `C`/`D`·보류·비대상으로 처분하고 이유를 남긴다.

구현은 이 프롬프트의 범위가 아니며, 이 설계를 받아 구현하는 작업에서 [검증 우선 구현 프롬프트](./verify-first-implementation-prompt.md)를 쓴다. 그 작업이 구현 초기에 먼저 확인할 수 있도록, §9.5(경계 안은 상세 §8)로 연결하는 가정 가운데 틀리면 결정이 바뀌는 것(외부 동작·기동 시간·권한·비용 등)을 빠뜨리지 않고, 그 가정의 검증은 §9.2(경계 안은 상세 §7)의 `시점`을 그것에 기대는 작업 앞으로 적는다.

기존 공개 계약·데이터·프로세스에 영향을 주면 다음 중 필요한 항목을 추가한다. 신규 시스템도 외부 연동 계약이나 가져올 데이터가 있으면 해당 호환성·이행을 검토한다. 이행 대상이 없으면 이유를 적고 생략한다.

- 기존/신규 소비자 호환, 배포 순서, 데이터 이전, 마이그레이션 검증.
- 상태/쓰기 소유권을 옮기는 동안의 권위와 이중 쓰기 방지.
- 단계별 완료 기준, 되돌릴 수 있는 범위, 불가역 시점과 실패 복구.
- 비교 테스트·운영 관측·점진 전환이 필요한 근거.

“롤백 가능”이라고 쓰려면 무엇을 어떻게 되돌리는지 명시한다. 파괴적 이전이나 외부 실행은 설계와 실행 권한을 구분한다.

## 4. 문서와 다이어그램

작성 전에 [양식 §3~§7](../guides/system-design-document-guide.md#3-핵심-문서-골격)과 예시 핵심 1편·상세 1편을 읽는다. 둘이 다르면 양식이 먼저다. 예시는 가상 시스템으로 쓴 [TO-BE 예시](../guides/examples/system-design/to-be/system-design-to-be.md)와 [양식 §11](../guides/system-design-document-guide.md#11-예시-산출물)의 TO-BE 상세이고, 이름·경로·수치는 예시 값이다.

기본 핵심 경로는 `docs/design/{DATE}/to-be/system-design-to-be.md`, 경계별 상세는 `to-be/details/<boundary>.md`다([양식 §2](../guides/system-design-document-guide.md#2-산출물-배치)). `DATE`는 한 번 확정한다. AS-IS가 있으면 같은 기준 날짜 또는 명시한 새 날짜를 사용하고, 없으면 설계 기준 날짜를 사용한다. 기존 문서 위치/사용자 지정을 우선한다.

핵심 문서는 [양식 §3.1](../guides/system-design-document-guide.md#31-절-번호표)의 **TO-BE 열**과 [§3.3](../guides/system-design-document-guide.md#33-절별-작성-규칙)의 작성 규칙을 따른다. 제목은 TO-BE 제목을 글자 그대로 쓴다(핵심 §2·§9와 상세 §7·§8이 AS-IS와 다르다). 번호를 고정하고 해당 없는 절도 제목을 남기며, 분량 목표는 두지 않는다. TO-BE에서 더 지킬 것:

- **머리·§0**: [머리 블록](../guides/system-design-document-guide.md#32-머리-블록)의 설계 유형·입력 근거를 채운다. 요구가 문장으로 주어졌으면 입력 근거에 원문을 번호와 함께 옮기고, R의 근거로 그 번호를 인용한다. §0 요지의 남은 위험에는 확인하지 못한 가정·미확인을 숨기지 않는다.
- **§2**: 2.1~2.4에 [1. 요구사항과 대안](#1-요구사항과-대안)의 결과를 쓴다. 열과 값은 [양식 §3.3](../guides/system-design-document-guide.md#33-절별-작성-규칙)을 따르고, 2.3의 `상태`에서 부분 반영을 `반영`으로 쓰지 않는다. 요구와 설계 항목은 다대다일 수 있으므로 R → C → 검증(§9.1·상세 §7)이 끊기지 않게 잇는다.
- **§5**: [양식 §4](../guides/system-design-document-guide.md#4-흐름-절--경계-수준-jobflow) 그대로 목표 계약으로 그리고, 새·바뀐 계약에는 `(제안)`을 붙인다. 대표 실패 흐름(타임아웃·부분 실패·회수)을 하나 이상 그림이나 불릿으로 보인다([양식 §4.2](../guides/system-design-document-guide.md#42-전체-한-장과-시나리오-분할)). 이는 그림의 표시 기준이며 시나리오 검증 범위를 대표 사례로 제한하지 않는다. AS-IS가 있으면 같은 시나리오는 **같은 소절 번호**를 쓰고, 없어지거나 새로 생긴 시나리오의 번호도 양식 §4.2를 따른다.
- **§9**: 9.1~9.5에 [3. 구현·검증과 이행](#3-구현검증과-이행)의 결과를 쓴다. 경계 안의 검증·위험은 상세 §7 검증 계획·§8 위험·미확정이 원본이고, §9.2·§9.5는 경계를 넘는 것만 모은다.
- **기존 시스템 개선**: 바뀌는 곳을 중심으로 쓰고 `AS-IS 대비` 열로 드러낸다. 유지 경계도 §3 행은 두되 상세는 새로 쓰지 않고, 유지되는 §4 소절·시나리오는 AS-IS 문서의 해당 절 링크로 대신할 수 있다. AS-IS 문서가 없으면 필요한 현재 맥락을 요약한다.
- **신규 설계**: AS-IS와 견주는 열·표시를 두지 않는다. 무엇을 빼고 어떻게 표기하는지는 [신규 설계에서 빼는 것](../guides/system-design-document-guide.md#신규-설계에서-빼는-것)을 따른다. AS-IS 없이 주요 경계·책임·의존과 대표 성공·실패 흐름이 읽혀야 한다.

상세는 신규·변경 경계마다 하나이며 [양식 §5](../guides/system-design-document-guide.md#5-상세-문서-골격)의 TO-BE 열을 따른다(8관점별로 나누지 않는다). 작은 설계는 상세 없이 핵심 하나로 끝낼 수 있고, 그 기준과 일부 경계에만 상세를 두는 예외는 [큰 분석과 작은 분석](../guides/system-design-document-guide.md#큰-분석과-작은-분석)을 따른다. 상세 §2의 새 계약은 `(제안)`으로 표시한다. `## 3. 내부 Job Flow — 드릴다운`([양식 §6](../guides/system-design-document-guide.md#6-경계-내부-job-flow-드릴다운))의 노드는 **제안 심볼**이고, 근거 열은 [양식 §6.3](../guides/system-design-document-guide.md#63-그림-아래-근거)을 따른다. 신규·변경 부분만 설계 판단이 필요한 깊이까지 열고 유지 부분은 AS-IS 드릴다운을 링크한다. 같은 계약을 여러 상세 파일에 복제하지 않는다.

- 구조·의존은 Mermaid `flowchart`(라벨 규칙은 [양식 §3.3](../guides/system-design-document-guide.md#33-절별-작성-규칙)), 필요한 데이터 관계는 `erDiagram`. 협력 흐름은 [jobflow](../guides/job-flow-diagram-guide.md), 사용자 이동은 [navigation](../guides/navigation-diagram-guide.md), 한 소유자의 상태는 [state](../guides/state-diagram-guide.md), 배치는 [layout](../guides/screen-layout-guide.md).
- 사용자 DSL을 다른 형식으로 치환하지 않는다. 외부 시스템의 시간순 통신은 필요할 때 별도 `sequenceDiagram`으로 설명한다.
- 첫 도표에 관련 가이드와 설계 범위·범례·핵심 분기를 짧게 밝힌다. 가이드 사본이 산출 문서와 같은 저장소 안에 있을 때만 상대 링크를 걸고, 그렇지 않으면 파일 이름과 절 제목만 쓴다([양식 §3.2](../guides/system-design-document-guide.md#32-머리-블록)). 전체 흐름 뒤에 실제 새 정보를 주는 상세만 추가한다.

## 5. 교차 비판·수정·평가

[협업 프롬프트](./multi-agent-task-prompt.md)에 따라 작성자 외 검토자가 요구·제약·TO-BE를 대조하고, 기존 시스템은 AS-IS 또는 확인한 현재 구조 근거도 대조한다. 독립 검토 도구가 없으면 순차 역할 검토임을 밝힌다.

검토는 `ID · 위치 · 반례/근거 · 영향 · 필수/권장 · 처리 · 재검증`으로 남긴다. 짧은 작업은 본문/최종 보고로 충분하고 장기 작업은 기존 review 문서를 갱신한다. 회차마다 새 파일을 의무 생성하지 않는다.

필수 확인:

- 요구가 누락되거나 부분 반영을 완료로 기록하지 않았는가?
- 다이어그램·시나리오 검증으로 발견한 요구와 확인이 필요한 가정을 구분하고, 요구·설계·검증 범위를 함께 갱신했는가?
- 요구·외부 연동과 기존 시스템이 있는 경우 실제 제약을 고려했으며 근거 없는 효과/호환성을 단정하지 않았는가?
- 신규 설계의 가정·제안과 관찰 사실을 구분하고, 존재하지 않는 AS-IS·코드·테스트에 의존하지 않았는가?
- 공개 계약·소유권·의존 방향·실패 책임이 일치하는가?
- 도출한 모든 대상 시나리오가 명시된 연결만으로 처리되며, 누락·오류에 따른 연결·객체 조정을 재검증했는가? 제외·미확인 범위와 그 근거가 있는가?
- 남긴 연결의 필요성과 객체별 책임을 설명할 수 있고, 분할·병합 대안의 트레이드오프가 최종 선택에 반영됐는가?
- 과분해, 전역 store/이벤트 버스의 숨은 결합, 불필요한 조율자가 없는가?
- 한 모듈 구현에 필요한 맥락이 명확하고 불필요한 상대 구현 탐색 없이 독립 검증이 가능한가?
- 최초 구현의 완료 기준과 성공·실패 시나리오의 검증 방법이 있는가?
- 이행/롤백과 직접 소비자 검증이 필요한 변경에서 빠지지 않았는가?
- 핵심·상세·도표·링크가 실제로 일치하고, 저장소 루트를 넘는 링크가 없는가?
- AS-IS가 있으면 절 번호·§5 시나리오 소절 번호·유지 계약의 노드 이름이 AS-IS와 대응하고, 없어지거나 새로 생긴 시나리오가 드러나는가?
- §5 그림이 경계 사이 소통만 담고(클래스·내부 함수·내부 단계 없음) 화살표 출발점이 [실제 요청자](../guides/job-flow-diagram-guide.md#scope-그림의-출발점은-실제-요청자다)인가? 상위 §5 노드와 상세 드릴다운 진입점의 이름·입력·출력·실패 의미가 같은가?
- [양식 §10](../guides/system-design-document-guide.md#10-검증)의 `design-doc-check` 결과와 렌더러로 그려 눈으로 본 결과를 구분해 §9.2(브리프가 있으면 브리프 §5)와 최종 보고에 남겼는가? 렌더러를 돌리지 않았으면 정적 검토라고 쓴다.

기계 확인은 링크·펜스·매핑 누락을 찾는 보조 수단이며 설계 의미 검토를 대체하지 않는다.

[모듈 경계 가이드](../guides/module-boundary-guide.md)의 평가축으로 근거를 남긴다. 현재 구조 근거가 있으면 변경 전후를 비교하고, 신규 설계는 최소 구조와 선택안을 대표 구현·변경 시나리오에 대입해 필요한 맥락·계약·검증 범위를 비교한다. 기존 구조를 확인하지 못했으면 비교 한계를 남긴다. 설계상 예상과 실행 결과를 구분하며 측정하지 않은 개선 효과를 단정하지 않는다. 점수·검토 회차 상한은 완료 조건이 아니다. 필수 결함을 수정한 뒤 영향 부분만 재검증한다. 같은 접근의 반복 상한에 이르면 원인/범위/해결 경로를 바꾸고, 유효한 다음 작업이 없으면 미완료와 필요한 입력을 보고한다.

최종 보고에는 설계 결과와 새로 발견한 요구, 연결·객체 구성의 대안 선택 이유와 감수할 비용, 핵심 비판의 처리, 시나리오 검증 범위·결과/한계, 구현할 독립 작업과 미확정 결정을 남긴다.
