# TO-BE 설계 분석 문서 생성 프롬프트

> **무엇을 하나**: AS-IS 산출물([AS-IS 프롬프트](./system-design-as-is-prompt.md) 결과)을 첨부하고 **설계 요청(변경·목표 요구사항)을 입력**해 TO-BE 설계 문서(+교차검증)를 생성한다. 설계 요청이 없으면 AS-IS 브리프의 이슈(R-0X) 전체 해소를 기본 요청으로 삼는다. `DATE`·`_evidence-brief.md`·`_dsl-읽는법.md` 는 AS-IS 가 확정·생성한 것을 그대로 재사용한다.
> **최우선 가치 — 독자의 이해 속도**: 독자는 핵심 문서만 읽고 5분 안에 "**무엇이 왜 어떻게 바뀌는지**"를 파악해야 한다. TO-BE 는 **변경점 중심**으로 쓴다 — 바뀌지 않는 것은 다시 설명하지 않고 AS-IS 링크 한 줄로 대신한다(AS-IS 재서술 금지).
> **종료 판정**: Step 4 Critic 이 기계 확인(분량·골격·추적 표)을 먼저, 의미 확인(요청 충족·설계 건전성·상세 실재)을 이어서 채점하고, Step 5 종료 술어로만 끝낸다. 충족까지 자가검증·자가수복하며 무중단 진행한다.

## 1. 출력 스타일 계약 (모든 산출물 공통 — 위반은 Critic 채점 대상)

### 두괄식 3계층 — 요점·키워드 먼저, 상세는 뒤에

| 계층 | 규칙 |
|---|---|
| 문서 | 첫 화면 = `## 0. 한눈에 보기`. **이것만 읽고도 "무엇이 왜 바뀌는지" 남에게 설명할 수 있어야 한다** |
| 섹션 | 첫 줄 = **볼드 한 줄 결론** → 표·다이어그램 → 보충 불릿. 결론이 제목의 재진술이면 위반 — 그 섹션에서 가장 중요한 **판단**을 담는다 |
| 다이어그램 | 바로 아래 설명 불릿 3~5개. 한 불릿 = 한 문장, 노드를 옮겨 적지 말고 "무엇이 무엇을 왜 하는지" |

### 쉬운 말 — 결론 구역과 용어 다이어트
- **독자는 신입 엔지니어다**: 이 프로젝트를 처음 보는 신입이 읽고 바로 이해할 수 있게 쉬운 말로 쓴다. 짧은 문장 · 전문용어는 첫 등장에 한 번 풀어쓰기 · 길고 장황한 설명 금지. 어려운 깊이는 상세 파일로 옮기되 결론은 항상 쉽게.
- **결론 구역**(= §0 전체 + 모든 섹션·소절·각론 블록의 첫 결론 줄)에는 **키워드 표에 없는 전문용어를 쓰지 않는다.** 방법론 용어(method-R·L1~L4·O-W·Orchestration/Choreography·PBS·6원칙)만이 아니라 도메인·인프라 약어도 같다. 첫 문장은 일상어로 열고, 전문용어는 둘째 줄부터.
- **방법론 용어는 문서 표면 어디에도 주인공이 아니다**: 본문에서 꼭 필요하면 첫 사용에 괄호로 풀어쓴다. "왜 이 깊이로 나눴나" 류의 분해 근거는 본문에 섞지 말고 상세 파일 말미 `## 부록: 분해 근거`로 접는다.
- 키워드 표(≤10개)에 없는 전문용어는 첫 등장에서 괄호로 한 번만 푼다(표와 중복 정의 금지). **10개로 부족하면 용어를 늘리지 말고 본문의 전문용어를 줄여라.**
- 짧은 문장 · 불필요한 수식어 제거 · 불릿은 한 줄.

### 분량 예산
- **총량이 최종 게이트**: 핵심 문서 ≤ **200줄**(`wc -l`, P0). 국소 상한은 배분 안내(초과는 P1)이며, 충돌하면 총량이 우선하고 초과분은 삭제가 아니라 **상세 파일로 이동**한다.
- 국소 상한: §0 ≤ 50줄 / 변경점 각론 블록 ≤ 10줄 / 상세 파일 ≤ 500줄 / 열거·예시 표 ≤ 8행. **추적성 SoT 표(변경점 표·요청 커버리지 표)는 전 항목 필수 — 행 상한 없음이며 §0 국소 상한 계산에서도 제외한다(총량에는 포함).** 다이어그램 최대 4장·장당 노드 ≤ 12(하한 없음 — 억지 다이어그램 금지).
- **관통 대표 다이어그램 예외**: 바뀐 뒤 전체 흐름의 jobflow 1장(과 바뀐 뒤 화면의 navigation 1장)은 진입→핵심 결과 관통을 위해 국소 상한 예외 — 단 jobflow 객체 ≤ 14·45줄, navigation ≤ 25줄 안에서, 한 단계 = 독자가 인지하는 한 동작으로 병합. **관통 다이어그램이 들어가는 섹션의 괄호 예산은 그 다이어그램을 제외한 산문·표에 적용한다.**
- 변경점이 8개를 넘으면 개별 나열 대신 **주제 묶음으로 C 를 재편**한다(대형 요청은 묶음 단위 설계 — 나열이 많아질수록 독자는 구조를 잃는다).
- **우선순위(충돌 시)**: ① 가이드 DSL 문법·의미 ② §3 골격의 섹션 제목·순서 ③ 분량·표현 계약. 관통 요건과 분량이 부딪히면 관통을 살리고 깊이를 상세로 옮긴다.

### 반복·근거·코드
- 같은 내용은 한 곳에만. 두 번째 등장부터는 링크. **변경 없는 영역의 재서술·필러 다이어그램 금지.**
- 근거는 인라인 `(경로:라인)` 또는 표의 근거 열로. 근거 전용 표는 상세 파일 말미 "부록: 근거"에만.
- 코드 붙여넣기 금지 — `경로:라인` 참조로 대체.
- 본문·표가 인용하는 ID(R-0X·C-0X)는 ⓐ §0 표에 있거나 ⓑ 인용 지점에 한 줄 뜻 병기 ⓒ 브리프·AS-IS 로 링크 중 하나를 만족한다. 맨몸 ID 인용 금지.

### 다이어그램 일반 규칙
- **DSL 읽기 보조**: **핵심 문서와 각 상세 파일에서 DSL 이 처음 등장하는 블록 바로 위**에 `읽는 법: ../../_dsl-읽는법.md`(상세 파일은 같은 깊이라 동일 경로) 링크 한 줄. 파일이 없으면 AS-IS 프롬프트 §1 정의로 1회 생성.
- **표기 통일**: AS-IS·TO-BE·상세가 같은 DSL 을 같은 문법으로(layout 문법 혼용 금지). 데이터 구조가 바뀌는 설계면 mermaid `erDiagram` 1장을 해당 상세 파일에 보장한다.
- **범례는 뜻으로**: 색·굵기·이모지(🟢 신규·🟡 변경)를 쓰면 바로 아래 범례 1줄 — 방법론 이름이 아니라 "무엇"으로 설명.
- **mermaid 방어 규칙**: 모든 노드·엣지 레이블 큰따옴표(`A["레이블"]`·`-->|"라벨"|`) · 레이블 안 괄호 금지(`·`나 `<br/>`로 치환) · `<br/>` self-closing 고정 · subgraph 타이틀 동일 · 레이블에 `end`·`subgraph`·화살표 연산자 금지.

## 3. 핵심 문서 골격 (섹션 제목·순서 verbatim · 괄호는 섹션 분량 예산)

**분해유형 판정(1회)**: 기본은 **B 변경점 나열형**(아래 골격). 요청이 시스템 경계 자체를 다시 그리면 **A 전면 재설계형** — AS-IS 핵심 문서의 5부 골격(§0~§5)을 그대로 쓰되 🟢 신규·🟡 변경 마킹과 §0 변경점 표를 더하고, 상세 파일도 코어 5부에 1:1(`{0..5}-{slug}`)로 만든다. 혼용 금지, 판정 1줄을 인덱스 옆에 남긴다.

```
# {시스템} TO-BE — {이번 설계를 한 구절로} ({DATE})
> 설계 요청: {원문 요약 1줄} · 기준: [AS-IS](../as-is/system-design-as-is.md) · _evidence-brief.md · 커밋 {hash}

## 0. 한눈에 보기  (SoT 표 제외 ≤50줄)
   ① 세 줄 요약: 어디가 문제인가 / 무엇으로 바꾸나(핵심 아이디어 한 구절) / 무엇이 좋아지고 무엇이 위험으로 남나
   ② 변경 조감 1장: AS-IS 조감과 같은 구도의 mermaid 에 🟢 신규·🟡 변경 마킹(방법론 계층도 금지) + 설명 불릿 + 범례 1줄
   ③ 키워드 표: | 새 개념 | 뜻 |  (≤10개 — 이번 설계가 새로 도입하는 개념·용어)
   ④ 변경점 표(SoT): | C-0X | 무엇을 어떻게 (한 줄) | 근거 | 상태 | 상세 |
      · 근거 = 해소하는 R-0X 또는 요청 키워드 · 상태 = 반영 | 부분 | 보류 | 잠정(검증 필요)
      · 각론에 못 실린 변경점이라도 롤백 불가·비가역 이행 위험이 있으면 "무엇을 어떻게" 열에 ⚠️ + 위험 한 구절을 남긴다
   ⑤ 요청 커버리지 표(SoT) — 요청 항목과 변경점이 1:1 이 아닐 때만: | 요청 항목 | 관련 C-0X | 종합 상태 |
      · 행 수 = 설계 요청 항목 수. 표에 없는 요청 항목 = 미반영으로 간주(P0)
      · 종합 상태 = 관련 C 중 가장 보수적인 값(보류 > 부분 > 잠정 > 반영)

## 1. 변경점 각론 — 하나씩 뜯어보기  (영향도 상위 최대 5개 × 블록 ≤10줄)
   (영향도 = 해소하는 이슈의 심각도 > 사용자가 겪는 변화 크기 > 구현 범위 순으로 판단)
   ### C-01 {이름} — **{한 줄 결론}**
   - 왜: 현재의 문제 (R-0X 또는 요청 배경)
   - 무엇을: 바꾸는 대상과 결과 모습
   - 어떻게: 핵심 수단 1~3개 (새 개념은 §0 키워드 표의 용어로)
   - 위험·이행: 잔여 리스크·롤백·마이그레이션 한 줄 (해당 시)
   - 상세: <상세 파일 링크>
   (나머지 변경점은 §0 변경점 표 한 줄 + 상세 링크로 갈음하고 여기 안 싣는다.
    제목+링크만 나열 금지 — 핵심 문서만 읽어도 주요 변경의 설계가 이해돼야 한다)

## 2. 바뀐 뒤 전체 흐름  (관통 jobflow 제외 ≤5줄)
   흐름이 바뀌면: 진입→핵심 결과 관통 jobflow 1장(변경 지점 표시) + 설명 불릿.
   흐름 변경이 없으면 제목 유지 + "변경 없음 — AS-IS §3 <링크>" 한 줄.
## 3. 바뀐 뒤 화면  (관통 navigation 제외 ≤5줄)
   화면·이동이 바뀌면: 전체 navigation 1장 + 설명 불릿. 없으면 "변경 없음 — AS-IS §5 <링크>" 한 줄.
## 4. 바뀌지 않는 것  (≤8줄)
   | 영역 | 유지 이유 한 구절 | AS-IS 링크 |  (재서술·다이어그램 금지)

## 상세 파일 인덱스  (≤10줄)
   | 파일 | 변경점 | 담는 것 |   + 분해유형 판정 1줄
```

- 추적성: 이슈 `R-0X` ↔ 변경점 `C-0X` 매핑은 §0 변경점 표가, 요청 항목 축은 커버리지 표가 SoT 다.
- §2 jobflow 헤더: `orchestrator:`/`scope:` 명시.

## 4. 작업 절차

### Step 2. TO-BE 핵심 문서 — `to-be/system-design-to-be.md`
- 입력: 첨부 AS-IS 산출물 + `_evidence-brief.md` + 설계 요청. §3 골격대로 작성한다.
- **분해는 method-R 로, 표현은 쉬운 말로**: "요청을 만족하려면 어디가 바뀌는가"를 매크로→시스템→모듈→상세 순서로 판단하고(불균등 깊이·멈춤 휴리스틱, 통신모드 재결정 포함), 그 용어를 결론 구역에 노출하지 않는다.
- 발견된 원칙 위반의 해소는 각론의 "왜/어떻게"에 쉬운 말로 녹이고, 어느 세트·어느 원칙인지는 상세 파일 부록에 명시한다.
- 요청 무관 부분은 §4 "바뀌지 않는 것" 표 한 줄로 끝낸다(변경 최소화).

### Step 3. TO-BE 상세 파일 (독립 파일 병렬 작성)
- **한 변경점 = 한 파일**: B형 `system-design-to-be-c{##}-{slug}.md`(C-01→`c01`) / A형 `{0..5}-{slug}`. slug 은 소문자 kebab-case 3~5단어(한글 금지). 혼용 금지.
- 서두 인용블록: `> 대상: C-0X (해소 R-0X 또는 요청)` + `> 핵심 파일: <경로>` + `> 읽는 법: ../../_dsl-읽는법.md`(DSL 을 쓰는 파일만) → 이어서 `## 0. 한눈에 보기`(AS-IS 문제 → TO-BE 해법 요지 3~5불릿 — 결론 구역 규칙 적용). 본문 소제목은 한국어 질문형으로.
- 담는 것: 변경점의 전체 설계 — 계층·조각별 `jobflow`, `navigation`·`state`, 데이터 모델(`erDiagram`)·API·경계 계약(데이터 소유권·메시지 계약·실패 처리), 마이그레이션 단계, 예외·실패 흐름, 통신 방식 결정 근거 1줄, 말미 `## 부록: 분해 근거`·`## 부록: 근거`.
- **DSL self-check**: jobflow round-trip 금지(매 단계 조율자로 되돌리지 않고 직접 연결) / navigation 은 API·`(process)`·백틱 `message` 노드 보존, 분기 라벨 괄호 금지, 전체→시나리오 순서(시나리오마다 트리거·화면/API·분기·예외 설명) / state 시작·종료 누락 금지.
- **계층 중복 금지**: 같은 흐름을 계층마다 다시 그리지 않는다 — 상위에 없던 분기·반환·경계 메시지가 처음 드러나는 경우에만 추가.
- 150줄 초과 파일은 서두에 목차. 500줄 초과 시 **응집 우선 분할** — 하나의 계약·상태기계·흐름을 여러 파일로 가르지 않는다. 응집 판단으로 분할하지 않은 500줄 초과 파일은 목차가 있으면 상한 위반으로 치지 않는다.

### Step 4. 교차 검증 (Critic) — `review/cross-review-iter-{N}.md`
비판적 Critic 시각으로 Step 2·3 + 첨부 AS-IS + 브리프를 교차 검증한다(AS-IS 결함의 전파 여부 포함). N 은 1부터.

- **frontmatter(파일 첫 줄, YAML)**: `iteration` / `status: clean|dirty` / `p0_count` / `p1_count`.
- **마커**: `### **P0-{slug}**` 아래 `- 근거:` / `- 위치:` / `- 수정 방향:`. slug prefix `as-is-`/`tobe-`/`cross-`.
- **판정 기준 정의**: *필러 다이어그램* = 하단 불릿이 노드 재진술뿐이고 새 분기·순서·조건·반환을 못 담는 것. *방법론 계층도* = 노드 레이블이 L1~L4·매크로/시스템/모듈/상세 등 방법론 어휘인 다이어그램(실제 구성요소 이름이면 허용). *새 정보* = 상위 계층에 없던 분기·반환·경계 메시지.

**① 기계 확인** (명령으로): `wc -l` 총량·상한 / §3 골격 제목 존재(placeholder 한 줄 통과) / §0 필수 요소 순서 / 커버리지 표 행 수 = 요청 항목 수 / 커버리지 표 종합 상태 ↔ 변경점 표 C 상태 정합(가장 보수적인 값인지) / C-0X ↔ 상세 파일명 대응 / 링크 파일 실존 / 고아 상세 파일 없음.

**② 의미 확인** (요청·AS-IS·브리프·가이드 대조로):

**P0 (반드시 수정)**
- 요청 항목이 커버리지 표(1:1 이면 변경점 표)에 누락 / 미반영·부분반영을 "반영"으로 오기
- R-0X ↔ C-0X 추적 불일치 / 분해유형 혼용 / 핵심 문서 200줄 초과 / `## 0` 필수 요소 누락·순서 위반 / 골격 제목 이탈
- 변경점 각론이 제목+링크 나열뿐(주요 변경의 설계를 핵심 문서에서 이해 불가)
- **상세 유실**: 핵심이 "상세로 옮긴" 각 항목이 상세 파일에 실재하는지 목록 대조 — 링크만 있고 내용이 요약 재탕이면 위반
- **설계 건전성**(표면 언어와 무관하게 채점): method-R 단계 순서 역전·건너뛰기 / 통신모드 위반(경계는 메시지, 내부 상세는 이벤트) / 조각 간 직접 호출(method-R 원칙3·O-W 수평적 고립) / Choreography 에 결과 연결자(원칙5)
- AS-IS 깊이 날조 전파 / 근거 브리프 미참조·환각 인용 / job flow 를 `jobflow` 아닌 sequenceDiagram 으로 그림

**P1 (권장)**
- 결론 줄 부재·제목 재진술 / 결론 구역에 키워드 표 밖 전문용어 / 맨몸 ID 인용 / 국소 상한 초과
- 변경 없는 영역의 재서술·필러 다이어그램 / 중복 서술 / 깨진 링크 / 다이어그램 하단 설명 누락·노드 재진술 / 범례 없는 색·이모지 / DSL 읽기 링크·표기 통일 위반
- 6원칙 일부 위반(어느 세트·원칙인지 명시) / 불균등 깊이 미적용(단순 조각 과분해) / 보조 계약 누락(데이터 소유권·메시지 계약·실패 처리) / 통신 방식 결정 근거 누락
- DSL self-check 위반 / 분해 근거가 본문 흐름에 혼입 / 근거 전용 표가 본문에 등장 / AS-IS↔TO-BE 다이어그램·본문 충돌
- **재구성 테스트 실패**: §0 만 읽고 "무엇이/왜/어떻게 바뀌나" 3문장을 재구성할 수 없음

**결산**: 말미에 `P0 {n}건, P1 {n}건. status={clean|dirty}.` 한 줄(frontmatter 와 자기정합). clean 이면 회귀검사 표(체크 항목|위치|결과 ✅)로 신규 회귀 0건 증명.

### Step 5. 반복 및 종료
- **종료 판정(단일 술어)**: `clean := status=="clean" AND p0_count==0 AND p1_count==0 AND 이번 회차 지적 영역의 활성 P0-/P1- 마커 0`. frontmatter↔본문 불일치 시 본문 카운트 채택. iter-1 이 clean 이면 즉시 종료.
- **반복(최대 3회 = iter-1..4)**: dirty 면 ① 지목 섹션만 덮어쓰기(무관 섹션 동결) ② 영향 상세 파일만 재작성 ③ §0 표·상세 인덱스 동기화 ④ 다음 `cross-review-iter-{N+1}.md`(직전 대비 diff 중심). iter-4 는 dirty 여도 종료 처리.
- frontmatter 파싱 불가·필드 누락 시 해당 회차 내 1회 보정 재작성(iter 상한 미가산).
- **보존**: 본문·상세는 최신만(덮어쓰기), review 는 회차별 보존(최대 4). `_evidence-brief.md`·첨부 AS-IS 는 불변 — AS-IS 결함은 마커로 보고만.
- **종료 보고**: 미해결 P0/P1 + 의도적 미분해 + 설계 요청 중 미반영·보류·잠정 항목을 사용자에게 명시 보고.
