# TO-BE 설계 문서 생성 프롬프트

다이어그램을 작성하거나 수정할 때 [예제 폴더](../examples/)의 현재 목차와 문서 제목을 살펴 비슷한 조건을 다룬 절을 먼저 참고한다. 해당 예제가 없으면 전용 가이드와 대상 자료로 진행한다. Navigation·State·Job Flow의 최종 문서 표기는 [설치된 출력 형식](../guides/diagram-output-guide.md)을 따른다.

요구사항과 제약을 바탕으로 신규 시스템 또는 기존 시스템의 목표 구조를 설계한다. AS-IS 문서는 있는 경우 참고하며, 별도 작성을 선행 조건으로 삼지 않는다. 확인된 현황과 제안·가정·미확정 사항을 구분한다.

책임 분리·공개 계약·시나리오 검증은 [모듈 경계 가이드](../guides/module-boundary-guide.md)를 따른다. 문서 내용은 이 프롬프트, 파일 배치는 아래 공통 가이드를 기준으로 한다.

## 파일 저장 위치

[공통 산출물 배치 가이드](../guides/system-design-output-guide.md#저장-위치와-고정-구조)의 고정 구조를 적용해 `docs/design/{DATE}/to-be/`에 작성한다. 날짜·폴더 재사용·상대 링크·파일 분리 규칙은 이 가이드를 따른다. 아래에서는 각 문서의 내용을 정의한다.

## system-design-to-be.md

`system-design-to-be.md`에는 다음 내용을 담는다.

- 개요: 목적·설계 범위·신규 설계 또는 기존 시스템 개선 여부
- 요구사항과 제약: 주요 요구와 성공 기준
- 시스템 구조
  - Mermaid로 작성한 목표 시스템 구성도와 간단한 설명
  - 서비스·모듈별 책임·공개 계약·데이터 소유권
- 핵심 용어 목록
- 기능 목록
- 주요 설계 결정: 검토한 대안과 선택 이유·비용·위험
- 구현 및 검증 계획: 작업 순서·시나리오별 검증 방법·미확정 사항

기존 시스템을 개선한다면 유지·변경·추가·제거할 부분을 구분하고, 필요한 호환성·데이터 이전·복구 계획을 적는다. 검증 계획과 실제 수행한 결과를 구분하며, 렌더링하지 않은 다이어그램은 정적 검토로 기록한다.

## scenario-state-analysis.md

**시나리오 기반 상태 전이 분석서**를 작성하고 `system-design-to-be.md`의 관련 기능에서 해당 시나리오 절로 연결한다. 사용자가 겪을 수 있는 상황을 폭넓게 찾아 요구사항·설계 결정에 따른 상태 변화와 사용자가 확인할 기대 결과를 E2E 사례로 정리한다. 결과나 다음 행동이 정해지지 않은 상황은 설계 검토 항목에 남긴다. AS-IS 자료 없이도 작성할 수 있다. [참여자별 시도와 독립 사건](../guides/scenario-state-analysis-guide.md#참여자별-시도와-독립-사건)을 사례 ID와 대조한다. 검증용이면 [상세 사례 판정 기준](../guides/scenario-state-analysis-guide.md#시스템-검증용-사례의-깊이)에 따라 불변조건·금지 전이·복합 사건의 관찰값을 명시한다. 고객의 비정상 순서·잘못된 대상 선택, 운영자와 외부 제공자가 먼저 일으키는 사건, 두 주체의 요청이 겹치는 결과를 포함한다. [공통 작성 가이드의 TO-BE 기준](../guides/scenario-state-analysis-guide.md)

각 그림에 [상태도 하단 설명](../guides/state-diagram-guide.md#상태도-하단-설명)을 붙이고, 사례의 준비·판정 가능 여부에 따라 [테스트 케이스와 설계 검토 항목](../guides/scenario-state-analysis-guide.md#테스트-케이스와-설계-검토-항목)의 소제목을 적용한다.

## job-flow 폴더

[Method-R](../guides/method-R.md)의 설계 깊이에 따라 `to-be/details/job-flow/`에 작성한다. 표기는 [Job Flow 가이드](../guides/job-flow-diagram-guide.md)를 따른다.

각 파일에서 [업무 사건과 시나리오의 범위](../guides/method-R.md#11-먼저-그릴-사건을-고른다)에 따라 제목을 나눈다. 한 업무의 신청부터 결과 확인까지 같은 그림에서 따라가되, 나중에 사용자가 입력하거나 외부가 통지하는 지점은 독립된 사건으로 표시한다. 정상 흐름과 주요 실패 흐름을 표현한다. 매크로뷰와 서비스뷰에서는 요구사항·설계 결정에 따른 [수신 객체의 판단과 결과별 후속 메시지](../guides/method-R.md#25-처리-결과의-분기로-메시지를-보내는-이유를-드러낸다)를 연결한다. 각 그림 아래에서 [굵은 출발점 → 도착점 표제와 설명](../guides/job-flow-diagram-guide.md#다이어그램-하단-설명)을 화살표와 대조한다.

| 파일 | 작성 내용 |
|---|---|
| `macro.md` | [매크로 시나리오 작성과 검토](../guides/method-R.md#33-매크로-시나리오-작성과-검토)에 따라 목표 업무의 시작 사건부터 결과를 받는 주체까지 설계한다. 분기와 인계는 해당 요구사항·설계 결정에 연결하고, 가정한 외부 역할·미확정 계약을 명시한다. |
| `system.md` | [시스템뷰의 작성과 검토](../guides/method-R.md#시스템뷰의-작성과-검토)에 따라 매크로의 시스템을 목표 서비스로 분해한다. 주요 사건마다 내부 서비스 간 요청·회신 또는 [구독 사건](../guides/job-flow-diagram-guide.md#시스템-수준의-이벤트-수신)을 따라 상태의 결정 주체와 최종 결과를 확인한다. 사용자가 설계 대상을 서비스 하나의 내부로 한정하여 서비스 간 협력이 범위 밖이면 본문에 그 이유를 기록한다. |
| `<service-name>.md` | 서비스마다 파일을 생성하고, 해당 서비스의 내부 흐름을 시나리오별로 표현한다. 파일명에는 서비스의 영문 이름을 사용한다. |

사용자가 매크로뷰와 시스템뷰까지만 요청한 경우에는 `macro.md`와 `system.md`에서 마친다. 서비스 내부 확대까지 요청 범위에 포함된 경우 파일 분리는 서비스 단위까지만 한다. 각 서비스의 내부는 모듈과 상세 수준으로 필요한 만큼 재귀적으로 확대하되, 시나리오·확대 대상별로 하위 제목을 나누어 해당 서비스 파일에 모두 담는다. 시나리오·모듈·상세별로 Job Flow 파일을 추가하지 않는다.

## navigation.md

설계한 화면 이동 흐름을 `to-be/navigation.md` 한 파일에 작성한다. 표기는 [Navigation 가이드](../guides/navigation-diagram-guide.md)의 `navigation` 문법을 따른다.

- [시나리오별 상세 분석](../guides/navigation-diagram-guide.md#시나리오별-상세-분석)에 따라 설계 범위의 과업별 이동·분기·관련 API/처리·결과와 복귀를 설계한다. 유지 시나리오도 포함하며 대표 흐름만으로 대신하지 않는다.
- 출력은 [간소화 구성·화면 확인 링크 기준](../guides/navigation-diagram-guide.md#문서-구성과-화면-확인-링크)을 따른다. `시나리오 색인`, `공통 가드와 표기`, `페이지 노드 대응`, `실제 작업 진입점 조사 목록`은 생성하지 않는다. 각 시나리오에 `진입·결과`, `화면·장면`, `근거` 표·절을 별도로 만들지 않고, 다이어그램과 바로 아래의 짧은 흐름 설명에 필요한 조건·결과를 담는다.
- 각 시나리오의 `화면 확인 링크` 표에 페이지별로 한 행을 두고, 기본 화면과 사용하는 장면의 HTML 직접 링크를 한 셀에 모으며 Layout 절을 연결한다. 설계 근거·가정·미확정 사항은 이 설계서에 기록한다.

UI가 없으면 해당 없음과 이유를 기록한다. UI가 있지만 화면 이동이 없는 과업은 현재 페이지의 동작·결과 장면을 설명하고 Layout·HTML로 연결한다.

## screen-layout.md

설계 범위의 모든 화면 배치를 `to-be/screen-layout.md` 한 파일에 작성한다. 처음에 [전체 페이지·장면 목록](../guides/system-design-output-guide.md#페이지장면-목록)을 두고, 표기는 [스크린 레이아웃 가이드](../guides/screen-layout-guide.md)의 `layout` 문법을 따른다.

- 화면별로 하위 제목을 나누고, 각 화면의 목표 영역 배치와 포함 관계를 그린다.
- 각 다이어그램 아래에는 영역별 역할·입출력·상호작용을 설명한다. 적용되는 로딩·빈값·오류·권한 상태와 반응형 배치 차이도 함께 적는다.
- 같은 화면의 배치 설명은 이 파일의 해당 절을 원본으로 두고, 다른 문서에서는 링크로 참조한다.

UI가 없으면 화면 0개라는 사실과 이유를 기록하고, 가상의 화면을 만들지 않는다.

## details/screens 폴더

[화면별 HTML 규칙](../guides/system-design-output-guide.md#화면별-html)에 따라 목표 화면의 실제 모양을 표현하는 바닐라 HTML을 `to-be/details/screens/`에 생성한다. 전체 화면과 Navigation 등장 화면의 누락·링크·화면 확인은 [공통 검증 기준](../guides/system-design-output-guide.md#검증)으로 확인한다.

Markdown 문서·다이어그램의 tools.camp 링크 생성 여부 확인과 전달은 [편집 링크 전달 기준](../guides/diagram-editor-link-guide.md)을 따른다.
