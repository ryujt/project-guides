# TO-BE 설계 분석 문서 생성 프롬프트

AS-IS와 변경 요구를 근거로 목표 구조를 설계한다. **어떤 변경이 어떤 모듈 안에서 끝나고, 어떤 공개 계약만 함께 알아야 하는지** 드러내는 것이 목표다. 문서·모듈 수를 늘리는 것으로 품질을 평가하지 않는다.

## 입력과 실행 규칙

- 입력: [AS-IS](./system-design-as-is-prompt.md) 산출물 또는 동등한 현재 구조 자료, 변경 요구·성공 기준·제약, 근거 코드/테스트.
- AS-IS의 날짜/커밋과 현재 상태를 대조한다. 오래된 부분은 관련 코드로 재확인하고 차이를 기록한다. AS-IS와 관찰된 결함을 목표 설계의 사실로 복제하지 않는다.
- [모듈 경계 가이드](../guides/module-boundary-guide.md)의 최소 맥락과 계약을 사용한다. 관련 모듈·공개 계약부터 읽고 호출자·소비자·조립 지점을 검색한다. 필요한 근거가 생기면 본문 범위를 확장한다.
- 이미 허용된 설계는 자율 진행한다. 코드와 원본 AS-IS는 보존한다. 기존 사용자 변경을 덮어쓰지 않는다. 중요한 미확정 정책은 잠정안·영향·필요 입력으로 남긴다.
- 독립 조사/대안 비교는 병렬화할 수 있다. 공유 계약을 정한 뒤 파일별 쓰기 담당을 나누고 종속 설계의 일관성을 통합 담당자가 확인한다.

## 1. 변경 요구와 대안

`요구 ID · 현재 문제/근거 · 성공 기준 · 우선순위`를 정리한다. 기존 이슈 ID가 있으면 유지한다. 모든 AS-IS 결함을 이번 요구로 자동 승격하지 않는다.

각 중요한 구조 결정은 다음을 비교한다.

- 현 구조의 작은 수정으로 해결하는 안.
- 경계/소유권을 재배치하거나 계약을 바꾸는 안.
- 필요할 때 독립 모듈/프로세스로 분리하는 안.

비교 기준은 변경 이유의 응집성, 의존 방향, 필요한 작업 맥락, 검증 가능성, 이행/운영 비용이다. 미래 확장 가능성만을 이유로 추상화·큐·분산 저장소를 추가하지 않는다.

## 2. 목표 경계와 계약

[method-R](../guides/method-R.md)로 필요한 깊이만 분해하고 [O-W 가이드](../guides/orchestrator-worker-pattern-guide.md)의 적용 경계를 명시한다. 메시지·직접 호출·이벤트 선택은 실제 실패/배포/응답 계약에 따른다. 조율자 시나리오 안의 Worker 고립과 모든 코드의 직접 호출 금지를 혼동하지 않는다.

모듈별로 다음을 설계한다.

| 관점 | 필요한 결정 |
|---|---|
| 책임 | 소유 규칙과 함께 바뀌는 이유 |
| 공개 계약 | 입력·출력·오류·부작용·호환성 |
| 데이터/상태 | 권위 소유자, 단일 쓰기 책임, 읽기 경로 |
| 의존 방향 | 호출자/소비자, 포트/adapter, 조립 위치 |
| 실패 | 타임아웃·취소·재시도·중복/역순·부분 실패 책임 |
| 검증 | 모듈 단독 검사, 계약 검사, 필요한 통합 검사 |
| 작업 맥락 | 담당자가 읽어야 할 계약·구현·테스트와 확장 조건 |

분할 후 항상 여러 조각의 내부를 함께 읽고 수정해야 하면 계약 보완 또는 병합을 검토한다. 모듈 하나가 너무 많은 규칙·상태를 소유하면 변경 이유별로 분리한다. 파일 길이나 역할 이름만으로 판정하지 않는다.

## 3. 이행과 호환성

공개 계약·데이터·프로세스가 바뀌는 경우에만 필요한 항목을 설계한다.

- 기존/신규 소비자 호환, 배포 순서, 데이터 이전, 마이그레이션 검증.
- 상태/쓰기 소유권을 옮기는 동안의 권위와 이중 쓰기 방지.
- 단계별 완료 기준, 되돌릴 수 있는 범위, 불가역 시점과 실패 복구.
- 비교 테스트·운영 관측·점진 전환이 필요한 근거.

“롤백 가능”이라고 쓰려면 무엇을 어떻게 되돌리는지 명시한다. 파괴적 이전이나 외부 실행은 설계와 실행 권한을 구분한다.

## 4. 문서와 다이어그램

기본 핵심 경로는 `docs/design/{DATE}/to-be/system-design-to-be.md`다. AS-IS와 같은 기준 날짜 또는 명시한 새 날짜를 사용하고 기존 문서 위치/사용자 지정을 우선한다.

약 200줄의 핵심을 목표로 아래 순서로 작성한다. 작은 설계는 한 문서로 충분하다.

1. **한눈에 보기**: 문제 → 선택한 해법 → 기대 효과/남은 위험.
2. **변경점 표**: `C-ID · 무엇을 바꾸나 · 근거 요구/이슈 · 소유 모듈 · 상태 · 상세`.
3. **주요 설계 결정**: 대안·선택 근거·경계/계약 차이.
4. **바뀐 뒤 흐름·데이터·화면**: 변경된 관점만 작성하고 유지 영역은 AS-IS 링크.
5. **이행·검증·작업 인계**: 독립 작업 순서와 완료 기준, 미확정 사항.

상태는 `반영/부분/보류/잠정`으로 구분한다. 요구와 변경점은 다대다일 수 있으므로 누락이 없도록 매핑한다. 핵심 문서에 담기 어려운 계약·흐름만 독립 모듈/변경 단위의 상세 파일로 분리한다. 같은 계약을 여러 변경점 파일에 복제하지 않는다.

- 구조·의존은 Mermaid `flowchart`, 필요한 데이터 관계는 `erDiagram`.
- 협력 흐름은 [jobflow](../guides/job-flow-diagram-guide.md), 사용자 이동은 [navigation](../guides/navigation-diagram-guide.md), 한 소유자의 상태는 [state](../guides/state-diagram-guide.md), 배치는 [layout](../guides/screen-layout-guide.md).
- 사용자 DSL을 다른 형식으로 치환하지 않는다. 외부 시스템의 시간순 통신은 필요할 때 별도 `sequenceDiagram`으로 설명한다.
- 첫 도표에 관련 가이드 링크를 달고 변경 범위/범례/핵심 분기를 짧게 설명한다. 전체 흐름 뒤에 실제 새 정보를 주는 상세만 추가한다.

## 5. 교차 비판·수정·평가

[협업 프롬프트](./multi-agent-task-prompt.md)에 따라 작성자 외 검토자가 AS-IS·요구·TO-BE를 대조한다. 독립 검토 도구가 없으면 순차 역할 검토임을 밝힌다.

검토는 `ID · 위치 · 반례/근거 · 영향 · 필수/권장 · 처리 · 재검증`으로 남긴다. 짧은 작업은 본문/최종 보고로 충분하고 장기 작업은 기존 review 문서를 갱신한다. 회차마다 새 파일을 의무 생성하지 않는다.

필수 확인:

- 요구가 누락되거나 부분 반영을 완료로 기록하지 않았는가?
- AS-IS의 실제 제약을 고려했으며 근거가 없는 효과/호환성을 단정하지 않았는가?
- 공개 계약·소유권·의존 방향·실패 책임이 일치하는가?
- 과분해, 전역 store/이벤트 버스의 숨은 결합, 불필요한 조율자가 없는가?
- 한 모듈 구현에 필요한 맥락이 작아지고 독립 검증이 가능한가?
- 이행/롤백과 직접 소비자 검증이 필요한 변경에서 빠지지 않았는가?
- 핵심·상세·도표·링크가 실제로 일치하는가?

기계 확인은 링크·펜스·매핑 누락을 찾는 보조 수단이며 설계 의미 검토를 대체하지 않는다. 렌더러를 실행하지 않았다면 문법 대조와 렌더링 미검증을 구분한다.

[모듈 경계 가이드](../guides/module-boundary-guide.md)의 평가축으로 변경 전후를 비교하고 근거를 남긴다. 점수·검토 회차 상한은 완료 조건이 아니다. 필수 결함을 수정한 뒤 영향 부분만 재검증한다. 같은 접근의 반복 상한에 이르면 원인/범위/해결 경로를 바꾸고, 유효한 다음 작업이 없으면 미완료와 필요한 입력을 보고한다.

최종 보고에는 설계 결과, 대안 선택 이유, 핵심 비판의 처리, 검증/한계, 구현할 독립 작업과 미확정 결정을 남긴다.
