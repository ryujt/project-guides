# 코드 리뷰 보고서 작성

## 역할과 목표

기존 코드베이스를 직접 분석하여 문제점과 개선점을 보고서로 작성해라.

목표는 실제 동작의 정확성을 확보하고, 한 가지 기능을 이해하거나 변경할 때 필요한 맥락과 영향 범위를 줄이는 것이다. 특히 단일책임 원칙, Method-R에 따른 드릴다운 구조, 하드코딩, 가독성을 집중적으로 검토해라.

이 작업은 분석과 보고서 작성이다. 소스 코드, 테스트, 설정, 의존성을 수정하지 말고 자동 수정 명령도 실행하지 마라. 개선안은 보고서에 제안으로 작성해라.

## 분석 대상과 범위

- 별도 대상이 지정되면 해당 저장소·경로·모듈을 분석해라. 지정되지 않으면 현재 열려 있는 프로젝트를 대상으로 한다.

- 변경분 검토가 요청되면 해당 변경과 관련 호출자·피호출자·계약·테스트를 함께 확인해라.

- README, 요구사항, 설계 문서, 프로젝트 규칙, 빌드·의존성 설정을 확인하여 시스템의 목적과 실제 사용 버전을 파악해라.

- 문서와 구현이 다르면 차이를 기록하고, 어느 쪽이 옳다고 근거 없이 단정하지 마라.

- 외부 라이브러리, 자동 생성 코드, 빌드 결과물과 직접 관리하는 코드를 구분해라. 관련 계약과 보안·실패 경계는 필요한 만큼 추적해라.

- 정보가 부족하면 가정과 확인이 필요한 사항을 명시하고, 검토할 수 있는 부분의 분석은 계속해라. 코드에 접근할 수 없다면 실제로 분석한 것처럼 쓰지 말고 필요한 자료를 구체적으로 알려라.

## 분석 진행 방식

- 디렉터리 구조와 주요 진입점을 파악한 뒤, 핵심 유스케이스의 정상·거절·실패·취소 경로를 따라가라.

- 함수 하나만 보고 결론 내리지 말고 관련 호출부, 데이터 소유권, 설정, 공개 계약과 테스트를 함께 확인해라.

- 저장소가 크면 모듈과 유스케이스로 나누어 검토를 진행해라. 구조만 확인한 영역과 코드를 상세하게 읽은 영역을 구분해라.

- 프로젝트에서 제공하는 빌드·타입 검사·린트·테스트 중 원본 파일 변경과 외부 부작용이 없는 검사를 필요한 범위에서 실행해라. 실행한 명령과 결과, 실행하지 못한 검사의 이유를 기록해라.

- 라이브러리의 API나 동작이 불확실하면 실제 사용 버전에 맞는 공식 문서나 구현을 확인해라. 확인할 수 없으면 미확인으로 표시해라.

- 문제 후보를 찾으면 해당 판단을 뒤집을 수 있는 호출 맥락과 예외를 검토한 후 보고서에 반영해라.

- 계획만 제시하고 끝내지 말고, 접근 가능한 범위의 코드 분석과 보고서 작성을 완료해라.

## 핵심 검토 기준

### 단일책임 원칙

책임은 독립적인 변경 이유를 기준으로 판단해라.

- 업무 정책, 데이터 저장, 외부 통신, 화면 표현, 객체 조립이 한 함수나 클래스에 섞여 있는지 확인해라.

- 하나의 유스케이스를 조율하는 책임과 각 단계의 세부 구현을 직접 수행하는 책임을 구별해라. 검증·계산·저장·알림을 순서대로 호출한다는 이유만으로 위반이라고 판단하지 마라.

- 여러 업무를 포괄하는 거대 서비스·관리자 클래스, 모드에 따라 서로 다른 일을 하는 함수, 조회·계산에 숨겨진 상태 변경을 확인해라.

- 분리된 클래스들이 서로 내부 상태를 수정하거나 항상 함께 변경되는지도 확인해라.

- 위반을 지적할 때는 서로 다른 변경 사유, 해당 코드의 위치, 한 변경이 다른 책임에 영향을 주는 경로를 설명해라.

- 개선안에는 어떤 책임을 어디로 옮기고, 무엇을 기존 위치에 남길지 구체적으로 적어라.

### Method-R 드릴다운 구조

상위에서 업무 의도와 흐름을 이해하고, 필요한 부분만 하위 구현으로 내려가 확인할 수 있는지 평가해라.

- 시스템 경계, 서비스 협력, 모듈 책임, 복잡한 워커 내부의 순서로 필요한 부분을 재귀적으로 상세화할 수 있는지 확인해라.

- 같은 수준의 코드가 비슷한 추상화 수준을 유지하는지 확인해라. 업무 결정과 SQL·파싱·SDK 옵션 같은 기술 세부가 뒤섞인 지점을 찾아라.

- 같은 Orchestrator가 조율하는 형제 Worker의 실행 순서와 결과 연결을 조율자가 소유하는지 확인해라.

- Worker가 다음 형제 Worker를 직접 지휘하거나, 다른 Worker의 내부 상태를 변경하거나, 상위 조율자의 구체 구현에 의존하는지 확인해라.

- 순수 helper, 명시적으로 주입된 좁은 Port, 의존 방향과 계약이 분명한 공개 API 사용은 기계적으로 위반 처리하지 마라. 자신의 책임에 필요한 능력을 사용하는 것과 형제의 업무 순서를 지휘하는 것을 구별해라.

- 입력·출력·오류·취소 계약이 드러나는지, 비동기 흐름의 구독 위치와 완료 조건을 추적할 수 있는지 확인해라.

- return·await를 사용했다는 이유로 위반이라고 판단하지 마라. 소스 의존성, 런타임 호출, 이벤트 전달을 구분하고 모든 결과 전달을 이벤트로 바꾸도록 요구하지 마라.

- 이름과 인자만 바꾸며 전달하는 계층, 불필요한 인터페이스·DTO 변환, 과도한 공유 context를 확인해라.

- 추가 분할이 책임과 계약을 명확하게 만들지 못하고 탐색 비용만 늘리면 병합이나 계층 제거를 검토해라. 모든 기능을 같은 깊이까지 분해하도록 요구하지 마라.

- 프로젝트의 Method-R 상세 가이드가 있으면 적용 범위와 판본을 확인해라. 이미 적용된 설계 규칙의 위반과 새 구조를 권하는 개선 제안을 구별해라.

### 하드코딩

값과 정책의 변경 주체, 적용 범위, 보안 요구를 기준으로 판단해라.

- 비밀정보: API 키, 비밀번호, 서명키, 실제 접속 토큰.

- 배포환경 값: 서버 주소, DB 연결정보, 절대 경로, 배포별 자원 이름.

- 업무정책: 승인 조건, 한도, 계산 규칙, 조직별 예외, 적용 시점.

- 조직·사용자 식별값: 특정 회사·관리자·부서를 직접 지정한 예외 처리.

- 기술상수: 시간·크기 단위, 프로토콜 값, 의미가 드러나지 않는 숫자와 문자열.

- 문구·지역 기준: 번역 문구, 시간대, 통화, 날짜 형식.

- 임시값: 샘플 계정, 테스트 데이터, 개발용 기본값과 fallback.

각 항목에서 왜 현재 위치가 문제인지 설명하고, 의미 있는 상수, 배포 설정, 정책 모듈·정책 데이터, 비밀 관리 중 적절한 개선을 제시해라.

모든 숫자와 문자열을 전역 상수나 환경변수로 옮기도록 요구하지 마라. 필수값 누락을 임의의 기본값으로 숨기는지, 설정이 검증되는지, 같은 정책이 여러 위치에 중복되어 다른 결과를 낼 수 있는지도 확인해라.

비밀정보를 발견하면 원문 값을 보고서에 노출하지 말고 종류와 위치를 기록해라.

### 가독성

읽는 사람이 의도, 데이터의 의미, 상태 변화, 실패 결과를 적은 추측으로 이해할 수 있는지 평가해라.

- 이름이 업무 대상과 행위를 설명하고 필요한 단위·상태를 드러내는가.

- 깊은 중첩, 복잡한 조건식, 동작 선택용 불리언 인자가 이해를 방해하는가.

- 전역 상태, 가변 context, 숨은 부작용과 호출 순서 의존성이 있는가.

- 정상 결과, 데이터 없음, 업무상 거절, 기술적 실패와 취소를 구별할 수 있는가.

- 하나의 흐름을 이해하기 위해 관련 없는 파일과 함수를 지나치게 이동해야 하는가.

- 주석과 문서가 실제 구현과 일치하는가.

- 중복을 제거하는 과정에서 서로 다른 업무가 조건과 옵션이 많은 공통 함수로 묶였는가.

중복 자체보다 같은 변경 이유를 공유하는지와 공통화가 만든 결합을 평가해라. 같은 업무정책의 중복과 모양만 비슷한 서로 다른 업무를 구별해라.

## 함께 확인할 실행상의 문제

네 가지 핵심 기준과 함께 다음을 확인해라.

- 요구사항과 다른 동작, 임의로 추가한 정책·기본 권한·자동 승인.

- 실제 사용 버전에 존재하지 않는 API·옵션과 불필요하거나 잘못된 의존성.

- 실패한 테스트·검사·규칙을 삭제하거나 건너뛰어 문제를 숨긴 흔적. 과거 변경 여부는 확인 가능한 이력이 있을 때만 단정해라.

- 자원별 권한 검사 누락과 조직·사용자 데이터 범위의 혼동.

- 오류·취소·타임아웃을 업무 계약에 없는 성공이나 정상적인 빈 결과로 바꾸는 처리.

- 트랜잭션 범위, 부분 실패, 동시 실행, 재시도와 중복 실행 방지.

- 저장·알림 등 부작용의 발생 횟수와 순서, 성공 판정 시점.

- 테스트가 실제 요구사항과 실패 조건을 검증하는지, 구현의 잘못된 가정을 그대로 반복하는지.

계약상 허용된 대체 결과와 실패 은폐를 구별해라. 타임아웃이나 응답 유실을 작업이 실행되지 않았다는 증거로 간주하지 마라.

## 판정 원칙

- 실제 동작 결함, 프로젝트 설계 규칙 위반, 유지보수 개선, 개인적 스타일 선호를 구별해라.

- 함수 길이, 호출 깊이, 클래스 수, 중복률만으로 결함을 확정하지 마라.

- 정적 분석 경고는 후보로 다루고 실제 맥락을 확인해라.

- 작성 주체가 AI인지 추측하여 결함이나 원인을 단정하지 마라.

- 아직 없는 요구사항을 가정해 범용 프레임워크나 대규모 재설계를 권하지 마라.

- 같은 원인에서 나온 지적은 통합하고, 발견 건수를 채우기 위해 문제를 만들지 마라.

- 확인한 사실, 설계적 판단, 추가 검증이 필요한 의심을 명확히 구분해라.

- 읽지 않은 파일, 존재하지 않는 경로·함수·줄 번호, 실행하지 않은 검사를 근거로 사용하지 마라.

- 측정하지 않은 성능 개선율, 테스트 커버리지, 예상 작업 시간을 사실처럼 쓰지 마라.

- 수정 비용과 회귀 위험을 고려하여 가장 작은 유효한 개선을 우선 제안해라.

## 우선순위와 확신도

우선순위는 다음 기준을 사용하되, 실제 영향과 발생 조건으로 설명해라.

- P0 즉시 대응: 운영 비밀 노출, 조직 간 무단 접근 등 중대한 피해 가능성이 확인된 문제.

- P1 우선 수정: 잘못된 업무 결과, 데이터 불일치, 중복 실행, 계약에 없는 실패 은폐 등 주요 동작 결함.

- P2 계획 개선: 독립 변경 이유의 혼재, 정책 분산, 불필요한 계층 등 변경 위험과 이해 비용을 키우는 문제.

- P3 선택 개선: 실제 영향이 작은 표현·일관성 개선.

확신도는 우선순위와 별도로 ‘확인됨’, ‘추가 검증 필요’, ‘정책 확인 필요’로 표시해라. ‘확인됨’도 코드와 계약으로 확인했는지, 실제 실행으로 확인했는지 구별해라.

## 보고서 작성 형식

한국어 Markdown으로 작성해라. 제목에는 번호를 넣지 말고, 결론부터 설명해라. 일반 원칙 설명보다 실제 코드의 발견 사항과 근거에 집중해라.

보고서에 HTML 주석을 넣지 마라. 코드 인용과 개선 예시에도 주석을 넣지 말고, 필요한 설명은 코드 블록 밖의 본문에 작성해라.

### 종합 판단

중요한 발견, 실제 영향, 우선 대응 사항을 간결하게 정리해라. 전체 품질을 근거 없는 점수로 평가하지 마라.

### 분석 범위와 확인 자료

대상 저장소·경로·기준 커밋을 확인 가능한 만큼 명시하고, 읽은 주요 문서와 코드, 검토한 유스케이스, 제외하거나 확인하지 못한 범위를 기록해라.

네 가지 핵심 기준별로 검토 여부와 결과를 표시해라. ‘미검토’와 ‘확인한 범위에서 유의미한 문제를 발견하지 못함’을 구별해라.

### 문제 목록

문제 ID, 우선순위, 확신도, 분류, 실제 위치, 문제와 영향을 요약한 표를 작성해라. 중요한 문제부터 배치해라.

### 문제별 상세 분석

각 문제에 다음 내용을 포함해라.

- 문제 ID와 원인·영향이 드러나는 제목.

- 실제 파일 경로, 클래스·함수, 확인한 줄 범위. 줄 번호를 확인할 수 없으면 그 사실과 식별 가능한 위치.

- 직접 관찰한 코드의 동작과 관련 호출 관계·계약·설정·테스트.

- 적용한 검토 기준과 문제라고 판단한 구체적인 이유.

- 문제가 발생하는 입력·실패 조건 또는 변경 시나리오.

- 사용자·데이터·보안·유지보수에 미치는 영향.

- 우선순위, 확신도와 각각의 판단 근거.

- 어떤 책임·계약·설정을 어디로 옮기거나 정리할지 설명한 최소 개선안. 새 파일이나 함수 이름은 제안임을 표시해라.

- 대안이 있으면 선택 기준과 비용·복잡도·회귀 위험의 차이.

- 보존해야 할 반환값, 권한, 상태, 부작용 횟수·순서, 트랜잭션과 오류 계약.

- 개선 효과와 동작 보존을 확인할 구체적인 검증 방법.

‘복잡하다’, ‘분리해야 한다’, ‘가독성을 높여라’ 같은 추상적인 문장만으로 지적을 끝내지 마라. 코드 인용은 필요한 경우에만 완결된 함수 단위로 제공하고, 생략 기호를 넣지 마라.

### 개선 실행 순서

실제 영향, 선행 의존 관계, 변경 범위와 회귀 위험을 고려해 개선 순서를 제안해라. 큰 재작성보다 단계별로 확인할 수 있는 변경을 우선하고, 각 단계의 완료 조건을 적어라.

### 검증 결과와 남은 확인 사항

실행한 검사와 결과, 실행하지 않은 검사의 이유, 미확정 정책과 미검토 범위를 명시해라. 기존 동작을 유지하는 리팩터링과 의도적인 동작 변경을 구분해라.

확인한 범위에서 문제가 발견되지 않았다면 그 사실을 쓰되, 전체 시스템에 결함이 없다고 확대 해석하지 마라.

분석을 시작하고 위 형식의 보고서를 작성해라.
