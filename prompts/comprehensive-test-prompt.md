# 통합 품질 검증·버그 수정 프롬프트

요청한 기능/변경 범위의 계약과 사용자 결과를 검증하고, 발견한 관련 결함을 수정한다. **테스트 수·커버리지 숫자보다 실제 실패를 잡는 검증**을 우선한다. 전수 감사가 명시된 경우에도 조사 범위와 실행 매트릭스를 먼저 고정한다.

## 입력과 공통 규칙

- 입력: 대상 저장소·기능/모듈, 변경 diff 또는 결함, 성공 기준, 실행 가능한 환경과 지원 플랫폼, 테스트 예산/제약.
- [모듈 경계 가이드](../guides/module-boundary-guide.md)의 최소 맥락으로 대상 계약·구현·기존 테스트부터 읽고 직접 호출자·소비자·조립 위치를 먼저 검색한다. 공개 계약 변경이나 영향 증거가 있을 때 관련 본문과 추가 경계로 확장한다.
- 이미 허용된 수정·검증은 자율 진행한다. 기존 사용자 변경은 보존한다. 운영 데이터 변경·외부 유료 호출·배포 등은 기존 권한과 테스트 환경을 확인한다. 필요한 권한이 없으면 해당 실행만 보류한다.
- 병렬 읽기·독립 테스트는 자원 충돌이 없을 때 묶어서 실행한다. 같은 DB·포트·파일을 쓰는 테스트는 격리하거나 순차 실행한다.
- 다중 에이전트는 [협업 프롬프트](./multi-agent-task-prompt.md)의 규모·쓰기 소유권·독립 검토 규칙을 따른다. 검증자가 구현자의 가정을 그대로 복제하지 않게 한다.
- 이 프롬프트를 실행했다는 이유로 전역 로깅 교체·전체 UX 재설계·모든 과거 버그 수정까지 확대하지 않는다. 무관한 발견은 후속 과제로 남긴다.

## 1. 검증 범위와 기준선

관련 실행 설정·README·계약·테스트를 근거로 아래 표를 작성한다. 필요한 값만 채우며 작은 변경은 몇 줄로 충분하다.

| 항목 | 기록할 내용 |
|---|---|
| 목표 | 성공 기준과 관찰할 사용자/호출자 결과 |
| 영향 경계 | 모듈, 공개 진입점, 직접 소비자, 데이터 쓰기 소유자 |
| 실행 환경 | 실제 시작/검증 명령, 테스트 자원, 환경 차이 |
| 위험 | 데이터 손상·권한·동시성·복구·변경 빈도 등 관련 항목 |
| 필수 검증 | 실패 시 완료할 수 없는 시나리오와 판정 기준 |
| 추가 검증 | 위험 기반 표본과 적용하지 않는 항목의 이유 |

기존 실패와 이번 변경으로 생긴 실패를 구분한다. 코드/로그로 확인하지 못한 원인은 가설로 남긴다. 원래 실패가 있었다는 이유로 새 실패를 허용하지 않는다.

## 2. 테스트 계층 선택

모든 기능에 모든 계층을 강제하지 않는다. 아래에서 위험을 가장 작고 직접적으로 검증하는 계층을 선택한다.

| 계층 | 확인할 것 | 선택 기준 |
|---|---|---|
| 정적 검사 | 빌드·타입·린트, 금지 import/순환 의존 | 해당 프로젝트의 기존 검사 |
| 단위 | 규칙·상태 전이·불변식·경계값 | 외부 프로세스 없이 검증되는 로직 |
| 계약 | 입력/출력·오류·호환성·부작용 | 모듈·API·이벤트 경계 변경 |
| 통합 | adapter·DB·큐·트랜잭션·권한 연결 | 실제 연결/설정에서만 드러나는 위험 |
| E2E | 진입부터 권위 상태 반영까지 사용자 결과 | 중요한 여러 경계의 여정 |
| 탐색/비기능 | 사용성·접근성·지연·복구·자원 | 요청 범위와 실제 제품 위험 |

- 버그 수정은 가능한 가장 작은 재현 테스트를 먼저 만든다. 자동화가 부적합하면 재현 입력·단계·판정 근거를 기록한다.
- 단위/계약 테스트는 외부 경계를 대역으로 격리할 수 있다. 대역은 실제 계약의 성공·실패 제약을 반영한다. E2E에서 목 처리한 범위는 표시하고 검증하지 못한 연결을 별도 보고한다.
- 커버리지는 미검증 위치를 찾는 보조 지표다. 100% 숫자를 위해 사소한 구현 복제 테스트를 늘리지 않는다. 기존 필수 품질 기준은 유지하고 누락된 위험을 설명한다.
- 수정한 방어 로직을 제거하거나 대표 잘못된 입력을 주면 테스트가 실패하는지 검토한다. 모든 테스트에 변이 도구를 추가할 필요는 없다.

## 3. 경계와 실패 시나리오

관련 있는 항목만 선택하여 `시나리오 · 입력/상태 · 기대 결과 · 검증 계층`으로 정리한다.

- 정상·빈 값·최소/최대·잘못된 입력, 공개 오류 계약과 실패 후 복구.
- 데이터/상태 소유자 밖의 직접 쓰기, 권한 없는 접근, 불변식 파괴, 공개 진입점을 우회한 import.
- 중복 요청·멱등성·순서 역전·늦은 응답·타임아웃·취소·부분 실패.
- 상태 복원·새로고침·재접속·프로세스 재시작, 이전 실행의 응답/구독이 남는 경우.
- 공개 계약의 기존 소비자와 새 소비자, 롤링 배포 시 구버전 호환성, 필드 부재와 기본값 의미.
- 동일 상태를 쓰는 다른 진입 경로. 한 경로의 수정이 형제 경로의 방어를 빠뜨리지 않았는지 확인한다.

UI는 로딩·빈 상태·입력 보존·오류/취소·중복 조작·키보드/포커스를 확인한다. 페르소나는 실제 제품 역할에서 고르고, 교육 서비스의 강사·수강자 등 특정 도메인을 전제로 하지 않는다. 지원 브라우저/기기 전수 실행은 출시 기준이나 관련 호환성 위험이 있을 때 수행한다.

## 4. 진단과 증거

기존 로그로 원인을 찾을 수 없으면 **가설을 구분할 지점에만** 계측을 추가한다. 필요할 때 [상세 로깅 프롬프트](./detailed-logging-prompt.md)를 적용한다.

- 요청/업무 ID로 경계별 수신·판정·완료를 연결한다. 로그 부재가 곧 동작 부재는 아니다.
- UI 성공 표시·전송 ACK만으로 업무 완료를 판단하지 않는다. 계약상 최종 저장 상태·상대 소비자 결과를 확인한다.
- 실패 증거는 최소 재현 데이터·관련 로그·필요한 화면만 보존한다. 토큰·쿠키·비밀번호·개인정보·원문 미디어가 trace/HAR/스크린샷/리포트로 새지 않게 한다.
- 재현에는 합성 데이터와 테스트 전용 자원을 사용한다. 테스트 종료 시 이번 실행이 만든 자원만 정리한다.

## 5. 수정 → 재검증

1. 실패를 `제품 결함/테스트 결함/환경 차단/요구사항 불명확`으로 근거와 함께 분류한다. 환경 원인은 통과로 바꾸지 않는다.
2. 원인 가설을 구분하는 가장 작은 실험을 실행한다. 같은 실패를 재시도만 늘려 숨기지 않는다.
3. 관련 결함을 최소 변경으로 수정한다. 근거 없는 sleep 증가, 예외 무시, assertion 삭제로 성공을 만들지 않는다.
4. 재현 테스트와 바뀐 모듈의 단위/계약 검증을 실행한다. 경계 변경이면 소비자 통합 검증, 필수 프로젝트 검사도 수행한다.
5. 독립 검토자는 무엇이 아직 검증되지 않았는지 확인한다. 새 변경·실패·미해결 위험이 없으면 전체 회귀를 반복하지 않는다.

탐색 테스트는 시작 시 대상 여정과 회차/시간 범위를 정한다. 미지정이면 위험이 높은 여정 1회와 수정 후 회귀 1회를 기본으로 한다. 새로운 실패 유형이 나오면 다음 조사 범위를 근거와 함께 좁힌다. “더 이상 버그가 없을 때까지” 무한 탐색하지 않는다.

검토 반복은 [협업 프롬프트](./multi-agent-task-prompt.md)의 기본 상한을 따른다. 필수 결함이나 필수 검증 차단이 남으면 **미완료**로 보고하며, 상한 도달을 품질 충족으로 해석하지 않는다.

## 6. 필요한 경우만 참고할 실패 패턴

아래는 모든 프로젝트에 의무 적용할 목록이 아니다. 관련 상태/경계가 있을 때만 재현 후보로 사용한다.

| 패턴 | 놓치기 쉬운 이유 | 검증 방법 |
|---|---|---|
| 오래된 응답이 최신 상태를 덮음 | 정상 단일 요청은 통과 | 역순 완료·버전/세대 변경 후 결과 확인 |
| 부분 실패를 전체 성공으로 표시 | ACK·합계만 확인 | 실제 대상별 결과와 권위 상태 대조 |
| 거짓 테스트 오라클 | 구현과 같은 가정을 복제 | 잘못된 결과/부분 성공 표본이 실패하는지 확인 |
| 테스트가 관찰 대상을 변경 | probe가 세션·lease를 갱신 | 관찰 부작용과 자원 해제를 별도 확인 |
| 허용적인 대역이 실패를 숨김 | 실서버 권한·오류를 재현 안 함 | 실패 계약과 실제 adapter 연결 검증 |
| 공유 정책의 복사본 불일치 | 각 복사본 테스트는 통과 | 정책 소유자·소비자의 계약 정합 대조 |
| 프록시/배포가 오류를 정상으로 위장 | 로컬 설정이 다름 | 승인된 테스트 환경에서 코드·형식·body 검증 |
| 로그/trace의 비밀 노출 | 화면 마스킹만 확인 | 최종 저장 결과의 중첩 값·오류·헤더 검사 |
| 재시도와 만료의 모순 | 각 설정은 개별로 유효 | 재전달 가능 시점과 폐기 시한 대조 |
| 한 소비자 정지를 전체 처리량이 가림 | 다른 소비자의 증가가 합계를 채움 | 같은 실행 세대의 대상별 진행과 부분 실패 확인 |

새 사례는 대상 프로젝트의 필요한 회귀 테스트/장애 기록에 남긴다. 작업 완료 때마다 이 공용 프롬프트를 자동으로 수정하거나 사례를 끝없이 누적하지 않는다.

## 7. 완료와 보고

완료는 **합의한 성공 기준과 필수 검증을 충족하고 관련 필수 결함을 해결한 상태**다. 수행한 범위 밖에 결함이 없다고 주장하지 않는다.

보고는 `검증 대상 · 변경 내용 · 실행 명령/환경 · 통과/실패/미실행 · 핵심 반례와 수정 · 남은 위험`으로 정리한다. 긴 작업이면 프로젝트의 기존 품질 보고 위치에 한 문서를 갱신하고, 짧은 작업은 최종 응답으로 충분하다. 환경 차단·불안정 테스트·표본 범위를 명시하고 실제 실행하지 않은 결과를 작성하지 않는다.
