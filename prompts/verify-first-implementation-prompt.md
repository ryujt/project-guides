# 검증 우선 구현 프롬프트

설계서나 요구사항을 구현한다. **설계를 바꿀 수 있는 가정을 먼저 실행으로 확인하고, 작은 제품 단위를 검증한 뒤 그 코드를 그대로 조립한다.**

설계 문서 작성은 [TO-BE](./system-design-to-be-prompt.md)·[기능 설계](./feature-design-prompt.md), 이미 구현된 범위의 검증·수정은 [통합 품질 검증](./comprehensive-test-prompt.md)을 쓴다. 이 문서는 구현 순서·증거 수준·재사용 단위 확정·조립·완료 기준을 정한다.

## 입력과 실행 규칙

- 입력: 설계서 또는 요구사항, 대상·범위, 성공 기준·제약, 실행 환경·권한·비용 한도, 검증 코드 위치(지정 시). 요구사항만 있으면 번호와 관찰 가능한 성공 기준을 붙인다. 별도 설계서는 만들지 않으며, 미정인 구조는 필요한 가정만 기록한다. 요구 충족이나 외부 계약을 바꾸는 결정은 확인받고 그 결정에 기대는 작업만 보류한다.
- **작은 작업**: 한 모듈 안에서 끝나고 외부 가정(모듈 밖의 동작·시간·권한·비용에 기대는 전제)이 없는 작은 수정에는 적용하지 않아도 된다. 적용하더라도 기존 테스트 위치에서 검증하고 기록·최종 보고로 끝낸다. 별도 계획 문서·조립 시작 보고는 생략한다.
- [최소 맥락](../guides/module-boundary-guide.md#6-ai에-전달할-작업-맥락)에 따라 설계의 작업 순서·검증 계획·미확정과 대상 계약·구현·테스트를 읽고, 호출자·소비자·조립 위치를 검색한다. 연결 문서는 해당 조건이 생길 때 필요한 절만 읽는다.
- 이미 허용된 구현·검증은 자율 진행한다. 실제 환경의 자원 생성·배포·유료 호출·운영 데이터 접근은 기존 권한을 확인하고, 없으면 그 실행만 보류한다. 자격 증명 보유는 권한이 아니다. 과금·외부 계정·운영 데이터에 닿지 않는 프로세스·컨테이너·에뮬레이터 실행은 설정·환경 변수를 확인한 뒤 별도 승인 없이 진행한다.
- 실물 검증의 자원·비밀 보호는 [진단과 증거](./comprehensive-test-prompt.md#4-진단과-증거)를 따른다. 이미 떠 있는 개발·운영 자원은 사용자가 지정해 허용했고 가정이 그 자원 자체에 관한 경우에만 읽기·관찰한다.
- 기존 사용자 변경을 보존한다. 검증·보조 코드는 기존 언어·런타임·도구로 작성하고 새 언어·런타임은 먼저 확인받는다. 실물 실행 도구는 필요한 검증 단위와 연결해 적으며, 없는 도구의 전역 설치는 필요한 입력으로 남긴다. 프로젝트 의존 설치·공개 컨테이너 이미지 내려받기는 전역 설치가 아니다. 무관한 기능·추상화는 더하지 않는다.

## 1. 검증 단위와 순서

검증 단위는 **질문 하나와 답에 필요한 가장 작은 범위**다. 테스트 계층의 단위 테스트나 모듈 하나와 일치할 필요는 없다.

1. 설계의 미확정·제안 계약·실행하지 않은 가정과 사용자 질문에서 후보를 찾고, 명시되지 않은 전제도 확인한다. 특히 외부 동작·시간·권한·비용, 대기·순서·기한·동시성에 기대는 결정을 확인한다. 설계가 없으면 [시나리오 검증](../guides/module-boundary-guide.md#연결-최소화와-시나리오-검증)으로 찾는다.
2. 질문마다 `틀리면 바뀌는 요구·결정`과 `틀렸음을 드러낼 관찰`을 정한다. 양쪽 경계에 걸친 질문은 양쪽을 지나는 최소 시나리오로 묶는다. 단순 전달·연결은 소유 모듈이나 조립 검증에서 확인하고, [분할 중단 조건](../guides/module-boundary-guide.md#2-무엇을-한-조각으로-묶는가)을 넘겨 쪼개지 않는다.
3. **① 설계를 바꿀 가정과 그에 기대는 상호작용 → ② 다른 단위의 선행 단위 → ③ 독립 단위** 순서로 실행한다. ①은 탐색 코드나 최소 구현으로 먼저 확인하며 양쪽 구현이 끝날 때까지 미루지 않는다. 기존 검증 ID를 재사용하고 질문을 나눌 때만 접미사를 붙인다. 설계의 순서와 다르면 이유를 기록하되 사용자가 직접 정한 순서를 우선한다.
4. 같은 책임의 기존 모듈·공개 진입점부터 찾아 재사용한다. 바꾸지 않는 기존 코드는 이번 요구가 기대는 계약만 다시 검증하며 전체를 재구성하지 않는다. 신규 프로젝트는 제품·조립 위치와 실행 명령부터 정한다([프로젝트 구조](../guides/project-structure-guide.md#1-구조-선택-원칙)).

**선행 조건**: 선행 단위가 `통과`하기 전에는 종속 구현·조립을 시작하지 않는다. 권한·환경·도구가 막히면 가능한 수준까지 실행하고 독립 작업을 진행한다. 관찰한 실패가 없고 실행 조건만 부족한 단위의 종속 작업은 다음 경우에만 **조건부 진행**한다.

- ①을 로컬 실물로 재현할 수 있으면 그 수준의 통과 기준을 채워야 한다. 대역만으로는 시작하지 않는다.
- 그 밖의 단위(①을 재현할 수단이 없는 경우 포함)는 독립 작업을 먼저 마친다.
- 사용자가 미검증 상태의 진행을 허용했으면 위 대기 없이 진행할 수 있다.

어느 경우든 남은 질문·진행 범위·가정이 틀릴 때 바뀔 범위를 기록하고 결과는 `부분 검증/미실행`, 재사용 단위는 `확정 미완`으로 유지한다. 조건부 진행은 [5절의 기존 경로 전환 조건](#5-조립과-통합-검증)을 면제하지 않는다.

계획과 결과는 **검증 단위 표 하나**에 기록한다. 질문과 재사용 모듈은 다대다일 수 있다. 전 구간 검증(E2E: 제품 진입점부터 최종 상태 반영까지)도 한 행으로 두고 재사용 정보만 비우며 조립 위치·결과는 남긴다.

| 항목 | 기록할 내용 |
|---|---|
| ID·질문·근거 | 질문 하나와 요구·설계의 ID 또는 위치 |
| 통과 기준 | 실행 전에 정한, 일어나야 할 관찰과 일어나지 않아야 할 관찰 |
| 필요 증거·선행 | [증거 수준](#2-단위-검증과-증거-수준)과 먼저 통과할 단위 |
| 실행 증거·결과 | 코드 위치·명령·환경·실행한 제품 경로, 결과·실제 증거 수준, 실행/건너뜀 수. 실물은 준비·정리 명령 포함 |
| 재사용·조립 | 예정 제품 위치 → 공개 진입점·계약·확정 여부, 실제 조립 위치·검증 결과. 제품에 쓰지 않는 코드는 `탐색` |
| 남은 일 | 미구현 요구·미검증 가정/구현/연결, 설계와 다른 점, 필요한 입력·권한, 조건부 진행 범위 |

모든 요구와 사용자 질문을 표에 연결한다. 범위 제외는 사용자나 설계가 정한 것만 인정한다. 실행 결과에 맞춰 통과 기준을 낮추지 않는다. 새 증거·누락·요구 변경이 있을 때 관련 행을 갱신한다.

작은 작업 외에는 기존 품질 보고 위치(없으면 검증 코드 위치의 README)에 이 표를 유지하고 계획 항목을 첫 진행 보고에 알린다. 부족한 권한은 `실행·자원·횟수/비용/영향·되돌리는 방법`을 밝혀 요청하고, 기다리는 동안 허용된 작업을 진행한다.

## 2. 단위 검증과 증거 수준

필요 증거는 **질문에 답하는 데 필요한 상대와 실행 환경**으로 정한다. 테스트 이름이나 실행 편의로 낮추지 않는다.

| 증거 수준 | 실행 상대 | 확인할 수 있는 범위 |
|---|---|---|
| 대역 | 가짜 구현·메모리 저장소·가짜 시계 | 외부 가정을 전제로 한 제품 규칙·상태 전이·오류 처리 |
| 로컬 실물 | 실제 프로세스·컨테이너·공식 에뮬레이터·클라이언트 런타임 | 해당 환경의 프로토콜·기동/접속 순서·동시성·설정 |
| 실제 환경 | 설계가 지정한 서비스·인프라·네트워크 | 실제 외부 동작·기동 시간·권한·할당량·비용·네트워크 경로 |

대역 이외를 실물 검증이라 한다. **가정은 그 가정이 말하는 대상에서 관찰한다.** 판정값을 대역이 만들었다면 가정은 미검증이며, 가정이 틀려도 통과하는 검증은 그 가정의 증거가 아니다. 외부 가정·실제 연결을 묻는 질문은 설치된 도구로 로컬 실물 재현이 가능한지 확인하고 가능하면 실행한다. 그 질문을 대역만으로 검증했으면 확인한 도구와 이유를 남긴다. 시간·비용·용량은 환경·횟수·범위와 설계 상한을 함께 적으며 다른 환경의 수치로 일반화하지 않는다.

- **제품 경로**: 재사용할 구현은 제품 위치 한 곳에 쓰고 검증·조립 코드는 공개 진입점을 호출한다. 내부 파일 import·내부 저장 형식 직접 쓰기·시험 전용 공개 메서드로 우회하지 않는다. 사전 상태는 공개 진입점이나 주입한 의존으로 만든다.
- **탐색과 대체**: 탐색 코드·시험용 adapter는 검증 위치에 분리한다. 탐색 성공은 별도 제품 구현의 성공이 아니다. 제품 구현·adapter·조립을 바꿔 끼웠거나 연결을 대역으로 대신했다면 빠진 제품 경로를 미검증으로 남긴다. 직접 만든 프로토콜과 실제 adapter는 실물 상대와 왕복 검증한다. 탐색 코드를 제품에 쓰려면 제품 위치로 옮겨 공개 진입점으로 재검증한다.
- **검증 코드 위치**: 사용자 지정 → 기존 예제 관례 → `examples/<재사용 단위나 시나리오 이름>/` 순이다. 같은 단위·시나리오의 질문은 한 실행 명령으로 묶고 질문마다 폴더를 만들지 않는다. 작은 작업과 그 밖의 테스트는 기존 테스트 관례를 따른다.
- **실행·판정**: 검증 코드에 증명 범위와 한계를 적고, 한 명령의 종료 코드·출력으로 판정한다. 대기는 기한이 있는 조건으로 확인한다. 건너뜀을 출력하고 **0건 실행은 통과로 세지 않는다**. 자동화가 부적합하면 입력·단계·관찰 근거를 남긴다. 대역 검증은 기본 테스트 명령에, 실물 검증은 별도 명령에 둔다.

결과는 다음 기준으로 기록한다. 기존 테스트를 인용할 때도 이번에 재실행하고 같은 기준을 적용한다.

| 결과 | 기준 |
|---|---|
| 통과 | 필요한 증거 수준과 제품 경로에서 통과 기준 충족 |
| 부분 검증 | 더 낮은 수준만 실행했거나 제품 경로를 우회·대체하여 질문의 일부가 미확인 |
| 실패 | 실행에서 통과 기준 위반 관찰 |
| 미실행 | 질문에 답하는 동작을 실행하지 못함. 빌드·타입·설정 문법만 확인한 경우 포함 |

실패를 환경 부족이나 일부 통과로 덮지 않는다. 정적 검사 결과와 답하지 못한 질문·실행 조건은 실행 증거와 남은 일에 구분해 적는다. 계층·반례는 [테스트 계층 선택](./comprehensive-test-prompt.md#2-테스트-계층-선택)·[경계와 실패 시나리오](./comprehensive-test-prompt.md#3-경계와-실패-시나리오), 소켓 통신은 [소켓 서버 안정성](../guides/socket-server-stability-guide.md)의 해당 기준을 적용한다.

## 3. 검증 결과가 설계와 다를 때

1. [수정 → 재검증](./comprehensive-test-prompt.md#5-수정--재검증)에 따라 제품·테스트 결함, 환경 차단, 요구 불명확을 구분한다. 가정이 틀렸다는 관찰도 유효한 결과다.
2. 가정·결정·수치가 설계와 다르면 그에 기대는 작업을 멈추고 `관찰 증거·영향받는 요구/결정·대안과 비용·선택 또는 확인 요청`을 표에 남긴다. 시간 늘리기·예외 무시·기능 축소로 조용히 우회하지 않는다.
3. 되돌릴 수 있고 요구 충족·비용·보안·사용자 동작·공개 계약의 뜻을 바꾸지 않는 선택은 근거를 적고 진행한다. 나머지는 사용자 확인이 필요한 결정에 기대는 작업만 보류한다. 결정이 바뀌면 영향받는 기준·순서를 갱신하고 재검증한다. 기존 성공 기준의 누락 조건은 검증에 반영하고, 새 기능이나 의미 변경은 미확정으로 두고 확인받는다.
4. 실행 증거의 원본은 표에 둔다. 설계서에는 검증별 결과·증거 수준과 표 링크, 해결/신규 미확정, 선택·정정을 해당 자리에 반영한다. `사실·실행` 표시는 실행한 결과와 명령에만 붙인다. 설계의 ID·고정 제목·표 구조와 `상태`·`(제안)`의 뜻은 보존하며 구현 진행률로 바꾸지 않는다([설계 문서 양식](../guides/system-design-document-guide.md#3-핵심-문서-골격)). 설계서 수정이 금지됐거나 설계서가 없으면 갱신안을 보고한다.

설계와 무관한 프로젝트 공통 제약을 새로 받으면 최종 보고에 구분하고 작업 규칙 문서로 옮길 것을 제안한다.

## 4. 재사용 단위 확정

재사용 단위는 제품이 쓰는 공개 진입점을 가진 모듈이다. 설계가 형태를 정하지 않았으면 같은 프로세스의 모듈·패키지부터 선택한다. 공용 폴더·서비스·추상화를 늘리는 절차가 아니다.

이번 요구로 만든 단위(이어받은 작업 포함)와 기존 단위의 변경 부분이 아래를 충족하면 확정한다. 바꾸지 않는 기존 부분까지 재구성하지 않는다.

- 연결된 검증 단위가 모두 `통과`하고 제품 구현에 미검증이 없다.
- [공개 계약](../guides/module-boundary-guide.md#모듈-계약-양식)과 사용법·검증 명령을 소유 모듈 가까이에서 찾을 수 있다.
- [제품 경로 원칙](#2-단위-검증과-증거-수준)을 지키며 검증 위치에 구현 복사본이 없는지 검색했다. 고정 자격 증명·오류 무시·검증 생략 같은 시험용 임시 코드가 없다.
- 기존 포매터·린트와 [코드 구조 기준](../guides/code-structure-guidelines.md)을 따르고, 이동·수정 후 공개 진입점으로 재검증했다.

미충족이면 `확정 미완`과 이유를 남긴다. [1절의 조건부 진행](#1-검증-단위와-순서)은 확정을 뜻하지 않는다. 검증 코드는 사용 예와 회귀 검증으로 유지한다.

## 5. 조립과 통합 검증

- 표에서 요구별 재사용 단위·공개 진입점을 찾아 **검증한 코드를 그대로 연결**한다. 조율·의존 주입과 도메인 판정의 경계는 [의존과 제어 흐름](../guides/module-boundary-guide.md#4-의존과-제어-흐름)을 따른다. 단순 전달·화면 연결은 이 단계에서 구현·검증한다. 계약 불일치는 소유 단위에서 고치고 해당 검증·소비자를 다시 확인한다.
- 조립 시작 시 결과·증거 수준·남은 미검증·설계와 다른 점을 한 번 보고한다. 필요한 단위가 확정된 핵심 시나리오부터 제품의 실제 조립 위치를 지나는 최소 전 구간 경로를 만든다. [조건부 진행](#1-검증-단위와-순서)을 적용할 때는 그 범위와 미확정을 함께 밝힌다.
- 이후 단위를 하나씩 연결하며 해당 단위와 영향받는 연결을 검증한다. 실패하면 다음 연결을 멈춘다. 단위 통과만으로 조립 통과를 대신하지 않고 실제 조립 위치를 지나는 전 구간 시나리오를 하나 이상 실행한다. 정상 흐름 다음에는 설계의 실패·복구 흐름을 확인한다.
- **기존 경로 교체·기본 진입점 전환은 새 경로의 전 구간 검증이 대역·시험용 구현으로 대신한 연결 없이 `통과`한 뒤에만 한다.** 그전에는 기존 경로를 유지한다. 이어받은 작업에서 이미 전환됐다면 임의로 되돌리지 않고 순서 차이를 기록해 전 구간 검증부터 한다. 설계의 이행·롤백 순서를 지킨다.
- 최종 변경 상태에서 필요한 단위·조립 검증과 필수 프로젝트 검사를 허용된 비용·횟수 안에 실행하고 표를 갱신한다. 기존 실행 방식에 묶음 명령을 두거나 표의 명령 목록을 사용한다. 새 변경·실패·미해결 위험이 없으면 같은 전체 검증을 반복하지 않는다.

## 6. 다중 에이전트 분할

역할·쓰기 소유·검토는 [협업 프롬프트](./multi-agent-task-prompt.md)를 따른다. 위임할 때는 그 문서의 [최소 맥락 패킷](./multi-agent-task-prompt.md#에이전트에게-주는-최소-맥락-패킷)에 질문·통과 기준·필요 증거·선행 관계, 제품/검증 위치, 허용 권한·전용 자원, 이 문서의 필요한 절을 담는다.

- 같은 제품 모듈을 쓰는 질문은 한 담당자에게 묶는다. 병렬은 선행 관계·쓰기 범위·테스트 자원 충돌이 없는 작업에만 쓴다. 종속 작업의 위임도 1절의 선행 조건을 따른다.
- 표·설계/공유 계약·공통 설정·조립 위치는 통합 담당자가 소유한다. 단위 담당자는 설계와 다른 점을 보고하고, 통합 담당자는 명령을 직접 실행하거나 실제 실행 출력을 확인한 뒤 결과를 반영한다.
- 작성자 외 검토자는 기준·증거 수준, 빠진 가정, 제품 경로 우회, 가정을 대신 구현한 대역, 선행·전환 조건 위반을 확인한다. 필수 지적을 수정한 뒤 재평가한다.

## 7. 완료와 보고

[협업 프롬프트의 완료 기준](./multi-agent-task-prompt.md#완료-기준과-보고)을 충족하고, **누락·미구현 요구, 통과하지 못한 검증, 미검증 가정/제품 경로, 확정 미완 단위, 확인되지 않은 설계 변경이 없어야 완료**다. 조건부 진행이나 승인 대기는 완료가 아니며 구현 상태와 검증 상태를 구분한다. 독립 검토와 반복은 [비판 → 개선 → 평가](./multi-agent-task-prompt.md#비판--개선--평가)를 따른다.

최종 보고에는 변경 요약, 검증 표의 위치와 결과·증거 수준, 설계와 다른 점·확인 여부, 남은 위험·필요 입력을 간결히 적는다. 기존 기록을 반복해서 복사하지 않는다. 진행 보고에서도 통과 옆에 증거 수준을 붙이며, 보고·산출 문서에 작성한 컴퓨터에서만 유효한 경로·링크를 남기지 않는다.
