# 검증 우선 구현 프롬프트

설계서나 요구사항을 받아 구현한다. 설계가 기대는 가정과 작은 단위를 먼저 실행으로 검증하고, 통과한 단위를 재사용 단위로 확정한 뒤 조립해 완성한다. 구현 속도나 예제 수보다 **전체를 만들기 전에 설계의 결함을 찾고, 검증한 코드를 그대로 조립하는 것**을 우선한다. 전체를 한 번에 구현한 뒤 검증하지 않는다.

설계 문서 작성은 [TO-BE](./system-design-to-be-prompt.md)·[기능 설계](./feature-design-prompt.md) 프롬프트를, 이미 구현된 범위의 검증과 결함 수정은 [통합 품질 검증 프롬프트](./comprehensive-test-prompt.md)를 쓴다. 이 프롬프트는 검증 단위의 순서, 증거 수준, 재사용 단위 확정, 조립, 설계와 달라진 점의 처리와 그에 따른 완료 기준만 정한다.

## 입력과 실행 규칙

- 입력: 설계서 또는 요구사항, 대상 저장소·범위, 성공 기준, 제약, 검증 코드 위치(지정한 경우), 쓸 수 있는 실행 환경과 권한(실제 환경 접근·테스트 전용 자원·비용 한도). 구현이 요청된 작업에만 쓴다. 한 모듈 안에서 끝나고 외부 가정(모듈 밖의 동작·시간·권한·비용에 기대는 전제)이 없는 작은 수정에는 이 프롬프트를 쓰지 않아도 된다. 그래도 쓰게 됐으면 [1절](#1-검증-단위와-순서)의 「작은 작업」 기준으로 줄인다.
- 요구사항만 받았으면 원문에 번호를 붙이고 성공 기준을 관찰할 수 있는 문장으로 정리한다. 이 프롬프트는 설계 문서를 새로 만들지 않는다. 정해지지 않은 구조 결정은 구현에 필요한 것만 가정으로 적고 진행한다. 요구 충족 여부나 외부 소비자가 쓰는 계약이 달라지는 결정이면 설계가 먼저 필요하다고 보고하고 그 결정에 기대는 작업만 보류한다.
- [모듈 경계 가이드](../guides/module-boundary-guide.md)의 최소 맥락으로 읽는다. 설계서의 작업 순서·검증 계획·미확정 절과 대상 모듈의 공개 계약·구현·테스트부터 읽고, 호출자·소비자·조립 위치를 먼저 검색한다. 소켓 통신(TCP·WebSocket 등)이 포함되면 [소켓 서버 안정성 가이드](../guides/socket-server-stability-guide.md)의 해당 검증 기준을 참고한다.
- 이미 허용된 구현·검증은 자율 진행한다. 권한은 사용자가 이번 작업에서 허용한 범위다. 자격 증명이 있어 명령이 실행된다는 사실은 권한이 아니다. 실제 환경의 자원 생성·배포·유료 호출·운영 데이터 접근은 권한을 확인하고, 없으면 그 실행만 보류한다. 실행하는 컴퓨터 안에서 끝나고 과금·외부 계정·운영 데이터에 닿지 않는 실행(프로세스·컨테이너·에뮬레이터·클라이언트 런타임)은 허용된 범위로 보고 승인을 기다리지 않는다. 띄우기 전에 그 설정·환경 변수가 실제 계정이나 운영 데이터를 가리키지 않는지 확인한다.
- 실물 검증(대역이 아닌 실제 상대로 하는 검증)의 자원과 비밀 보호는 [진단과 증거](./comprehensive-test-prompt.md#4-진단과-증거)를 따른다. 테스트 전용 자원에서 하고 이번 실행이 만든 것만 정리한다. 이미 떠 있는 개발·운영 자원은 사용자가 그 자원을 지정해 허용했고 가정이 그 자원 자체에 관한 것일 때만 읽기·관찰로 쓴다.
- 기존 사용자 변경을 보존한다. 직접 쓰는 검증 코드와 보조 스크립트는 프로젝트가 이미 쓰는 언어·런타임·도구로 쓰고, 새 언어·런타임은 사용자에게 먼저 확인한다. 실물 상대를 띄우는 데 필요한 도구는 어느 검증 단위의 증거 때문인지 적고 쓴다. 없는 도구를 컴퓨터 전역에 설치하지 않고 필요한 입력으로 적는다(프로젝트 안에 두는 의존 설치와 공개 컨테이너 이미지 내려받기는 전역 설치가 아니다). 설계에 없는 기능·추상화를 더하지 않고 무관한 발견은 후속 과제로 남긴다.
- 설계와 무관한 프로젝트 공통 제약(쓰지 않을 언어·도구 등)을 작업 중에 받으면 최종 보고에 따로 적고 저장소의 작업 규칙 문서에 옮길 것을 제안한다.
- 다중 에이전트는 [협업 프롬프트](./multi-agent-task-prompt.md)의 역할·쓰기 소유·검토 규칙을 따르고 [6절](#6-다중-에이전트-분할)대로 나눈다.

## 1. 검증 단위와 순서

구현을 시작하기 전에 검증 단위를 정한다. 검증 단위는 **답할 질문 하나와 그 답에 필요한 가장 작은 범위**다.

- **종류**: 설계가 기대는 가정(외부 동작, 기동·대기 시간, 프로토콜, 권한, 비용), 두 부분 사이의 상호작용(대기·순서·기한·실패 처리에 기대는 연결), 공개 계약을 가진 모듈·기능. 예: 보조 서버가 필요할 때 기동하고 필요 없을 때는 기동하지 않는가(가정), 클라이언트가 서버 준비를 기다렸다가 접속하는가(상호작용).
- **찾는 곳**: 설계서의 작업 순서, 검증 계획, 미확정·위험·미확인, `(제안)` 계약, 실행으로 확인하지 않은 서술, 타임아웃·기한 값. [설계 문서 양식](../guides/system-design-document-guide.md#3-핵심-문서-골격)을 따른 설계서라면 핵심 §2.2·§2.4·§5·§8.1·§9.1·§9.2·§9.5와 [상세](../guides/system-design-document-guide.md#5-상세-문서-골격) §2·§5~§9이고, (`사실·실행`) 표시가 없는 런타임 서술은 실행으로 확인하지 않은 것이다. 설계가 밝히지 않은 전제도 찾는다. 결정마다 무엇이 사실이어야 성립하는지 묻고, `필요할 때만`·`자동으로`·`기다렸다가`·`동시에 와도 한 번만`·`~초 안에` 같은 표현과 직접 구현하는 프로토콜·adapter를 후보로 본다. 설계서가 없으면 [시나리오 검증](../guides/module-boundary-guide.md#연결-최소화와-시나리오-검증)으로 도출한다. 사용자가 예로 든 질문은 반드시 넣는다.
- **판정**: "틀리면 어느 요구·결정이나 다른 단위가 바뀌는가", "무엇을 관찰하면 틀렸다고 말할 수 있는가"에 답이 있어야 검증 단위다. 답이 없는 함수·전달 코드·단순 연결은 소유 모듈의 테스트나 조립 검증에서 다룬다. 분할은 [분할 중단 조건](../guides/module-boundary-guide.md#2-무엇을-한-조각으로-묶는가)에서 멈춘다. 설계서의 작업 한 행이나 검증 한 항목에 질문이 여럿이면 나누고, 이미 질문 하나면 그대로 쓴다.
- **묶기**: 한 질문이 여러 경계에 걸치면 양쪽을 지나는 가장 작은 시나리오 하나로 묶는다. 한쪽 로직만 검증하고 반대쪽의 대기·재시도·기한 처리를 남기지 않는다. 실행 환경에 묶이는 쪽은 상태 전이 로직을 분리해 따로 검증한다.
- **순서**: ① 틀리면 설계 결정이 바뀌는 가정과, 그 가정 위에서 대기·순서·기한으로 이어지는 상호작용 ② 다른 단위가 기대는 단위 ③ 서로 독립인 나머지. 구현이 쉬운 순서로 정하지 않는다. ①의 상호작용은 양쪽 구현이 끝난 뒤의 조립으로 미루지 않고, 탐색 코드나 최소 구현으로 양쪽을 지나는 가장 작은 시나리오를 먼저 실행한다. 설계서에 있는 검증 항목의 이름과 ID는 그대로 쓴다(한 항목에 필요 증거가 다른 질문이 섞였으면 접미사를 붙여 나눈다). 필요 증거와 실행 시점은 이 프롬프트의 기준으로 정하고, 설계서의 작업 순서·검증 계획과 어긋나면(실물 검증을 구현 뒤로 미룸, 상대를 대역으로 두고 병렬 구현 등) 달라진 순서를 설계와 달라진 점으로 기록한다. 사용자가 이번 요청에서 순서를 직접 정했으면 그것을 따른다.
- **선행 조건**: 선행 단위가 `통과`하기 전에는 그것에 기대는 단위·조립, 기존 경로의 교체, 기본 실행 진입점 변경을 시작하지 않는다. 권한·환경·도구가 없어 필요한 수준을 실행하지 못한 단위는 허용된 가장 높은 수준까지 실행한다. 그런 단위에 기대는 단위·조립은 다음 경우에만 시작한다.
  - 로컬 실물([증거 수준](#2-단위-검증과-증거-수준))로 재현할 수 있는 ①: 로컬 실물에서 통과 기준을 채우고 남은 질문과 틀렸을 때 바뀌는 범위를 표에 적었을 때. 대역에서만 채웠으면 시작하지 않는다.
  - 그 밖의 단위(허용된 도구로 재현할 수단이 없는 ① 포함): 그 단위에 기대지 않는 작업을 먼저 끝냈을 때.
  - 사용자가 미검증인 채 진행하기로 했으면 바로 시작한다. 어느 경우든 결과는 `부분 검증`이나 `미실행`으로 두고 완료로 보고하지 않는다.
- **작은 작업**: 한 모듈 안에서 끝나고 외부 가정이 없는 작은 수정이면 검증 단위 한두 개와 표 몇 줄이면 충분하다. 검증 코드는 그 모듈의 기존 테스트 위치에 더하고, 조립 시작 보고는 생략하며, 링크한 문서는 필요한 절만 읽는다. 검증 단위로 삼을 것이 없으면 이유를 한 줄 적고 조립 검증으로 확인한다.
- **기존 프로젝트**: 새로 쓰기 전에 같은 책임의 기존 모듈과 공개 진입점을 검색한다. 있으면 그것을 재사용 단위로 삼고 이번 요구가 기대는 계약의 검증만 더한다. 기존 코드 전체를 다시 나누지 않는다. 이미 있는 검증은 이번에 다시 실행해 인용하되 증거 수준과 제품 경로 우회(내부 파일 import, 내부 상태 쓰기)를 판정해 적는다. 우회가 있으면 `부분 검증`이다.
- **신규 프로젝트**: 제품 코드 위치, 조립 위치, 실행 명령을 먼저 정한다. 설계가 정하지 않았으면 [프로젝트 구조 가이드](../guides/project-structure-guide.md#1-구조-선택-원칙)의 관례를 따른다.

계획과 결과는 검증 단위 표 하나로 관리한다. 행 하나가 검증 단위 하나이고, 전 구간 검증(제품의 진입점에서 최종 상태 반영까지. 테스트 계층으로는 E2E)의 시나리오도 한 행이다(조립 검증으로 세고 재사용 단위 열은 비운다). 검증 단위(질문)와 재사용 단위(모듈)는 다대다일 수 있다.

| 열 | 채우는 때 | 기록할 내용 |
|---|---|---|
| ID · 질문 | 계획 | 설계서의 검증 항목 이름이나 ID(없으면 짧은 이름), 답할 질문 하나, 근거가 된 요구·결정의 ID 또는 위치 |
| 통과 기준 | 계획 | 요구·설계에서 가져온 관찰 가능한 기준. 일어나야 하는 관찰과 일어나지 않아야 하는 관찰을 함께 적는다. 실행 전에 적고 관찰값에 맞춰 고치지 않는다 |
| 필요 증거 · 선행 | 계획 | 이 질문에 필요한 최소 [증거 수준](#2-단위-검증과-증거-수준), 먼저 통과해야 하는 단위 |
| 검증 | 실행 | 위치, 실행 명령, 환경. 실물 검증이면 준비·정리 명령 |
| 결과 | 실행 | `통과/부분 검증/실패/미실행`, 실제로 실행한 증거 수준과 제품 코드 경로, 실행된 검증 수와 건너뛴 수 |
| 재사용 단위 | 계획·확정 | 계획 때는 예정 형태와 제품 코드 위치, 확정 뒤에는 공개 진입점과 계약 위치. 조건을 못 채웠으면 `확정 미완`, 제품에 쓰지 않는 탐색 코드는 `탐색` |
| 조립 위치 | 조립 | 제품에서 이 단위를 연결하는 진입점·배선·설정, 조립 검증의 결과와 증거 수준 |
| 남은 일 | 수시 | 미검증으로 남은 가정·제품 구현·연결, 설계와 달라진 점, 필요한 입력·승인 |

- 계획 열을 채운 표를 첫 진행 보고로 알린다. 권한이나 환경이 필요한 검증은 이때 승인 요청(`무엇을 · 어떤 권한·자원으로 · 예상 횟수·비용·영향 · 되돌리는 방법`)을 함께 내고, 답을 기다리지 않고 허용된 범위부터 진행한다.
- 작은 작업의 표는 작업 기록과 최종 보고로 충분하다. 그 밖에는 계획 열을 채울 때부터 문서 하나로 유지한다(프로젝트의 기존 품질 보고 위치 → 검증 코드 위치의 README 순).
- 표에 연결되지 않은 요구가 없어야 한다. 범위 제외는 사용자나 설계서가 정한 것만 인정하고, 구현하지 못한 요구는 미구현으로 적는다. 검증 단위는 계획 때 정하고, 그 뒤에는 실패, 설계와 다른 결과, 실행 중 드러난 미검증 가정이 있을 때만 더한다.

## 2. 단위 검증과 증거 수준

단위 검증은 검증 단위 하나를 확인하는 실행이다. 테스트 계층의 단위 테스트를 뜻하지 않는다.

- 검증 코드의 위치는 사용자 지정 → 대상 저장소의 기존 예제 관례 → 대상 저장소의 `examples/<재사용 단위나 시나리오 이름>/` 순으로 정한다. 검증 단위마다 폴더를 만들지 않는다. 같은 재사용 단위나 같은 시나리오를 상대로 하는 질문은 검증 코드 하나(위치·실행 명령 하나)에 모은다. 이 위치 순서는 검증 단위의 검증 코드에만 적용하고, 그 밖의 테스트는 저장소의 테스트 관례를 따른다.
- 재사용할 구현은 처음부터 제품 코드 위치에 쓴다. 검증 코드는 그 공개 진입점을 부르는 준비·실행·판정만 가진다. 구현을 복사하지 않고, 내부 파일을 직접 import하거나 내부 저장 형식에 상태를 써 넣지 않는다. 사전 상태는 공개 진입점과 주입한 의존(시계 등)으로 만들고, 검증을 위해 공개 진입점에 시험 전용 메서드를 더하지 않는다.
- 가정만 빨리 확인하는 탐색 코드는 탐색 코드로 표시해 검증 코드 위치에 남기고 제품 코드가 가져다 쓰지 않게 한다. 탐색 코드로 통과한 질문에 답하는 제품 구현이 따로 있으면 그 구현을 미검증으로 적고, 같은 시나리오를 제품 코드로 다시 실행해 통과해야 지운다. 탐색 코드를 제품에 쓰려면 제품 코드 위치로 옮겨 [4절](#4-재사용-단위-확정)의 조건을 채운다.
- 검증은 한 명령으로 실행되고 종료 코드와 출력으로 판정돼야 한다. 대기는 고정 시간이 아니라 기한이 있는 조건으로 판정한다. 실행 조건(권한·환경·도구)이 없어 건너뛴 검증은 건너뛴 사실을 출력에 드러내고 통과로 세지 않는다. 0건 실행은 통과가 아니다. 자동화가 맞지 않는 검증(비용·권한·장시간 관찰)은 입력·단계·판정 근거를 기록한다.
- 검증 코드 첫머리에 무엇을 증명하고 무엇을 증명하지 않는지 적는다. 대역 수준의 검증은 프로젝트의 기본 테스트 명령에도 넣고, 실물 검증은 따로 실행하는 명령으로 둔다.

증거 수준은 테스트 계층과 별개로 **어떤 제품 코드를 무엇을 상대로 실행했는지**를 말한다. 통합 테스트라도 질문이 묻는 상대가 대역이면 대역 수준이다. 필요 증거(필요한 증거 수준)는 질문의 종류로 정하고, 실행하기 쉬운 수준에 맞춰 낮추지 않는다. `통과`는 필요한 수준에서 통과 기준을 채운 것이다. 대역이 아닌 두 수준의 검증을 실물 검증, 그 상대를 실물 상대라 한다.

| 증거 수준 | 실행 상대 | 답할 수 있는 질문 |
|---|---|---|
| 대역 | 가짜 구현(직접 만들었든 남이 만든 모의 구현이든)·메모리 저장소·가짜 시계 | 제품 코드의 규칙·상태 전이·오류 처리. 외부가 가정대로 동작한다는 전제가 붙는다 |
| 로컬 실물 | 실행하는 컴퓨터에 띄운 실제 프로세스·컨테이너·공식 에뮬레이터·실제 클라이언트 런타임 | 프로토콜, 기동·대기·접속 순서, 데이터 저장소의 동시성, 설정 적용 |
| 실제 환경 | 설계가 지정한 실제 서비스·인프라·네트워크 경로 | 외부의 실제 동작, 기동 시간, 권한·할당량·비용, 네트워크 경로 |

- **가정은 그 가정이 말하는 대상에서 관찰한다.** 판정에 쓰는 관찰값을 누가 만들었는지 적는다. 대역이 만든 값이면(예: 대역이 기동 요청에 곧바로 준비됨을 돌려주고 검증이 그 준비됨을 확인한다) 결과 옆에 「가정을 전제로 한 논리 검증」이라고 적고 가정은 미검증으로 남긴다. 가정이 틀려도 통과하는 검증은 가정을 확인한 것으로 세지 않는다([실패 패턴](./comprehensive-test-prompt.md#6-필요한-경우만-참고할-실패-패턴)).
- 대역으로만 검증하기 전에 로컬 실물로 재현할 수 있는지 설치된 도구부터 확인하고, 할 수 있으면 가장 작은 실물 시나리오를 실행한다. 대역으로만 검증했으면 확인한 도구와 그 이유를 표에 적는다.
- port 뒤의 실제 adapter와 직접 구현한 프로토콜은 실물 상대와 한 번 이상 왕복시켜 검증한다. 제품의 adapter나 조립을 시험용 구현(실물 상대에 이어 주는 검증 전용 adapter. 값을 지어내면 대역이다)으로 바꿔 끼웠으면 바꾼 것을 적고, 실행되지 않은 제품 구현은 미검증으로 남긴다. 질문과 무관한 주변 상대만 대역으로 대신했으면 그 연결을 미검증으로 적는다. 시험용 구현은 검증 코드 위치에 두고 제품 코드가 가져다 쓰지 않게 한다.
- 필요한 수준보다 낮게 실행했으면 `부분 검증`이다. 정적 검사(빌드·타입·설정 문법)만 했으면 그 검사는 검증 열에 적고 동작에 관한 질문의 결과는 `미실행`으로 둔다. 답하지 못한 질문과 필요한 실행 조건을 적는다.
- 시간·비용·용량은 환경·횟수·범위를 적고 설계의 상한과 비교한다. 로컬에서 잰 값을 실제 환경의 수치로 쓰지 않는다.
- 계층 선택과 대역의 조건은 [테스트 계층 선택](./comprehensive-test-prompt.md#2-테스트-계층-선택), 다룰 실패 흐름은 [경계와 실패 시나리오](./comprehensive-test-prompt.md#3-경계와-실패-시나리오), 로그 보강은 [상세 로깅 가이드](../guides/detailed-logging-guide.md)를 따른다.

## 3. 검증 결과가 설계와 다를 때

- 실패는 [수정 → 재검증](./comprehensive-test-prompt.md#5-수정--재검증)의 순서로 분류하고 원인 가설을 가른다. 요구가 불명확하거나 관찰이 설계와 다른 경우만 설계 문제로 다룬다. '가정이 틀렸다'도 유효한 결과이며 통과 기준을 낮춰 덮지 않는다.
- 검증 결과가 설계의 가정·결정·수치와 다르면 그 가정에 기대는 작업을 멈추고 `관찰 증거(명령·환경·결과) · 영향받는 요구·결정 · 대안과 비용 · 선택 또는 확인 요청`을 표에 기록한다. 코드에서 조용히 우회하지 않는다(대기 시간 늘리기, 예외 무시, 판정 삭제, 기능 축소, 구성요소 교체).
- 되돌릴 수 있고 요구 충족·비용·보안·사용자에게 보이는 동작·공개 계약의 뜻이 바뀌지 않는 선택은 가정과 영향을 기록하고 진행한다. 그 밖의 선택은 사용자 확인을 요청하고 그 선택에 기대는 작업만 보류한다. 같은 결정에서 고른 대안이 다시 틀리면 더 고르지 않고 관찰 증거와 남은 대안을 정리해 사용자 확인을 요청한다.
- 설계가 바뀌면 영향받는 검증 단위의 통과 기준과 순서를 다시 정하고 확정한 재사용 단위도 다시 검증한다. 새로 드러난 요구는 범위에 넣지 않고 미확정으로 적는다.
- 설계서는 사용자가 막지 않았으면 아래 범위만 고치고, 추정을 사실처럼 쓰지 않는다. 실행 기록(명령·환경·증거 수준·결과)과 재사용 단위·계약 위치는 검증 단위 표가 원본이다. 설계서가 정한 실행 기록 위치(없으면 검증 절)에는 검증 항목마다 결과 한 줄(증거 수준 포함)과 표의 위치만 적는다. 설계서가 (`사실·실행`) 표시를 쓰면 실제로 실행한 결과 줄 끝에 그 표시와 실행 명령을 함께 적는다. 풀렸거나 새로 생긴 미확정은 미확정 절에 쓴다. 설계와 달라진 점과 그 선택, 사용자가 작업 중에 준 정정·새 제약은 해당 요구·결정 자리에 쓴다. 기존 ID는 다시 매기지 않고, 표의 열·고정 제목과 설계 항목의 `상태` 열·`(제안)` 표시는 구현 진행에 맞춰 고치지 않는다. 요구·결정의 뜻이 바뀌는 수정은 사용자 확인 뒤에 한다. 사용자가 설계서 수정을 막았거나 설계서가 없으면 갱신안을 보고에 적는다.

## 4. 재사용 단위 확정

재사용 단위는 제품이 실제로 쓰는 공개 진입점을 가진 모듈이다. 형태(라이브러리·서비스·SDK·인프라 모듈)는 설계를 따른다. 설계가 정하지 않았으면 같은 프로세스의 모듈·패키지가 기본값이고, 서비스는 독립된 수명·확장·권한이 필요할 때만 고른다. 공용 폴더로 올리거나 인터페이스를 늘리라는 뜻이 아니다. 확정 조건은 이 설계·요구를 구현하면서 새로 만든 단위(이어받은 작업분 포함)와, 기존 단위에서는 그 구현으로 바꾼 부분에만 적용한다. 아래를 모두 채우면 확정하고, 못 채우면 표에 `확정 미완`과 남은 질문을 적는다.

- 연결된 검증 단위가 모두 `통과`이고 이 단위의 제품 구현에 미검증이 남지 않았다. 권한·환경·도구가 없어 `부분 검증`·`미실행`으로 남은 검증 단위가 있으면, [1절](#1-검증-단위와-순서)의 선행 조건이 그 단위에 기대는 작업의 시작을 허용한 때에만 확정한다.
- 공개 진입점과 계약이 있다. 계약은 [모듈 계약 양식](../guides/module-boundary-guide.md#모듈-계약-양식)에서 해당 항목만 적는다. 사용법과 검증 명령은 소유 모듈 가까이에 둔다.
- 구현이 제품 코드 위치 한 곳에만 있고, 검증 코드와 조립 코드는 공개 진입점만 쓴다. 검증 코드 위치에 같은 로직의 정의가 없는지 검색으로 확인한다.
- 시험용 임시 코드(고정 주소·자격 증명, 고정 대기, 오류 무시, 검증 생략 분기, 시험 전용 전역 상태)가 없다.
- 저장소의 포매터·린트와 [코드 구조 가이드](../guides/code-structure-guidelines.md)를 따른다.
- 옮기거나 고친 뒤 같은 검증을 공개 진입점으로 다시 실행해 통과했다. 옮기기 전의 통과로 대신하지 않는다.

확정한 뒤 검증 코드는 그 재사용 단위의 사용 예이자 회귀 검증으로 남긴다.

## 5. 조립과 통합 검증

조립 코드는 조율자와 조립 위치(진입점·배선·설정)의 코드다. 조립 검증은 재사용 단위를 연결할 때마다 그 연결을 지나는 통합 검증과 전 구간 검증을 함께 이른다.

- 조립 전에 표에서 요구별 재사용 단위와 공개 진입점을 찾는다. 검증 단위였던 기능은 확정한 재사용 단위로만 조립하고 조립 코드에서 다시 구현하지 않는다. 바꾸지 않고 쓰는 기존 모듈은 지금의 공개 진입점을 그대로 쓴다. 이번 요구가 기대는 계약의 증거 수준은 1절대로 판정하고, 그 밖의 확정 조건에 못 미치는 점만 후속 과제로 적는다. 검증 단위가 아닌 부분(전달 코드·단순 연결·화면 연결 등)은 조립 단계에서 만들고 조립 검증으로 확인한다.
- 조립을 시작할 때 검증 단위별 결과·증거 수준·남은 미검증·설계와 달라진 점을 한 번 보고하고 진행한다.
- 핵심 시나리오 하나가 제품의 실제 조립 위치로 전 구간을 통과하는 가장 작은 경로를 먼저 만든다. 그 경로에 필요한 재사용 단위가 확정되면 나머지를 기다리지 않고 조립해 검증한다. 그 뒤 재사용 단위를 확정되는 대로 하나씩 연결하고, 연결할 때마다 그 단위의 검증과 영향받는 조립 검증을 실행한다. 실패하면 다음 단위를 연결하지 않는다.
- 조율자에는 호출 순서와 실패 연결만, 조립 위치에는 생성·의존 주입·설정만 두고 도메인 판정은 재사용 단위에 둔다([의존과 제어 흐름](../guides/module-boundary-guide.md#4-의존과-제어-흐름)). 계약이 맞지 않으면 조립 코드에서 보정하거나 재사용 단위 내부를 직접 부르지 않고, 그 재사용 단위로 돌아가 계약을 고친 뒤 단위 검증과 다른 소비자를 다시 확인한다.
- 조립 위치도 전 구간 시나리오 하나 이상으로 검증한다. 단위 검증 통과를 조립 검증으로 대신하지 않는다. 확인 범위는 [변경과 검증](../guides/module-boundary-guide.md#7-변경과-검증)을 따르고, 대역이나 시험용 구현으로 대신한 연결은 표에 미검증으로 적는다.
- 기존 경로의 교체와 기본 실행 진입점 전환은 새 경로의 전 구간 검증이 대역·시험용 구현으로 대신한 연결 없이 `통과`한 뒤에만 하고, 1절 선행 조건의 예외로 앞당기지 않는다. 그 전에는 기존 경로를 실행할 수 있게 둔다. 이어받은 작업에서 이미 전환돼 있으면 되돌리지 않고 달라진 순서로 기록한 뒤 전 구간 검증부터 한다. 기존 프로젝트는 설계의 이행·롤백 순서를 지킨다.
- 정상 흐름이 통과하면 설계가 정한 실패·복구 흐름을 더한다. 끝나면 허용된 범위와 승인된 횟수 안에서 단위 검증 전체와 조립 검증을 묶음 명령으로 다시 실행하고 결과를 표에 적는다. 묶음 명령은 프로젝트의 기존 실행 방식에 더하고, 없으면 표의 명령 목록으로 대신한다.

## 6. 다중 에이전트 분할

- 위임할 때는 검증 단위를 [최소 맥락 패킷](./multi-agent-task-prompt.md#에이전트에게-주는-최소-맥락-패킷)의 단위로 삼고, 같은 제품 모듈에 쓰는 검증 단위는 한 패킷으로 묶는다. 패킷에는 다음을 넣는다.
  - 성공 기준: 표의 질문·통과 기준·필요 증거
  - 읽기 시작점: 이 프롬프트의 [2절](#2-단위-검증과-증거-수준)과 [4절](#4-재사용-단위-확정)
  - 필수 제약: 「입력과 실행 규칙」의 권한·자원·도구 규칙, 허용된 권한, 배정한 테스트 전용 자원, 설계·공유 계약과 다르면 우회하지 않고 보고
  - 쓰기 범위: 그 단위의 제품 코드와 검증 코드 위치
  - 반환할 결과: 실행 명령, 실제 증거 수준, 남은 미검증
- 표, 공유 계약, 공통 설정(의존 목록·기본 테스트 명령·묶음 명령), 조립 위치는 통합 담당자가 소유한다. 단위 담당자는 설계나 공유 계약과 어긋난 점을 직접 고치지 않고 보고한다. 통합 담당자는 보고받은 통과를 표에 적기 전에 그 명령을 직접 실행하거나 출력을 확인한다.
- 병렬은 선행 관계가 없고 쓰기 범위와 테스트 전용 자원(네트워크 포트·컨테이너·데이터 저장소)이 겹치지 않는 패킷에만 쓴다. 조립과 조립에 기대는 구현은 거기에 쓰이는 재사용 단위가 확정된 뒤에 맡긴다.
- 통과 기준과 필요 증거는 단위 담당자와 다른 쪽이 정하거나 확인한다. 검토자는 다음을 찾는다.
  - 빠진 가정, 질문에 맞지 않는 필요 증거, 설계 위험과 무관하게 늘어난 검증 단위
  - 제품 경로를 우회한 검증, 가정을 대신 구현한 대역, 실제 실행과 다른 표의 증거 수준
  - 1절의 선행 조건에 맞지 않게 시작한 조립·교체·진입점 변경

## 7. 완료와 보고

검토와 반복 상한은 [협업 프롬프트](./multi-agent-task-prompt.md#비판--개선--평가)를 따른다. 완료는 [협업 프롬프트의 완료 기준](./multi-agent-task-prompt.md#완료-기준과-보고)을 채우고 **아래가 하나도 남지 않은 상태**다. 하나라도 남으면 **미완료**로 보고한다.

- 검증 단위의 결과가 `부분 검증/실패/미실행`이거나, 표에 미검증으로 적은 가정·제품 구현·연결이 남아 있다. 승인이 없어 보류했으면 구현 완료와 검증 미완료를 구분해 적는다.
- `확정 미완` 재사용 단위나 검증하지 않은 조립 위치가 제품 경로에 있다.
- 사용자 확인이 필요한 설계 변경이 닫히지 않았다.
- 표에 연결되지 않은 요구나 미구현 요구가 있다.

진행 보고와 최종 보고 모두 '통과' 옆에 증거 수준을 적는다. 최종 보고는 협업 프롬프트의 보고 순서에 `검증 단위 표 · 설계와 달라진 점 · 미검증 가정과 승인 요청`을 더한다. 설계와 달라진 점은 3절의 기록에 사용자 확인 여부와 남은 위험을 더해 적는다. 보고와 문서에 작성한 컴퓨터에서만 유효한 경로·링크를 남기지 않는다.
