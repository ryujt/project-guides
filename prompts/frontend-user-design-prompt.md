# 프론트엔드 사용자·회원 시스템 설계 생성 프롬프트

회원 영역의 화면 흐름과 구현에 필요한 인증·API·데이터 계약을 설계한다. **UI는 사용자 상호작용을, 인증 서비스는 신원·세션을, 회원 모듈은 프로필·서비스 계정 상태를 소유**하게 하여 각 조각을 작은 맥락으로 구현할 수 있게 한다.

이 프롬프트는 설계 문서 작성용이다. 코드 변경이나 회원 영역과 무관한 주문·정산·콘텐츠 재설계는 포함하지 않는다. 부분 기능 변경이면 [특정 요구사항 설계](./feature-design-prompt.md)를 사용한다.

## 입력과 실행 규칙

| 입력 | 확인할 내용 |
|---|---|
| 프로젝트·범위 | 루트, 관련 화면/모듈, 기존 구현 또는 신규 설계 |
| 제품 요구 | 사용자 유형, 가입 자격, 식별자, 대상 기능, 성공 기준 |
| 인증 계약 | 기존 인증 서비스/관리형 IdP, 세션 방식, 위임 범위 |
| 정책 | 개인정보 수집·보유·삭제, 동의, 잠금/탈퇴/재가입 |
| 기술 제약 | 라우터, 상태 관리, API client, 저장소, 디자인 시스템 |
| 참고 자료 | 실제 읽을 경로/URL, 채택할 패턴과 복제 금지 사항 |

- [모듈 경계 가이드](../guides/module-boundary-guide.md)의 최소 맥락과 계약을 사용한다. 라우트·인증/회원 공개 API·상태 소유자·관련 테스트부터 읽고 직접 호출자·소비자·조립 위치를 검색한다. 실제 영향이 있을 때 관련 본문으로 확장한다.
- 이미 허용된 설계는 자율 진행하며 확인된 사실·설계 선택·미확정 정책을 구분한다. 기존 변경을 보존하고 무관한 문제는 후속 과제로 남긴다.
- 인증·권한·개인정보 보유·불가역 삭제 정책을 근거 없이 확정하지 않는다. 입력이 없으면 선택지와 잠정안을 설계하고 해당 결정을 미확정으로 표시한다. 문서 초안을 작성할 수 있어도 구현 준비 완료와 구분한다.
- 라이브러리/IdP/표준의 구체적 보안 설정은 구현 시점 공식 자료와 대상 버전으로 확인한다. 예제를 운영 보안 검증의 대체물로 취급하지 않는다.
- 독립된 조사만 병렬로 진행한다. 계약 확정 전 종속 상세 문서를 독립된 사실처럼 작성하지 않는다.

## 1. 기능 범위 확정

전체 회원 영역을 새로 설계할 때 기본 후보는 아래와 같다. 실제 제품 정책과 인증 방식에 맞춰 `적용/제외 + 이유`를 정한다. 표를 채우려고 존재하지 않는 기능을 추가하지 않는다.

| 기능 | 설계할 결과 |
|---|---|
| 가입 | 동의·입력 검증·중복/실패·가입 후 진입 |
| 로그인·세션 | 로그인, 시작 시 복원, 만료/거부 후 복구 |
| 로그아웃 | 서버 세션 정책, 로컬 인증 상태·민감 캐시 정리 |
| 자기 정보 | 조회·수정·충돌·실패 시 입력 보존 |
| 보안 설정 | 채택한 인증 방식의 민감 변경·재인증 |
| 탈퇴 | 영향 안내·명시적 확인·차단·삭제/보존 결과 |
| 접근 제어 | 공개/게스트/인증 필요 라우트와 서버 API 권한 |

연락처 소유 검증, 계정 복구, 세션 갱신/기기 관리, 탈퇴 유예, 소셜 로그인, 패스키, MFA, 조직/역할은 요구사항과 위험에 따라 추가한다. 비밀번호 없는 인증에 비밀번호 변경 화면을 강제하지 않는다. 가입 후 자동 로그인도 정책으로 확정한다.

요구사항에는 `FR-ID · 성공 기준 · Must/Should/Optional · 적용 흐름`을 붙인다. 기준 날짜는 한 번 확정하고 현재 구현의 근거 커밋/시점을 함께 남긴다.

## 2. 모듈 경계와 소유권

[method-R](../guides/method-R.md)의 필요한 깊이까지만 분해하고 [O-W 가이드](../guides/orchestrator-worker-pattern-guide.md)를 적용할 유스케이스를 선택한다. 모든 화면에 별도 조율자·Worker·이벤트 버스를 만들지 않는다.

| 책임 | 공개 계약 | 알 필요 없는 내부 |
|---|---|---|
| Page/폼 | 입력, 제출 요청, 표시용 상태·오류 | 토큰 검증·DB·IdP SDK |
| 인증 상태 소유자 | 세션 조회/복원 결과와 상태 구독 | 다른 feature의 store 내부 |
| 인증 gateway | 인증 서비스와의 요청/응답 변환 | 화면 이동·제품 권한 규칙 |
| 회원 API/모듈 | 프로필·서비스 계정 상태·동의·탈퇴 계약 | UI 컴포넌트 구조 |
| 인증 서비스/IdP | 신원 검증·인증 세션·위임한 자격 증명 | 앱의 비즈니스 데이터 내부 |
| 탈퇴 조율자 | 적용한 저장소별 차단·삭제 결과 | 각 저장소의 직접 내부 쓰기 |

이 표는 책임 후보이며 폴더/클래스의 의무 목록이 아니다. 작은 기능은 응집된 한 모듈로 구현할 수 있다.

- `데이터/상태 · 권위 소유자 · 쓰기 주체 · 읽기 계약 · 보유/삭제 책임` 표를 만든다. 자격 증명, provider subject, 세션, 앱 userId, 프로필, 동의, 서비스 계정 상태, 삭제 작업을 필요에 따라 구분한다.
- 관리형 IdP에 위임한 자격 증명·세션을 애플리케이션 저장소에 중복 구현하지 않는다. 로컬 사용자와 외부 주체는 불변 식별자 매핑으로 연결한다.
- UI route guard는 표시/이동을 제어한다. 서버는 실제 요청의 인증·권한·계정 상태를 확인한다. `토큰 존재`나 body/query의 `userId`를 권위로 신뢰하지 않는다.
- 계정 수명주기, 클라이언트 인증 상태, 탈퇴 작업 상태는 서로 다른 소유자의 상태로 모델링한다.
- 계약 변경 시 직접 소비자, 호환성, 오류 변환, 만료·중복·취소를 명시한다. 내부 store 구조를 feature 간 공유 계약으로 삼지 않는다.

## 3. 인증·화면 흐름

- 시작 상태는 `restoring/unknown`으로 두어 익명과 구분한다. 복원이 끝나기 전 보호 콘텐츠 노출 정책을 정한다.
- 인증 상태의 이름은 실제 필요한 것만 고른다. 복원·로그인·로그아웃·만료·거부·네트워크 실패를 구분하고 실패 후 사용자가 취할 행동을 정의한다.
- 세션 갱신을 채택하면 동시 요청 합류, 재시도 상한, 취소, 갱신 실패 시 정리 범위를 계약에 둔다. 무한 401 재시도는 허용하지 않는다.
- 서버 세션/쿠키 또는 클라이언트 토큰 방식의 선택 근거와 XSS·CSRF·만료·폐기·다중 탭 제약을 기록한다. 비밀을 URL·일반 로그·분석 이벤트에 남기지 않는다.
- IdP redirect를 채택하면 callback 검증·실패·원래 목적지 복귀를 해당 공급자 계약과 대조한다. 복귀 주소는 허용한 대상만 사용한다.
- 로그아웃/잠금/탈퇴마다 **언제부터 기존 요청이 거부되는가**를 정한다. 로컬 화면 전환, 서버 세션 폐기, 외부 IdP 폐기를 같은 순간의 성공으로 가정하지 않는다.
- 공개 오류는 안전한 외부 메시지와 내부 진단 코드를 분리한다. 계정 존재 여부 노출, 권한 부족, 세션 만료, 일시 장애의 표시/복구 정책을 설계한다.
- 모든 제출에는 관련된 중복 방지·입력 보존·취소/시간 초과·재시도·초점/오류 안내를 둔다. 클라이언트 검증과 서버 권위 규칙을 중복 복사하지 않는다.

## 4. 데이터와 외부 정합성

논리 모델보다 **접근 패턴과 소유권**을 먼저 정한다.

`패턴 · 호출자 · 조회/쓰기 키 · 정합성 요구 · 원자성/고유성 · 만료 · 오류/멱등성` 표를 만들고 선택한 저장소에 맞는 키·인덱스를 연결한다. 실제 패턴이 없는 엔터티·테이블은 만들지 않는다.

- provider-subject 매핑과 로그인 식별자 고유성은 단순 선조회 후 쓰기로 보장하지 않는다. 선택한 저장소/IdP의 원자적 계약을 확인한다.
- 프로필 동시 변경의 충돌 정책을 정하고, 버전 충돌 시 기존 입력과 재시도 경로를 보존한다.
- 만료는 사용 시점에 판정한다. TTL 자동 삭제가 즉시 실행된다고 가정하지 않는다.
- IdP 변경과 앱 저장소 변경은 하나의 로컬 트랜잭션으로 원자화되지 않는다. 필요한 경우 단계 상태·멱등 요청·실패 정리·정합성 재확인을 설계한다.
- 저장소 분리는 독립 소유권·트랜잭션·접근 패턴의 실제 필요가 있을 때 선택한다. 단순 회원 시스템에 분산 동기화를 먼저 추가하지 않는다.
- 분리했으면 원본 소유자, 읽기 복제본, 허용 지연, 변경 전달·중복·역순·실패 재처리·삭제 책임을 명시한다. 프론트엔드가 두 저장소를 직접 쓰지 않는다.
- 개인정보 수집/보유/삭제는 확정된 제품 정책에 매핑한다. 해시·익명화·백업·법적 보존의 의미를 추측으로 확정하지 않는다.

### 탈퇴를 포함하는 경우

탈퇴 의도 확인 → 서비스 접근 차단/세션 폐기 → 정책상 유예 → 불가역 삭제/익명화 → 결과 확인을 기본 검토 순서로 삼는다. 실제 순서는 제품 정책과 공급자 계약으로 확정한다.

- 저장소별 완료/실패를 구분하며 일부만 삭제됐을 때 전체 완료를 표시하지 않는다.
- 불가역 경계 이전의 취소와 이후의 재처리를 구분한다. 삭제된 개인정보를 복원하는 보상을 임의로 설계하지 않는다.
- 여러 외부 경계에 걸치면 단계별 상태·재시도 상한·운영 재처리·완료 증거를 둔다. 구현이 간단한 단일 저장소 삭제에는 불필요한 큐/분산 조율을 추가하지 않는다.

## 5. 산출물과 다이어그램

기본 문서는 `docs/design/{DATE}/frontend-user/frontend-user-design.md`다. 기존 문서 위치/사용자 지정이 있으면 따른다. 한 문서로 충분하면 상세 파일을 만들지 않는다. 길어지면 **모듈 계약 또는 독립 사용자 흐름별**로 `details/`에 나누고 핵심에서 링크한다. 섹션마다 별도 파일을 의무 생성하지 않는다.

핵심은 약 200줄을 목표로 `요구/범위 → 구조·소유권 → 전체 navigation → 주요 결정 → 계약/상세 링크 → 검증·미확정 사항` 순서로 쓴다. 숫자를 맞추려고 필요한 계약이나 예외를 삭제하지 않는다.

| 설계 질문 | 사용할 표기 |
|---|---|
| 시스템/신뢰/모듈 경계 | Mermaid `flowchart`와 계약·소유권 표 |
| 사용자 화면 이동과 이동을 가르는 API/판단 | [navigation](../guides/navigation-diagram-guide.md) |
| 유스케이스 안의 객체 협력 | [jobflow](../guides/job-flow-diagram-guide.md) |
| 한 소유자의 상태 변화 | [state](../guides/state-diagram-guide.md) |
| 실제 바꾸거나 새로 설계할 화면 배치 | [layout](../guides/screen-layout-guide.md) |
| 필요한 데이터 관계 | Mermaid `erDiagram` |

- 사용자 DSL을 다른 형식으로 치환하지 않는다. 헤더·화살표·컨테이너 문법은 링크한 가이드가 원본이다.
- 전체 navigation 후 필요한 시나리오 상세를 둔다. 페이지 내부 처리·모듈 협력은 navigation에 섞지 않는다.
- 프로토타입 기본 시나리오는 가입, 로그인/로그아웃, 세션 복원·보호 라우트 진입, 프로필/보안 변경, 탈퇴 중 적용한 흐름이다. 실제 Page/API로 작성하며 예제 라우트를 그대로 복제하지 않는다.
- 모든 Page에 서로 같은 layout을 복제하지 않는다. 공통 배치는 한 번 정의하고 차이만 추가한다. 상태가 없거나 변경되지 않는 대상은 기존 문서를 참조한다.
- 각 다이어그램에는 트리거·상태 소유자/경계·핵심 분기·근거를 이해할 만큼 짧게 설명한다. 실제 렌더러가 없으면 문법 대조와 렌더링 미검증을 구분한다.

## 6. 검증과 구현 인계

`FR ↔ 책임 모듈/계약 ↔ 필요한 화면·다이어그램 ↔ 검증 방법`으로 추적한다. 한 요구가 여러 설계 요소에 대응할 수 있고, 해당 없는 열은 이유를 붙여 생략할 수 있다.

필수 검토:

- UI, 인증, 회원 상태/데이터의 권위와 쓰기 소유자가 명확하다.
- 서버 인증/권한 검증, 선택한 인증 방식의 보안 제약, 민감 정보 처리와 폐기 성공 조건이 정의됐다.
- 채택한 흐름의 성공·대표 실패·중복/만료·복구가 계약과 화면에서 일치한다.
- 외부 정합성을 실제보다 강하게 가정하지 않았고, 고유성/동시성/탈퇴 실패 책임이 정해졌다.
- 존재하지 않는 동작·파일·출처를 확인한 사실처럼 쓰지 않았다. 산출물 링크가 유효하고 사용자 DSL 의미가 유지됐다.
- 담당 모듈 계약과 관련 테스트만으로 구현할 수 있는 인계가 있다. 다른 모듈 내부를 알아야 하면 계약 보완 또는 경계 재검토를 한다.

[협업 프롬프트](./multi-agent-task-prompt.md)에 따라 독립 검토와 수정 후 재평가를 진행한다. 필수 요구 또는 핵심 보안/삭제 결정이 미확정이면 구현 준비 미완료다. 통과한 부분, 남은 결정, 필요한 입력을 분리해 보고한다. 초안 작성 완료를 운영 안전성 검증 완료로 표현하지 않는다.
