# 사이트 설계 프롬프트

요구사항에 맞는 사이트 설계 문서를 작성한다. **사용자 목적별 페이지 이동 → 필요한 화면 배치 → 각 화면이 소유하는 상태** 순서로 설계하여 화면별 작업 맥락을 작게 유지한다. 코드 구현은 별도 요청에 따른다.

## 입력과 실행 규칙

- 입력: 제품/사용자, 핵심 과업과 성공 기준, 신규/기존 사이트, 대상 범위, 브랜드·디자인 시스템·기술 제약, 참고 서비스.
- [모듈 경계 가이드](../guides/module-boundary-guide.md)에 따라 관련 라우트·Page·상태 소유자·API 계약부터 읽고 호출자/공유 UI 연결을 검색한다. 다른 feature 내부는 실제 영향이 있을 때 읽는다.
- 이미 허용된 설계·조사는 자율 진행한다. 가정과 미확정 정책을 표시하고 기존 변경을 보존한다. 무관한 기능을 추가하지 않는다.
- 독립 조사는 병렬화하며 공통 화면/계약의 쓰기 담당을 정한다. 반복 검토는 [협업 프롬프트](./multi-agent-task-prompt.md)를 따른다.

## 1. 사용자 과업과 범위

`사용자 · 목적 · 진입점 · 성공 결과 · 주요 실패/취소 · 관련 화면`을 정리한다. 제품이 지원하는 역할과 흐름만 다룬다.

전체 사이트면 실제 범위의 페이지 맵을 만들고, 부분 설계면 관련 화면과 직접 연결만 표시한다. 공개/보호 접근, 직접 URL 진입, 새로고침/뒤로 가기, 세션 만료가 해당하면 포함한다.

## 2. navigation 중심 설계

[navigation 가이드](../guides/navigation-diagram-guide.md)의 DSL을 따른다.

- 대상 범위 전체의 간략한 화면 이동을 먼저 그리고 사용자 목적별로 필요한 상세를 추가한다.
- Page는 라우트 페이지, Component는 Page에 포함되는 단위로 구분한다. 사용자에게 의미 있는 주요 하위 모드/오버레이만 가이드 허용 범위에서 표시한다.
- 이동을 가르는 API·판단만 넣고 내부 store·queue·Worker 흐름을 섞지 않는다. 내부 협력은 필요할 때 [jobflow](../guides/job-flow-diagram-guide.md)로 분리한다.
- 시나리오마다 진입 방법, 트리거, 정상·실패/취소 분기, 실제/제안 API 계약을 짧게 설명한다.
- 예제 `HomePage`를 강제하지 않는다. 실제 진입점을 사용하고 존재하지 않는 이동 화살표를 만들지 않는다.

## 3. 화면·상태·계약

- [layout 가이드](../guides/screen-layout-guide.md)의 배치·컨테이너·크기 문법을 그대로 사용한다. 프롬프트에서 별도 문법을 재정의하지 않는다.
- 새로 설계/변경하는 화면만 배치를 작성한다. 같은 공통 배치는 한 번 정의하고 각 화면의 차이를 연결한다. 모든 화면에 같은 레이아웃을 복제하지 않는다.
- [state 가이드](../guides/state-diagram-guide.md)로 한 상태 소유자의 로딩·입력·제출·오류·복구를 표현한다. 상태가 없는 화면은 상태도를 만들지 않는다.
- 화면 이동은 navigation, 화면 내부 상태는 state로 구분한다. 공통 인증/세션 상태를 모든 Page가 각각 소유하게 설계하지 않는다.
- `Page/feature · 표시 상태 소유자 · 입력/출력 · 사용하는 공개 API · 실패/재시도`를 정리한다. 서버의 업무·권한 정책을 UI가 추론하지 않게 한다.
- 반응형·키보드·포커스·입력 보존·오류 공지는 관련 화면의 검증 기준에 포함한다.

## 4. 참고 서비스 조사

유사 서비스와 공식 디자인 자료에서 관련 패턴을 확인한다. [UX/UI 개선 프롬프트](./ux-ui-improvement-prompt.md)의 근거 수집 기준을 필요한 범위에 적용한다.

`출처 · 실제 확인한 사실 · 적용/제외 · 우리 맥락과 차이`를 남긴다. 로그인/유료 벽 뒤 화면을 확인했다고 주장하지 않는다. 전체 도움말 전수 방문을 기본 요구로 삼지 않는다. 경쟁 서비스의 패턴을 사용자 효과가 검증된 사실로 표현하지 않는다.

## 5. 문서 구성

사용자 지정 또는 기존 문서 위치에 한 문서로 작성한다. 위치가 없으면 `docs/design/{DATE}/site/site-design.md`를 사용한다. 큰 사이트만 독립 사용자 흐름별 상세로 나눈다.

순서: **요구/범위·가정 → 전체 navigation → 필요한 시나리오 상세 → 화면 배치·상태/계약 → 검증·미확정 사항**. 참고 근거는 개선/설계 결정 근처에 둔다.

사용자 DSL을 다른 형식으로 치환하지 않는다. 각 도표 아래 핵심 설명을 붙이고 문법은 가이드 링크를 원본으로 사용한다. 출력 분량이나 도표 개수를 맞추려고 빈 설계를 추가하지 않는다.

## 6. 교차 검토와 완료

Architect는 사용자 과업·화면/상태 소유권을 설계하고, Critic은 누락/불필요한 흐름과 경계 침범을 비판한다. 작성 담당은 필요한 도표를 반영하고 Tester는 실제 요구·계약과 대조한다. 작은 작업은 역할을 합칠 수 있으나 독립 검토 여부를 밝힌다.

검증 기준:

- 주요 사용자 목적의 성공·실패/취소 경로와 실제 진입점이 설명된다.
- navigation·layout·state에서 Page·모드·상태 소유권이 일치한다.
- 기존 배치/상태 재사용과 생략 근거가 분명하며 모든 Page에 새 도표를 강제하지 않는다.
- 공개 계약을 통해 구현할 수 있고 다른 feature의 내부 상태를 알아야 하는 연결이 없다.
- 근거·제안·미확정을 구분하고 링크/DSL 문법을 확인했다. 실제 렌더링을 하지 못했으면 명시한다.

필수 결함을 수정하고 영향 부분을 재검증한다. 최종 보고는 문서 위치, 주요 결정, 비판 반영, 검증과 미확정 사항을 포함한다. 설계 검토와 구현/실사용 검증을 구분한다.
