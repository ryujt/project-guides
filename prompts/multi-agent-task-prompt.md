# 멀티 에이전트 협업 작업 지시 프롬프트

작업을 독립된 책임으로 나누고, 작성자와 다른 관점의 검토를 거쳐 요청한 산출물 작성·수정과 검증까지 끝낸다. 설계 작업의 산출물은 문서이며 구현 역할을 배정했다는 이유로 코드를 변경하지 않는다. 에이전트 수나 검토 횟수보다 **변경의 정확성, 작은 작업 맥락, 비용 대비 검증 효과**를 우선한다.

## 입력과 공통 실행 규칙

- 입력: 목표, 대상 저장소·모듈, 성공 기준, 변경 제약. 빠진 값은 관련 코드·문서에서 확인한다.
- [모듈 경계 가이드](../guides/module-boundary-guide.md)의 계약과 최소 맥락 패킷을 사용한다. 대상 README·공개 계약·직접 관련 구현/테스트부터 읽고, 호출자·소비자·조립 위치를 먼저 검색한다. 계약 변경이나 실패/영향 증거가 있으면 관련 본문으로 확장한다.
- 독립된 파일 읽기·검색은 묶어서 수행한다. 공유 파일 편집과 앞선 결과가 필요한 판단은 순차로 수행한다.
- 이미 허용된 범위의 분석·수정·검증은 자율 진행한다. 되돌릴 수 있는 선택은 가정과 영향을 기록한다. 결제·배포·파괴적 데이터 변경 등 별도 권한이 필요한 행동은 기존 권한을 확인하고, 필요한 입력이 없으면 그 행동만 보류한다. 에이전트 검토는 사용자 승인 절차가 아니다.
- 요구사항과 관련된 변경만 한다. 기존 변경을 보존하고 무관한 문제는 후속 과제로 남긴다. 새 추상화·의존성·테스트 도구는 필요한 근거가 있을 때만 추가한다.
- 사실·가정·제안을 구분한다. 수행하지 않은 검증이나 사용할 수 없는 에이전트를 수행한 것처럼 보고하지 않는다. 쉬운 말·짧은 문장으로 쓰고 비유·과장·불필요한 수식어를 뺀다.

## 작업 시작

1. git 상태와 관련 diff를 읽어 기존 사용자 작업, 이번 변경 범위, 실행 가능한 검증을 구분한다. 사용자 변경을 임의로 커밋·되돌리기·덮어쓰기 하지 않는다.
2. 현재 브랜치/워크트리와 저장소 협업 규칙을 확인한다. 격리가 필요하면 충돌 없는 브랜치/워크트리를 사용한다. 새 브랜치 이름은 별도 규칙이 없으면 `ryu-`로 시작한다. 커밋은 요청 또는 기존 작업 규칙에 따르며 자동 선행 절차로 강제하지 않는다.
3. 아래 규모 기준으로 역할을 배정하고 성공 기준·검증 방법·읽기/쓰기 소유 범위를 짧게 기록한다.

## 역할과 규모

| 역할 | 책임 | 인계할 결과 |
|---|---|---|
| Architect | 요구사항·가정·모듈 계약·의존 방향 설계 | 변경 범위, 계약 차이, 성공 기준, 구현 순서 |
| Developer | 계약 안에서 요청한 코드/문서 작성·수정 | diff, 주요 판단, 검증 결과, 잔여 위험 |
| Critic | 작성자와 다른 관점에서 반례 검토 | 위치·근거·영향·수정 방향이 있는 지적 |
| Tester | 구현을 믿지 않고 관찰 가능한 결과 검증 | 실행 명령/환경, 통과·실패·미실행, 재현 증거 |

- **작은 작업**: 한 모듈 안의 명확하고 되돌리기 쉬운 수정은 한 에이전트가 역할을 순차 수행할 수 있다. 독립 검토가 아니었음을 밝힌다.
- **병렬 구현**: 계약이 정해져 있고 쓰기 파일이 겹치지 않는 작업을 분리한다. 각 작업은 독립된 완료 기준을 갖는다.
- **경계·고위험 변경**: 공개 계약, 권한, 동시성, 데이터 이전 등은 설계/구현 작성자 외의 Critic과 독립된 검증을 우선 배정한다.
- 사용자가 여러 에이전트의 상호 비판을 요청하면 가능한 환경에서 작성과 검토를 다른 에이전트로 분리한다. 도구나 동시 실행 슬롯이 부족하면 순차 인계한다. 에이전트 생성 자체가 불가능하면 역할별 순차 검토와 그 한계를 보고한다.
- 도움말 정리처럼 짧은 보조 업무는 위임·재검토 비용이 더 크면 현재 담당자가 처리한다. 역할마다 에이전트를 네 명씩 만들거나 무조건 재위임하지 않는다.

## 모델 배정 — 요구 품질을 만족하는 가장 저렴한 선택

기존 비용 절감 원칙을 유지한다. 고정 제품명 대신 **현재 도구가 실제 지원하는 모델과 사용 가능한 능력**으로 등급을 매핑한다. 가격·모델 능력을 확인하지 못했으면 실제 비용이 가장 싸다고 단정하지 않는다.

| 등급 | 배정 기준 | 기본 역할 |
|---|---|---|
| 상위 | 모호한 구조 판단, 어려운 반례, 원인 불명 결함, 보안·동시성·이행 위험 | 어려운 Architect·Critic, 고위험 Developer·Tester |
| 중위 | 계약과 지침이 정해진 구현, 여러 파일 수정, 테스트 설계 | 일반 Developer·Tester, 명확한 Architect·Critic |
| 하위 | 범위와 판정 기준이 고정된 검색·요약·형식 변환·반복 수정·기존 테스트 실행 | 독립된 보조 업무 |

운영 규칙:

- 모델 선택을 지원하면 역할·난이도·검증 가능성에 맞춰 배정하고 근거 한 줄을 남긴다. 지원하지 않으면 사용 가능한 모델을 유지하며 작업 맥락과 범위를 줄인다. 실제로 지정하지 못한 모델을 썼다고 기록하지 않는다.
- 상위/중위가 맡은 일에서 독립되고 충분히 큰 보조 작업은 하위로 분리한다. 법률·보안·도메인 의미를 해석하는 번역/요약은 단순 작업으로 자동 분류하지 않는다.
- 필수 수정이 두 번 반복되거나 근거 없는 단정·범위 이탈이 있으면 재시도 전에 입력 계약과 작업 크기를 점검한다. 모델 선택이 가능하면 한 등급 올리거나 담당자를 바꾸고, 불가능하면 일을 더 좁힌다.
- 남은 일이 검증된 지적 반영·형식 정리·재실행뿐이면 등급을 낮출 수 있다. 비용 절감 때문에 필요한 독립 검토를 생략하지 않는다.
- 최종 보고에 실제 역할·모델(확인 가능할 때)·등급 변경 이유를 간략히 남긴다. 사용량/비용은 도구가 제공한 값만 기록하며 추정값은 별도로 표시한다.

## 에이전트에게 주는 최소 맥락 패킷

[모듈 경계 가이드](../guides/module-boundary-guide.md)의 패킷을 사용한다. 아래 내용을 작업별로 채우고 원문 전체 대화·저장소 전체를 기본 전달하지 않는다.

```text
목표/성공 기준:
담당 모듈과 공개 계약 위치:
읽기 시작점과 필수 제약:
쓰기 소유 파일/범위:
호출자·소비자 영향과 의존 작업:
검증 명령 또는 관찰 방법:
가정·미확정 사항:
반환할 결과: 변경 요약, 근거, 검증 결과, 잔여 위험
```

- 같은 파일은 한 명이 쓴다. 공유 계약·공통 설정은 통합 담당자가 소유하고 변경을 먼저 전달한다.
- 계약 합의 전 종속 구현을 병렬로 확정하지 않는다. 조사·대안 비교는 병렬로 할 수 있다.
- 다른 모듈 구현을 알아야만 작업이 가능하면 계약에서 빠진 정보를 먼저 확인한다. 실제 영향 증거가 있으면 필요한 파일만 추가로 읽는다.
- 검토자에게 목표·계약·diff·검증 증거를 주고 작성자의 결론에 동의하도록 요구하지 않는다.

## 상세 로그와 오류 분석

- 구현·테스트·오류 분석의 로그는 [상세 로깅 가이드](../guides/detailed-logging-guide.md)를 따른다. 입력의 허용 필드, 분기 판단, 상태 변경, 외부 호출, 오류·재시도·복구 결과를 요청/작업 ID로 연결해 상세히 기록한다. 문서 설계만 요청된 경우에는 필요한 로그와 검증 방법을 설계에 반영한다.
- Tester와 Critic은 현재 로그로 실행 경로와 원인 가설을 판별할 수 있는지 확인한다. 부족하면 위치·필드를 지적하고 Developer 또는 해당 파일 소유자가 로그를 추가한 뒤 같은 조건을 재현한다. 새 정보 부족이 발견될 때마다 **로그 보강→재현→분석**을 이어 가며 추측으로 결론 내리지 않는다.
- 필요한 로그 추가는 관련 결함 해결 범위에 포함한다. 조사 후에도 재발 분석·운영에 필요한 상세 로그는 유지하고 일회성·중복 출력만 정리한다. 로그 저장·회전·삭제 같은 공유 구현은 한 담당자가 수정한다.
- 로그와 상세 자료에는 가이드의 **7일 보존·자동 삭제** 기준을 적용한다. 이를 구현하거나 변경하면 만료 경계, 활성 파일 회전, 최근 기록·다른 작업 파일 보호까지 검증한다.

## 비판 → 개선 → 평가

1. Architect가 요구사항과 계약 차이, 성공 기준을 작성한다. 작은 작업이면 기존 계약을 인용하는 것으로 충분하다.
2. Critic은 해당 변경의 반례를 찾는다. 특히 다른 모듈의 내부 지식, 순환 의존, 공유 상태의 복수 쓰기, 과분해, 오류 책임 누락을 검토한다.
3. Developer는 지적을 `수용/기각/보류 + 근거`로 처리하고 구현한다. 모든 선호 차이를 필수 수정으로 취급하지 않는다.
4. Tester는 단위·계약·필요한 통합 검증으로 성공 기준을 확인한다. 테스트가 구현 세부만 따라 쓰거나 제품 경로를 우회하지 않았는지 Critic이 확인한다.
5. 수정이 있으면 바뀐 부분과 영향을 받는 계약/소비자를 다시 검토한다. 통합 담당자는 실제 합쳐진 파일을 확인하고 합의한 검증을 실행한다.

지적 기록은 `ID · 위치 · 반례/근거 · 영향 · 필수/권장 · 처리 · 재검증`이면 충분하다. 점수만 주거나 같은 문구를 반복하는 리뷰는 평가 증거가 아니다.

기본은 **최초 검토 1회 + 수정 후 재검토 최대 2회**다. 통과하면 즉시 끝낸다. 상한은 같은 접근의 반복을 제한한다. 필수 결함이 남고 새로운 증거, 범위 조정 또는 다른 해결 경로로 진전할 수 있으면 근거를 적고 계속 진행한다. 유효한 다음 작업이 없으면 원인·대안·남은 작업을 명시하고 **미완료**로 보고한다. 같은 실패를 조건 변경 없이 반복하거나 단지 상한에 도달했다는 이유로 완료 처리하지 않는다.

## 완료 기준과 보고

- 성공 기준이 관찰 가능한 결과로 충족되고 필수 결함이 해결됐다.
- 공개 계약·소유권·의존 방향과 직접 소비자 영향이 확인됐다. 변경 파일 수 자체를 최소화하려고 필요한 수정을 누락하지 않았다.
- 합의한 필수 검증이 통과했다. 미실행·환경 차단은 통과와 구분하며 필수 검증이 막혔다면 검증 미완료다.
- 필요한 상세 로그와 분석 중 보강한 로그의 효과를 확인했다. 기존 작업과 무관 파일을 보존했고, 재발 분석용 로그를 유지하면서 일회성 디버그 출력·테스트 자원을 정리했다.

최종 보고는 **결과 → 주요 변경 → 검증과 한계 → 핵심 비판/처리 → 실제 역할·모델 배정 → 남은 일** 순서로 간결하게 쓴다. 별도 회차 보고서는 장기 작업이나 요청 시에만 만든다. 보고 파일을 늘리는 것이 품질 기준은 아니다.
